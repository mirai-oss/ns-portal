# 指示書（設計担当）売上データの「スプレッドシート・GAS経由」をやめる設計書を作る — 2026-11-05

発行: 担当C（ns-daily-import）。**やることは設計書の作成だけです。コード変更・本番の変更は一切しません。**
成果物: `docs/設計書_売上データ基盤_スプレッドシート脱却_<日付>.md`（このリポジトリ ns-portal の docs 配下）

## 1. 背景（ユーザーの要望）
2026-11-05 のやりとり（原文の要点）:
- 「今、売上ダッシュボードにスプレッドシートは管理システムの反映に使っている？ Supabase しか使っていないなら、人件費の差額などももう必要なくなる。GAS が必要なくなるなら、分析テーブルの再生成のやり方も変えた方が良さそう。**BigQuery に入った時点で分析テーブルの再生成がされるとか**」
- 今日（11/5）起きたこと: 朝の取込が遅れ、取込が揃った後に分析テーブルが作り直されず、売上が管理システムに出なかった（暫定対応は済み。下の §3）。

## 2. 現状の流れ（担当Cが 2026-11-05 にコードで確認した内容）
```
Mac mini の日次取込（ns-daily-import）
  └ GAS（取込WebApp・売上DB側）経由で スプレッドシート「売上DB」へ書込
       支払いDB（dinii-payment-ns/nstyle・zeroregi・現金売上の修正も） / 媒体別DB（dinii-media）
       仕入れDB（infomart-siire） / 人件費DB（smaregi-payroll） / 入金DB / 口コミ推移ログ ほか
  └ GAS が シートから「分析テーブル」を再生成（分析_日別店舗・分析_媒体別日次）  ← buildAnalysisTables（約75秒）
  └ GAS bqSyncSales が シート→BigQuery へ全件洗い替えコピー（約2.5〜4分）
       BQ: tori-analytics.sales.fact_daily_store / stg_payment / stg_media / stg_siire / stg_jinken / stg_deposit / stg_spot / stg_loan_principal
  └ Supabase の kd_* 表は、Edge `keiei-kd-refresh`・`dash-sync` が GAS の bqDailyStore（BQ読み出し）を呼んで作る
  └ 画面: ns-portal「経営」＝Supabase kd_*／tori-dashboard（GitHub Pages）＝GAS経由／Lark日報＝tori-dashboard
```
- **つまり BigQuery の売上はスプレッドシートの写し**。Supabase だけでは動いていない。
- すでにシートを通らない（直接 BigQuery／Supabase）もの: Dinii 注文明細（bqLoadOrders）・予約（stg_reservation）・デリバリー売上（stg_delivery_order／Supabase）・**アルバイト人件費（GAS の API_LABOR_COST_FROM_YM_='2026-10' 以降は Supabase labor_cost_daily が正）**。
- そのため「シートの人件費 vs BQ の人件費」の突合は 10/3 から毎日ずれていた（構造的に当然）→ 2026-11-05 に突合対象から外した（§3）。

## 3. すでに担当Cが済ませた暫定対応（設計の前提）
- ns-daily-import `9dc944e`: 朝の取込8本が出そろった直後（遅れて終わったときも）に dispatch が「分析再生成→BQ同期→突合」を実行。人件費合計の突合は対象外。
- 残る弱点（設計で解消してほしい）: ①取込が変わるたびに GAS が重い処理を丸ごと再実行（分析75秒＋BQコピー数分）②GAS の再デプロイはユーザーの手作業 ③GAS URLFetch の一時エラー・6分制限・同時実行に弱い ④シートが事実上の正本のまま（手修正・列ずれ・startRow 事故が起きうる）。

## 4. 設計書で決めてほしいこと
1. **目指す形（候補を比較して推奨を1つ）**
   - A: 取込ジョブが直接 BigQuery（または Supabase）へ書き、分析テーブルは BigQuery のビュー／スケジュールクエリで自動生成（「BQに入った時点で再生成」）
   - B: 正本を Supabase（Postgres）に置き、BQ は不要（または参照用の写し）にする
   - C: 暫定のまま（シート＋GAS）で堅牢化するだけ
   → 費用・速度・運用負荷・壊れやすさ・移行の難しさで比べ、推奨を理由つきで示す。
2. **テーブル設計**: 支払い・媒体別・仕入れ・人件費・入金・口コミ・分析（日別店舗/媒体別日次）の正本の置き場所、主キー（店舗ID＋営業日 等。店舗は**店舗IDで参照**・名前一致に頼らない）、上書き（upsert）規則（現行は「同店舗・同営業日を削除して追加」）。
3. **分析テーブルの再生成のきっかけ**: 取込完了のイベント駆動か、スケジュールクエリか、ビューで常時最新か。遅れて届いたデータ・手修正（現金の「レジに合わせて修正」）が即反映される方式。
4. **手入力データの行き先**: 目標・目標月次（BQ未ミラー）、DB_広告、DB_PL、祝日、媒体分類など「人が入力するシート」をどう扱うか（Supabase の画面入力へ移すか）。
5. **読み取り側の切替順**: ns-portal「経営」・tori-dashboard・Lark日報・精算ダッシュボード（現金売上の読み書き: cashReconRead / paymentDailyReplace）・PL システム（pl_system.gs）・nippo。**読み取り元を切り替える順序と、旧経路と並行稼働して突合する期間**。
6. **GAS の廃止範囲**: 何を残し何を消すか（Lark日報の GAS トリガ・アカウント認証・精算GASなど、売上と関係ない GAS は別扱い）。
7. **段階移行と巻き戻し**: 追加のみのフェーズから始め、各フェーズの完了条件・ロールバック手順・ユーザーの手作業（GAS 貼替等）の回数を最小にする計画。
8. **監視**: 取込の遅れ・未到着・件数ゼロを検知する仕組み（現行の import_runs・未取得アラートとの関係）。突合は「旧経路との一致」が済んだら不要にする。

## 6. 守ってほしい制約
- **設計だけ**。本番の SQL・Edge Function・GAS・BQ への変更は行わない（ユーザーの確認が要る）。
- GAS の変更が出る場合は「ユーザーの貼り替え＋`ping` の ver を上げる」運用を前提に、回数を最小にする計画にする。
