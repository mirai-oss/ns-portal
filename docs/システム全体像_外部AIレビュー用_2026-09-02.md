# N-Styleグループ 社内システム全体像（外部AIレビュー用の案内書）

作成: 2026-09-02（司令塔） ／ 目的: **このシステム群を初めて見るAI（または人間のエンジニア）が、構成・コード・データ構造を正しく理解し、深いレビューができるようにするための自己完結の案内書**。
使い方: 本書を最初に読ませたうえで、§2のリポジトリ一式へのアクセス（またはzip）を渡してください。§9に「確認してほしい観点」を明記しています。

## 1. これは何のシステムか（前提）

飲食店グループ（12店舗・複数法人: トーホーエージェンシー／N-Style／LiveGate／SK）＋不動産事業（SK・構築中）の**社内業務システム一式**。日報・シフト・勤怠・給与・予約・請求書・会計連携・PL管理・売上分析・本部タスク・社内機密情報までを、少人数（経営者1名＋AIエージェント群）で内製している。

- 開発・運用は**複数のAIエージェント（Claude Codeセッション）による並行開発体制**（担当A〜H・I・P のレーン制。§8参照）
- 利用者は非エンジニアの経営者と店舗スタッフ。**「AI=下書き・人=承認」**が全自動化の共通原則

## 3. アーキテクチャ（データの流れ）

```
[外部サービス]                [取込]                    [正本]                  [表示]
スマレジ(POS/タイムカード) ─┐
dinii(モバイルオーダー)    ─┤ Mac mini ns-daily-import
食べログノート/ダイニー台帳─┤ (Playwright・毎朝) ────→ ハブSupabase ──┬→ ポータル/nippo/invoices…(直読み・速い)
銀行CSV(PayPay銀行等)     ─┘ ＋GitHub Actions(日次)      │           └→ BigQuery tori-analytics(分析ミラー)
Gmail(請求書メール)  ──── GAS(5分毎) ──────────────────→ 同上                        │
                                                                                    ↓
Googleスプレッドシート(旧正本・手入力) ⇄ GAS(tori-dashboard/精算/PL管理) ──→ 経営ダッシュボード(遅い・脱GAS移行中)
マネーフォワード会計 ←─ Edge Function mf-journal(OAuth・仕訳・証憑添付)
```

**重要な設計判断（確定済み・要件定義書§16）**: 正本は「業務=ハブSupabase／分析=BigQuery」。スプレッドシートは入力UIと出力先に**降格**していく方針（移行中）。経営ダッシュボードだけがまだ「シート＋GAS」の旧構成で、**現在この部分の脱GAS移行計画が進行中**（§7）。

## 4. データ構造の要点

### 4.1 ハブSupabase（プロジェクトref: `uuvsxzhpxtghojoubjcc`・東京）
接頭辞でドメインを分離（=レーンの縄張りでもある）:
- `users`/`user_stores`/`employee_profiles`/`stores`/`store_aliases`（共有マスタ。store_aliasesが**店舗名表記ゆれの正規化辞書**）
- `sf_*`: シフト・給与（`sf_shifts`・`sf_payroll_sync`=スマレジ給与明細API・`sf_payroll_allocations`=店舗按分）
- `hq_*`: 本部タスク（tasks/steps/comments/activity/テンプレ）
- `invoice_*`: 請求書メール（emails/attachments/audit_logs・処理ロック）
- `mf_*`: マネーフォワードOAuth（複数事業者）・同期ログ
- `rsv_reservations`: 予約正本（食べログノート＋ダイニー台帳・月次洗い替え・`cancel_detected_at`でキャンセル検知履歴）
- `labor_cost_daily`: スマレジ勤怠API由来の日次人件費／`api_cost_daily`: Anthropic API費用
- `export_*`/`tpl_*`: 帳票・テンプレ／`ck_*`: コックピット／`kd_*`: 脱GAS移行の新集計層（作成中）
- `app_secrets`: 共有シークレット置き場（**コードに秘密を書かない**規約の受け皿）
- SQLは`ns-portal/supabase/`に**日付入りファイルの追記のみ**（既存SQL編集禁止の規約）。Edge Functionsは`ns-portal/supabase/functions/`

### 4.2 BigQuery（`tori-analytics`データセット`sales`）
- `fact_daily_store`: 店舗×日の確定実績（売上・原価・人件費 等）＝分析の柱
- `stg_*`: シート/Supabaseからの日次ミラー（`stg_pl`・`stg_media`・`stg_siire`・`stg_deposit`・`stg_spot`・`stg_reservation`・`stg_loan_principal`ほか）
- dinii注文明細（bqLoadOrdersで毎朝ロード）＝明細分析の元
- **ミラーは全て再生成可能な派生データ**（正本はシート/Supabase側）

### 4.3 スプレッドシート（縮小予定の旧正本）
- 経営D本体シート（`分析_日別店舗`・DB_PL・入金DB・DB_スポット人件費 等）／広告費用対効果_管理シート（💾広告費DB・💾売上DB・💾予約DB・⚙単価設定）／社員人件費DB／PL管理システム
- **既知の弱点**: 表記ゆれ・空行・列ズレがそのまま数字の誤りになる（→§7の移行理由）

## 9. 外部AIに確認してほしい観点（レビュー依頼）

1. **アーキテクチャ妥当性**: §3の構成と§7-1の脱GAS移行計画は妥当か。より良い移行順・見落としているリスクはないか
2. **データ整合性**: 「数字が狂わない4原則」で穴は塞げているか。表記ゆれ（店舗・媒体）対策として更に構造的な打ち手はあるか（例: ID化の徹底）
3. **信頼性**: 取込ジョブ群（Mac mini依存含む）の単一障害点・監視の抜け。バックアップ/復旧設計（週次Drive・`docs/バックアップと復旧.md`系）の妥当性
4. **セキュリティ**: RLS設計・SSOハンドオフ・`app_secrets`運用・公開リポジトリ（GitHub Pages）に置いてよい情報の線引き。**指摘は公開リポに書かず、レビュー結果として別途返すこと**
5. **保守性**: 巨大単一ファイル（nippo/index.html 7000行・app.js 6000行）の今後。フレームワーク導入の要否とタイミングの助言
6. **スケール**: 店舗数・法人数（不動産SK追加）・従業員数が2〜3倍になった時に破綻する箇所
7. コードを読む際の入口: `tori-dashboard/HANDOFF.md`（経営Dの地雷一覧）→`gas/Code.gs`／`nippo/index.html`冒頭の定数群／`ns-portal/supabase/`のSQL群（時系列でスキーマの歴史が読める）

## 10. レビュー時の注意（必読）

- **シークレットはどのリポジトリにも無い**（`app_secrets`テーブル・GitHub Secrets・GAS Script Properties・Mac miniの`.env`のみ）。レビュー中に平文の鍵を見つけたらそれ自体が最重要指摘
- `ns-portal`・`nippo`・`tori-dashboard`は**公開リポジトリ**（GitHub Pages配信のため）。セキュリティ所見・脆弱性の詳細をこれらのリポジトリ内のファイルに書き込まないこと
- 個人情報（従業員・応募者・予約者）はSupabase内のみ。レビュー用に実データのエクスポートは渡さない前提（スキーマとコードで判断してほしい）
- 本番への変更は一切不要。**読むだけ**でよい
