## 2. 【A】店舗情報と物件契約を「1つにする」か

**結論: 画面は1つにする。テーブルは分けたままにする。**

- 1店舗に物件契約は複数ありうる（本店＋セントラルキッチン（TOHOビル2F/3F）、移転前後、駐車場・倉庫）。テーブルを1つにすると「店舗1行に契約1つ」しか持てず、移転や契約更新の履歴が消える。
- なので **`stores`（1） : `properties`（N）** の関係は維持し、画面を「店舗カルテ」に統合する。

### 店舗カルテの画面構成（タブ）

```
店舗カルテ: 04 鳥一代 恵比寿店                        [営業中] [営業許可 2027/03/15 まで 残188日]
┌ 基本 ┬ 物件・契約 ┬ 初期投資 ┬ ライフライン ┬ 許認可・期限 ┬ ID/PW ┬ 取引先 ┬ 書類・写真 ┐
```

| タブ | 中身 | 元テーブル |
|---|---|---|
| 基本 | 店名・住所・電話・店長・営業時間・緊急連絡先・URL・ポスト（現行の店舗情報） | `info.stores` |
| 物件・契約 | 現行契約（賃料・共益費・坪数・契約日・更新日・保証金・償却・大家・管理会社）＋過去契約の履歴 | `info.properties`（**共益費・更新料・解約予告期間・原状回復条件** を追加） |
| 初期投資 | 【B】で新設。区分別の明細と合計 | `info.store_investments`（新設） |
| ライフライン | 電気・ガス・水道・通信の契約先・お客様番号 | `info.utilities`（既存。店舗単位に表示） |
| 許認可・期限 | 営業許可・深夜酒類・防火管理者・消防点検・契約更新など、この店舗の期限すべて | `info.deadlines`（【C】で強化） |
| ID/PW | この店舗に紐づくID/PW | `credential_stores`（既存） |
| 取引先 | この店舗で使う取引先（仕入・広告など） | `info.suppliers`（【D】v2） |
| 書類・写真 | 契約書PDF・許可証・店舗写真 | `documents`/`photos`（`store_id` で絞る） |

- 現行の「店舗情報」「物件・契約」「通信・水道光熱」の一覧画面は、店舗カルテの入口（店舗一覧カード）に置き換える。
- 全店横断で見たいもの（賃料の合計、更新日一覧）は「店舗一覧」の右側に集計として残す。

## 3. 【B】初期投資（開業コスト）と経営PLへの反映

### 3.1 テーブル案 `info.store_investments`

| 列 | 説明 |
|---|---|
| store_id / property_id | どの店舗・どの契約に対する投資か |
| category | 区分（下記） |
| amount | 金額（税抜） |
| tax | 消費税 |
| paid_on | 支払日 |
| supplier_id | 支払先（`info.suppliers`） |
| treatment | **資産計上／費用／返還される預け金** の3択（下記） |
| depreciation_years | 耐用年数（資産計上のときだけ。内装15年・厨房機器6〜8年など） |
| document_id | 見積書・請求書・契約書PDF |
| memo | |

**区分（初期値）**: 敷金・保証金／礼金／仲介手数料／償却（保証金の償却分）／内装工事／厨房機器／什器・備品／看板・サイン／POS・通信工事／求人費用（開業前）／開業前人件費（研修）／開業前家賃（フリーレント外）／許認可・登記費用／その他

**treatment の考え方（合計を3つに分けて出す）**

| treatment | 例 | 合計の見せ方 |
|---|---|---|
| 返還される預け金 | 敷金・保証金（償却分を除く） | 「預け金」＝出ていくが戻る |
| 資産計上（減価償却） | 内装工事・厨房機器・什器 | 「設備投資」＝月々の減価償却でPLに乗る |
| 費用 | 礼金・仲介手数料・求人費・開業前人件費・償却 | 「開業費用」＝開業月（または開業費として償却）にPLに乗る |

画面には **「初期投資合計」「うち戻る分」「うち月々の償却額」「回収見込み（合計 ÷ 月次営業利益）」** を自動表示する。

### 3.2 経営PLへの反映ルート

既存の借入返済連携（F-8: `info.loan_repayment_monthly` → 経営D）と同じ型で作る。

```
info.store_investments
   └ ビュー info.v_store_investment_monthly（店舗×年月: 減価償却額・開業費用・投資累計）
        └ keiei-kd-refresh（op=investment_monthly）が読み取り
             └ kd_pl_monthly_summary に depreciation（減価償却）・opening_cost（開業費用）列を追加
                  └ 経営PLボードに「減価償却」「開業費」「投資回収」の行が出る
```

- PLボード側は既に「簡易CF（法人税等・減価償却費・返済元金）は未計算」と記録されている（WORKLOG 2026-09-06）。この提案でその減価償却の穴が埋まる。
- 減価償却は**簡易計算（耐用年数から定額・月割）で確定**（§9-1）。会計（MF）との連携は将来。

## 4. 【C】期限アラートの自動生成とポータルホーム連携

### 4.1 期限を「手入力」から「元データから自動生成」へ

今は物件の更新日を登録したうえで、別途「期限の管理」にも同じ日付を入れている。これをやめる。

| 期限の種類 | 元データ | 自動生成ルール |
|---|---|---|
| 物件契約の更新 | `properties.renewal_date` | 解約予告期間（例: 6ヶ月前）を逆算して「判断期限」も同時に作る |
| 営業許可証 | `deadlines`（種類=営業許可） | 手入力のまま（元データが無いため）。**種類を選択式**にし、許可証PDFを必須添付 |
| 深夜酒類提供・防火管理者・消防点検・食品衛生責任者 | 同上 | 種類を選択式に追加 |
| リース満了 | 取引先ルール（【D】）のリース契約終了月 | 自動 |
| 借入完済・据置終了 | `loans` | 自動 |
| 在留期限（外国籍従業員） | `employees`（在留期限列を追加） | 自動。**90日前**に人事へ |
| 保険更新 | `deadlines` 手入力 | 種類を選択式に追加 |

`deadlines` に追加する列: `kind`（選択式）／`severity`（重要・通常）／`remind_days`（何日前に知らせるか。種類ごとの既定値）／`source_table`・`source_id`（自動生成元）／`document_id`／`done_at`（更新済み）。

### 4.2 ポータルホームへの連携（重要なものだけ）

- ポータルの「⚠️要対応（横断）」ウィジェット（`panel_alerts`）に **社内情報の期限** を1つの情報源として追加する。
- `info` スキーマはRLSが別なので、ポータルからは **RPC `info_alerts_for_portal()`**（security definer）1本で取る。返すのは「severity=重要 かつ 期限まで60日以内 or 超過」のみ。役割で絞る（マスター・本部＝全店、店長＝自店のみ）。
- 表示例: `🔴 恵比寿店 営業許可証 あと12日` → クリックで社内情報の店舗カルテ「許認可・期限」タブへSSO遷移（既存の `/sso?to=` を使う）。
- 通知: 既存の本部タスクの通知経路（Chatwork）に「期限の30日前・7日前・当日」を流す。社内情報側の通知画面は残す。

**ポータルに出す／出さない の線引き（初期値）**

| 出す（重要） | 出さない（社内情報の中だけ） |
|---|---|
| 営業許可・深夜酒類・防火管理者の期限 | 保険更新・ドメイン更新などの軽微なもの |
| 物件契約の解約予告期限・更新期限 | 完了済み・90日より先のもの |
| 在留期限（90日以内） | |
| 承認待ちの変更申請（既にバナーあり） | |

## 5. 【D】取引先マスタの一本化（v2: 正本は社内情報側）

**結論（ユーザー決定）: 正本は社内情報の `info.suppliers`。ポータルの `public.vendors` は会計に必要な情報だけを自動で受け取る。**

理由: 取引先には銀行・保険・行政書士・大家など会計の請求書処理に出てこない相手も多く、それらをポータルの会計用マスタに置くのは不自然。逆に、住所・電話・担当者・メール・名刺・契約書といった「会社の連絡先台帳」は社内情報の役割。

### 5.1 `info.suppliers` を正本として拡張する項目

| 項目 | 内容 |
|---|---|
| 基本 | 取引先名・正式名称・法人番号・種別（仕入／広告／リース／通信／水道光熱／銀行／保険／専門家／不動産／その他）・取引状況 |
| 連絡先 | 住所・電話・FAX・メール・Web・担当者（複数: 氏名・部署・携帯・メール）・**名刺画像**（`documents` に supplier_id を追加して添付） |
| 契約 | 契約書PDF・契約開始/終了月（→ 期限【C】へ自動連携）・取扱店舗（複数） |
| 支払ルール（会計へ連動する部分） | 頻度／金額の性質・月額目安／勘定科目・補助科目の既定値／支払方法／支払口座（自社側）／支払ルール文（「月末締め・翌月16日振込」）／対象店舗 |
| フラグ | **`is_accounting`（会計対象＝ポータルへ連動する）** |

### 5.2 ポータル `public.vendors` への連動（一方向・自動）

```
info.suppliers（正本・社内情報で入力）
   └ is_accounting = true の行だけ
        └ DBトリガー（同じSupabase内・cross-schema）で public.vendors を upsert
             （名称・勘定科目既定・支払方法・支払ルール・頻度・対象店舗・info_supplier_id）
                  └ 請求書処理・自動仕訳・振込タスク・支払予定表が使う
```

- `vendors.info_supplier_id`（9/8に追加済み）をそのまま連動キーにする。
- **取引先の振込先口座（`vendor_bank_accounts`）は請求書処理用なのでポータル側に残す。** 社内情報からは参照表示のみ。
- ポータル側で「新しい取引先」が必要になったとき（請求書処理中など）は、ポータルのフォームから **RPCで `info.suppliers` に登録**し、トリガーで `vendors` に出る（入力は常に1箇所）。ポータル側の取引先の直接編集は「会計項目のみ」に制限する。
- 移行: 既存 `vendors` の行を `info.suppliers` へ取り込み（名称一致で紐付け、残りは新規作成・`is_accounting=true`）。9/5の取引先ルール一覧（103社）はCSVで `info.suppliers` に取り込む。

## 6. 【E】従業員: 基本情報はnippo参照、給与はスマレジ連携データを表示（v2）

要件定義の原則（人の本籍地＝nippo、給与＝社内情報の特別機密）に現状を合わせる。**給与データはポータルが既にスマレジ・タイムカードAPIから取得している**（`sf_payroll_sync`: 支給合計・固定給・通勤手当・控除内訳・差引支給額、月次）ので、社内情報はそれを表示する側になる。

| 情報 | 今 | 提案（確定） |
|---|---|---|
| 氏名・カナ・生年月日・連絡先・住所・国籍・入社日・雇用形態・役職・所属店舗 | 社内情報とnippoの両方に手入力 | **nippoが正本**。社内情報は参照表示のみ。社内情報側の入力欄は「切替日」に削除（§9-7） |
| 給与体系（時給・固定給・賞与・交通費） | `employee_salaries` | そのまま社内情報が正本（機密） |
| **給与明細（毎月の支給実績）** | `sf_payroll_sync`（スマレジAPI）＋PDFは `payroll-pdfs` バケット（給与仕訳時に添付） | 社内情報の従業員カルテ「給与」タブで **月別一覧・年別推移（支給額・控除・振込額）・PDF閲覧** を表示。新テーブルは作らず、`sf_payroll_sync` と `payroll-pdfs` を参照する。閲覧は本人・マスター・給与権限者のみ（RLS/Storageポリシーを本人条件で追加） |
| **年末調整・源泉徴収票・法定調書** | 無し。スマレジ・タイムカード上で年末調整を実施 | 新設 `info.tax_documents`（従業員×年×種類: 源泉徴収票／扶養控除等申告書／保険料控除申告書／源泉徴収簿、PDF）。**スマレジAPIでの取得は現時点で確認できない**（ヘルプ上は管理画面からPDF/CSV出力）ため、年1回の**一括アップロード（ファイル名の氏名・年で自動振り分け）**で保管する。API提供が確認できたら `smaregi-payroll-sync` と同じ型で自動取得に切り替える |
| 人件費（経営PL） | DB_PL手入力＋精算書 | **スマレジ連携の `sf_payroll_sync`（＋`sf_payroll_allocations` の店舗按分）を人件費の正本にする方向**（ユーザー決定）。経営D側の切替はレーンP/担当Aの範囲 |
| 労働条件通知書・雇用契約書・在留カード | `documents` に店舗単位 | `documents` に **employee_id** を追加し、従業員カルテの「書類」タブから見る |
| 在留期限・資格更新 | 無し | `employees` に列追加 → 【C】の期限へ自動連携 |

- 給与計算そのものは作らない（要件定義§19）。

## 7. 【H】データ交通整理表（この情報はここに入れる）

| 情報 | 正本（入力する場所） | 参照する側（自動） |
|---|---|---|
| 法人（名称・番号・代表者・口座） | 社内情報 `info.corporations`（ハブと統一済み） | ポータル・経営D・請求書処理 |

## 8. 【G】UI整理の方針

**狙い: 「今日やること・危ないもの」が最初に目に入り、それ以外は静かに並んでいる状態。**

| 項目 | 今 | 提案 |
|---|---|---|
| 色 | 青・赤・黄・緑の4色＋絵文字 | **基本1色（今の青 #1f5fbf）＋警告2色**（赤＝期限超過・要対応／黄＝30日以内）。緑は使わない（「正常」は色を付けない）。絵文字は見出しから外し、必要なら単色アイコン |
| トップ画面 | 承認待ちバナー→期限→店舗一覧→12カテゴリの縦積み | 上段「要対応」（承認待ち・期限・自分宛て）だけ色付き。中段「店舗カルテ」の一覧カード（店舗ごとに 営業許可残日数・契約更新・未入力の項目数）。下段は4グループのメニュー |
| カテゴリ | 12個が横並び | 4グループに整理: **会社**（法人・銀行・借入・不動産）／**店舗**（店舗カルテ＝物件・ライフライン・許認可・ID/PW・取引先・広告媒体）／**人**（従業員・給与明細・申請）／**横断**（書類・写真・期限・検索） |
| 一覧表 | カード羅列 | 表形式（見出し固定・並び替え・検索欄を常に上部）。スマホはカード |
| 文字の階層 | 見出しと本文の差が小さい | 見出し16px太字／ラベル12px灰／数値は右揃え・等幅 |
| 法人切替 | 上部で切替 | 維持。ただし店舗カルテでは店舗→法人が自動で決まるので切替不要にする |
| 入力画面 | 1画面に全項目 | 必須項目を上に、任意は折りたたみ。保存後は一覧に戻らずカルテに留まる |

まず「トップ画面」と「店舗カルテ」の2画面をモックで作って確認 → 他画面へ展開、の順が安全。
