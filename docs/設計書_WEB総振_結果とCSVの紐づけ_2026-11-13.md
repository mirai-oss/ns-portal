# 設計メモ（下書き）: PayPay 銀行 WEB総振の「結果の画面」と「CSV」の紐づけ

作成: 2026-11-13　状態: **下書きだけ**。本番への適用・デプロイ・commit・push・DB への書き込み・銀行や外部への接続・Playwright の実行は、どれもしていない。
書き方: 確かめた事実は「事実」、確かめていないことは「未確認」「確認待ち」と書く。口座番号・名義・金額そのものは、このメモに書いていない。

## 0. 先に結論（4 行）

1. **CSV には、1 件ごとの成功・失敗が入っていない**（事実）。だから「CSV の件数・合計が合った」だけでは、だれも「成功」にしない。
2. 行ごとの結果を「成功」と記録するのは、**詳細の画面の行（明細番号・科目＋口座番号・名義・金額・状態）と CSV の行が、全件 1 対 1 で結べたときだけ**。
3. 結べないとき（画面が読めない・形が変わった・1 対 1 にならない）は、**何も送らずに止まる**。一覧と件数だけが取れた場合は、取引（合計）だけを記録し、行の結果は「不明」のまま＝バッチは「確認待ち」。
4. 後日の組戻し・振込先エラーが画面にどう出るかは **未確認**。確かめ方は §6。

## 3. 画面の行と CSV の行の結び方（1 対 1）

結ぶ鍵は **科目＋口座番号（7 桁）＋名義（そろえたカナ）＋金額** の 4 つ。4 つとも同じときだけ結ぶ。名義だけ・金額だけ・口座だけでは結ばない。

- 名義は、画面が全角カナ・CSV が半角カナなので、DB と同じ決まり（全角にそろえる・小さいカナを大きく・伸ばし棒とハイフンを同じ・空白を消す）でそろえてから比べる。
- 銀行・支店は、画面には **名前しか出ない** ので、画面の行と CSV の行の間では比べられない（確認待ち: 名前とコードを結ぶ表を持つかどうか）。代わりに、
  - CSV は、その受付番号の詳細の画面から落としたもの（同じ画面・同じ回）、
  - CSV のヘッダーの出金口座・振込指定日が、画面と同じ、
  - 件数・合計が、一覧・詳細・CSV の 3 つで同じ、
  を全部確かめる。金融機関コード・支店コードは CSV の値を使う。

手順

1. 明細番号が 1〜N の連番で、明細番号 k の行と CSV の k 行目が、**全件**この鍵で一致 → 位置で結ぶ。
2. 1 が成り立たないとき → 鍵が、画面の側でも CSV の側でも **1 つずつしか無い** 行だけを結ぶ。全行が結べたら OK（「並びが違った」と記録）。
3. 1 行でも結べない（鍵が合わない・同じ鍵が 2 行・口座が読めない・件数が違う）→ **何も送らない**。

つじつまの確かめ（1 つでも合わなければ、何も送らない）

- 一覧の件数＝CSV の件数。一覧の振込金額＝CSV の合計。一覧の振込金額＋手数料＝合計金額。
- 一覧の振込日＝CSV のヘッダーの振込指定日（月日）。一覧・詳細の出金口座＝CSV のヘッダーの出金口座。
- 詳細の受付番号＝一覧で選んだ受付番号。
- 詳細の「正常件数」＝行ごとに読んだ「正常」の数。
- 一覧が「振込正常」なら、エラー 0 件・正常件数＝件数・全行が「正常」。
- ページ送り: 「総件数 N 件（a〜b 件表示）」が、1 から N まで抜けも重なりも無くつながること。同じ明細番号が 2 回出ないこと。

止めずに「気づき」として残すもの: 実行日と振込日が違う／正常件数＋エラー件数が件数と違う（実行中など）／行の状態に知らない言葉がある（その行は「不明」）。

## 4. 「CSV の金額が合っただけでは完了にしない」の守り方（3 段）

| どこまで確かめられたか | ジョブが渡すもの | DB での結果 |
|---|---|---|
| **A. 詳細の画面の全行が、CSV の行と 1 対 1 で結べた** | 出どころ `screen_rows`。行ごとに、画面で読んだ状態（正常→success など） | 行が予定者と結べて、全件成功・一覧が「振込正常」なら「PayPay 銀行明細照合済み」（自動完了のスイッチが OFF のあいだは、ここで止まる） |
| **B. 一覧の「振込正常」＋「正常 N 件・エラー 0 件」＋ CSV の件数・合計の一致だけ**（行は読めていない） | 出どころ `summary`。行の結果は **不明** | 口座・名義・金額が予定者と全部合っても、行は成功にならず、バッチは「確認待ち（銀行の結果が確定していない）」。人が「完了にする」も押せない |
| **C. CSV だけ／画面と合わない** | 何も送らない | 何も変わらない |

DB の側の守り（追加の SQL）

- 出どころが `summary` の取り込みで、行に「成功・失敗・組戻し」が入っていたら、**取り込みごと断る**。
- 画面の行で確かめた結果（`screen_row`）は、あとから来た `summary` の取り込みで **上書きしない**。
- ロボット（サービス用の鍵）からの取り込みは、スイッチ `bank_read_enabled` が ON のときだけ。出どころの指定が必須。

B をどこまで根拠にできるか（整理）

| 根拠 | 言えること | 言えないこと |
|---|---|---|
| 一覧「振込正常」 | 銀行が、その受付番号の処理を「正常に終了」と表示している（画面の説明どおり） | 1 件ずつの結果。あとから組戻しになった行があるか（未確認） |
| 詳細「正常 N 件・エラー 0 件」 | N 件すべてが正常、と銀行が数えている | **どの口座の N 件か**（数だけなので） |
| CSV の件数・合計＝一覧 | CSV が、その取引と同じ件数・同じ合計であること | CSV の各行が、画面の各行と同じであること（同じ合計になる別の組み合わせを、数だけでは区別できない） |

→ 3 つがそろえば「全件成功」と **推定はできる** が、行と行の対応を目で（機械で）確かめたわけではない。そこで、既定では成功にしない。スイッチ `summary_success_ok`（既定は無い＝OFF）を ON にしたときだけ、B の 3 つがそろった場合に成功として受け付ける入口を用意した（**使うかどうかは確認待ち**。使わないなら、この入口は消してよい）。

## 6. 後日の組戻し・振込先エラー（未確認）と、確かめ方

未確認のこと

1. 詳細の行の「状態」が、エラーのとき・組戻しのあとで、どんな言葉になるか（いまの読み取りは、推定で「エラー・不能→失敗」「組戻・返却→組戻し」に当てている。当たらない言葉は「不明」＝確認待ち）。
2. 「振込正常」になったあとで組戻しがあった場合、一覧の状態・詳細の正常件数が変わるか。それとも、別の画面（一般取引の「組戻（資金返却）依頼・組戻回答受付」）や、普通預金の入金明細にだけ出るか。
3. 振込先エラーのとき、一覧が「振込先エラー」になるのは、1 件でもエラーがあるときか、全件エラーのときか。エラーの行の金額は、振込金額・手数料にどう入るか。
4. 「エラーのみ」を選んでダウンロードした CSV の形（全銀形式のままか・エラーの理由の列が足されるか）。
5. 表示が「照会日から 31 日前まで」なので、31 日を過ぎた取引は読めなくなる。それより後の組戻しを、どこで知るか。

確かめ方（どれも、読むだけ。**「再振込」「組戻」は押さない**）

| # | 確かめ方 | 分かること |
|---|---|---|
| 1 | 振込の翌営業日・1 週間後に、同じ受付番号の詳細を、第 2 段階のジョブでもう一度読む（保存先の `data/detail.json` を、前の回と比べる。比べるのは状態の言葉と件数だけ） | 後日、状態・件数が変わるか |
| 2 | 過去 31 日の一覧に「振込先エラー」「振込元エラー」の取引があれば、その詳細を読む（無ければ、起きたときに読む） | エラーの言葉・件数と金額の出方 |
| 3 | 毎日の入金取得（普通預金の明細）で、「振込金の返却」に当たる入金が無いかを見る（摘要の言葉は未確認。まず、入金の行のうち摘要に「返」「組戻」「フノウ」を含むものの件数だけを数える） | 組戻しのお金が、どんな摘要で戻るか |
| 4 | 銀行のヘルプ・操作マニュアル（WEB総振の「振込結果照会」の章）を読む | 状態の言葉の正式な一覧・31 日を過ぎたあとの照会の方法 |
| 5 | 銀行のサポートに問い合わせる（依頼主から） | 「振込正常のあとの組戻しは、WEB総振の画面に反映されるか」 |

それまでの扱い: 完了のあとも、設計どおり 10 営業日は読み直す。読み直して「正常」以外になった行があれば、その行を失敗・組戻しにする（既存の作り）。画面に出ない組戻しは、入金明細の側から人が気づいて手で記録する（確認待ち）。

## 7. 再振込の振込先の決め方（直す点）

これまで: 再振込は、**いまの登録口座** を無条件に使う（既定）。→ 口座の変更が承認されたばかりで本人の意図と違う・逆に、直したはずの口座が使われない、を見分けられなかった。

これから

1. 元の行の振込先（固めたときの控え）と、いまの登録口座を、金融機関・支店・種別・口座番号＋名義カナで比べる。
2. **同じ** → そのまま使える（比べた結果「同じ」を残す）。
3. **違う**（いまの登録口座が無い・読めない場合も含む）→ 呼ぶ側が、行ごとに「元の口座」か「いまの口座」かを **理由つきで** 選ぶまで、固められない。選ぶ前は、「どこが違うか（金融機関・支店・種別・口座番号・名義のどれか）」だけを返す（口座番号そのものは返さない）。
4. 比べた結果・選んだ人・理由は、行の列（書きかえ不可）と履歴（`retry_account_decided`）に残る。
5. まとめての指定（`p_account_source`）は、再振込では使えないようにした（行ごとに決めるため）。追加・差額は今までどおり。

注意（確認待ち）: 元の行が「口座の誤り」で失敗していて、登録口座が直っていない（＝同じ）場合、そのまま再振込すると、また失敗する。関数は止めない（「同じ」と返すだけ）。画面で、失敗の理由と一緒に注意を出すかどうか。
