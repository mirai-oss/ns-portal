# N-Styleグループ ダッシュボード統合・アカウント1本化 要件定義書

作成日: 2026-08-05 ／ 承認: 未 ／ 版: 1.0

## 1. 背景と目的

グループ内に4つのシステムが並立し、URL・アカウント・店舗の呼び名がバラバラになっている。

| システム | 画面 | データ | ログイン方式（現状） |
|---|---|---|---|
| 経営ダッシュボード (tori-dashboard) | GitHub Pages | GAS + スプレッドシート + BigQuery | 独自ID/PW（アカウントシート） |
| 精算ダッシュボード (seisan-dashboard) | GitHub Pages | GAS + 精算書スプレッドシート | 独自ID/PW（権限シート） |
| 社内情報管理システム (ns-info-system) | Vercel (Next.js) | Supabase `wciefkpooncglahqdtmu` | Supabase Auth（メール+PW） |
| 日報・週報システム (nippo) | GitHub Pages | Supabase `uuvsxzhpxtghojoubjcc` | Supabase Auth（メール+PW） |

目的:
1. **アカウントの1本化** — 1人につき1つのメールアドレス+パスワードで全システムに入れる状態にする
2. **入口の1本化** — ポータル1ページから権限に応じて各システムへ遷移
3. **店舗マスタの1本化** — 社内店舗番号（01〜12）を全システム共通の正準キーにする

### ハブを日報プロジェクトにする根拠

- 日報システムには決定した役割体系がほぼそのまま実装済み（`CEO=社長 / HQ=本部 / TEAM=チーム長 / TENCHO=店長 / SHAIN=社員 / AL=アルバイト`）。マスターのみ追加
- 従業員全員（アルバイト含む）のアカウントが既に存在する唯一のシステム
- stores（8店舗）の店舗名が経営ダッシュボードの正式名と完全一致
- 招待リンク・スマレジ連携・Lark通知・権限マトリクスなどアカウント管理機能が既に揃っている
- 社内情報管理システム側のSupabaseは利用者が少数（社長・本部中心）なので、後からハブへ寄せる方が移行が小さい

## 5. 認証アーキテクチャ

### フェーズ1（今回）
- **ポータル** (GitHub Pages / `mirai-oss/ns-portal`): ハブのSupabase Authへメール+PWでログイン → `users`テーブルから役割を取得 → マトリクスに従いシステムのタイルを表示
- **日報**: 既にハブ直結。同じメール+PWでそのまま入れる（=1本化済み）
- **経営D・精算D・社内情報**: タイルからリンク遷移（ログインは当面それぞれの方式）

### フェーズ1b（経営ダッシュボードのSSO）
- app.jsのログイン画面に「統合アカウントでログイン」を追加
- 流れ: ポータル/経営DでSupabaseログイン → `access_token`をGASへ送信 → GASが`GET {SUPA_URL}/auth/v1/user`で検証（公開キーのみで可・秘密鍵不要） → メールアドレスをアカウントシートの新設「メール」列と突き合わせ → 従来のセッショントークンを発行
- 既存ID/PWログインは並行稼働（削除しない）。GAS再デプロイ1回必要

### フェーズ2
- 精算D本部ユーザーのSSO（委託先は対象外・従来どおり）
- 社内情報管理システムをハブプロジェクトへ移設（テーブルは`info`スキーマ等に分離して衝突回避）し、アカウントを完全統合
- 独自ドメイン（例: `portal.ns0314.com`）+ 配下パスに集約 → **同一オリジンになるためログインセッション自体も共有可能になる**

### フェーズ3（脱スプレッドシート）
- 経営ダッシュボードのデータ基盤をGAS+シートからSupabase（ハブ）へ段階移行。BigQueryは明細分析専用に残す
- 現状の初回表示28秒はGAS往復が原因（実測済み）。移行前の暫定策としてGAS側の無駄取り（setupIfNeeded毎回実行の停止等）で5〜7秒まで短縮可能

## 6. 非機能要件・制約

- 稼働中の自動処理（Lark自動日報 毎日12:00 / 精算トリガー 1日・5日・18日 / ns-daily-import 毎朝 / PL取込）を止めない。既存テーブル・シートの列削除や改名はしない（追加のみ）
- 公開リポジトリに秘密情報を置かない（Supabaseのpublishableキーは公開前提の設計なので可。service_roleキー・PATは絶対に不可）
- ハブのRLSポリシーは今回変更しない（列追加・行追加のみ）
- 委託先がハブのアカウントを持たないこと（精算の分離要件）

## 6.5 データ横断の方針（2026-08-05 追記）

ユーザー要望: **「どの管理システムからでも横断して情報がやりとりできる状態にしたい」**。
具体例として、従業員の給与情報・評価項目・評価点数を社内情報管理システムか日報のどちらかで見たい。

そのための原則:

1. **同じ人・同じ店舗は同じIDで指す** — 人＝ハブ `public.users.id`、店舗＝`store_no`（01〜12）。
   新しいテーブルを作るときは、氏名や店舗名の文字列ではなく必ずこのIDを外部キーにする。
2. **評価データはハブに置く** — 評価は「日報の提出状況・売上実績・勤怠」と突き合わせて意味を持つため、
   日報と同じデータベース（ハブ）に置くのが最も自然。社内情報管理システム側から見せる場合も、
   ハブの `info` スキーマへ移設後であれば単純なJOINで済む。
3. **給与は分離した金庫に置く** — 社内情報管理システムは既に `employee_salaries` を
   別テーブル＋RLSで保護している。移設後も同じ分離を維持し、閲覧は役割ベースで絞る。
4. **どのシステムから書いても正は1箇所** — 例: 評価点数を日報から入力しても社内情報から入力しても、
   保存先は同じ `info.employee_evaluations`（仮）1テーブルとする。

この方針により、後から「日報側で評価を見る」「社内情報側で見る」のどちらにも対応できる。
