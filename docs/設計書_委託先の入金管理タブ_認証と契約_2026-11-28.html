委託先の入金管理タブ — 認証と契約の設計書

作成 2026-11-28 ／ 読み取り調査のみ（コード・DB・GAS・本番設定は一切変更していません）／ 公開リポジトリのため、口座番号・金額の実額・秘密の値は書いていません。
表記：【事実】＝ファイルで確認できたこと　【推測】＝ファイルから読み取った推測　【未確認】＝分からなかったこと
結論（先に）
  • 現行の精算ダッシュボードの認証（平文パスワード・失敗回数の制限なし・トークンを平文で保存）は、銀行入金を委託先に出す認証としては不十分。
  • MVP（自店舗の入金日・入金額だけ）は、新しい認証（招待＋ワンタイムリンク、ハッシュ保存のトークン）とサーバー側で契約から店舗を確定する仕組みを最初から入れる。現行ログインは止めず、入金タブを開くときだけ別の認証を求める。
  • MVPの実作業は約24時間（1人で連続3日分、2人並行なら約16時間）。本番公開に必要な承認は6件（§1-5）。売上・入金予定・差額はMVPの後。
最初に知っておくべき食い違い：作業用の seisan-dashboard フォルダは古い版（最終コミット 2026-10-01・GAS版）。WORKLOGによると本番は 2026-11-26 に Supabase の Edge Function seisan-api へ切替済み（旧GASは凍結、11/28 にメールアドレスでのログインを追加）。seisan-api のソースはこの手元には無いため、現在の本番の認証の中身は読めていません。§2 の評価は「手元のGAS版」についての事実で、本番の seisan-api については【未確認】です。また sd_dash_grant の定義（CREATE文・RLS・GRANT）は、手元のどのSQLにも見つかりません（WORKLOG・計画書に名前が出るだけ）。

1. MVP（最小構成）— 最優先

1-1. MVPの範囲

出す自店舗（契約対象店舗）の入金日・入金額（日ごとの合計と件数）。既存の精算書画面に「入金」タブを1つ足す（閲覧専用）。
出さない口座番号・残高・CSV原本・摘要（振込人名等が入り得る）・他店舗／他法人の情報・訂正や承認の履歴・保留中の金額。売上・入金予定額・差額はMVPの後（§5-3）。
必須条件①
認証		平文パスワードに頼らない／トークンはハッシュだけ保存／有効期限あり／失効できる（契約終了・本人・管理者）。
必須条件②
他店舗の防止		ブラウザから委託先ID・店舗IDを一切受け取らない。トークン → 担当者 → 委託先 → 有効な契約 → 対象店舗・期間を、サーバー側で毎回確定する。

1-2. MVPの構成（これだけ作る）

  1. DB（新規表・追加のみ）：contractors（委託先）／contractor_users（担当者・メール）／contractor_contracts（開始日・終了日・閲覧可能期間）／contractor_contract_stores（契約の対象店舗）／contractor_invites（招待・ログインリンク・確認コードのハッシュ）／contractor_access_log（追記専用の監査・回数制限の元）。トークンの入れ物は既存 sd_dash_grant にnullable の列を足して使う（§3-2・先に本番のDDLを読んで確認する）。
  2. DB関数（RPC）：contractor_deposit_view(p_user uuid, p_from date, p_to date)（service_role だけが実行可。引数は担当者IDと月の範囲だけ。店舗IDも委託先IDも引数に無い）。管理用：招待発行・契約登録・失効（本部／マスターだけ、理由必須）。
  3. Edge Function contractor-portal（1本・verify_jwt=falseで独自トークン）：redeem_invite（招待リンク＋確認コード→セッション）／login_request・login_verify（メールのワンタイムリンク）／logout／deposits（月を受け取り、許可リストの項目だけ返す）。サービスキーはこの関数の環境変数にだけ置く。
  4. 画面：精算書の画面に「入金」タブ。開くとき現行ログインとは別に、この認証を求める（段階的な本人確認＝step-up）。トークンはURLに載せず、Authorization ヘッダ＋sessionStorage（タブを閉じれば消える）。

1-3. MVPの認証の流れ（利用者目線）

  1. 本部が担当者（メール）と契約（開始日・終了日・対象店舗）を登録し、招待リンク（72時間・1回限り）を発行 → 委託先へメールで送る。
  2. 本部が別の経路（電話・LINE等）で6桁の確認コードを伝える（本人確認。5回間違えると無効）。
  3. 委託先が招待リンクを開き確認コードを入れる → セッション発行（アイドル60分・最大12時間）。
  4. 2回目以降は、登録メールを入力 → メールのワンタイムリンク（10分・1回限り）→ セッション。パスワードは存在しない。
  5. 画面の「ログアウト」で自分のセッションを全て失効。管理者は強制失効できる。契約終了日を過ぎると、翌リクエストから自動で空になる（毎回、契約の期間を計算するため。ジョブに頼らない）。

観点確認できたこと（根拠）評価
パスワードの置き場所【事実】スプレッドシートのシート 権限_精算ダッシュボード のB列に平文で置く（gas/SeisanDashboard.gs の sd_authSheet_・sd_findAccount_）。照合は文字列の単純比較（sd_login：String(acc.pw) !== String(pw)）。このシートを開ける人は全員のパスワードが見える。誰が開けるかは【未確認】。不十分
初期パスワードの強さ【事実】新規作成時の初期パスワードは Utilities.getUuid().split('-')[0]（16進8桁＝約32bit）で、シートと実行ログに平文で出る。弱い
総当たり対策【事実】失敗時は Utilities.sleep(500) だけ。失敗回数の記録・ロックアウト・IP制限はコード上に無い。READMEの手順では、Webアプリは「アクセスできるユーザー：全員」で公開。【推測】並列に試せば1リクエストごとの0.5秒待ちでは止まらない。Supabase側に回数制限の表も手元のSQLに見当たらない。対策なし
セッションの持ち方【事実】トークンは UUID（ランダム）。GASの Script Properties に sdtok_<トークン> の名前で、さらに Supabase の ds_sessions（token が主キー）にトークンそのまま保存（ハッシュではない）。期限は使うたびに +336時間（14日）の延長。ブラウザは localStorage の sd_token に保存（index.html）。ds_sessions は RLS ポリシー無し＝service_role だけ（ns-portal/supabase/2026-09-18_ds_sessions.sql）。ハッシュ保存なし・14日の延長式
URLパラメータ経由【事実】doGet は ?fn=…&args=[…] で関数を呼べる。画面（apiGet_）は POST がネットワークで失敗するとGETに自動で切り替え、引数（トークン、ログイン時はIDとパスワード）をURLのクエリに載せる。履歴・中継・サーバーの記録に残り得る。漏れ得る
委託先の店舗の絞り込み【事実】サーバー側で行っている（sd_allowedStores_・sd_listAttachments・sd_getPdfB64 が権限を確認）。ブラウザから店舗IDを受けて信用する作りではない。ただし担当店舗が空欄または「全店」なら、委託先でも全店が見える（sd_allowedStores_ の先頭の条件）＝入力ミスで全店が見える。店舗は名前の文字列一致。役職の不明な文字列は「委託先」扱い（安全側）。概ね良いが空欄で全開
GASの権限の大きさ【事実】「次のユーザーとして実行：自分」で、Drive・スプレッドシートを所有者の権限で触る。さらに SUPABASE_SERVICE_KEY（service_role）を Script Properties に持つ読み取りコードがある（sd_sessionSupaHeaders_）。GASのスクリプトを編集できる人・侵害された場合、DB全体に届き得る（鍵の現在の有無は【未確認】）。侵害時の被害が大きい
機械間の合言葉【事実】sd_api* は PL_SYNC_TOKEN を !== で比較（定数時間比較ではない）。委託先の画面とは別系統だが、同じ公開URLで呼べる。軽微
統合ログイン【事実】本部・マスターは Supabase のトークンを検証して入る設計で、パスワードはGASを通らない。委託先は対象外（sd_supaLogin）。公開キー（publishable）は公開してよい種類。良い
本番の現状（11/26〜）【事実（WORKLOGより）】画面は seisan-api（Edge Function）に切替済み。11/28「ログインIDまたはメールアドレス」。メールの場合、本部・マスターは先にポータルのパスワード、だめなら精算側のパスワード、委託先も登録メールで可。パスワード再設定・利用申請メールは実画面で未確認。【未確認】ハッシュ・回数制限の有無

評価の結論：手元のGAS版は「パスワード＝平文」「失敗回数の制限なし」「トークン＝平文保存・14日延長」「URLに引数が載る経路あり」。銀行入金を委託先に出す認証の土台には使わない。本番の seisan-api が改善済みの可能性はあるが、確認できていないため前提にしない。MVPは現行ログインから切り離した別の認証を入金タブにだけ追加する。

3. 提案する構成（完全版）

3-1. 経路

  • ブラウザ（精算画面・GitHub Pages）→ Edge Function contractor-portal（独自トークンの検証・回数制限）→ DB関数（service_role 専用）→ 許可リストの項目だけ返す。
  • ブラウザはサービスキーを持たない。GASは入金タブの経路に入れない（GASの侵害・鍵の保管を避ける）。
  • 委託先は Supabase Auth のユーザーにしない。【推測】Supabase の認証済みトークン（authenticated）は PostgREST から直接テーブルに届く。既存のポリシーは to authenticated を前提にしたものが多く、11/26 にも匿名の露出を閉じる作業があった。委託先が authenticated になると、既存表の取り違えのリスクを背負う。独自トークンなら、DB関数以外には届かない。
  • CORSは精算画面のオリジンだけ許可（既存関数は * が多いが、これは新規なので絞る。CORSは認証の代わりではない）。

3-2. トークンの発行・保存・有効期限

項目設計
誰が発行招待＝本部／マスター（理由・発行者を記録）。セッション＝本人確認に成功した委託先の担当者（Edge Functionが発行）。
形式256bitの乱数（base64url）。DBには SHA-256（さらにサーバー秘密でHMAC）のハッシュだけを保存。平文はブラウザにしか無い。ログ・エラーに出さない。
保存先セッション＝既存 sd_dash_grant（token_hash・scope_key・user_name・user_role・expires_at）に、nullable の列を追加：contractor_user_id uuid・kind text（'session'）・issued_at・idle_expires_at・last_used_at・revoked_at・revoked_by・revoke_reason。expires_at は最大期限。scope_key は参考表示で、権限の判断には使わない（毎回、担当者→契約から再計算）。【未確認】sd_dash_grant の既存の使われ方・行・RLS。それが確認できるまで、使い道が違う場合は別表 contractor_sessions にする。招待・ログインリンクは別表 contractor_invites。
有効期限招待リンク72時間・1回限り／ログインリンク10分・1回限り／確認コード10分・5回失敗で無効／セッション：アイドル60分・最大12時間（銀行情報なので現行の14日延長は踏襲しない）。
URLに載せない招待・ログインのトークンは URLのフラグメント（#以降）に置き、画面がPOSTで引き換える（メールのリンクチェック機能が先に開いても消費されない・サーバーの記録に残らない）。セッションは Authorization ヘッダのみ。GETでは受けない。
消費の原子性引き換えは update … where used_at is null and expires_at > now() returning の1文（同時に2回使えない）。

3-3. 失効・再発行

種類方法
契約終了① 毎リクエストで有効な契約を計算（終了日を過ぎたら即、空）。② 夜間ジョブで、有効な契約が1つも無い担当者のセッションを失効（念のため）。
本人から「ログアウト」「すべての端末から失効」（自分のセッション全て）。
管理者の強制失効本部／マスターが contractor_user_suspend(user, reason)：担当者を停止、未使用の招待・セッションを全て失効、記録に残す。自己承認禁止（登録者と契約確定者を別にする）。
自動短時間に多数の失敗、または同じセッションが複数の端末から使われた場合は、そのセッションを失効し、本部へ通知（既存の通知の仕組みの流用。内容に金額は入れない）。
再発行本部が新しい招待を発行（旧招待・旧セッションは失効）。メールアドレスの変更は本部が別経路で本人確認してから（メール変更＝乗っ取りの入口のため、自動では変えない）。

3-4. 本人確認と多要素

選択肢強さ運用負荷推奨
招待リンク＋別経路の確認コード（初回のみ）中（本部が電話等で本人を確かめる）低（委託先は少数と読める。【推測】運営委託先は約2〜3社、実数は【未確認】）MVPで採用
毎回のメールのワンタイムリンク中（メールの持ち主であること）低MVPで採用
TOTP（認証アプリ）高中（設定・機種変更時の復旧）入金タブを広げる段階で必須化を検討
パスキー高・手間が少ない中（対応状況・復旧手順を要確認）【未確認】要調査
SMS低〜中（SIM乗っ取り）・番号管理中・費用採用しない

メールの持ち主＝本人、という前提が崩れる（共有メール・乗っ取り）リスクは残る。担当者は1人ずつのメール（共有メールは不可）を条件にする。

3-5. 回数制限・ロックアウト・監査ログ

  • 表 contractor_access_log（追記専用・更新削除不可）：時刻・担当者ID（不明なら空）・動作・成功／失敗・IPのHMAC・UAのハッシュ・件数・期間。金額・口座・メールの平文は記録しない。保持期間は例：2年（要決定）。
  • 確認コード：1コードにつき5回失敗で無効。ログインリンクの発行：同じメール宛に1時間3回まで。IP単位：15分に10回失敗で429＋待ち時間。応答は登録の有無で変えない（メールの存在を教えない）。比較は定数時間。
  • クライアントIPの取り方（Supabaseの転送ヘッダの信頼性）は【未確認】。IPが信用できなくても、担当者単位・コード単位の制限は有効。

3-6. サーバー側の確定（パラメータに委託先ID・店舗IDを受けない）

  1. 入力は Authorization のトークンと「月（YYYY-MM）」のみ。それ以外のフィールドは無視ではなく拒否（400）。
  2. トークンのハッシュ → sd_dash_grant の行（失効なし・最大期限内・アイドル内）→ contractor_user_id。
  3. 担当者 → 委託先（状態＝有効）→ 今日（JST）有効な契約（valid_from ≤ 今日 ≤ valid_to）→ contractor_contract_stores。
  4. 見える範囲＝契約の閲覧可能期間 ∩ 店舗の適用期間 ∩ 要求された月。範囲外は空（エラー文で理由を詳しく言わない）。
  5. DB関数も同じ導出を自分でもう一度行う（Edge Functionが誤っても関数側で防ぐ二重化）。応答の店舗は、画面用の表示名だけ（内部のUUIDは返さない）。

7. 既存利用者への影響・移行・テスト・承認

7-1. 既存の精算ダッシュボード利用者への影響と移行手順

  1. 段階0（影響なし）：事実確認（承認A）。
  2. 段階1（影響なし）：新規表・関数・Edge Functionを追加。既存の表・関数・画面は変更しない。入金タブはスイッチOFFで非表示。
  3. 段階2（影響なし）：本部の担当者を「テスト委託先」として登録し、使い捨てデータで通す（終了後に完全削除）。
  4. 段階3（パイロット1社）：既存の精算書ログインはそのまま。入金タブを開いた時だけ新しい認証（step-up）。既存のログインで入った人が、入金タブを開けるわけではない。
  5. 段階4：他の委託先へ展開。売上・予定・差額（§5-3の条件後）。
  6. 段階5（別承認）：委託先のログイン全体を同じ「招待＋ワンタイムリンク」へ移し、旧平文パスワード（委託先分）を廃止。本部・マスターは従来の統合ログイン。
  7. 段階6（別承認）：GASに残る service_role 鍵の要否を確認し、不要なら除去。

影響を受けるのは「入金タブを使う委託先」だけで、現行ログインを止める段階は5まで来ない。

7-2. テスト項目

  • 契約外の店舗・日付・月が取れない／契約終了日の前日・当日・翌日／閲覧可能期間の延長あり・なし／店舗が途中で外れる。
  • 他社の担当者のトークンで他社の店舗が出ない／失効後・期限切れ・アイドル切れのトークンが拒否される。
  • 招待・ログインリンクの再使用の拒否／確認コード5回失敗で無効／同時に2回引き換えても1回だけ成功。
  • DB上にトークン・コードの平文が無い（ハッシュのみ）／匿名・認証済みのキーから新規表と関数を直接呼べない。
  • 未知のフィールド（store_id・contractor_id）を付けると400。
  • 応答に許可リスト以外の項目が無い（キー一覧の完全一致テスト）。
  • 本部の画面（bank_deposit_daily）と店舗・日付ごとに数字が一致。保留・未確定の行が合算されない。
  • ログ（監査・Edge）に平文のトークン・メール・金額が無い。スマホ幅・ライト／ダークの表示。
  • 本番でのテストは使い捨ての委託先・店舗・契約で行い、終了後に完全削除して0件を確認。

7-3. 承認が必要な点（まとめ）

§1-5の承認A〜F。そのほか：メールの送信手段の選定（【未確認】）／委託先に入金情報を見せることの契約上・銀行規約上の扱い／売上・予定・差額の公開（MVPの後に別承認）／旧パスワードの廃止（段階5）／GASの鍵の除去（段階6）。
