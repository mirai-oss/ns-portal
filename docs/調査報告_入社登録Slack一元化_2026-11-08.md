## 0. 結論（先に 10 行で）

1. 入社登録の土台は **ほぼ揃っています**。採用管理（応募者→採用→招待リンク→LINE送信→リマインド）、入社フォーム、従業員マスタ、スマレジ従業員登録 API、賃金 API（時給・月給）、本部タスク、Slack 通知基盤（スレッド返信・更新・ボタン・リマインド）はすべて稼働中です。
2. **ないもの**は 4 つ：①入社ワークフローの「状態」を 1 か所で持つ表、②Slack からの賃金・交通費の入力画面、③交通費の経路検索と照合、④スマレジ管理画面の Playwright 操作（交通費・源泉所得税・Web給与明細・メール）。
5. スマレジ API は **賃金（時給 0／日給 1／月給 2・適用開始日・事業所別）は書けます**が、**メール・交通費・源泉所得税・個別Web給与明細は API では書けません**（2026-10-17 に公式仕様で確認済み。GET では読める）。ここだけ Playwright が必要です。
4. Playwright の実行基盤は **Mac mini の ns-daily-import（launchd 3 分ポーリング）** が本命です。既にスマレジタイムカードへ自動ログインして CSV を落とす仕事（smaregi-payroll）が毎朝動いているので、同じ仕組みで「管理画面を操作する仕事」を足せます。
5. 経路検索は **駅すぱあと（Ekispert）API を第一候補**にします。nippo に受け口（EF `ekispert-fare`・設定画面）が既にありますが、**キー未設定で、無料プランでは運賃が取れません**。法人プランの見積り（または買い切り 5,000 件 ¥5,500）が必要です。Google Routes は無料の予備。
6. 日給は DB の制約（division 0/2 のみ）を外せば既存 API でそのまま反映できます。
7. 本部タスク「入社登録（○○さん）」は今後も作りますが、**自動化する 4 項目（時給・交通費・源泉・Web明細）は本部タスクのチェック欄から外し、ワークフロー表の状態で管理**します（重複防止）。
8. 採用管理のバックレは今 `status='noshow'` の 1 値だけです。**離脱段階・離脱理由の列を足し、status は残す**ことで過去との比較を保ちます。
9. 推奨順序は指示書どおり Phase 1（Slack 通知＋スレッド＋賃金設定）→ 2（交通費）→ 3（Playwright）→ 4（例外・中止）→ 5（本人登録確認・完了判定）。Phase 1 は既存部品の組み合わせだけで作れます。
10. 承認いただきたい判断が 6 つあります（§12）。特に「駅すぱあとの契約」「Playwright のための立会い 1 回」「本部タスクのチェック欄の扱い」です。

  5. EF hr-wage-notify：`hr_wage_requests` に 1 行＋ Slack #本部-人事 に「賃金登録をお願いします（Slack 入力は準備中）」。

### 1-3. その後（本部の手作業）
- 賃金：nippo 従業員編集「💴 賃金設定」→ RPC `hr_save_wage` → EF smaregi-sync `wage_push`（**稼働中・214 行 synced**）。

| 交通費 | （書き込み API なし） | — | GET の `transportationCostApply` で読める → **保存後の照合に使える** |
| 源泉所得税 | （書き込み API なし） | — | GET の `withholdingIncomeTaxes` で読める |
| 個別Web給与明細 | （書き込み API なし） | — | GET の `personalWebStatementScreenDisplayFlag` で読める |
| 本人アカウント登録状況 | 要確認 | — | 公式仕様書は開発者サイトのログインが必要（今回は見られず）。GET staff に `mail` 以外のログイン状態項目があるかを要確認 |
| 給与明細 | `GET /budgets/monthly/0/{staffId}` | smaregi-payroll-sync | 読むだけ |

## 4. 既存本部タスクとの関係

- 入社時に `hq_tasks`「入社登録（○○さん）」が自動で 1 件できます（§1-2 ④）。工程②のチェック 4 項目が **今回自動化する対象そのもの**です。
- 重複を避ける方針：
  - 本部タスクは**残す**（人が見る一覧として便利）。ただし工程②は「自動処理の状況を見る」だけにし、チェック欄 4 項目は **ワークフロー表の状態から自動で ✓ を付ける**（手で付けない）。
  - 自動処理が `manual_required` になったときだけ、工程に「手動対応：交通費を入力（理由…）」を**追加**し（既存の `hq_add_onboarding_affiliation_step` と同じ作法）、手動完了時にスマレジ GET で照合→ `completed`。
  - 既存の `hq_create_onboarding_task` に **重複防止（同じ user_id の未完了タスクがあれば返す）** を足します。担当者名の固定（青山純→齋藤）は設定表へ。
- 退職タスク（offboarding）・退職申請（hr_change_requests）には触れません。

## 7. Playwright の実行構造

- **場所**: Mac mini の `/Users/mirai/ns-daily-import`（launchd が 3 分おきに `dispatch.js` を起動。※ Claude フォルダ側の ns-daily-import は古いクローンなので触らない）。
- **仕組み**: `dispatch.js` の末尾に「`ui_automation_jobs` の pending を 1 件取る→`status=eq.pending` 条件付き PATCH で claim→Playwright 実行→結果を書き戻す」を追加（既存の `cash_recon_fix_requests` と同じ作法）。
- **ブラウザ**: 同梱 Chromium＋専用プロファイル `profiles/ns`（ユーザーの Chrome には触らない、`channel:'chrome'` は使わない）。スマレジ自動ログイン＋契約選択は `tasks/smaregi-payroll.js` から共通化。
- **操作**: 従業員 ID（smaregi_staff_id）で直接 URL を開く→現在値を読む→入力→保存→**API GET（transportationCostApply 等）で保存値を照合**→ `result` に保存。
- **安全**: dry_run（入力まで・保存しない）、失敗時スクリーンショット、同一人×同一項目の二重実行禁止（unique index）、自動再試行は **しない**（UI 書き込みは冪等でないため。再試行は本部が Slack ボタンで指示）、ログに住所・口座は出さない。
- **結果の Slack 反映**: `ui_automation_jobs` の更新トリガー → pg_net → EF `onboarding-notify` → 該当スレッドへ結果投稿＋親メッセージ更新。
- **制約**: Mac が起動・ログイン中であること、最大 3 分＋朝の取込中は待ち、時刻指定不可。**画面の項目名・保存手順は 1 回立会いで確認が必要**（スマレジ管理画面に私はログインできません）。
- **利用規約**: スマレジの管理画面を自動操作することの可否は、仕様書と同様に開発者サイト／利用規約の確認が必要です（今回は読めていません）。

## 9. 経路検索 API の推奨案と費用、交通費の自動判定ルール

### 9-1. 比較（出典 URL は末尾）
| | 駅すぱあと API（ヴァル研究所） | Google Routes API（TRANSIT） | NAVITIME | HeartRails |
|---|---|---|---|---|
| 片道/往復運賃（IC） | ○ | △（日本で返るか要検証） | ○（要問い合わせ） | × |
| 定期代 1/3/6 か月 | ○（sort=teiki1/3/6） | × | ○ | × |
| バス | ○ | ○ | ○ | × |
| 住所→駅 | ○（/address/station） | 住所を直接入力可 | ○ | 緯度経度のみ（nippo で使用中） |
| 費用 | 無料プラン ¥0（**経路探索は URL 回答のみ＝運賃不可**）／買い切り 5,000 件 ¥5,500（平均待ち時間探索のみ）／法人プランは要問い合わせ・90 日評価版無料 | 月 10,000 件まで無料 | API は要問い合わせ、Tools は 100 件 ¥2,200（CSV 手作業） | 無料 |
| 実装 | GET JSON、Deno から簡単 | POST JSON、簡単 | REST | GET |

**推奨**：第一候補 **駅すぱあと API**。月 5〜15 名の入社なら買い切り 5,000 件でも数年分です。まず **90 日評価版**で実際の住所 10〜20 件を試し、買い切りか法人プランかを決めるのが安全です。予備として Google Routes（経路・所要・徒歩・乗換は無料で取れる。運賃は日本で返るか要検証）。**AI が運賃を推測する実装はしません。**

### 9-2. 自動判定ルール（案・数値は設定表で変更可）
1. 入力：自宅住所（既存）・最寄り駅（既存）・通勤手段・降車駅・経路文・本人申請片道額・バス有無・特記（新規 7 項目）。店舗側は `stores.nearest_station`（既存）。
2. 検索：自宅周辺の駅候補（上位 3）× 店舗最寄り駅で経路探索、各候補の片道運賃・所要・徒歩・乗換・定期代を保存。
3. 「合理的経路」＝ **最速経路＋15 分以内**・乗換 2 回以内・徒歩 1.5 km 以内 の中で **最安**。
4. 判定：
   - 申請額 ≦ 合理的経路の運賃 → **自動承認可能**（申請額で確定）。
   - 申請額 > 合理的経路 だが ≦ 候補の最高額、またはバス利用・徒歩 1.5 km 超・深夜勤務あり → **本部確認待ち**（差額と理由候補を Slack に表示）。
   - 申請額 > 候補の最高額 ＋ 許容差（例 ¥100 または 20%） → **本人確認待ち**（LINE／メール／Slack のうち連携済みの手段で「経路と金額の理由」を質問、回答を保存）。
   - 検索失敗（駅不明・住所不明） → **経路検索失敗**（本部確認待ち）。
5. 支給形態と金額：勤務回数ごと／勤務日数ごと＝往復運賃、月額＝定期 1 か月と比較。上限は AL 既定 6,000 円（**単位＝月か回かはスマレジ画面仕様の確認後に確定**、確認までは「上限額」として保存のみ）。
6. 最安だけで機械的に否認しない：上記の理由候補を必ず表示し、最終決定は人（Slack ボタン）。
