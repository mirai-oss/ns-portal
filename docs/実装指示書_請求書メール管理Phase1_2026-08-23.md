# 実装指示書: 請求書メール管理システム Phase 1（MVP）

作成: 2026-08-23 ／ 対象: 実行スレッド ／ 元資料: Codex作成の先行実装指示書（本書はそれを当社スタックに適合させた自己完結版。**本書だけで実装可能**）
ユーザー確定事項: ①処理担当=**社長＋本部の数名**（CEO/HQ/マスター） ②初回同期=**直近3ヶ月** ③実装場所=ns-portal＋ハブSupabase ④**返信機能もPhase 1に含める**（2026-08-23確定）

## 0. 目的（これだけは外さない）

「info@ns0314.com に届く請求書メールを、**誰が開いたか・誰が処理中か・二重処理できない・添付が保存される・履歴が残る**状態にする」。メールビューアではなく**処理ワークフロー**を作る。

```
Gmail受信 → info@宛のみ抽出 → 一覧 → 詳細・添付 → 開封記録 → 処理開始(担当ロック) → 完了 → 履歴
```

## 1. アーキテクチャ（Codex案からの重要な変更点）

**Gmail取込はOAuth/Gmail APIではなく、GAS方式にする。**

理由: ①`info@ns0314.com`は`shunji.nakayama@ns0314.com`のエイリアスであり、同アカウントには**既にGmailをポーリングして取り込む稼働実績がある**（Indeed応募取込 `indeed-intake.gs`・5分間隔・ラベル方式の重複防止）②OAuthクライアント作成・同意画面・トークン管理が丸ごと不要になり**数日短縮**③「トークンをコードやGitHubに保存しない」というCodexの禁止事項を構造的に満たす（GASは本人アカウントとして動くためトークンが存在しない）。
※Gmail Push通知が必要になったらPhase 2以降でGmail API方式へ拡張（DBは変えずに取込元だけ差し替え可能な設計にしてある）。

```
GAS(新規プロジェクト invoice-intake / 5分トリガー)
 「deliveredto:info@ns0314.com」でGmail検索 → ラベル「請求書取込済」で重複防止
 → メタデータ＋本文＋添付(base64)を Edge Function `invoice-intake` へPOST(共有シークレット)
 → Edge Functionが service_role で invoice_emails 登録＋添付を非公開バケットへ保存(SHA-256ハッシュ計算・重複判定)
 → 画面(ns-portal/invoices.html)はハブSupabaseをRLS付きで直読み
```

**注意**: GASは**新規の独立プロジェクト**とする（indeed-intake.gsへの追記はしない。過去に共有GASプロジェクトへの追記で取込全滅事故があるため障害を分離する）。プロジェクト作成はclasp（Mac miniに認証済み実績あり）またはユーザーへ貼り付け手順書を渡す。5分トリガーの設置のみユーザー作業（1分・要リンク付き手順）。

## 2. DB設計（ハブSupabase・新規SQLファイル `2026-08-23_invoices.sql`）

既存テーブルとの重複なし（監査済み: ハブに請求書・メール系テーブルは存在しない）。全テーブルRLS有効。

```sql
-- invoice_emails: メール本体
id uuid PK / gmail_message_id text UNIQUE / gmail_thread_id / oauth_parent_account text default 'shunji.nakayama@ns0314.com'
/ target_alias text default 'info@ns0314.com' / from_address / to_address / delivered_to / cc_address
/ subject / body_text / body_html / received_at timestamptz
/ mail_status text CHECK (unread/read/processing/completed/archived) default 'unread'
/ processing_user_id uuid→users / processing_started_at / locked_at / lock_expires_at
/ lock_released_by / lock_released_at / lock_release_reason
/ completed_by uuid→users / completed_at / completion_note / created_at / updated_at

-- invoice_email_reads: 開封履歴（unique(email_id,user_id)ではなく毎回insert=履歴として全部残す）
id / email_id→invoice_emails / user_id→users / opened_at

-- invoice_attachments: 添付
id / email_id / file_name / mime_type / storage_path / file_hash text(SHA-256) / size_bytes / created_at
（file_hashにindex。同hash既存ありなら invoice_emails.duplicate_suspected を立てる）

-- invoices: 請求書エンティティ（Phase 1では金額等は手入力任意。OCRはPhase 3用の器）
id / email_id / attachment_id / vendor_name / invoice_number / amount numeric / due_date
/ invoice_status CHECK (draft/registered/duplicate_suspected/waiting_payment/paid/cancelled)
/ assigned_user_id / duplicate_suspected bool / created_at / updated_at

-- invoice_audit_logs: 監査ログ（取込/開封/担当/ロック解除/完了/状態変更/重複警告 すべて）
id / entity_type / entity_id / action / user_id / actor_type text CHECK (human/ai) default 'human'
/ old_value jsonb / new_value jsonb / note / created_at
```

### 二重処理防止（最重要・DBレベルで保証）

処理開始はRPC `invoice_start_processing(p_email_id)`（security definer）で:
```sql
update invoice_emails set processing_user_id=auth.uid(), processing_started_at=now(),
  locked_at=now(), lock_expires_at=now()+interval '24 hours', mail_status='processing'
where id=$1 and (processing_user_id is null or lock_expires_at < now())
returning *;
```
→ **同時に2人が押しても1人しか成功しない**（0行更新=「○○さんが処理中です」を返す）。ロック解除RPC=本人または`portal_is_master()`/CEO/HQのみ・理由必須。完了RPC=担当者本人のみ。すべてaudit_logsへ記録。

### RLS・権限

- SELECT: `role in ('CEO','HQ') or is_master`（＋既存の`portal_user_overrides`方式で個人単位の追加開放を可能に。system_key=`invoices`を`portal_permissions`へ追加し、ポータルのタイルと権限設定タブに載せる）
- INSERT/UPDATEは直接不可、全操作RPC経由（経費申請`expense_*`の実装パターンを踏襲）
- audit_logsのactor_type='ai'は将来Mirai用の器（Phase 1では常にhuman）

### Storage

新規**非公開バケット `invoice-files`**（署名URL閲覧のみ・20MB上限・PDF/画像/一般文書MIME許可）。`report-photos`（公開バケット）は**使用禁止**（監査R5の教訓: 請求書は機密）。パス規約 `{email_id}/{添付連番}_{ファイル名}`。

## 3. 取込仕様（GAS `invoice-intake` 新規プロジェクト）

1. 検索クエリ: `deliveredto:info@ns0314.com -label:請求書取込済`（To/Cc/Delivered-To経由はこのクエリで包括される。取りこぼし検証として実装時にTo/Cc直接指定との件数比較を1回行う）
2. 各スレッドの各メッセージ: ヘッダー（From/To/Delivered-To/Cc/Subject/Date/Message-ID）＋text/html本文＋添付を収集 → Edge Function へPOST → 成功したらラベル付与
3. Edge Function `invoice-intake`: 共有シークレット検証（**環境変数に保存。コード直書き禁止**=過去のINTAKE_SECRET平文事故の教訓）→ `gmail_message_id`で重複スキップ → 添付をバケットへ保存しSHA-256を計算 → 同hash既存なら`duplicate_suspected`
4. **初回バックフィル**: `newer_than:90d`で直近3ヶ月分を取込（1回きりの手動実行。件数が多い場合は日付を区切って複数回）
5. 平常運転: 5分間隔トリガー。GAS実行失敗はメール通知（GASの標準エラー通知でよい）

## 4. UI（ns-portal に `invoices.html` 新規・expenses.htmlの雛形を流用）

- 認証・SSO・ナビ・権限判定はexpenses.htmlのボイラープレートをコピーして開始（最短）
- 配色はユーザー提供のプロトタイプ準拠: 黒/ダークブラウンのナビ・ベージュ背景・白カード・赤=期限/重要・緑=完了・黄=注意・青=情報。PC/スマホ両対応
- **一覧**: タブ=未処理/処理中/完了/すべて。列=送信元・件名・受信日時・📎添付有無・状態バッジ・担当者（「○○さんが処理中」）・最終更新。重複疑いは⚠️バッジ
- **詳細**: ヘッダー情報・本文（HTMLはsandbox付きiframeで表示=XSS対策必須）・添付一覧（署名URLでプレビュー/DL）・開封履歴・処理履歴（audit_logs）・状態と担当
- **操作**: 「この請求書を処理する」（ロック取得）／「処理完了」（メモ任意）／「ロック解除」（管理者・理由必須）／金額・支払期限・請求元の手動登録（invoicesテーブルへ・任意）
- 詳細を開いたら`invoice_email_reads`へ自動insert（開封記録）
- ポータル(index.html)のSYSTEMSタイルに「📨 請求書管理」を追加（roles: CEO/HQ＋individual override）

## 4.5 返信機能（Phase 1に含める・ユーザー確定）

**方針: 既存メールへの「返信」のみ。新規送信は不可。送信前に必ず確認画面。全送信を監査ログへ。**

- **DB**: 新テーブル `invoice_email_outbox`: id / email_id→invoice_emails（返信元・必須） / body_text / status CHECK (queued/sent/failed) / queued_by→users / queued_at / sent_at / gmail_sent_message_id / error。RPC `invoice_queue_reply(p_email_id, p_body)`（処理権限者のみ・security definer・audit記録）
- **送信経路**: GAS `invoice-intake` プロジェクトを**トークン認証付きWebAppとしてもデプロイ**し、Edge Function `invoice-send` がRPC後に即時コール → GASが `GmailApp` で元スレッドへ返信（**差出人=info@ns0314.com**。Gmail設定の「他のメールアドレスから送信」にエイリアスが登録済みであること＝ユーザー確認1分）→ 送信済みIDをoutboxへ書き戻し。GAS側が失敗した場合は5分トリガーがqueuedを拾う保険（即時＋保険の二段構え）
- **UI**: 詳細画面に「✉️ 返信」→ 本文入力 → **確認画面（宛先・件名Re:・本文を表示して「送信する」）** → 送信結果表示。送信済み返信は詳細のスレッド履歴に表示（次回取込で自動記録される送信メールと突合し、direction=outboundバッジ）
- **安全装置**: 宛先は元メールのFrom/Reply-To固定（編集不可）／添付送信はPhase 1では不可／audit_logsにaction='reply_sent'で本文込み記録
