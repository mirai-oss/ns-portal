先に結論
  • 旧シート（入金DB）は、1行も削除・統合・修正しません。全行をそのまま「移行元の控え」として別の表に保存し、そのうえで、すでに取り込んだ銀行CSV由来の1,341件と1件ずつ突き合わせます。
  • 突き合わせた行は「対応づけ（二重にしない）」、銀行側に対応が無い旧行は「旧のみの行として移行」（いまの数字を保つ）、旧シートに無い銀行の入金は「保留」（自動では加算しない）にします。差異はすべて一覧にして、保留・承認・訂正を区別して記録します。
  • 移行の前後で、店舗別×日付別の件数と金額が1件も違わないことを合格条件にします（説明のつく差異＝保留の5件だけ）。
  • 画面の切り替え・旧シートとBigQueryの停止・既存処理の停止は、この段階では行いません（計画を§6に書くだけ）。

2. 移行の約束（変えないこと）

  • 旧シートの行は削除・統合・上書きしない。移行の作業は旧シートを読むだけ。
  • 同日・同額の別取引を1件にまとめない（個数で対応づける）。
  • 銀行CSV由来の行（原本の事実）は、書き換えない（段階1の守りのとおり）。直すときは、理由つきの訂正値だけ。
  • 旧シートに無い銀行の入金は、自動では加算しない（保留）。
  • 何度流しても結果が同じ（再実行で増えない）。流す前に、必ず「リハーサル（流して必ず巻き戻す）」で結果を見てもらう。

3-3. 突き合わせの規則（取引単位・決まった順番・再実行しても同じ結果）

  1. 対象は、店舗ごとに「売上入金として数える入金」（旧の行と、正本の銀行CSV由来の行）。調整系の旧行は突き合わせに使わず、そのまま移行する（銀行に対応が無いのが正常のため）。
  2. グループ＝（店舗・日付・金額）。グループの中で、旧の行と銀行の行を個数どおりに1対1で対応づける。旧が2件・銀行が2件なら2組、旧が1件・銀行が2件なら1組＋銀行の1件が差異。1件にまとめない。
  3. グループ内の順番：時刻が使えるとき（PayPayの旧行は取引時刻つき）は、時:分が同じもの同士を先に対応づけ、残りを時刻順に。時刻が無いとき（GMOの手動取込）は、残高の鎖の順。時刻・順番で決められない曖昧なグループ（同日同額が複数で時刻も同じ等）は proposed にして人の確認を待つ（金額・件数は変わらないので数字には影響しない）。
  4. 銀行の行に対応する旧が無い → 差異：旧シートに無い入金。当日分は取込時刻の差があり得るので別扱い（timing）。
  5. 旧の行に対応する銀行が無い → 銀行CSVの期間より前なら正常（before_csv_window）、期間の中なら 差異：旧のみ（要確認）。どちらも旧の数字は保つため移行する。

現時点の実データでは、期間内の約1,000行のうち、対応が取れない旧行は0件、銀行側だけにあるものは本厚木の5件です（今回の確認結果）。同日同額の32組は、旧シートの時刻・摘要を取り出した後に、一覧にして人が目で確認できる形にします。

3-4. 備考・手動訂正・照合状態を失わない方法

旧シートにあるもの移行先失わないための決まり
備考（DB_入金備考）bank_deposit_notes（段階1で作成済み）日付×店舗で1件のまま移す（更新者・更新日時はupdated_by_labelに保存）。移行後に1件ずつ、旧と新が同じ文面であることを比較。店舗名は店舗マスタ（別名つき）で解決し、解決できない備考は、捨てずに差異一覧へ
手動の調整行（79行：調整分・sss入金分 等）正本に tx_kind=adjustment・売上入金として数える・legacy_pending の行として移行（旧のまま）いまの数字に入っているので、数字を変えないために移す。差異一覧に「手動調整（要承認）」として全件載せ、人が1件ずつ承認するまで、元の値のまま残す（承認＝確定の記録。金額・日付を直すときは訂正値で、理由つき）
シートを直接直した値旧の行の値のまま（控えに保存）銀行CSVと食い違えば差異として出る（旧のみ／旧シートに無い）。人が決めるまで数字は動かさない
照合状態行ごとの印は旧シートに無い移行直後は、対応づけた行＝照合済み（銀行CSVと一致）、旧のみ＝移行済み・照合待ち。画面の「完了／未入金あり」は計算なので、切り替え後も同じ計算で出す（§6）

3-5. すでに保存した1,341件との重複防止

  • 移行で「銀行CSV由来の行」をもう1行作らない：期間内の旧行は、新しい行を作らず、paired の対応づけ（bank_legacy_links）だけを作る。数字は銀行CSV由来の1行ぶんだけ。
  • 旧のみの行だけを、legacy_pending の行として作る（この行は、銀行の口座・時刻・残高が空）。
  • 将来、古い銀行CSV（たとえばGMOの遡り）を取り込んだとき、同じ（店舗・日付・金額）の legacy_pending があれば、新しい行を作らず、その行に銀行の事実（時刻・残高・目印）を1回だけ埋めて照合済みにする（段階1で用意した「埋めるのは1回だけ」の守りを使う。取込関数をこの動きに拡張）。
  • 一意制約：旧行1つに対応は1つ／明細1つに旧行は1つ（paired）／旧行の指紋（バッチをまたいで）／legacy_batch+legacy_seq。再実行すると「追加0・変更0」になることをテスト。

3-6. 差異の一覧：保留・承認・訂正を区別する

状態意味数字への影響誰が・どう変える
保留（held／open）人が決めるまで、自動では何もしない。本厚木の5件（旧シートに無い入金）、期間内の旧のみ、曖昧な対応づけ、店舗が決まらない行銀行側のみの行は集計に入れない。旧のみの行は、いまの数字を保つため入れる（印つき）自動では動かない
承認（approved）人が「このままでよい」と決めた（例：手動調整の79行、正しいと確認した銀行側の入金）承認した内容で集計に入る本部・社長・マスターだけ。理由と日時が履歴に残る
訂正（corrected）日付・金額・店舗などを直す決定（原本の事実は直さず、訂正値で）訂正値で集計される段階1の bank_tx_correct（理由必須・修正前後が履歴に残る）
却下（rejected）「その行は集計に入れない」と決めた集計から外れる（行は残る）本部・社長・マスターだけ。理由必須

一覧の項目：種類（旧シートに無い／旧のみ／同日同額の曖昧／手動調整／備考の不一致／店舗未解決）・店舗・日付・金額・旧の行番号・正本の明細・状態・決めた人・理由・日時。社長が見るためのHTMLの一覧と、画面（段階6で追加する「取得履歴・CSV確認」）の両方で見えるようにします。

5. PayPayの並行稼働（既存GAS送信＋新しい取込）で、どちらかが失敗したとき

現在の1回の流れ：ログイン → 口座ごとに「CSV取得 → 新しい取込（いまは手動の確認用） → GAS送信」。並行稼働の準備として、順番を「GAS送信が先、新しい取込が後」にし、新しい取込を独立した枠（時間制限つき）で包みます。

状況期待する動き試験
GASが失敗・新しい取込は成功いまと同じ失敗扱い（既存の通知）。正本は確定済み。翌日のGAS送信は重複判定で二重にならないGASの応答を失敗にする模擬サーバーで確認
GASは成功・新しい取込が失敗既存の取込は成功のまま（結果を変えない）。失敗は取得履歴（failed＋理由）と取得状態（error）に残り、別枠で通知。その口座の新しい取込だけ止まる。次回の実行は、重複しないので自動で追いつく各段階（登録・保存・読み戻し・取込・確定）で故障を差し込んで確認
両方失敗既存の失敗扱い＋新しい取込の失敗を別に記録。互いに影響しない同上
Supabaseに届かない・遅い新しい取込は時間制限（呼び出しごと30秒・口座ごと2分）で諦める。GAS送信は待たされない（送信が先のため）。失敗はログに残し、取得履歴に書けないときはローカルの失敗記録に残して通知通信を遮断した状態で確認
原本の読み戻しが一致しない取込を確定しない（段階1の守り）。failed＋理由読み戻しを壊して確認（段階2で確認済み）
同じ口座が二重に動く実行中の印（30分で期限切れ）で2つ目は始まらない同時起動で確認（段階2で確認済み）

実装は、paypay-bank.js の口座ごとの処理を小さな関数に切り出し（挙動は変えない）、CSV取得・GAS送信・新しい取込を差し替えられる形にしてテストします（ログインや本物のGASを使わずに、上の表を自動テストで確認）。毎日の自動実行への登録（BANK_LEDGER_MODE=ingest）は、別途承認です。

  2. 6b 社長・本部だけ切り替え：スイッチ（deposit_source=ledger）を役割ごとに。app.js の ?v を更新・GASの ping のverを更新（既存の運用ルール）。
  3. 6c 全員に切り替え：店長・社員は所属店舗だけ（bank_store_visibleがDB側で強制）。
  4. 6d 後始末（別途承認）：BigQuery失敗時のシート直読みの退避を廃止、GASの入金DBへの書き込み停止（段階7）。

戻し方：スイッチを戻すだけ（6dより前は旧経路が生きている）。画面の「入金差異」（現金売上−入金）は、これまでと同じ計算のまま、入金の入力だけ正本に変える。

7. 検証方法（一覧）

  • 単体（Node）：突き合わせの規則（同日同額・時刻つき・曖昧・当日分・期間外）／旧シートの6列の解析（日付・時刻の表記ゆれ）／店舗名の解決／備考の解析。
  • DB（PGlite）：新しい表・関数の権限（anon・店長・社員・チーム長は読めない／本部・社長・マスターだけ）／追記専用／一意制約／保存則／再実行／承認・訂正の履歴／既存の1,341件が変わらない。
  • 実環境（流して必ず巻き戻す）：実データで移行全体を実行し、§4の比較表・差異一覧を出す（書き込み前の最終確認）。既存の表・関数・ポリシーの指紋が変わらないこと。
  • 人の確認：差異一覧（保留・承認・訂正）を社長が確認。同日同額32組と、手動調整79行は全件を目で確認。
  • 並行稼働：§5の故障試験（自動テスト）。段階4で、14日連続の店舗×日付の差異0。

8. 実施順序・承認のポイント・ロールバック

順作業本番への影響承認

9. リスクと、確認したいこと

リスク対策
同日同額32組の誤対応時刻・順序で決まらないものは proposed。金額・件数は変わらないので数字は動かない。人が目で確認
