## 2. 実装方針の骨子（回答前の提案）

- **器は既存の統合ポータル＋ハブSupabaseをそのまま使う**（新システムを別に立てない）。SK用の画面はポータルのサイドバーに「🏠不動産（SK）」グループとして追加し、役職・法人で出し分け（既存の役割別メニュー機構）
- **従業員の法人分離（項目10・全部の土台）**: `users`/`employee_profiles`に法人（corporation）を持たせ、①一般ユーザーは自分の法人の画面・データだけ②マスター/社長は**法人切替スイッチ**で横断閲覧。スマレジ連携もアカウント2本（トーホー/SK）を法人に紐付け（会計Q1の回答と整合）
- **請求書作成（項目9）**: SK用の請求書テンプレ（品目・金額・宛先=取引先マスタ）→下書き→「支店長へ承認依頼」→支店長の承認タブで承認→**PDFに支店長の印影画像を焼き込み**→本部タスク（送金/入金）へ自動起票＋請求書一覧に確定版保存。既存の請求書メール管理（invoices）とは別物（こちらは**発行**側）だが、PDF生成・保存の部品は流用
- **入金・送金タブ（項目7）**: `hq_tasks`に種別（送金/入金/通常）を追加し、本部タスクボードに「送金」「入金」タブ（不動産タスクのみ表示）。**急ぎボタン**=現場が送金依頼時に押すと、本部側で🔥バッジ＋タブに件数表示＋**Chatworkの「重要」と専用チャットへ即通知**（急ぎ以外は通知しない）
- **現場ダッシュボード（項目8）**: 自分の売上・売上予定（データ源はQ6）・自分のインセンティブ（給与仕訳/sf_payroll系と接続するかはQ6）・請求書作成への導線・マニュアル（nippoマニュアル機構を流用）・取引先情報（SK用取引先マスタ）

## 2.5 UI参照（2026-09-01 ユーザー提供のスクリーンショット2枚を書き起こし。設計・実装時はこの構成を基準にする）

**①ポータルサイドバー「不動産（SK）」グループの構成例**:
```
🏢 不動産管理
 ├ 📊 管理概要
 ├ 🧾 請求書
 ├ ✅ 支店長承認
 └ 💸 入出金管理
```

**②本部タスク画面の構成例**（サブタイトル「全社の本部対応を1か所に集約。不動産は入金・送金・請求書で切り分け。」）:
- 上部KPIカード4枚: 期限超過／今日が期限／3日以上停止（停滞タスク）／今月完了
- 検索バー＋表示切替（かんばん・リスト・カレンダー）＋「＋タスク追加」
- **法人フィルタ**: すべての法人／LiveGate／SK／N-Style／トーホー（チップ切替）
- 頻度フィルタ: すべて／毎日／毎週／毎月／単発／自分の担当／自分が依頼
- **種別タブ（新設・重要）**: 「すべて｜入金｜送金｜請求書｜入社登録」— **送金タブに🔴「急ぎ N」バッジ**・請求書タブに件数バッジ
- タブ下の説明文（そのまま採用）: 「**請求書＝広告宣伝費・システム費・通常経費などの通常支払い。不動産の支店長が支払依頼時に『送金』または『請求書』を選択。請求書を選んだものはここへ。**」
- かんばん列の例: **未着手 → 会計入力中（マネーフォワード入力待ち）→ 完了（支払・会計入力完了）** ※種別=請求書のときの状態遷移。カードには法人バッジ（SK）・種別バッジ・タイトル（例: 広告宣伝費｜SUUMO 9月分）・金額・**支店長承認済**表示・支払期限

**このUI例から確定する設計上のポイント**:
1. 本部タスクに**法人軸**と**種別軸（入金/送金/請求書/入社登録）**の2つのフィルタ軸を追加する（入社登録タブ=E-6のタスクの置き場所にもなる→E-6実装時にこのタブ設計を先取りしてよい）
2. 「急ぎ」は送金タブのバッジ＋カード表示＋Chatwork重要通知（§1の項目7どおり）
3. 請求書種別のタスクは「支店長承認済→会計入力中（MF入力待ち）→支払・会計入力完了」という**会計側の状態と連動**する（C-7の会計ダッシュボードと同じ状態を共有）
- ※スクリーンショットの原本はチャット添付（画像）のため、本節の書き起こしが正本。HTMLモック化する場合は`docs/mockups/`へ保存して本節からリンクする

## 2.6 外部AIレビューによる方針確定（2026-09-02・実装条件）

**「システムは分けない・データ領域と画面領域を分ける」で確定**（レビュー採用・司令塔承認）:
1. 同じ統合ポータル・同じ認証・同じ法人/店舗/従業員マスタ（**IDで共通化**）の上に不動産専用モジュールとして追加
2. **不動産画面を開いた時だけ不動産データを読む**。飲食の売上ダッシュボード初期表示では不動産データを一切読まない・経営Dの重いJS（app.js）には混ぜない（独立した画面ファイルにする）
3. テーブルは**`re_`接頭辞**で分離: `re_deals`（案件/契約）・`re_invoices`（請求書）・`re_payments`（入金）・`re_remittance_tasks`（送金依頼）・`re_incentives`（インセンティブ）
4. 本部タスクとの連携は`task_type=入金/送金/請求書`（§2.5のタブ設計と一致）
5. **実装時期は経営ダッシュボードの速度改善（脱GAS Phase 1〜2）後**。それまでは設計のみ先行（ユーザー合意済みの新機能スローダウンと整合）
