# 設計書: Slack 通知の共通フォーマット（親メッセージは 2 行・詳細と操作はスレッド）

作成 2026-11-11。**設計と変更対象の洗い出しまで。実装・通知文面の本番変更・チャンネル作成・フラグ変更はしていない（別途承認）。**
関連: [従業員情報変更の連動 設計書](設計書_従業員情報変更の連動_2026-11-10.md) §17（共通承認基盤と 2 チャンネル構成）・§18（第 1 段階）。

## 0. 結論（先に）

- 親メッセージは全種類で同じ 2 行にそろえる。変更前後・説明・ボタン・履歴はスレッドに集める。申請 1 件につき親 1 件で、進捗は同じメッセージを更新する。
- 送信の出口・台帳・重複防止・メッセージ更新・ボタンの受付・リマインドは、いまあるものをそのまま使える。足りないのは次の 4 つ。
  1. 「だれにメンションするか」を決める仕組み（**いまはメンションを 1 つも使っていない**）。
  2. 親メッセージとスレッドの控えを、種類共通で持つ表（いまは種類ごとに別の場所）。
  3. 親・スレッド・操作カードを組み立てる共通部品（いまは 5 か所に分かれている）。
  4. リマインドをスレッドへの返信にする（いまは元のメッセージを複製して新しい親を増やしている）。
- 稼働中の入社登録と勤怠は最後に切り替える。種類ごとにスイッチを持ち、進行中の案件は古い形のまま終わらせる。
- 実装規模は全体で 5.5 単位ほど（1 単位＝これまでのステップ 1 つぶん）。
- **2026-11-11 夕方に方針確定**（§9）: チーム長全員を #本部-人事 に参加させる／勤怠は #勤怠確認 のまま（形式だけ共通化）／社員に店長を含む・本部メンバーに社長を含む／メンションできないときに通知先を広げない。
- **チーム長を参加させる前に必要なこと**（§11）: いまの #本部-人事 には、入社登録のスレッドに賃金と交通費の金額が出ている。先に金額の表示を止める。

## 1. 親メッセージの形

```
{絵文字}【{通知種別}】{日付}｜{店舗}｜{氏名}
{メンション}　{進捗の丸} {進捗の言葉}
```

| 部分 | 決め方 |
|---|---|
| 通知種別・絵文字 | 種類の設定表から（§5） |
| 日付 | 勤怠＝対象の勤務日／それ以外＝申請・発生の日（入社日・退職日・適用開始日はスレッドに書く） |
| 店舗 | 対象の従業員の主な所属店舗の短い名前（`stores.display_name`）。所属なしは「—」 |
| 氏名 | 対象の従業員 |
| メンション | いま対応すべき人だけ（§4）。Slack の実ユーザー ID で書く |
| 進捗 | 下の 5 つ。2 段階承認などは言葉で段階を出す（例: 🟡 本部確認待ち／🟡 社長承認待ち） |

親メッセージに出さないもの: 変更前後の値・金額・口座番号・住所・理由・ボタン・履歴。

### 1.1 進捗

| 丸 | 基本の状態 | 使う場面の例 |
|---|---|---|
| ⚪ | 未対応 | 作られたが、まだだれも見ていない（担当が未連携で通知できていない、を含む） |
| 🟡 | 確認待ち | 人の確認・承認を待っている（本部確認待ち／社長承認待ち／外部の変更を検知・確認待ち） |
| 🔵 | 対応中 | だれかが着手した（入社登録の手続き中／勤怠をスマレジで修正中／差し戻しの修正中） |
| 🟢 | 完了 | 必要な確認まで済んだ（承認して反映・同期まで済み／却下・取り下げで終了は「完了（却下）」「完了（取り下げ）」と書く） |
| 🔴 | 要対応 | エラー・期限超過・給与の締めに間に合わない・同期の失敗 |

- **「外部で変わったこと」と「本部が確認したこと」は別に持つ。** 例: 勤怠の修正をスマレジ側で検知しただけでは 🟢 にしない。「🟡 修正を検知・確認待ち」にして、確認の操作が済んでから 🟢 にする。データでは `external_state`（未検知／検知済み）と `review_state`（未確認／確認済み）の 2 つに分ける。
- 完了のときは、親メッセージの担当者を「メンション」ではなく「名前の文字」にする（再通知しない）。

## 2. スレッドの中

| 順 | 中身 | 更新のしかた |
|---|---|---|
| 1 通目 | **詳細カード**: 申請・変更の詳細、変更前と変更後（出してよい項目だけ）、適用開始日・入社日など | 内容が変わったら同じメッセージを更新 |
| 2 通目 | **操作カード**: いま押せるボタン（確認・承認・差し戻し・却下・管理画面を開く）と、いまの担当 | 段階が変わるたびに同じメッセージを更新（古いボタンが残らない） |
| 3 通目〜 | **履歴**: だれが・いつ・何をしたか（確認者・承認者・処理日時・同期の結果）。1 出来事 1 行 | 追記 |
| 必要なとき | **エラー**: 内容と対応方法 | 追記。直ったら「解消」を追記 |
| 必要なとき | **担当の引き継ぎ・リマインド**: 次の担当者へのメンションつきの返信 | 追記 |

- スレッドの中でも、権限を超える機密（金額・口座番号・住所の全文など）は出さない。種類ごとの「出してよい項目」（`approval_routes.slack_fields` と同じ考え方）で決め、それ以外は「管理画面で確認」のリンクにする。
- ボタンを押した人の権限は、これまでどおり管理システム側で判定する（メンションされたかどうかとは無関係）。

## 3. チャンネル

| 場所 | 使い方 |
|---|---|
| #本部-人事（既存） | 入社・退職・各種の人事変更・通常の承認。賃金変更の「本部確認」まで |
| #本部-重要承認（新規・非公開・未作成） | 社長の最終承認が要る案件だけ。本部確認が済んだ時点で、ここに親メッセージを 1 件（社長にメンション） |
| #勤怠確認（既存） | 勤怠修正・勤怠確認（★確定: 引き続きここ。#本部-人事 には移さない。表示の形だけ共通化） |
| アプリとの 1 対 1 の DM | 従業員本人の申請窓口・本人への結果通知 |

賃金変更の流れ: 申請 → #本部-人事 に親（🟡 本部確認待ち・本部の担当にメンション）→ 本部確認 → #本部-人事 の親を「🟡 社長承認待ち」に更新（メンションなし）＋ #本部-重要承認 に親（🟡 社長承認待ち・社長にメンション）→ 最終承認 → 両方の親を 🟢 完了に更新（メンションなし）、同期の結果をスレッドに追記。

## 4. メンション

### 4.1 初期ルール（2026-11-11 ユーザー確定）

| 通知 | メンション先 | 管理システムでの引き方 |
|---|---|---|
| 勤怠修正 | 対象店舗の社員全員（店長を含む・確定）＋その店舗を担当するチーム長 | 社員＝その店舗に所属（`user_stores`）する役割「社員」「店長」／チーム長＝役割「チーム長」で、所属チーム（`users.team_id`）がその店舗を担当（`team_stores`） |
| 賃金変更 | 社長本人。本部確認が済んで最終承認を依頼するときだけ | 役割「社長」。本部確認の段階は、いまの担当者ルール（本部タスクの担当）のまま |
| 入社登録 | 本部メンバー全員（社長を含む・確定）＋チーム長全員 | 役割「本部」「社長」全員＋役割「チーム長」全員 |
| 退職処理 | 本部メンバー全員＋チーム長全員 | 同上 |

### 4.2 しくみ

- **メンション先と承認権限は別に持つ。** メンション先は新しい設定表（下）、承認権限は承認ルート（`approval_routes`）と既存の権限関数。メンションされても、権限が無ければ押せない。権限があっても、メンションされないことがある。
- 設定表（案 `notice_mention_rules`）: 通知の種類 × 場面（開始／段階ごと／完了）ごとに「対象の決め方」を並べる。決め方の部品は 5 つ: 役割の全員／対象店舗の役割の人／対象店舗を担当するチーム長／指定した人／本部タスクの担当。あとで管理画面から変えられる形にする（最初は SQL で入れる）。
- 解決の関数（案 `notice_mention_targets`）: 上の設定から従業員を集め、①重複を 1 人にまとめる ②退職済み・無効のアカウントを除く ③通知から外す印のついたアカウント（テスト用・連携用）を除く ④Slack の紐付け（`user_slack`）がある人だけメンションにする。紐付けの無い人は「未連携」として返す。
- **通知が飛ぶのは 2 つの場面だけにする**: ①親メッセージを最初に出すとき ②担当が替わったとき・リマインドのときの、スレッドへの返信。親メッセージの更新では通知を飛ばさない前提で設計し、実装の最初に実機で確かめる（§8 の段階 A）。
- 完了の更新ではメンションを使わない（名前の文字にする）。同じ案件の同じ場面の通知は、重複防止の鍵（案件×場面）で 1 回だけ。

### 4.3 未設定・Slack 未連携のとき（★2026-11-11 確定: 通知先は広げない）

**メンションできないことを理由に、通知を見られる人・メンションする人を増やさない。** とくに賃金・退職・銀行口座は、決めた対象以外には知らせない。

| 状況 | 動き |
|---|---|
| 対象の一部が未連携 | 連携済みの人だけメンション。未連携の人については、**指定した本部管理者に確認タスク**（本部タスク）を作り、Slack の紐付けを促す。タスクは未連携の人ごとに 1 件（同じ人のタスクが開いているあいだは増やさない）。届いていない通知の種類を書く。スレッドには「通知できていない人: ○ 名」と人数だけ出す |
| 対象が 1 人もメンションできない | 通知先は広げない。メンションなしで親を出して ⚪ 未対応にし、本部管理者に「至急」の確認タスクを作る |
| 社長が未連携（賃金の最終承認） | #本部-重要承認 の親は ⚪ 未対応。本部管理者に確認タスク。最終承認は管理画面から社長だけができる（だれにも代わりに通知しない） |
| メンション先がチャンネルに参加していない | 未連携と同じ扱い（本部管理者に確認タスク。参加の操作は人が行う） |
| 本人への通知（DM）ができない | 既存の順（Slack → LINE → スレッドに「店長から声かけを」）をそのまま使う |

- 「指定した本部管理者」は設定で持つ（1〜2 名。だれにするかは要決定）。
- 毎朝の #Slack未連携リマインド（既存）はそのまま使う。

## 5. 共通の部品（新しく作るもの）

| 部品 | 中身 |
|---|---|
| 種類の設定表（案 `notice_types`） | 種類の鍵・表示名・絵文字・出す先のチャンネル（段階ごと）・日付の決め方・スレッドに出してよい項目・リマインドの設定・形式の版（旧／新） |
| 案件の控え（案 `notice_cases`） | 種類×元の記録ごとに 1 行。対象の従業員・店舗・日付・親メッセージの控え（チャンネルごと）・詳細カードと操作カードの控え・進捗・いまの担当・外部の状態と確認の状態・完了日時。承認の案件（`approval_cases`）とは元の記録でつなぐ |
| メンションの設定表と解決の関数 | §4.2 |
| 組み立ての共通部品（Edge Function の共有コード） | 親 2 行・詳細カード・操作カード・履歴 1 行・エラー・引き継ぎの返信。種類ごとの違いは「詳細カードに何を出すか」と「どのボタンを出すか」だけにする |
| 送信の入口（1 つ） | 開始／進捗の更新／スレッドへの追記／担当の引き継ぎ／完了。送信そのものは既存の `notify-slack` を呼ぶ |

そのまま使う既存のもの: `notify-slack`（送信・台帳・重複防止・更新・スレッド・再試行）／`slack-interact`（署名の検証・押した人の照合・ボタンの名前はいまのまま）／`pending-reminders`（毎時）／判断依頼／本人への連絡の順（Slack → LINE）／毎朝の未連携リマインド。

## 6. いまの通知と、変える点（洗い出し）

|---|---|---|---|---|

| 入社時の賃金・交通費・源泉など | 入社のスレッドの中 | 稼働中 | スレッドのまま。履歴 1 行の形だけそろえる | 軽い |

| 退職申請 | 文字だけ 6 行。更新なし・ボタンなし | 稼働中 | 親 2 行＋スレッド。承認・スマレジ処理の結果で進捗を更新（新規）。本部全員＋チーム長全員にメンション | 中 |
| 移籍・兼務（所属店舗の変更） | Slack 通知なし（交通費の再確認の通知だけ・フラグ OFF） | — | 新しい種類として追加 | 中 |
| 住所・最寄り駅・雇用形態の変更 → 交通費の再確認 | ブロック 3 段＋ボタン | フラグ OFF | 新しい形で出す | 軽い |
| 賃金・口座の変更申請 | ブロック 2〜3 段＋従業員ページへのボタン。更新なし | フラグ OFF | 新しい形。賃金は 2 チャンネル（第 2 段階と同じ作業） | 軽い（動いていないため） |
| 振込データからの除外 | 氏名の一覧を親に出す | フラグ OFF | 親は「月と人数」だけ、氏名はスレッドへ | 軽い |
| 勤怠の異常（店長向け） | 親に 7〜10 行＋ボタン 3 つ。結果で親を書き換え | 稼働中（#勤怠確認） | 親 2 行＋スレッド。対象店舗の社員＋チーム長にメンション。進捗は 確認待ち → 対応中 → 修正を検知・確認待ち → 完了 | 重い |

| 勤怠フォームの申請 | マスターへの DM＋#勤怠確認 に文字だけ | 稼働中 | 親 2 行＋スレッド | 中 |
| スマレジ側での直接の修正 | 4 行＋確認ボタン | 稼働中 | 関係する案件があればそのスレッドに「修正を検知」を追記して 🟡 に。無ければ新しい親 | 中 |
| リマインド | 元のメッセージを複製して、新しいメッセージとして再送 | 稼働中 | スレッドへの返信（担当にメンション）に変える。親は増やさない | 中 |
| 入社手続きの停滞まとめ・入社後提出の催促・本人への連絡 | まとめのブロック・本人あての文字 | フラグ OFF | まとめは 1 日 1 件の別種類として残す。本人あては変えない | 軽い |
| 判断依頼・監視・経理・レポート系 | それぞれの形 | 稼働中 | 今回の対象外（人事の申請・確認ではないため） | — |

共通化の妨げ（調査で分かったこと）
- 親メッセージの控えの場所が種類ごとに違う（入社は専用の列、勤怠は台帳の番号の配列、賃金・口座は控えなし）。
- ブロックの組み立てが 5 か所に分かれ、承認依頼は同じものが 2 か所に重複。
- スレッドを使っているのは入社だけ。
- 親メッセージを文字だけで更新すると、ブロックが消える作りになっている（親を文字 2 行にすれば問題にならない）。
- 宛先は「決まったチャンネル」か「DM」の 2 種類だけで、店舗やチームから担当を引く仕組みが無い。
- 日付・店舗名の書き方が関数ごとに違う。
- 本部タスクの担当を決める処理に、担当者の氏名が直接書かれている（設定表へ移す）。

## 7. 既存の運用を止めないための進め方

- 種類ごとにスイッチ（旧い形／新しい形）を持つ。案件ごとにも版を持ち、**進行中の案件は旧い形のまま終わらせる**（途中で形が変わらない）。
- ボタンの名前（action_id）は変えない。受付側（`slack-interact`）の権限判定・処理はそのまま。
