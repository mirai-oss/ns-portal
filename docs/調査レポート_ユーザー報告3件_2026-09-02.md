# 調査レポート: ユーザー報告3件（2026-09-02・担当D調査）

作成: 2026-09-02 ／ 担当D ／ 対象ファイルはすべて`tori-dashboard`（担当A管轄。担当Dは直接編集していない）

ユーザーから3件の不具合報告があり、`Explore`エージェントで並行調査した結果を担当Aへ引き継ぐ。

## ①目標管理: 入力途中に画面が更新され、入力内容が消える（一時保存も無い）

**再現条件（仮説）**: タブを開いた直後や画面表示直後に「✎ 目標を入力」でモーダル（`targetModal()` app.js:6240 / `targetDayModal()` app.js:6297）を開いて入力を始めると、裏で走っているデータ取得の完了通知が届いたタイミングで`render()`が呼ばれ、モーダルのDOMごと作り直されて入力中の値が消える。

- **2026-08-30に一度対策済みの経路**: 60秒ごとの自動同期`syncIfChanged()`（app.js:1694-1701）には`if(S.modal) return;`という明示的なガードが既にある（コメントに「モーダル入力中に巻き戻る不具合をユーザー報告で対策済み」とある）
- **対策が及んでいない経路（今回の直接原因と推定）**: `fetchData()`本体（app.js:1529）や各`fetchXxxBQ()`（`fetchDailyBQ`/`fetchPlBQ`/`fetchDepositBQ`/`fetchMediaBQ`/`fetchSpotBQ`/`fetchLoanBQ`/`bqFallbackToSheet_`、app.js:1584-1655）は、取得完了時に`S.modal`を見ずに**無条件で`render()`を呼ぶ**。目標管理タブはBQゲート対象タブ（`bqGateTabs`、app.js:1892）のため、タブを開いた直後にこれらのBQ取得が裏で数秒〜十数秒走っており、その完了と入力開始のタイミングが重なると発生する
- **参考にできる既存パターン**: 広告管理タブの`adInput`/`adSales`モーダルは、`fetchData().then(()=>{ if(S.modal&&S.modal.type!=='adInput') render(); })`（app.js:7954, 7984）のように、**取得自体は続けつつ該当モーダル表示中だけrenderを抑制する**、より粒度の細かいガードを既に使っている
- **提案する修正**: `targetModal()`/`targetDayModal()`のモーダル種別（`type:'target'`/`'targetDay'`のような識別子。無ければ新設）を、目標管理タブが依存する上記fetch系関数のrender呼び出しに同様のガードとして適用する
- **あわせて要望のあった「一時保存」**: 上記のrender巻き戻り自体を防げれば「うっかり消える」問題は解消するが、それとは別に「入力の途中で一旦離れても次回開いたときに続きから入力できる」機能が欲しいという趣旨であれば、入力中の値を`localStorage`または`S`に都度保存しておき、モーダルを開く際に下書きがあれば復元する仕組みが別途必要（優先度・実装要否は担当Aの判断）

## ②予約管理: チーム長など一部の権限で開くと経営ダッシュボードが表示されてしまう

**結論: コードの不具合というより、運用データ（権限設定シート）の更新漏れの可能性が高い。**

- `portal.html`側のURL生成・受け渡し（`keieiTab("reservation")`＝`?embed=1&tab=reservation`、925・994行目）は全役職共通で正しく動作しており、原因ではない
- `tori-dashboard/app.js`側の`myTabs()`（1279-1289行目）が、ログインした役職ごとに許可されたタブの配列を返す。**Google Sheet「DB_権限定義」の設定がコード内既定（`ROLE_TABS`）より優先される**設計（675-681行目）
- `afterLogin()`（1824-1833行目）で`S.tab=tabs[0]`（常に`'dash'`）を先に設定し、その後`pendingTab`（URLの`tab=reservation`）が`myTabs()`の許可リストに含まれている場合だけ上書きする。**含まれていなければ無条件でスキップされ、`dash`のまま表示される**（postMessageでの高速タブ切替も同様のガードで無視される、8305行目）
- コード内既定の`ROLE_TABS`（29-37行目）自体は、社長・本部・マネージャー・店舗いずれも`reservation`を含んでおり、コード上「チーム長だけ予約が使えない」設計にはなっていない
- **予約管理タブは2026-08-28に追加されたばかりの新しいタブ**。「DB_権限定義」シートの該当行（役職＝チーム長、または権限＝マネージャーの行）の「表示タブ」列が、このタブ追加より前の内容のまま更新されていなければ、そのアカウントの許可タブリストに`reservation`が漏れ、症状と一致する
- **確認・対応方法**:
  1. 「DB_権限定義」シートの該当行（または個別アカウントの「表示タブ」列）に`reservation`を追加する（運用データ側の修正・即効性あり）
  2. あわせてコード側の保険として、シート未設定時のコード内既定（`ROLE_TABS`）に`reservation`が含まれる役職なら、シート側に古い設定が残っていても救済的に許可する、といった移行ロジックの追加を検討（今回のような「新しいタブを足したらシート更新が追いつかない」再発を防げる）

## ③明細分析: 営業区分「ランチ」で客数が0人になり、客単価もおかしい

**原因を特定済み**: 客数の推定方法自体が、ランチ帯と構造的に相性が悪い。

- `bqDetail()`（gas/Code.gs）は客数を「dinii明細の中の“お通し”という名前の注文行数」で推定している（`G = "SUM(IF(menu LIKE '%お通し%', qty, 0)) AS guests"`、Code.gs:1249）
- **お通しは居酒屋の夜営業（ディナー）特有の慣習で、ランチには基本的に出ない**。そのためランチ帯だけに絞ると、この推定方法は常に0に近い値を返す
- 営業区分で絞り込んだときの按分ロジック（Code.gs:1382-1390、2026-08-30追加）は「絞り込み後の明細推定 ÷ 全日の明細推定」という構成比を、実績値（レジ実績）に掛けて按分する設計。**ランチのその構成比の分子（お通し数）がほぼ0のため、按分後のランチ客数も0になる**
- **副作用**: 分母となる「全日の明細推定客数」は、お通しがほぼ全てディナーに集中している影響で「実質ディナー分の推定値」とほぼ同じになる。その結果、ディナー側の構成比が「ほぼ100%」になり、**ディナーの客数が実際のディナー分ではなく、その日全体（ランチ＋ディナー）の実績客数とほぼ同じ値になってしまう**（ユーザーの「ディナーも合計になっているのでは」という指摘のとおり）。売上・会計数（`COUNT(DISTINCT check_id)`が母数のため常に非ゼロ）は正常
- **提案する修正**: 客数の按分だけ、お通し数ベースの構成比ではなく、**会計数（`VCHK`）ベースの構成比**を使う（客数と会計数は一般に強く相関するため、代替の構成比として十分実用的。かつ`VCHK`はランチでも必ず非ゼロ）。具体的には Code.gs:1389 の
  ```js
  finalGuests = dayGuests * (segGuests0 / full.guests);
  ```
  を
  ```js
  finalGuests = dayGuests * (segChecks0 / full.checks);
  ```
  に変更する案（客数配分の根拠を会計数の構成比に統一）。もしくは「`full.guests`が0または極端に小さい場合だけ会計数ベースにフォールバックする」形でも良い（担当Aの判断で決めてほしい）

## 担当・優先度

いずれも`tori-dashboard`（app.js／gas/Code.gs）のため担当A管轄。①②は実害が「使いにくい／画面が違う」レベル、③は数字そのものが誤っているため優先度は③が高いと考える。②は運用データ（DB_権限定義シート）側の確認が先に必要なため、担当Aからユーザーへ「該当アカウントの表示タブ設定を確認してよいか」の確認が要るかもしれない。
