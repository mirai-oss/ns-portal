# 仕様書：引き落とし・振込の自動照合（MF API 確認結果つき）

作成：2026-10-16 担当C（請求書・MF連携）　状態：**案（承認前）**

## 1. 目的

請求書の「振込待ち」のうち、**口座引き落とし**（および他行からの振込）が実際に行われたことを、
銀行口座の動き（金額・日付・摘要）から自動で見つけ、**「振込済み」にする候補**として出す。
人が候補を確認して承認する（AIが勝手に完了にしない。社内の基本方針どおり）。

## 2. MF API の確認結果

### 2-1. 確認できたこと（公式ページ・当社の実装で裏付けあり）

| 項目 | 内容 | 根拠 |
|---|---|---|

### 2-2. 確認できなかったこと（要確認）

| 項目 | 状況 |
|---|---|
| **取引明細を「取得（読み出し）」できるか** | 公式ページには「送信して作成」のみ記載。第三者の資料には取得(getTransactions)や仕訳化の記述があるが、**公式の仕様書では確認できていない**。公式プレスリリース（2026-03-26）では「取引明細の操作は順次リリース予定」とあり、時期未定。 |
| 取引明細系のスコープ | `mfc/accounting/transaction.write`（明細の作成・更新）、`mfc/accounting/connected_account.read`（連携サービスの参照）が存在。**当社はまだ許可していない**。read 用スコープの有無は未確認。 |
| 銀行の自動取得（MF画面の「連携サービス」で取り込まれた生の明細）を API で読めるか | **公式ページに記載なし → 未確認** |
| 当社の契約がクラウド会計か会計Plusか | 会計Plusは「APIドキュメントは利用者に提供（担当者に問い合わせ）」の形。公開されている仕様書では詳細が見えない。**MFの担当者／管理画面のAPIドキュメントで確認が必要。** |

### 2-3. 結論

- **今の許可範囲だけで、確実にできる方法がある**（案1：MFに入った仕訳を証拠にする）。
- 銀行連携の生の明細をAPIで読む方法（案2）は、**仕様の確認と、スコープの追加（再認可）が必要**。確認が取れるまで前提にしない。

## 3. 方式

### 案1（採用案）：MFに仕訳として入った出金を証拠にする

銀行連携の「自動で仕訳」や手入力で、出金がMFに**仕訳として確定**したあとの話。
貸方が預金（普通預金など）で、借方が買掛金・未払金（＋補助科目＝請求先）の仕訳を探す。

**照合の流れ**
1. 対象：請求書のうち、会計登録済みで支払方法が「引き落とし」または「他行口座から振込」、かつ未払い（振込待ち）のもの。
2. 法人ごとのMF（トーホー=default／N-Style=nstyle）に対し、請求書の期日の前後（既定：期日の−3日〜＋10日）の仕訳を `list_journals` で取得。
3. 次の条件で候補を作る（点数の高い順に表示）。
   - 金額が一致（必須。請求書の合計額＝預金側の金額）
   - 借方に買掛金／未払金があり、補助科目が請求先と一致（強い証拠）
   - 摘要に請求先名・覚えさせた引き落とし名が含まれる
   - 日付が期日に近い
4. 候補は「振込待ち」の画面に「✅ 照合候補」として出し、**人が確認してまとめて「振込済み」にする**。
5. 確認した組み合わせ（摘要の名前 ⇔ 請求先）は `payment_match_rules` に覚えさせ、次回から候補の精度を上げる。

**長所**：今の許可範囲で作れる／自動取得の口座も手入力の口座も同じ扱い／法人ごとのMFを使う。
**短所**：MFで仕訳になるまで時間差がある（銀行連携の自動仕訳が済んでから照合）。

### 案2（要確認）：MFの連携明細を直接読む
取引明細を取得できるAPIがあり、`transaction` 系の読み取りスコープが取れるなら、仕訳になる前の明細から照合できる。
**確認先**：MFの管理画面（App Portal）のAPIドキュメント、またはMF担当者。確認でき次第、案1と同じ照合の仕組みに「明細」を入力として足す。

### 案3（補助）：CSVアップロード
MF連携がない口座用。列の形は銀行ごとに違うため、サンプルCSVを見て取り込み形式を決める。

## 4. 追加するデータ（案）

- `payment_match_rules`：`vendor_id`、`corporation_id`、`desc_pattern`（摘要の一致文字列）、`created_by`、`created_at`
- `payment_match_candidates`：`invoice_id`、`mf_journal_id`、`tenant_id`、`score`、`reasons`（理由の説明）、`status`（候補／承認／却下）、`decided_by`、`decided_at`
- 既存の請求書の `payment_status`（wait→paid）を、承認時に更新する（今の「選択を振込済みにする」と同じ処理を使う）。

## 5. 画面（案）

- 請求書一覧「振込待ち」に **「🔎 引き落とし照合」ボタン**。押すと、対象の請求書ごとにMFの仕訳を探し、候補を一覧表示。
- 各候補に「金額・日付・請求先・MFの仕訳へのリンク・一致した理由」を表示。
- 「選択を振込済みにする」「却下」の2操作。承認は人が行う。
- 定期実行（毎朝）で候補だけ作っておき、バッジで「照合候補 n件」を出す（承認はしない）。

## 6. リスクと対策

| リスク | 対策 |
|---|---|
| 同じ金額の別請求を誤って結びつける | 補助科目・摘要・日付も条件にして点数化。**人が確認して承認**。 |
| MFの仕訳が重複して入っている | 同じ仕訳に複数の請求書を結ぶ場合は警告。 |
| 引き落とし日がずれる（休日など） | 期日の前後で幅を持たせる（設定可能）。 |
| APIの呼び出し回数 | 法人・期間単位でまとめて取得し、画面からの連打を防ぐ。 |
| スコープ追加（案2）が必要になる | 再認可はマスター操作。追加前に権限範囲を確認する。 |

## 7. 確認してほしいこと（ユーザー向け）

1. MFの契約は「クラウド会計」ですか「会計Plus」ですか。（MF担当者に取引明細APIの有無を聞く際に必要）
2. MFの管理画面（App Portal）で、「API仕様書／ドキュメント」が見られますか。見られれば「取引明細（transactions）」「連携サービス（connected_accounts）」の項目を教えてください。
3. 引き落としが銀行連携で自動仕訳されるまで、だいたい何日かかりますか。（照合する期間の既定値に使います）
4. 照合の対象は、引き落としだけでよいですか。他行口座から振込も入れますか。

## 8. 段取り

1. （並行）MF側のAPI仕様確認（案2の可否）
2. 案1の下ごしらえ：MFの実際の仕訳を数件取って、貸方預金／借方買掛金の形・摘要の内容を確認
3. 照合ロジックと画面を実装（試験は取り消せる形で）
4. 承認フローと、覚えさせる仕組みを追加
