# 設計メモ: 入社時の賃金の承認

> **2026-11-12 午後の改訂（ユーザー決定・本番に適用済み・機能のスイッチは OFF）**: 判定は「正式な雇用区分」だけを基準にする。下の §2 の表（役割×給与形態）は改訂前の案で、いまは使っていない。
>
> | 雇用区分 | 判定 |
> |---|---|
> | アルバイト・パート（役割がアルバイト） | 承認なし（月給でも同じ） |
> | 正社員（役割が社員） | 社長の承認（時給・日給でも同じ） |
> | 店長・チーム長・本部（役職） | 役職だけでは決めない。入力する人が雇用区分を選ぶ。選んでいない＝確認待ち／「正社員」＝社長の承認／「アルバイト・パート」＝最初の 1 回は確認待ち（社長が確かめたら、次からは承認なし） |
> | 登録の食い違い（採用時と今の区分が違う・登録と入力の雇用区分が違う・時給と月給の混在・区分が空） | 確認待ち |
>
> - 社長本人が画面で内容（対象者・雇用区分・賃金・適用開始日）を確かめて「確定」したときは、その確定が承認（`p_confirm`）。「下書き（承認待ち）で保存」と分ける。本部の人の確定は承認待ちのまま。Slack からの入力は、社長でも「入力（承認待ち）」になり、確定は管理システムの画面で 1 回行う。
> - 雇用区分が決まっていない確定依頼は、承認する社長が雇用区分を選ぶ（選ばないと承認できない）。
> - 承認の迂回防止は DB の引き金（入社手続き中の人だけ。既存の従業員の賃金変更は止めない）。却下の理由と金額は管理システムの中だけ。
> - 適用: SQL `2026-11-18_onboarding_wage_approval.sql`（本番適用済み）・画面 nippo `49fb1c3`（公開済み）・EF は 11/12 に配置済みの版のまま。テスト（取引内）10 件 OK。


## 1. 目的と範囲
- 入社登録の賃金だけが対象。アルバイトは担当者の確定でスマレジへ反映、社員は社長が管理システムで承認するまで反映しない。
- しくみの要点: **承認されるまで、正式な賃金の表（employee_wage_settings）に行を入れない**。スマレジへ送るのはこの表の「反映待ち・エラー」の行だけなので、入れなければ送られない。
- 金額の妥当性は判断しない（AI・プログラムは金額を決めない・推測しない）。見るのは「雇用区分と給与形態の組み合わせ」だけ。

## 2. 判定の表（関数 `onboarding_wage_rule`）
正式な雇用区分＝`users.role`（既存の `post_join_class` と同じ見方: AL＝アルバイト、それ以外＝社員の扱い）。

| 雇用区分（役割） | 時給 | 月給 | 日給 |
|---|---|---|---|
| アルバイト（AL） | **承認なし** | 確認待ち | 確認待ち |
| 社員・店長（SHAIN・TENCHO） | 確認待ち | **社長の承認** | 確認待ち |
| チーム長・本部（TEAM・HQ） | 確認待ち | **社長の承認** | 確認待ち |
| 社長（CEO） | 確認待ち | 確認待ち | 確認待ち |

次のときは、給与形態に関係なく **確認待ち**: 役割が空・想定外の値／今の役割と、入社登録を始めた時の区分（`onboarding_workflows.role`）が違う／今の役割と、招待（採用）の時の区分（`invitations.role`）が違う／時給と月給が混ざっている。

理由:
- アルバイト×時給は在職者の大半（123 人）と同じ形。ここだけを「承認なし」にする。
- 日給は在職者 0 人。例外なので人の確認に回す。
- チーム長・本部の時給は実在する（3 人）が、役割は雇用区分そのものではなく、社員かアルバイトかを役割から決められない。依頼時の案（一律で社長の承認）から、**時給だけ「確認待ち＋理由の表示」に変えた**。どちらも社長の承認が要る点は同じ。
- 区分の食い違いを確認待ちにするのは、「社員として採用した人を、あとからアルバイトに書き換えて承認を通さずに入れる」誤り・抜け道を止めるため。
- 確認待ちは「社長の承認に回し、理由を画面と Slack に出す」。出口は 3 つ: ①社長が理由を見て承認 ②区分を直して入れ直す ③取り下げ。

## 3. 状態の流れ
```
入力（onboarding_wage_submit）
 ├ 承認なし → その場で hr_save_wage（正式な賃金・反映待ち）→ スマレジ反映 → 読み直して照合 → 項目「賃金」完了
 └ 社長の承認／確認待ち → 確定依頼を pending で作るだけ（正式な賃金には入れない）
        項目「賃金」＝ manual_required ＋ last_error「社長の承認待ち」＋ payload.approval='pending'（金額なし）
      ├ 承認（onboarding_wage_decide）→ ここで初めて hr_save_wage → 項目 running → スマレジ反映 → 照合 → 完了
      ├ 却下 → 何も入れない。項目 manual_required「社長が却下しました（入れ直し）」
      └ 入れ直し・取り下げ → 前の依頼は cancelled（行は残る）
```
- 確定依頼の状態: pending / approved / rejected / cancelled（表 `onboarding_wage_requests`）。承認待ちは 1 つの入社登録に 1 件まで。
- 項目の状態に `manual_required` を選んだ理由: ①完了判定（全項目 completed）に入らない ②親メッセージが今の作りのまま「🛑 止まっています: 賃金（社長の承認待ち）」と出る ③`running` は「機械が処理中」の意味で wage_sync が使っており、紛らわしい。承認後〜反映完了までは `running`＋`payload.approval='approved'`。
- 注意して塞いだ穴（EF パッチ）: `wage_confirm`（✅ この日付で確定）は manual_required を完了にできる／`wage_sync` は送る行が無いと「完了」にしてしまう → 承認待ちの確定依頼があるあいだは、どちらも断る。
- スマレジへの反映と照合は今までの `wage_sync`（wage_push → wage_pull）をそのまま使う。画面から承認したときは DB から onboarding-notify（op=wage_decided）を呼ぶ（既存の `pay_change_notify_op` と同じ通り道。送るのは id と出来事の名前だけ）。

## 4. 権限
- 入力・確定: 本部・社長・マスター（今の hr_save_wage と同じ）。設定 `confirmer_ids` に人を並べると、その人だけに絞れる。自分の賃金は入力できない。
- 承認・却下: **役割が社長（CEO）の人だけ**。マスター権限では代用できない。自分の賃金は承認できない。却下は理由が必須。
- 取り下げ: 入力・確定できる担当者。
- 金額を見られる人: 本部・社長・マスター（正式な賃金の表を読める人と同じ）。確定依頼の表は画面から直接読めず、関数 `onboarding_wage_status` が権限のある人にだけ金額を返す。Edge Function（Slack 用）には金額を返さない。
- **採用担当者（本部以外）を足すことは、今回は入れていない**: hr_save_wage と項目の更新（onboarding_set_item）が「本部・社長・マスター」固定で、hr_save_wage を変えない条件と両立しないため（→ 決めてもらう点）。

## 5. 履歴
- `onboarding_wage_requests`: 入力者・入力日時・給与形態・金額・適用開始日・店舗・判定と理由・その時点の区分の控え・確定者／承認者・日時・却下の理由・正式な賃金に入れた日時と行の id。入れ直すたびに新しい行（前の行は消さない）。
- `onboarding_wage_request_events`: 入力／確定／承認／却下／取り下げ／入れ直し／登録失敗（だれが・いつ・どこから。金額なし）。
- 既存の記録もそのまま残る: 入社登録の履歴（onboarding_events）・正式な賃金の `created_by`。

## 6. Slack の表示（金額は出さない。承認・却下のボタンは置かない）
- 親メッセージの賃金の行: 「⏳ 社長の承認待ち」「↩️ 却下（入れ直し待ち）」「🔄 承認済み（スマレジへ反映中）」。確認待ちは理由も出す。
- スレッド: 承認待ち（区分・理由・「従業員ページで確認・承認」のリンク）／承認した（このあと反映の結果）／却下した（「💴 賃金を入れ直す」）／取り下げ。却下の理由は Slack に出さない（金額が書かれることがあるため。管理システムで見る）。
- 賃金モーダル: 有効のときだけ「社員などは社長の承認後に反映」の案内と、ボタン名「登録する」。

## 7. 管理システムの画面（nippo）— 承認の場所は「従業員ページの賃金カード」
- 選んだ理由: 金額が見えるのは今もこのカードだけ（本部・社長・マスター）。既存の「📝 承認待ちの申請」も「一覧は金額なし → 名前を押して従業員ページで金額を見て操作」という同じ作り。ポータルの requests.html は金額を出さない一覧なので、承認の場所にしない。
- 変更点は `ob1/nippo_notes.md`（賃金カードの保存先の切り替え・承認待ちの表示と承認／却下・一覧への追加）。

## 8. 既存の機能との境界
| 既存のもの | 今回の扱い |
|---|---|
| スマレジ側の変更の控え `wage_external_changes`（未承認 12 件） | 読まない・書かない。一括承認しない |
| スイッチ B `wage_import_hold`・賃金 2 段階承認 `wage_approval_required`／`approval_routes`・`payroll_wage_guard`・`wage_import_precheck` | 値を読まない・変えない |
| 変更申請 `profile_change_requests`・`pay_change_*` | 使わない（既存従業員の変更用）。通知の通り道 `pay_change_notify_op` だけ借りる |
| `hr_save_wage` | 変えない。新しい関数が条件を満たしたときだけ呼ぶ |
| 直接登録の禁止 `employee_change_pay_guard` | 変えない。別の引き金 `onboarding_wage_direct_guard` を足す（下） |
- 新しい引き金（設定が有効のときだけ）: 入社手続き中の人の賃金を、確定依頼を通さずに人が直接入れることを止める。従業員ページや切り替え前の Slack から hr_save_wage を直接呼ぶと、社員の賃金が承認なしで入ってしまうため。スマレジからの取り込み・同期状態の更新は通す。入社手続きが終わった人には何もしない。

## 9. 切り替えのスイッチと順番
- `app_settings.onboarding_wage_approval`: `enabled`（既定 **false**＝今までどおり）／`block_direct`（既定 true。直接登録の制限だけ外したいとき false）／`confirmer_ids`（既定 空）。
- 順番: ①SQL を適用（無効のまま＝動きは変わらない）→ ②Edge Function 2 本を反映（無効なら今までどおり）→ ③nippo を反映 → ④テスト従業員で確認 → ⑤`enabled=true`。戻すときは `enabled=false`（承認待ちの行と履歴は残る）。
- ③より前に⑤にすると、従業員ページからの賃金の保存が入社手続き中の人だけ止まる（Slack からは入力できる）。

## 10. 進行中の入社登録の扱い
- 賃金がすでに完了している入社登録: 何もしない（さかのぼって承認を求めない）。
- 賃金がまだの入社登録: 有効にしたあとの入力から、新しい判定になる。
- 有効にする前に開いた Slack のモーダル: 古い入口に送られるが、社員などは引き金が止めて、スレッドに理由が出る（入れ直せば新しい入口）。
- 入社登録を始めたあとに役割を変えた人: 「区分の食い違い」で確認待ちになる（社長が理由を見て承認）。

## 11. 分かっている制限
- 本部タスクの「時給」を人が ✓ すると、承認待ちでも項目は完了になる（今の作りのまま。正式な賃金には入らず、確定依頼は承認待ちで残る）。
- 入社登録が完了したあとの賃金の変更は対象外（既存のスイッチが OFF のあいだは、今までどおり直接入れられる）。
- 画面から承認した直後の反映は DB → Edge Function の呼び出しに頼る。失敗したときは、賃金カードの「未反映の N 件をもう一度反映」で送れる（項目の完了は手で）。
- 入社手続き中の人の移籍（賃金のコピー）は、有効のあいだ引き金に止められる。
