# 計画書: 採用管理の共通 API と、Slack からの操作

作成 2026-11-12 午後。**調査と計画まで。本番の変更はしていない（採用の通知は配置済み・スイッチ OFF）。応募者への送信は一切していない。**
関連: [設計書 採用管理の Slack 通知](設計書_採用管理のSlack通知_2026-11-12.md)。

## 0. 方針（2026-11-12 ユーザー決定）

- **管理システムの DB が正本。** 応募者・やり取り・面接日時・担当・状態・操作の履歴は、すべて管理システムに持つ。Slack だけにある情報、Slack だけで変わる状態は作らない。
- 管理システム（Web の画面）・Slack・将来の専用アプリは、**同じ業務処理（共通 API）**を呼ぶ。メッセージの送信・状態の変更・面接の調整を、Slack 専用のコードに作り込まない。
- いまの管理システムの採用の機能は、変えない・消さない。Slack は、同じ情報を見て操作できる追加の入口。
- 応募者への返信は、Slack では必ず［応募者へ返信］ボタンから。**スレッドへのふつうの返信は社内メモで、応募者へは送らない。** 送信の前に、宛先と本文を確認できるようにする。
- 管理システム側で行った操作も、Slack の同じスレッドに反映する（新しい親は作らない）。反映と通知（メンション）は分ける。
- 応募者 1 人の 1 つの採用案件につき、親は 1 件。再応募は新しい採用案件として持ち、過去の案件と履歴でつなぐ。
- 権限で制御する（チャンネルにいるだけでは返信できない）。Slack での操作も、管理システムの履歴に残す。
- **応募者への実際の送信を伴うテストは、別途承認を取る。**

## 1. いまの仕組み（本番のコードで確認）

### 1.1 応募媒体ごとの、受信と送信

| 媒体 | 受信 | 管理システムから応募者への送信 |
|---|---|---|
| **LINE** | LINE からの受信を、その場で取り込んで保存。重複受信は媒体のメッセージ番号で防いでいる | **送れる。** LINE の Messaging API（push）。応募者が公式アカウントと連携済み（合言葉で紐づけ）のときだけ。直近 30 日: 受信 32・送信 35 |
| **Indeed** | Indeed からのメールを GAS が 5 分ごとに取り込む。送り手の向きは推定 | **送る API は無い。** 担当者が Indeed の画面から返信し、その控えのメールが後から取り込まれる。管理システムの画面は、Indeed のページへ誘導するだけ。直近 30 日のやり取りの記録は 0 件 |
| **自社の応募フォーム** | フォームの送信・GAS の取り込み。メッセージは作らず、回答と面接の希望日時を応募者の行に入れる | 媒体としての返信手段は無い。LINE が連携済みなら LINE、そうでなければ文面をコピーして人が送る |
| 手動登録・紹介・CSV | 画面から登録 | 同上 |

- **Slack から応募者へ送れるのは、いまは LINE だけ。** Indeed とフォームは、「文面を作ってコピー」＋「Indeed のページを開く」までになる（媒体側に送信の API が無いため）。
- 選考中の応募者 15 人のうち、LINE 連携済みは 10 人。

### 1.2 いまの送信の問題点（管理システムの画面から送る場合）

| 問題 | 中身 |
|---|---|
| 二重送信を防ぐ仕組みが無い | 押しているあいだボタンを押せなくしているだけ。読み込み直して押すと、もう一度送られる |
| 送ったのに記録が無い、が起こりうる | 送信は成功したが記録に失敗した場合、その結果を確かめていない |
| 送った人の記録が後付け | 送信のあと、画面が「最後の送信は自分」と印を付ける方式。画面が閉じると空のまま。2 人が同時に送ると取り違えるおそれ |
| 失敗の見え方 | 失敗したときは記録が残らない（成功したようには見えないが、失敗した事実も残らない） |

### 1.3 いま、応募者へ自動で送っているもの（変えない）

面接の確定と同時の案内／採用時の招待リンク／面接前日のリマインド／入社登録がまだの方への催促（最大 3 回）／入社登録の完了時の案内／LINE の連携が済んだときの返信。

### 1.4 面接・状態・担当

| 操作 | いまの作り |
|---|---|
| 面接の希望日時 | 自社フォームの回答から入る。画面に［この日時で確定］ |
| 面接の確定・変更 | 画面が順に実行: カレンダーの予定（GAS）→ 確定の保存 → LINE で案内 → 送信済みの印。**順番を画面のコードが制御している** |
| 面接の取り消し | 予定を消し、応募者の行を直接書き換え。応募者へは送らない |
| 面接の結果 | 専用の項目は無い。状態を変えるだけ |
| 状態の変更・不採用・辞退 | 画面が応募者の行を直接書き換え |
| 採用決定 | 専用の処理（招待を作り、入社登録へつながる）。ただし、詳細画面の［保存する］で「採用」を選ぶと、この処理を通らない（招待が作られない） |
| 担当者 | 画面が直接書き換え。店舗の「面接担当」から自動で割り当てる仕組みあり |
| 対応済み | 専用の処理あり |

### 1.5 権限と履歴

- 採用の権限は 2 つ: 「採用」（閲覧・返信・面接・状態の変更・採用決定をまとめて）と「全店の採用」。役割ごとの既定: 社長・本部＝両方／チーム長＝採用だけ（担当の店舗）／店長・社員・アルバイト＝なし。個別に付けている人が 1 人。
- 閲覧・返信・面接の変更・採用決定は、権限が分かれていない（どれも「採用」1 つ）。
- 履歴: 「最後に操作した人」しか残らない。だれが・いつ・何を、を順に残す表は無い。Indeed の送信・自動送信・取り込みは、操作者が空。

### 1.6 共通 API にするうえでの課題

- 業務処理の多くが、画面のコードに埋まっている（応募者の行の直接の書き換えが 15 か所ほど・送信の順番の制御が 6 か所ほど）。
- いまある処理（面接の確定・採用決定・対応済みなど 17 本ほど）は、どれも「ログインしている本人」が前提で、Slack やアプリから「この人の操作として」呼ぶ引数が無い。

## 2. 共通 API の設計（案）

```
応募媒体（LINE・Indeed・フォーム）
        ↓ 受信（今までどおり）
管理システムの DB（正本）＋ 共通の業務処理
        ↓ 同じ処理を呼ぶ
Web の画面 ／ Slack ／ 将来のアプリ
        ↓ 変化があれば
Slack のスレッドへ反映（配置済みの通知。入口がどこでも同じ）
```

どの処理も、同じ約束で作る。

| 約束 | 中身 |
|---|---|
| 操作者 | 「だれの操作か」を必ず受け取る。Web＝ログインしている本人／Slack＝Slack の利用者から管理システムの利用者を引く（勤怠確認と同じ方式）／アプリ＝ログインしている本人 |
| 権限 | 共通の判定 1 つを通す（採用の権限があり、その応募者の店舗を見られること）。チャンネルにいるだけでは通らない |
| 履歴 | 新しい表「応募者の出来事」に、必ず 1 行残す（何を・何から何へ・だれが・どこから〈Web／Slack／アプリ／自動〉・いつ） |
| 二重防止 | 依頼ごとの鍵を受け取り、同じ鍵の 2 回目は「処理済み」を返すだけ |
| Slack への反映 | 処理の中では Slack を呼ばない。DB の変化を、配置済みの通知が拾ってスレッドに書く（入口がどこでも同じ動き） |

| 共通の処理（案） | 中身 | いまの何を包む・置き換えるか |
|---|---|---|
| メッセージを送る | 送信箱に「送る依頼」を入れる（依頼中 → 送信中 → 送信済み／失敗）。実際に送るのは送信の関数 1 つ。成功したときだけ、やり取りに「こちらから」の 1 通を、送った人つきで記録。失敗は失敗として残す | 画面の LINE 送信（送信 → 記録 → 送った人の印、の 3 段を 1 つに） |
| 面接を確定・変更・取り消す | 日時・方法・場所。カレンダーの予定はサーバー側で扱う。応募者への案内は「送る」と指定したときだけ送信箱へ | 面接の確定の処理＋画面の直接の書き換え |
| 状態を変える | 連絡済み・面接済み・不採用・辞退・連絡なし（理由つき）。採用はここでは受けず、下の「採用を決める」へ | 画面の直接の書き換え |
| 採用を決める | 招待を作り、入社登録へつなぐ。有効な招待が既にあれば作り直さない | 採用決定の処理（＋詳細画面の［保存する］の抜け道をふさぐ） |
| 担当者を決める | 担当者の設定・変更 | 画面の直接の書き換え |
| 対応済みにする | 未対応の印を消す・戻す | 既存の処理 |
| 社内メモを残す | 応募者ごとのメモ（応募者には送らない） | 新規（Slack のスレッドのふつうの返信を、メモとして残す場合に使う） |

- 送信箱は必要。理由: Slack は 3 秒以内に返事が要り、再送もある／いまの「送ったのに記録が無い」「二重送信」「送った人の取り違え」をまとめて防げる／失敗を失敗として残せる。
- いまの画面は、すぐには書き換えない。共通の処理を先に用意し、Slack から使い始め、画面は 1 か所ずつ同じ処理に寄せる（どちらから操作しても同じ結果になるように）。

## 3. Slack から応募者へ返信する（必要な実装）

流れ

1. 応募者からメッセージが届く → 管理システムが保存 → スレッドに「💬 応募者から」と本文の冒頭（担当にメンション）。← **配置済みの通知で出来ている**（スイッチを入れると動く）。
2. スレッドのカードに［応募者へ返信］ボタン。
3. 押すと入力の窓: 宛先（応募者名・媒体）と本文の入力欄。LINE が未連携・Indeed の応募者は「この応募者には、ここから送れません」と出し、文面のコピーと管理画面・Indeed のページへの案内にする。
4. ［確認する］→ 宛先と本文を表示 →［送信する］。
5. 共通の「メッセージを送る」を呼ぶ（操作者＝押した人・入口＝Slack・二重防止の鍵＝その窓の番号）。
6. 送信の関数が LINE へ送る → 成功: やり取りに記録 → スレッドに「↩️ こちらから（送った人・日時）」と本文。失敗: スレッドに「⚠️ 送信できませんでした（理由）」と、押した人だけに見える知らせ。成功したようには出さない。

作るもの

| # | 作るもの | 規模 |
|---|---|---|
| 1 | 送信箱の表・「メッセージを送る」の処理・応募者の出来事の表・共通の権限の判定 | 中 |
| 2 | 送信の関数（いまの LINE 送信の中身を、送信箱から呼べる形に分ける。**いまの画面からの送信はそのまま動かす**） | 中 |
| 3 | Slack 側: ボタン・入力の窓・確認・送信（処理は共通の処理を呼ぶだけ） | 小 |
| 4 | 送信の結果をスレッドへ（配置済みの通知に、失敗の行を足す） | 小 |
| 5 | 管理システムの画面の送信を、同じ処理に寄せる（別の段階。nippo の公開が要る） | 中 |

応募者に送らずに確かめる方法

- 送信箱に「試し」の印を持つ（設定が「試し」のあいだは、LINE へは送らず、送ったことにもせず、「試しとして処理した」と記録する）。Slack の窓・確認・二重防止・失敗の出方まで、応募者に何も送らずに確認できる。
- 実際の送信の確認は、テスト用の応募者（社長ご自身の LINE を合言葉で連携したもの）で 1 通だけ。**別途承認をもらってから。**

| 管理システムでの操作の反映（返信・面接の確定や変更・状態・担当・採用・入社登録への移行） | — | 段階 1（配置済み） | スレッドへの記録。親の状態を更新 |

| 採用決定 → 入社登録 | 詳細・一覧 | 段階 3 | ［採用を決める］→ 役割・店舗を選ぶ → 入社登録へ（招待の送信は確認つき） |
| 対応済み | 詳細 | 段階 3 | ［対応済みにする］ |
| 電話番号・メール・回答の内容の確認 | 詳細 | 出さない | ［管理画面で開く］ |

| 応募者の登録・CSV・削除 | 画面 | 出さない | 管理システムだけ |

## 5. 担当が決まっていない応募（ユーザー決定の反映）

- 担当者がいる → 担当者にメンション。
- 担当者がいない・応募店舗は決まっている → その店舗の責任者（店長）と担当チーム長。
- **店舗も担当者も決まっていない → 採用管理の共通担当者に割り当てる（通知なしで放置しない）。** 共通担当者は設定で持つ（だれにするかの指定が必要）。
- メンションの相手は、採用の権限があり、Slack と紐づいている人だけ。紐づいていない人には広げず、共通担当者へ回す。

## 6. 氏名だけの照合の修正（計画。データは変えない）

影響範囲と移し方の案は、[設計書 採用管理の Slack 通知](設計書_採用管理のSlack通知_2026-11-12.md) の末尾。要点:

- いまは、Indeed の取り込みが氏名だけで照合し、同じ氏名なら既存の応募者の行に上書きで足している（自社フォームは 電話 → メール → 氏名）。同じ氏名の応募者が 2 人以上いる組は、いま 0。
- 直したあと: 同じ応募の重複受信（媒体の応募番号が同じ）＝自動で同じ案件／電話かメールが一致し氏名も同じ＝同じ応募者の再応募（新しい採用案件・過去とつなぐ）／氏名だけ一致、または電話・メールは一致するが氏名が違う＝新しい応募者として入れて「確認待ち」（画面の「同じ人かも」で人が決める）。
- 再応募を「新しい採用案件」にするには、いまの「1 人＝1 行で上書き」に、案件の単位を足す必要がある。段階を分ける:
  1. まず「記録だけ」: 新しい判定の結果を控える（動きは今までどおり）。数日見て、取り違えそうな件数を確かめる。
  2. 氏名だけの一致では足さない（新しい応募者として入れ、確認待ちにする）。← ここまでは、表の作りを変えずに出来る。
  3. 案件の単位を足す（再応募＝新しい案件。Slack の親は案件ごと）。← 表の作りが変わるため、別に設計して承認をもらう。
- 過去の応募者は、分割も一括変更もしない。

## 7. 実装の順番

| 順 | 中身 | 状態 |
|---|---|---|
| 1 | 採用の通知を本番に配置（スイッチ OFF） | **済み**（11/12） |
| 2 | 通知アプリをチャンネルに招待 → テスト投稿（使い捨ての応募者）→ スイッチを入れる | 招待待ち。スイッチを入れるのは、テストの結果を報告して承認をもらってから |
| 3 | 管理システムでのメッセージ・面接の変更をスレッドへ反映 | 配置済みの通知で対応済み（スイッチを入れると動く）。「だれの操作か」が空になる場合がある点は、順 4 の履歴の表で埋める |

| 5 | Slack から面接・状態・担当・採用を変更 | 未着手 |

| 並行 | 氏名だけの照合の修正（§6 の 1 → 2） | 未着手。承認が必要 |

## 8. 追加の承認・判断が必要なこと

1. 採用管理の**共通担当者**をだれにするか（店舗も担当も決まっていない応募の割り当て先）。
2. 通知のスイッチを入れる時期（招待とテスト投稿のあと）。
3. Slack からの返信の実装に進んでよいか（送信箱と共通の処理を本番に足す。応募者への実送信はしない設定で配置）。
4. 実際の送信のテスト（テスト用の応募者＝社長の LINE で 1 通）。
5. 氏名だけの照合を「記録だけ」→「氏名だけでは足さない」に進めてよいか。
6. 閲覧・返信・面接の変更・採用決定の権限を分けるか（いまはどれも「採用」の権限 1 つ）。
7. スレッドのふつうの返信を、社内メモとして管理システムに保存するか（保存しない場合は、Slack の中だけのメモになる）。
