## `stg_delivery_order` スキーマ（3担当共通・正本）

BigQuery `tori-analytics.sales.stg_delivery_order`。重複排除キー=`(channel, order_no, txn_type, txn_at)`（日次速報→月次精算確定でMERGE上書き）。

| 列 | 型 | 内容 |
|---|---|---|
| `channel` | STRING | `'rocketnow'`（将来`'ubereats'`等追加） |
| `store_id` | STRING | 当社store_id（UUID文字列。delivery_store_map経由で解決済み） |
| `channel_store_id` | STRING | チャネル側店舗ID（例`'54887'`） |
| `txn_date` | DATE | 取引日 |
| `txn_at` | DATETIME | 取引日時（JSTの壁時計表記そのまま） |
| `txn_type` | STRING | `'PAY'` / `'CANCEL'`（CANCELは金額がマイナス） |
| `order_no` | STRING | 注文番号 |
| `items_text` | STRING | 注文内容（商品名） |
| `sales` | NUMERIC | 売上高 |
| `coupon_store` | NUMERIC | 店舗負担クーポン金額 |
| `fee_total` | NUMERIC | 総手数料（3%決済手数料込み） |
| `tax` | NUMERIC | 消費税 |
| `fee_discount` | NUMERIC | 手数料の割引金額 |
| `payout_expected` | NUMERIC | 精算予定金額（＝店舗への入金相当額） |
| `is_settled` | BOOL | true=月次精算ファイル由来（確定値）／false=日次ファイル由来（速報。月次が来ると自動でtrueへ上書き） |
| `source_file` | STRING | 取込元ファイル名 |
| `imported_at` | DATETIME | 取込日時（UTC） |

`delivery_store_map`（Supabase）: `channel` / `channel_store_id` / `store_id` / `channel_store_name`。現在ロケットナウの2店舗（鳥一代本店=54887・鳥一代はなれ=55662）のみ登録済み。他店舗が増えたら同じ形で追記するか、未知IDのLark通知を見て担当Dへ連絡してください。

4. **⚠️着手前に必ず確認（二重計上防止・設計書§6-Q2）**: ロケットナウの売上が、レジ（dinii/スマレジ）側の売上に**既に含まれているか**を先に確認してください。含まれている場合、`fact_daily_store`の売上とデリバリー売上をそのまま合算すると二重計上になります。含まれていない（デリバリー注文はPOSに打っていない）場合のみ、単純合算で問題ありません。含まれているかどうかは店舗オペレーション（レジ入力方法）次第で店舗ごとに違う可能性があるため、実データの整合性チェック（例: ある日のdinii/スマレジ売上に、ロケットナウの`payout_expected`相当が上乗せされていないか突合）で確認することを推奨します。

6. 着手タイミング: 担当D完了後（今すぐ着手可）。ただし実データが流れ始めるのはGAS本番デプロイ後です（WORKLOG参照・デプロイ自体は担当Dが対応中）。

## 担当C（売上入金・会計UI刷新）へ

**元指示**: 設計書§2「売上入金（会計WS）との接続: 月次精算ファイルの店舗×精算期間サマリ（精算予定金額合計）＝入金予定として`ar_`売上入金フローへ（PayPayと同型: 予定vs実入金→一致で自動消込・差異のみ要確認）」

### 現状（担当Dが確認したC側テーブルのスキーマ）
`ar_receivables` / `ar_deposits` / `ar_matching` / `ar_recurring_master` は作成済み・すべて0件（まだデータ投入なし）でした。既存の列構成を尊重し、以下は担当Dからの**提案**です（列名の解釈が違えば調整してください）。

### やること（提案）
1. **`ar_recurring_master`にロケットナウの定期入金定義を1行登録**:
   - `name`: 例「ロケットナウ（デリバリー精算）」
   - `kind`: 御社の分類に合わせて（請求書ではなく売上入金側の想定）
   - `import_job`: `'delivery-sales'`（担当Dの`import_runs.job`・`import_schedule.job`と揃えてあります。Phase2でこのjobをスケジュール登録する際も同じキーになります）
   - `frequency`: 月次
   - `expected_day_from`/`expected_day_to`: ロケットナウの精算サイクルに合わせて設定（設計書の実ファイル例では「8/12〜9/11」のような約30日サイクルでした。正確な精算確定日は担当Dが把握していないため、ユーザーかロケットナウ側の資料で確認をお願いします）
   - `fetch_method`: 現状は手動（Phase1）。Phase2でPlaywright自動化されたら更新
   - `automation_level`: 設計書のLv定義に沿って選択
2. **`stg_delivery_order`（月次精算・`is_settled=true`のみ）→`ar_receivables`への投入バッチ**: 店舗×精算期間（`txn_date`の範囲、またはファイル単位）で`payout_expected`を合計し、`ar_receivables`へ1行（`source_table='stg_delivery_order'`・`store_id`・`year_month`または期間・`expected_amount`=合計`payout_expected`・`expected_date`=精算予定日）として登録。**`is_settled=false`（日次速報）の行は入金予定の根拠にしない**でください（速報値は変動するため。設計書の注意書きどおり「金額は月末の精算時に変更される可能性がある」）。
3. **消込**: 既存のPayPay向けロジック（予定vs実入金→一致で自動消込、差異のみ要確認）と同型で運用できます。実入金の照合元（銀行口座の入金明細）は別途確認が必要かもしれません（ロケットナウの入金が振込CSV等どの形で銀行口座へ着金するかは担当D未確認）。
4. **【2026-09-11 ユーザー確認より・★訂正版】ロケットナウ精算書は会計入力（MF仕訳）を経由してPLへ**: ユーザーへ「毎月のロケットナウ精算書の売上と手数料はPLに乗るか」と聞かれ、担当Dが一度「会計入力を経由せず直接PLへ書き込む」（広告費自動連携A-8と同じパターン）と回答したところ、**ユーザーから明確な訂正あり**：「会計入力は、経由するはずだよ！ロケットナウの精算書を毎月ダウンロード→自動アップロードに反映→会計入力→PLに反映、こうなるはず」。**正しい理解はこちら**です。担当Dの前回の提案（会計入力レス直接反映）は撤回します。
   - **意図する流れ**: ①（Phase2で）ロケットナウ精算書を自動ダウンロード→②会計WS「自動取込」の対象として認識→③**会計入力（MF仕訳）を実際に作成**（`mf-journal` Edge Function・`create`アクションが複合仕訳=1つの仕訳に複数行を対応済み。借方=普通預金(`payout_expected`)＋支払手数料(`fee_total`)／貸方=売上高(`sales`合計)、のような3行仕訳を想定）→④**MFに実際に仕訳が登録される**→⑤既存の「支払手数料」PL連携済み科目の仕組みにより自動でPLへ反映。
   - **AI-OCRは不要**: 通常の請求書はAIがPDFを読んで金額等を推測しますが、ロケットナウ精算書は担当D側の`stg_delivery_order`で**既に構造化済み**（店舗別・精算期間別の売上/手数料/精算予定額が数値で確定している）ため、AI解析をスキップしてこのデータから直接仕訳案（または`invoices`の1レコード）を作る形にできます。自動化レベル（設計書§9-14のLv1〜4）はLv3（自動仕訳＋人間確認）かLv4（完全自動）が候補です。
   - **⚠️担当Aとの二重計上に要注意**: 担当Aが売上ダッシュボード（媒体別「ロケットナウ」・営業区分「デリバリー」）へロケットナウ売上を表示する作業と、この会計入力経由のPL反映は**別の経路で同じ売上高を扱う**ことになります。**PLの「売上」数値がどちらか一方からだけ計算されるように**してください（両方を足すと二重計上）。既存の業務委託精算4店舗と同じく「会計側（MF仕訳・精算書ベース）を正=PLの実額」「売上ダッシュボード側は速報・営業可視化用」という役割分担が本システムの既存パターンと整合します。この切り分けは担当A・担当Pとも要相談です。
5. 着手タイミング: スキーマは確定済みのため今すぐ着手可能（GASデプロイ・実データ投入を待たずに設計・実装を進めてOK）。実データでのテストはGAS本番デプロイ後になります。

## 共通の注意

- **重複排除キー`(channel, order_no, txn_type, txn_at)`**を前提にした集計にしてください。同じ注文が日次と月次の両方でBigQueryに存在することはありません（MERGEで1行に統合される）が、**`is_settled`の値は変わりうる**（速報→確定）ため、集計クエリは実行のたびに最新の`is_settled`を見るようにしてください（キャッシュ済みの古い集計を使い回さない）。
- Uber Eats等の追加チャネルは`channel`列を増やすだけで済む設計にしてあります（テーブル・カラムの追加は不要な想定）。
