# 設計書: 予約データ基盤（食べログノートCSV取込・店舗ごとの予約状況の見える化）

作成: 2026-08-27（司令塔） ／ 状態: **v1.0確定（2026-08-27 ユーザーがQ1〜Q7全回答・実CSVサンプル提供済み。§8が確定仕様＝§8が§2〜§6と食い違う場合は§8が正）**
発端: 2026-08-27ユーザー要望「今使っている食べログのノートはAPI公開されてないので、毎日朝10時とかに食べログノートのCSVデータを取り込んで、店舗ごとに予約の状況を見れるようにしてほしい」

---

## 1. ゴール（できるようになること）

1. **店舗ごとの予約状況が毎日自動で見られる**（今日・明日・先の日付の予約件数・人数・時間帯）
2. **日報・週報との連携**: 日報の「明日の天気予報」の並びに「明日（配信日）の予約状況」を表示（ユーザー要望・予約データ紐付け完了後）
3. **将来の分析につながる**: 予約数と実売上の関係、広告の予想売上（担当G持ち越しタスク。ネット予約人数を使う計算式が設計済み）への実データ供給

## 2. 全体の流れ（案）

```
毎朝10:00  Mac mini（ns-daily-importと同じ仕組み）が
           食べログノートに自動ログイン → 予約一覧CSVをダウンロード
    ↓
           ハブSupabaseへ保存（reservations テーブル・新設）
    ↓
           日次サマリーをBigQueryへミラー（stg_reservation・新設）
    ↓
表示       ポータル / 経営ダッシュボード / 日報配信（§6のQ5で確定）
```

- **取得方式**: スマレジCSVと同じ「Mac miniの自動ブラウザ操作（Playwright）」方式が第一候補（食べログノートはAPI非公開のため）。`ns-daily-import`に新ジョブを1本追加する
- **既存ルールとの関係**: `ns-daily-import`への変更は「触る必要が出たらWORKLOGで宣言」ルールの対象。本設計が確定したら宣言して着手する

## 3. 保存先（確定済みの設計判断に沿った提案）

要件定義書§16の原則「**業務データ=ハブSupabase／分析=BigQuery**」に従う:

| データ | 置き場所 | 理由 |
|---|---|---|
| 予約の生データ（1件=1予約。日時・人数・経路・状態） | ハブSupabase `reservations`（新設・RLSで店舗権限を制御） | 画面表示・日報連携・権限管理はこちらが得意 |
| 日次サマリー（店舗×日付×時間帯×件数×人数） | BigQuery `tori-analytics.sales.stg_reservation`（新設） | 売上（fact_daily_store）と並べた分析・広告予想売上への供給 |
| 予約者の氏名・電話番号など個人情報 | **Q4の回答で決定**（保存する場合はSupabaseのみ・閲覧権限を絞る・BigQueryには入れない） | 個人情報を分析基盤に混ぜない |

## 4. 表示（案・Q5で確定）

- **案A: 経営ダッシュボードに「予約」タブ**（担当A縄張り）— 売上と同じ場所で見たい場合
- **案B: 統合ポータルのホームウィジェット**（担当F縄張り・F-7のウィジェット機構に載せるだけ）— 朝いちで全店舗をパッと見たい場合
- **案C: nippoに予約ページ**（担当B縄張り）— 店長・現場も見る場合
- 複数併用も可能（データはSupabaseに一元化されるため、画面は後から増やせる）

## 6. ユーザーへの質問（回答をもらってから設計確定）

- **Q1. CSVの出どころ**: 食べログノートの管理画面に「予約一覧のCSVダウンロード」機能はありますか？（あるなら、どの画面のどのボタンか。スクリーンショット1枚あると確実です。**もし無ければ**、画面に表示された予約を読み取る方式を検討するので、その旨だけ教えてください）
- **Q2. アカウント構成**: 食べログノートのログインは全店舗共通の1アカウントですか？店舗ごとに別ログインですか？（対象にしたい店舗数と、ログインの数を教えてください）
- **Q3. 取得方式の承認**: スマレジCSVと同じ「Mac miniが毎朝自動ログインしてダウンロード」方式でよいですか？（ログインID・パスワードをお預かりして、いつもの`app_secrets`／環境変数の仕組みで安全に保管します。コードには書きません）
- **Q4. 見たい深さ**: どこまで見たいですか？
  - A: 件数・人数・時間帯のサマリーだけで十分
  - B: 予約者名・コース・電話番号など1件ずつの明細まで見たい（→閲覧できる人を絞る権限設計を含めます）
- **Q5. 表示場所**: §4の案A（経営ダッシュボード）／案B（ポータルウィジェット）／案C（nippo）のどれがよいですか？（複数選択可。まず1つに絞るならどれか）
- **Q6. 電話予約**: 電話で受けた予約も食べログノートに手入力していますか？（していれば食べログノートだけで予約の全量が取れます。していなければ「ネット予約のみ」の数字になります）
- **Q7. 過去分**: 過去の予約もさかのぼって取り込みたいですか？（食べログノート側で過去分がCSVで出せる場合のみ。分析用に3ヶ月〜1年あると予約×売上の相関が見られます）

## 7. リスク・注意（設計段階で分かっているもの)

- **画面変更に弱い**: 自動ブラウザ操作は食べログノート側の画面リニューアルで止まることがある → 「朝の見張り番」（D-3）に予約取込の成否チェックを追加して、止まったら気づける形にする
- **利用規約**: 自社アカウントの自社データを自社利用のためにダウンロードする範囲で設計する（外部提供・再配布はしない）
- **個人情報**: Q4でBを選ぶ場合、閲覧権限（役職）・保持期間をユーザーと決めてから実装する

### 8.2 実CSVの形式（受領サンプルより）

- 文字コード**Shift_JIS**（取込時にUTF-8へ変換）・ヘッダー1行
- 列: `予約No, 顧客No, 来店数, キャンセル数, 連絡なしキャンセル数, 来店日, 来店時間, 滞在時間, 人数, お子様人数, ステータス, 受付窓口, Vポイント, 卓, コース, メニュー/コース, 予約属性, 予約メモ, 作成日, 作成時間, インポート時に指定した作成日, 同作成時間`
- ステータス実測値: `来店済み／来店前／着席済み／退店済み／ユーザーキャンセル／キャンセル／店舗キャンセル／無断キャンセル／インフルエンサー料金会計済み`
- 卓は`"T3, T4"`のようにカンマ入り引用符あり → CSVパーサは引用符対応必須
- ウォークインの行は`予約No`が数値・`顧客No`空欄。**`顧客No`があるためリピーター（再来店）分析が予約データだけで可能**（カメラ不要のおまけ成果）

### 8.3 取込ルール（月次洗い替え・ユーザー指定）

1. 毎朝10:00、全店舗をループして**「当月分」CSVを取得し、店舗×対象月を丸ごと洗い替え**（delete→insert。キャンセル発生・変更を確実に反映するため）
2. **実行日が25日以降なら「翌月分」も同様に取得・洗い替え**（例: 9/25以降は9月分＋10月分）
3. キャンセル行も**必ずDBに保存する**（2026-08-27ユーザー追加指示で確定: キャンセル分析に使うため取込対象。**ただし予約帳の表示・日報への表示ではキャンセル系を除外**）。詳細は§8.6
4. **洗い替え時の引き継ぎ**: 同じ`予約No`の行を消して入れ直す際、`first_imported_at`（最初に取り込んだ日時）と`cancel_detected_at`（ステータスがキャンセル系に変わったのを最初に検知した日時）は**引き継ぐ**。CSVにはキャンセルされた日時が無いため、この日次検知が「予約が入ってからどれぐらいでキャンセルになったか」の測定手段になる（粒度は日単位・運用開始以降の分のみ測定可能）
5. 初回に過去月バックフィル（店舗×月でループ。食べログノート側で取れる範囲まで）
6. 取込成否は「朝の見張り番」（D-3）方式でLark通知（0件・ログイン失敗を検知）

### 8.4 保存先（§3の方針で確定）

- ハブSupabase `rsv_reservations`（新設。接頭辞`rsv_`をレーンIの名前空間として所有権マトリクスに追加）: CSV全列＋`store_id`＋`source_month`（洗い替え単位）＋`imported_at`
- BigQuery `tori-analytics.sales.stg_reservation`: **`予約メモ`を除く**全列をミラー（メモに個人名が書かれる可能性があるため分析基盤には入れない）＋日次集計ビュー（店舗×来店日×時間帯×組数×人数×チャネル）

### 8.6 キャンセル分析の要件（2026-08-27ユーザー追加指示）

「予約帳・日報の表示では除くが、**分析では見たい**」を実現する:

- **見たい指標**: ①何組・何名がキャンセルされたか（店舗×月×媒体（受付窓口）別）②キャンセル率（キャンセル組数÷全予約組数。無断キャンセル率も別掲）③**予約が入ってからキャンセルまでの日数**（`作成日`→`cancel_detected_at`。日次取込のため日単位・運用開始後の分から蓄積）④どの媒体がキャンセルが多いか
- **実装**: BigQueryに集計ビュー`stg_reservation_cancel_summary`（店舗×年月×受付窓口×ステータス別の組数・人数・平均キャンセルまで日数）を用意し、A-6の予約タブ内に「キャンセル分析」パネルとして表示（既定の予約帳ビューとは分ける）
- **注意**: `ユーザーキャンセル／キャンセル／店舗キャンセル／無断キャンセル`の4種を区別して集計（「店舗キャンセル」は店都合のため、媒体別キャンセル率の既定からは分けて表示するのが公平）

### 8.7 ダイニー台帳（dinii予約台帳）にも対応する（2026-08-27ユーザー追加指示・実CSVサンプル検証済み）

「今後はダイニー台帳も使われる」ため、**予約の取込元を2系統**にする。取込先は同じ`rsv_reservations`（`source`列で区別: `tabelog_note`／`dinii`）。

**実CSVの形式（「うお蔵 新横浜店_予約一覧データ_2026-08-01_2026-08-31.csv」サンプルより）**:
- UTF-8（BOM付き）・全列引用符・店舗×期間指定でエクスポートされる形式（ファイル名に店舗名と期間が入る）
- 列: `予約日, 曜日, 予約時間（"18:00〜20:00"の範囲形式）, 合計人数, うち子供, テーブル, コース, グルメサイト備考, 属性, タグ名, お客様名, お客様名フリガナ, 電話番号, 内部メモ, 予約経路, ステータス, キャンセル日時, 予約作成日時`
- ステータス実測値: `退店済／キャンセル／予約／来店中`
- 予約経路実測値: `Ring-style／ウォークイン／いちご屋／食べログ／ホットペッパー／ぐるなび／黒HP／黒TL／レッティ／リピーター…`（**店舗略称＋媒体の独自ラベルが混ざる** → 媒体名の正規化が必須。担当Gの「媒体マスタ恒久統一」テーマと共通の対応表を使う）
- **キャンセル日時列がある** → ダイニー台帳分は「予約からキャンセルまでの時間」を**正確に**測れる（食べログノート分は日次検知の近似。§8.3-4）

**列マッピング（統一テーブルへの対応）**: 予約日→来店日／予約時間の開始側→来店時間（滞在時間は範囲から算出）／合計人数→人数／うち子供→お子様人数／予約経路→受付窓口（正規化後）／ステータス→ステータス（`退店済`→`来店済み`等の対応表）／予約作成日時→作成日時／キャンセル日時→`cancel_at`（正確値。`cancel_detected_at`より優先）

**個人情報の扱い**: ~~お客様名・フリガナ・電話番号は取り込まない~~ → **§8.8のR3回答で更新: お客様名・フリガナは取り込む（Supabaseのみ・権限限定）。電話番号は取り込まない**。`内部メモ・グルメサイト備考`は予約メモと同じ扱い（Supabaseのみ・BQに入れない）

**残確認（ユーザーへ・I-1着手前）**: → ✅**2026-08-27回答済み（§8.8）**

### 8.8 R1〜R3の回答と反映（2026-08-27確定）＋UI参照デザイン

**R1: 店舗×台帳の対応表（現時点）**

| 台帳 | 店舗 |
|---|---|
| 食べログノート | 鳥一代5店舗／川崎 鶏武者／川崎 匠味（鶏武者のサブブランド※**鶏武者の予約も混在**）／新横浜 鶏武者／新横浜 匠味（同上）／新横浜 黒霧屋 |
| ダイニー台帳 | うお蔵 新横浜（黒霧屋のサブブランド※**黒霧屋の予約も混在**） |

- **サブブランド台帳には本体ブランドの予約も入っている** → 店舗・ブランドへの振り分けは`予約経路`ラベル（例: `黒HP`=黒霧屋×ホットペッパー・`うおTL`=うお蔵×食べログと推定）の**対応表**で行う。対応表は実データを見ながら整備し、担当Gの媒体マスタ統一と共通化する
- **⚠️黒霧屋の予約が食べログノート（黒霧屋アカウント）とダイニー台帳（うお蔵側）の両方に存在する可能性** → 初回取込時に同一日・同一時間帯で突合し、重複があれば「どちらを正とするか」をユーザーに確認してから本稼働する

**R2: CSVの出力場所**: 食べログノートは**分析タブ→「当月の予約情報CSV出力」ボタン**（スクリーンショット受領・確定）。ボタン名が「当月」のため、**過去月・翌月分が同じ画面で出せるかは実装時に実機確認**（出せない場合、過去バックフィルは取れる範囲・翌月分は月替わり後の取得に切替）。ダイニー台帳（うお蔵）側の出力画面はファイル名形式が異なるため、実装時にユーザーと一緒に実画面で確認する

**R3: お客様名の表示=したい** → 方針を更新:
- ダイニー台帳の`お客様名（＋フリガナ）`は**取り込む**。ただし**Supabaseのみ（BQには入れない）・予約帳を閲覧できる役職に限定**。電話番号は引き続き取り込まない
- **注意（ユーザー了承事項）**: 食べログノートのCSVには**お客様名の列が無い**（顧客Noのみ）ため、食べログノート経由の予約は名前表示ができない（予約メモに書かれていれば見える）。名前が必要なら食べログノート側のCSV仕様確認（顧客一覧CSV等との突合）を将来課題とする

### 8.9 既存の予約取込（スプレッドシート）の調査結果と移行方針（2026-08-27夜・司令塔がコード実査）

**既存フロー（稼働中・手動）**: 広告費用対効果_管理シートの`💾予約DB`タブに予約一覧CSVを**追記**する仕組みが2ルートある。
