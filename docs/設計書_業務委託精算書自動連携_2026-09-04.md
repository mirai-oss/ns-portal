# 設計書: 請求書（ns-portal）→ 業務委託精算書（seisan-dashboard）→ 店舗PL 自動連携

作成: 2026-09-04（担当A） ／ 状態: **調査完了・API設計案（v1）。実装着手前にユーザー確認待ち**
発端: ユーザー要望「請求書システムから既存の精算書へ経費を自動登録し、既存PLへ連携したい」

---

## 0. 結論（先に要点）

- 想定していた経路 **【ns-portal → seisan-dashboard API → 既存精算書明細 → 既存PL連携】** は、
  **土台が既にほぼ存在する**（8/31〜9/1に「A-9」として作った`sd_apiAddExternalLine`が、まさにこの形の
  外部連携APIそのもの。カード手数料等のMF仕訳自動反映で実際に使われている）。
- 今回新しく作る必要があるのは主に3つ:
  1. **①登録・②取得・③更新を1本のAPIに統合**し、**invoice_id起点の外部参照キー**を専用列に持たせる
     （現状は「備考」列を冪等キー置き場と兼用しており、本来の備考が書けない）
  2. **⑤PL反映状態（対象外/反映待ち/反映済み/エラー）の追跡機構**（現状は「振込済みかどうか」までしか
     分からず、実際にPLへ書き込めたかは追跡していない）
  3. **費目→PL科目のデフォルトマッピング**（現状は明細ごとに人が毎回選ぶ設計。自動適用の仕組みが無い）
- 二重計上防止は**既に設計・実装済み**（`pl-fee-reflect`の`confirm`が精算対象店舗を明示的に拒否している）。
  今回はこの「精算書経由」の入口を、ns-portalから直接使えるAPIとして正式に整備する位置づけ。

## 1. 調査結果①: 業務委託精算書の明細保存構造（現状）

**バックエンドはGoogle Sheetsで、店舗ごとに1枚の「精算入力DB」シートがある**（固定シート名ではなく、
起動のたびに`年月/区分/費目名/金額`列を持つシートを自動スキャンして検出＝`sd_detectRaw_`）。
店舗名とシートの対応は「店舗設定マスター」シートの`店舗名`列（文字列一致。**store_idという概念は無い**）。

## 2. 調査結果②: 既存の精算書→PL連携の仕組み

`tori-dashboard/gas/Code.gs`の`syncSeisanCategoriesToPl`（[tori-dashboard/gas/Code.gs:2994](../../tori-dashboard/gas/Code.gs)）が本体。
呼び出しは**毎朝の時間主導トリガー**（Apps Scriptエディタで手動設定・コード上には見当たらないため
GAS UIの「トリガー」設定と推測。次回確認したい）。

| 質問 | 回答 |
|---|---|
| どの条件でPL対象になるか | 明細の`勘定科目`が空でも`対象外`でも`運営委託費`でもない（`運営委託費`は別の既存連携`syncSeisanFeeToPl`が担当・重複防止のため除外） |
| どのタイミングでPLへ入るか | **その店舗の属する法人・月が「振込済み」確定した後**、次の日次同期実行時（`sd_isLocked_`が`true`になるまでは`sd_apiCategorizedLines`が空配列を返す＝未確定の金額はPLに一切送られない） |
| どの店舗へ入るか | `store_directory_v`の`seisan_target=true`の店舗全部を毎回総当たり（新規追加店舗も自動的に対象になる） |
| どの対象月へ入るか | 呼び出し時の引数`ym`（単月）または`ymFrom〜ymTo`（さかのぼり一括、最大36ヶ月） |
| どのPL科目へ入るか | 明細の`勘定科目`・`補助科目`をそのまま使用（科目名の変換・マッピングはしていない＝精算書側で選んだ科目がそのままPL科目になる） |
| どの金額が入るか | 同一店舗・月・勘定科目・補助科目の明細を**税抜換算した上で合計**（個々の明細ではなく**集計値**としてDB_PLに書き込む。→5章で後述する制約の元） |
| PL対象外科目はどう判定しているか | `勘定科目 === '対象外'`（固定ロイヤリティ等、精算書はするがPLには乗せない経費用の特別値） |
| 反映済みをどう判定しているか | ❌**個々の明細単位では判定していない**。DB_PL側は「その月×その店舗×`自動｜精算書`というメモが付いた行」を**毎回全部消してから、その時点の集計値で丸ごと書き直す**方式（差分ではなく完全上書き） |
| 二重反映をどう防いでいるか | 上記の「自分のメモの行を先に削除してから書き直す」方式そのものが二重化を防ぐ仕組み。個々のリクエスト単位の冪等性チェックは無い（そもそも個別リクエストではなく日次バッチ） |

**重要な制約（今回の設計に直結）**: `sd_apiCategorizedLines`は明細を**勘定科目×補助科目で集計してから返す**ため、
DB_PL側は「どの個別明細（sourceKey）がその集計に含まれていたか」を突き合わせられない。
→ **「この1件のinvoice由来の明細がPLに反映されたか」を正確に追うには、集計前の情報を今より1段階多く
保持する必要がある**（5-3章で設計）。

## 3. 既に実装済みの外部連携API（A-9・今回そのまま土台にする）

`seisan-dashboard/gas/SeisanDashboard.gs`に、想定とほぼ同じ形のAPIが**既に動いている**:

- **`sd_apiAddExternalLine(token, store, monthKey, line)`**（[:1558](../../seisan-dashboard/gas/SeisanDashboard.gs)）
  - `PL_SYNC_TOKEN`によるサーバー間認証（ログイン不要）
  - `line.sourceKey`で冪等（同じキーなら上書き、無ければ新規追加）＝**現在は備考列に`外部連携:<sourceKey>`として保存**
  - 振込済み（ロック中）の月は追加・更新を拒否（`{ok:false, locked:true}`）
  - 呼び出し元は現状tori-dashboard側の`syncSeisanCategoriesToPl`系（カード手数料等のMF仕訳→精算書自動追加、
    設計書_広告費自動連携と精算書PL科目連携_2026-08-31.md §5）
- **`sd_apiCategorizedLines(token, store, monthKey)`**: 上記2章のPL集計取得API

**つまり①登録・③更新は既にできる。**今回作るのは②取得・④状態取得・⑤PL反映状態、および
sourceKeyの置き場所を備考列から分離すること。

## 4. 現状とinvoice連携要件のギャップ

| 要件 | 現状 | 対応方針 |
|---|---|---|
| invoice_id + 対象店舗 + 明細番号 の外部一意キー | `sourceKey`は既にあるが**備考列と共用**で本来の備考が書けない | **新規列「外部参照ID」を追加**（勘定科目・補助科目と同じ自己修復パターンで自動作成）。`sourceKey`形式は`invoice:<invoice_id>:<line_no>`を提案。備考列はns-portalから渡された自由記述をそのまま書けるようにする |
| 複数店舗・複数明細対応 | 1回の呼び出しは1店舗1明細のみ | ns-portal側が**店舗×明細ごとに1回ずつ**`sd_apiAddExternalLine`相当を呼ぶ設計のまま踏襲（GAS側の1リクエスト=1行という単純さを保つ。バッチ化は今回は過剰と判断） |
| 金額を勝手に按分しない | 既にそうなっている（呼び出し側が金額を決めて渡すだけ） | 変更不要 |
| ②invoice_idによる既存明細取得 | 無し | 新規`sd_apiGetLines(token, items:[{store,monthKey,sourceKey},...])`（バッチ対応。1invoiceの全店舗・全明細を1リクエストで取得） |
| ④明細の状態取得 | 無し | ②のレスポンスに含める（別APIにしない。呼ぶ側の往復を減らすため） |
| ⑤PL反映状態の取得 | 無し（店舗×月が振込済みかどうかまでしか分からない） | 5-3章で新設計 |
| 証憑をファイル複製しない | 現状の添付機構（Drive）はそもそも呼んでいない＝複製の心配は無い | 「外部参照ID」列（invoice_id入り）をUI上で見えるようにし、精算書画面から元請求書へのリンクを表示（ファイルは一切コピーしない） |

## 5. API設計（提案）

共通: 認証は既存と同じ`PL_SYNC_TOKEN`（Script Properties）。エンドポイントはGAS Web AppのPOST 1本
（`{fn:'...', args:[...]}`形式、既存の`sd_apiCategorizedLines`等と同じ呼び出し規約）。

### 5-1. ①登録・③更新（統合）: `sd_apiUpsertInvoiceLine`

```
POST {fn:'sd_apiUpsertInvoiceLine', args:[token, store, monthKey, {
  sourceKey,      // 必須。"invoice:<invoice_id>:<line_no>" 形式を推奨
  item,           // 費目名
  amount,         // 金額（税込）
  tax,            // '10%'|'8%'|'非課税'（省略時10%）
  account,        // 勘定科目（空なら6章のデフォルトマッピングで自動補完）
  subAccount,     // 補助科目（任意）
  note,           // 備考（自由記述。sourceKeyとは別列に保存）
  invoiceRef      // 元請求書への参照（例: invoice_id。UI表示用。sourceKeyと重複してもよい）
}]}
```
- `sd_apiAddExternalLine`をベースに、**「外部参照ID」列にsourceKey、「備考」列にnoteをそれぞれ独立して書く**よう修正
- 既存どおり：振込済みロック中は`{ok:false, locked:true}`で拒否
- 既存どおり：同じsourceKeyなら上書き（idempotent）、無ければ新規追加

### 5-2. ②取得・④状態取得（統合）: `sd_apiGetLines`

```
POST {fn:'sd_apiGetLines', args:[token, [
  {store, monthKey, sourceKey}, ...   // 1invoiceの全行分をまとめて渡せる
]]}
→ { ok:true, lines: [
  { sourceKey, found:true, item, amount, tax, account, subAccount, note,
    locked,        // 振込済み確定 true/false
    editedAt,       // 修正日（既存の「修正日」列）
    plStatus: '対象外' | '反映待ち' | '反映済み' | 'エラー'   // 5-3で定義
  }, ...
]}
```
- 1件ずつ`store`シートを読みに行くと店舗数分I/Oが発生するため、**store単位でグルーピングしてから
  シートを1回だけ読む**実装にする（既存`sd_readRowsCached_`のキャッシュをそのまま使えば速度面も問題ない）

### 5-3. ⑤PL反映状態の追跡（新設計・今回いちばんの新規実装）

**課題**（2章末尾の制約より）: 現在のPL連携は集計後の値をDB_PLへ書くため、個々のsourceKey行が
実際にPLへ含まれたかを直接は追えない。

**提案**: 「集計単位（店舗×月）の同期結果」を精算書側に記録し、そこから個々の明細の状態を導出する。

1. `syncSeisanCategoriesToPl`（tori-dashboard側）が店舗×月の同期に成功/失敗したら、**新規API
   `sd_apiMarkPlSynced(token, store, monthKey, {ok, error, syncedAt})`を呼んで結果を精算書側へ書き戻す**
   （新規シート「PL反映ログ_精算ダッシュボード」に店舗×月をキーに1行、随時上書き）
2. 個々の明細のPL状態は、この同期ログと明細自体の状態から導出する:
   - `account === '対象外'` → **対象外**
   - `!locked`（振込済みでない） → **反映待ち**
   - `locked`かつ 同期ログが無い、または同期ログの`ok===false` → **エラー**
   - `locked`かつ 同期ログの`syncedAt >= その明細のeditedAt` → **反映済み**
   - `locked`かつ 同期ログの`syncedAt < editedAt`（振込確定後に明細を編集したが、まだ次の日次同期が
     走っていない） → **反映待ち**
3. この設計なら明細1件ごとの真の反映有無ではなく「同じ集計に含まれる他の明細と合わせて同期済みか」
   という粒度になるが、**ユーザーが求めている表示（振込確定待ち→PL反映済みに自動で変わる）には
   これで十分**と判断。より厳密な行単位トラッキングにするには「毎回全部消して書き直す」現在のPL書き込み
   方式自体を差分方式に変える必要があり、影響範囲が大きいため今回は見送りを提案

### 5-4. 費目→PL科目のデフォルトマッピング

現状`sd_guessAccount_`（[:1410](../../seisan-dashboard/gas/SeisanDashboard.gs)）に**キーワード推定**の一覧が既にあるが、
ユーザーが挙げた「費目名→勘定科目の確定マッピング」ではなく「電気→水道光熱費」のような緩い正規表現推定に留まる。

**提案**: 新規シート「PLデフォルトマッピング_精算ダッシュボード」（列: `費目名` `PL反映ON/OFF` `PL反映先勘定科目`）を追加し、
`sd_apiUpsertInvoiceLine`が`account`未指定で呼ばれた場合、優先順位:
1. このマッピングシートに完全一致する費目名があればそれを使う
2. 無ければ既存の`sd_guessAccount_`のキーワード推定
3. どちらも無ければ空欄（人が精算書画面で確認・選択＝現行の「明細を入力」画面の動線をそのまま使う）

例（ユーザー提示のとおり初期データを投入）:
```
食材費        ON   原材料費
ガス料金      ON   水道光熱費
消耗品費      ON   消耗品・備品費
広告費        ON   広告宣伝費
固定ロイヤリティ OFF  （対象外）
```
ns-portal側は明細登録時に`account`を省略すれば自動適用され、例外時だけ明示的に指定すればよい。

## 6. 証憑（資料）について

ファイルは複製しない。「外部参照ID」列に`invoice:<invoice_id>:...`が入るため、精算書の「明細を入力」画面に
**「元の請求書を見る」リンク**（ns-portal側の請求書詳細URLへ、invoice_idをクエリ付きで飛ばすだけ）を
追加する程度に留める。Google Drive添付機構（店舗×月単位）は今回のinvoice連携では一切使わない。

## 7. 二重計上防止（既存の設計を確認）

`ns-portal/supabase/functions/pl-fee-reflect/index.ts`の`confirm`アクションが、**`stores.seisan_target=true`の
店舗をallocationsに含む場合は明確にエラーで拒否**し「精算書側で入力してください」と案内する実装が
**既に入っている**（[pl-fee-reflect/index.ts:155-166](../supabase/functions/pl-fee-reflect/index.ts)）。
つまり「精算対象店舗の経費はns-portalから直接PLへ反映できない」というユーザーの最重要要件は、
**既存コードで既に強制されている**。今回追加する「業務委託精算書へ登録」ボタンの動線は、この既存ガードと
矛盾しないよう、担当Cが同じ判定（`stores.seisan_target`）を使って「PLへ反映」パネルと「精算書へ登録」パネルを
出し分ける形になる（設計書_広告費自動連携と精算書PL科目連携_2026-08-31.md §5と同じ考え方）。
