# 設計案: 給料確定ボタン・現金手渡しの連動と取消履歴（担当B・2026-11-09）

ユーザー決定: 質問一覧 U-23・U-24（「全部推奨で」）。本番SQLの適用は、この設計案の確認後・ユーザーの実行承認後。実額・氏名は含めない。

## 1. 二重になるか → **なる**（対応案あり）
原因（リポジトリの最新定義で確認）:
- `hq_create_payroll_tasks` は既存タスクの有無を `payroll_task_links` の主キー `(year_month, kind)` だけで見る。月次テンプレ由来の「【振込トーホー】給料」「【振込Live】給料」はこの表に載っていないため、11月分で確定ボタンを押すと**別の「給料振込」タスクが新規に作られて二重**になる。
- さらに主キーに法人が無いので、法人別（U-17①）に呼ぶと、2法人目が「既存あり」と誤判定されて作られない（または1つ目に紐づく）→ **主キーに法人を足す必要がある**（U-17①の関数を土台に「修正して進める」）。

対応案（U-17①の差し替え済み関数への追加修正に含められる）:
1. `payroll_task_links` に列 `corp text` を追加し、主キーを `(year_month, kind, corp)` に変更（既存4行は corp='トーホー' で埋める）。
2. 振込(transfer)の作成時、同じ月×法人の「既存のテンプレ由来の振込タスク」（title が `{月}月分 【振込{トーホー|Live|SK}】給料`・corp一致・template_id あり・未削除・未完了）があれば、**新しいタスクは作らず、その既存タスクに工程「振込対象者の確認（給料確定リスト）」を1つ追加してチェックリスト（対象者）を載せ、`payroll_task_links` に紐づける**。無ければ従来どおり新規作成。法人名→タイトル断片の対応は関数内のCASE（トーホー=振込トーホー／LiveGate=振込Live／SK=振込SK）。
3. 現金手渡しにテンプレは無いので従来どおり新規作成（紐づけは同じ表）。
4. 11月分（SK取り消し済み・トーホー1/4完了・Live3/4完了）は、確定ボタンを押すと既存2タスクに工程が1つ追加される（二重にならない）。

## 2. 確定の印と cash_handoff_targets の変更（U-23③）
- 印: 新テーブル **`payroll_finalized(year_month text, corp text, finalized_at, finalized_by, primary key (year_month, corp))`**。`hq_create_payroll_tasks` が権限確認の直後に `insert ... on conflict do nothing`（**タスクを1つも作らない場合でも**確定した事実を残すため、`payroll_task_links` ではなくこの専用テーブルにする）。
- `cash_handoff_targets(p_year_month)`: 行の支払法人（`corp_name`）が `payroll_finalized` に `(p_year_month, corp_name)` で載っているものだけ返す。兼務は法人ごとに別行のまま（合算しない）。
- 既存月の移行（同一トランザクションで先にやる）: すでにサイン記録（`sf_cash_handoff_signatures`）または `payroll_task_links` がある年月は、トーホーを確定済みとして `payroll_finalized` へ補充（既存の画面が空にならないため）。
- 新RPC `cash_handoff_finalized_corps(p_year_month) returns text[]`: 画面が「確定前」と「対象者なし」を区別するため。
- 変更するもの: 新テーブル1・`hq_create_payroll_tasks`（確定印の挿入・紐づけ・法人キー）・`cash_handoff_targets`（確定済みだけ）・新RPC1・nippo `cashHandoffView`（確定前の案内文「この月の○○分は、給与仕訳で給料確定のあとに表示されます」）。
- 確定の取り消し（印を消す）は今回は作らない（必要なら管理者がSQLで削除）。

## 3. 取消処理（U-24）
- 新テーブル **`sf_cash_handoff_cancellations(id, signature_id, user_id, year_month, contract_id, cancelled_by, cancelled_at, reason, payer_id, payer_checked_at, receiver_checked_at, completed_at, amount, payer_signature_path, receiver_signature_path, handoff_photo_path, archived_*_path)`**: 取り消し直前の状態のスナップショット（誰が・いつ・理由・写真のパス）を残す。
- 新RPC **`cash_handoff_cancel(p_user_id, p_year_month, p_contract_id, p_reason, p_archived jsonb)`**（書込権限は既存の `cash_handoff_can_write(store)` と同じ）: ①スナップショットを cancellations に保存 ②`sf_cash_handoff_signatures` の `payer_id・payer_checked_at・payer_signature_path・receiver_checked_at・receiver_signature_path・handoff_photo_path・completed_at・amount_confirmed` を空に戻す（引き出し確認(withdrawn_*)は別操作のまま触らない）→再サインできる。
- 画像: **Storageから消さない**。nippoが取り消しの前に `storage.copy` で履歴用の別名へコピー（元のオブジェクトも残す）。命名案: `{user_id}/archive/{year_month}_{contract_id}_cancelled_{YYYYMMDDHHmmss}_{payer|receiver|handoff}.{ext}`。コピー先パスは RPC の p_archived で cancellations に保存。再サインの新しい画像は従来どおり `{user_id}/{year_month}_{payer|receiver}_{timestamp}.png`（上書きされない）。
- nippo: 詳細画面の「完了を取り消す」を「↩️ 受け渡しを取り消す（サイン・完了をやり直す）」に置き換え（理由の入力つき）。画面下に「取消履歴」（誰が・いつ・理由・写真を見る）を表示。
- 給与仕訳の「振込完了」印(`payroll_journal_records.paid_at`): 現状の「完了を取り消す」は触らない。**要確認**: 取消で、その法人(tenant)の paid_at も戻すか（戻す案を推奨。戻さないと完了していないのに振込完了と表示される）。

## 4. 適用順序と戻し方（旧定義へ戻さず、修正して進める）
1. 追加のみ（安全）: `payroll_finalized`・`sf_cash_handoff_cancellations`・`payroll_task_links.corp`＋主キー変更・既存月の確定補充（同一SQL内で、③より先）。
2. 関数: `hq_create_payroll_tasks`（確定印・紐づけ・法人キー。U-17①適用済みの定義を土台に create or replace）→ `cash_handoff_targets`（確定済みだけ）→ `cash_handoff_finalized_corps`・`cash_handoff_cancel`。
3. nippo の公開（確定前の案内・取消UI）。1〜2の適用後。nippoは新RPCが無い間は従来どおり動くように作る（今回の法人別と同じ互換方式）。
4. 戻し方: 関数を旧定義へ戻さず前に進めて直す。画面が空になった場合は `payroll_finalized` に該当の年月×法人を入れれば表示が戻る（応急処置）。取消機能は追加のみなので、問題があれば nippo 側のボタンを外すだけで影響は止まる。

## 5. 確認したいこと（司令塔→ユーザー）
- 取消のとき、給与仕訳の「振込完了」印(paid_at)も戻すか（推奨=戻す）。
- 11月分の既存テンプレ2本には、確定ボタンで「振込対象者の確認」工程を1つ足す形でよいか（推奨）。
