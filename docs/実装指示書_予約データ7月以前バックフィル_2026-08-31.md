## 結論：もう実装は済んでいる。あとは実行するだけ

- **食べログノート**（`tasks/tabelog-note-reservation.js`）: 分析タブのCSV出力リンクが`yearMonth`クエリパラメータで任意の月を直接指定できると判明し、実装済み（実機で2ヶ月先まで動作確認済み）。対象9店舗（鳥一代 恵比寿を含む）はこの経路。
- **ダイニー予約台帳**（`tasks/dinii-reservation.js`）: 日付ピッカーを直接クリックする方式で実装済み。対象は`うお蔵 新横浜`（＝`黒霧屋 新横浜`）のみ。
- **重要な追加発見**: 実装時のテストで`TARGET_MONTH=2026-07`をダイニー側で試したところ**1,391件の実データが取得できた**。2026-08-28の事前調査では「うお蔵 新横浜の7月データは0件＝存在しない」と結論していたが、これは件数表示の読み取りタイミングに不備があり「読込中の一時的な0表示」を「本当に0件」と誤認していたバグが原因だったと判明（同日中に修正済み）。**つまり過去データは実際には存在していた可能性が高い**。
- ただし2026-08-31時点で、BigQuery`stg_reservation`を確認したところ**まだ7月分は反映されていない**（下記フェーズB未実行のため）。食べログノート側（鳥一代 恵比寿含む9店舗）は7月分のバックフィル実行自体もまだ行われていない。

## 残っている作業（Mac miniで実行するだけ）

### フェーズA: バックフィル実行

```bash
cd ~/ns-daily-import
# 食べログノート経由の9店舗（鳥一代 恵比寿を含む）
TARGET_MONTH=2026-07 node run.js tabelog-note-reservation
# 必要なら6月・5月…とさらに遡る（食べログノート側に実データが残っている範囲まで）
TARGET_MONTH=2026-06 node run.js tabelog-note-reservation

# ダイニー予約台帳（うお蔵 新横浜/黒霧屋 新横浜）。7月分は上記のテストで既にSupabaseへ
# 投入済みの可能性が高いが、念のため確定させたい場合は再実行しても洗い替えなので安全
TARGET_MONTH=2026-07 node run.js dinii-reservation
```

`washAndReplace`は店舗×月単位の洗い替えのため、何度実行しても重複しない（冪等）。

### フェーズB: BigQueryへミラー同期

```bash
node run.js bq-reservation-sync
```

`bqSyncReservation`（GAS側）はSupabase `rsv_reservations`の**全件を毎回フルミラー**する実装（日付での絞り込み無し）のため、フェーズAで投入した過去分もこのタスク1本で自動的にBigQueryへ反映される。コード変更は不要。

### フェーズC: 確認

- tori-dashboard本番（`https://mirai-oss.github.io/tori-dashboard/`）の「予約」タブ→予約分析で、7月・対象店舗を選びデータが表示されることを確認
- または担当A側の読み取り専用診断action `rsvDateRangeDiag`（`tori-dashboard`リポジトリ・`.github/workflows/rsv-date-range-diag.yml`、`gh workflow run rsv-date-range-diag.yml`で起動）を実行し、対象店舗の`minDate`が7月以前まで遡っていることを確認
