## 2. 設計（提案）
### 2.1 画像レイアウト（確定デザインどおり・`daily-report-card.mjs` を改修）
- ヘッダー: 店舗名／日報 Daily Report／対象日／チップ「祝日」「祝前日」／「祝日まであと N日」（祝日表から算出・直近14日以内のみ表示）
- 上段左: 本日の売上（最大）・予算比・前年比。上段右: 本日のイベント（最大2件＋「ほかN件」、無ければ「本日のイベントなし」）
- 中段 本日のKPI: 客数・客単価・L率・F率・FL比率（FL=日次L+日次F。数値のみ、達成✓は既存の目標比で維持）
- 月間累計（11/1〜当日・**暫定/確定**）: 累計売上・予算進捗・L率・F率・FL比率。**L/F/FL に4段階評価バッジ**（優秀=緑／普通=淡緑／要改善=橙／危険水準=赤・名称必須）。FL を強調（枠・トロフィー）。基準未設定は「基準未設定」
- 下段左 口コミ・評価: 口コミ増減（月間）・低評価（§3 Q4）・ダイニー点数（/75）。下段右 売上内訳: ランチ／ディナー／（取扱店のみ）デリバリー。金額＋予算比（予算がある時のみ）。デリバリーは 取扱あり＆当日0行＝「未取得」、0円の行あり＝「¥0」
- 最下段 要確認: 重要度順・最大2件。危険水準があれば最優先。「要確認｜月間人件費率が目標20.0%を0.8pt超過」の形
- 評価判定は丸める前の値で行う（VM側で判定して返す。画像側は表示だけ）

### 2.2 データ（VM v6）
- `daily_report_card_vm` に追加: `fl_ratio_today`、`mtd_fl_ratio`、`is_holiday_eve`、`days_to_holiday`、`delivery`（{enabled, sales, orders, status:'ok'|'zero'|'missing', budget_ratio}）、`ratings`（{labor:{grade,thresholds}, food:{…}, fl:{…}}）、`mtd_status`（'暫定'|'確定'）
- 評価は新関数 `fl_rating_grade(value, excellent_max, normal_max, warn_max)` で統一（境界は ≤）

### 2.3 評価基準テーブル（Supabase・新規）
- `fl_rating_thresholds(store_id uuid, year_month text, metric text check in ('labor','food','fl'), excellent_max numeric, normal_max numeric, warn_max numeric, updated_by uuid, updated_at, primary key(store_id, year_month, metric))`（**目標値とは別データ**。制約: excellent_max ≤ normal_max ≤ warn_max）
- `fl_rating_threshold_history(id, store_id, year_month, metric, before jsonb, after jsonb, changed_by, changed_at)`（トリガーで自動記録）
- `daily_report_card_snapshots(store_id, date, vm jsonb, generated_at)`: 配信時の VM（評価基準・評価結果込み）を保存 → 過去日報は当時の基準で再現。配信済み画像は上書きしない（`upload` を「同日2回目は別名」に変更）
- RLS: 3表とも PUBLIC/anon なし。閲覧・更新は `users.is_master` のみ（RPC も SECURITY DEFINER で is_master を判定、authenticated にだけ grant）。日報VM（service_role）からの参照は可
- RPC: `fl_thresholds_list(ym)`／`fl_thresholds_upsert(rows jsonb)`（重複は主キーで防止）／`fl_thresholds_copy(from_ym, to_ym, store_ids[], dry_run)`（前月コピー・複数店舗一括・dry_run で確認用の差分を返す）／`fl_thresholds_missing(ym)`／`fl_threshold_history(store_id, ym)`／`me_is_master()`

### 2.4 管理画面（経営D・目標管理タブ内）
- 「✎ 目標を入力」の隣に「FL評価設定」ボタン（**`me_is_master()` が true の時だけ描画**）。押すと目標管理タブ内のパネル（サブタブ）に切替。新しいサイドバーメニュー・独立画面は作らない

## 4. 確定事項（2026-11-10 ユーザー回答・修正版実装指示書）
### 4.1 売上KPIとFL計算の分離（最重要）
- **売上KPI**（本日の売上・月間累計売上・売上予算達成率・前年比・ランチ/ディナー予算達成率）＝**店内売上のみ**（従来どおり。予算・前年比の比較対象も変えない）
- **FL計算用売上 ＝ 店内売上 ＋ デリバリー売上**。L率＝人件費÷FL計算用売上、F率＝食材原価÷FL計算用売上、FL比率＝L率＋F率。日次・月間累計の両方
- デリバリー売上は原則「プラットフォーム手数料控除前の店舗に帰属する売上」。手数料を原価に混ぜない・入金額を売上にしない。**確定前に §5 の確認（売上定義・税区分・人件費/原価の計上範囲・重複なし・返金/値引き）を報告する**
- デリバリー取扱店舗の画像には「FL計算用売上（店内＋デリバリー）」を小さく補足表示
### 4.2 経営ダッシュボードとの整合
- F/L/FL の計算定義を**共通化**し、経営ダッシュボード（日次・月次）と日報で同じ値を表示する。実装は「共通の SQL 関数／ビュー 1 本」を正本にし、日報VM・`kd_store_monthly_summary`・ダッシュボード表示がそれを参照する形（担当A が影響範囲を事前報告）
- 既存の PL・融資（銀行返済）・会計目的の集計は変更しない。変更が必要なら事前報告
### 4.3 その他の確定
- 4段階評価は月間累計のみ（日次は数値のみ）。今回は「暫定」固定。基準未設定は「基準未設定」
- 低評価＝**ダイニー点数（100点満点）で 75点以下**の回答件数（75点ちょうどを含む。当社独自の管理基準で「5段階の2以下」とは別物。2026-11-10 ユーザー確定・当初の「2以下／40点以下」は撤回）。しきい値は定数1か所で管理し、VM・集計API・画面で共通。表示名「ダイニー低評価」（Google 口コミの低評価とは区別）
- 管理画面: 目標管理タブ「目標を入力」の隣に「FL評価設定」。9境界値・前月コピー・一括コピー・未設定一覧・変更履歴・保存前プレビュー。初期提案: F/L 目標を普通上限、優秀=−2pt、要改善=+3pt、FL は F+L 目標の合計を参考。提案値は保存前に編集可・自動確定しない
- 権限: ポータル統合アカウントのマスターのみ（ボタン非表示＋URL/API 拒否＋RLS）
- Slack: 店舗別チャンネルへ日報カード、#経営-レポートは全店比較サマリ・週報・月報。画像基本・失敗時のみ文章。Lark/Chatwork の**日報だけ**を、店舗別配信 3 日連続成功後にユーザー承認を得て停止（週報・月報・他は継続）
- 計算検証例（テストに含める）: 店内 700万・デリバリー 100万・人件費 160万・原価 200万 → 売上KPI 700万・FL計算用 800万・L 20.0%・F 25.0%・FL 45.0%
- 次の段階（今回は対象外）: デリバリー利益率（売上−食材原価−容器代−手数料）の分析
