# 計画書: 経営ダッシュボードの高速化と脱GAS移行（サクサク動く・数字が狂わない土台への作り直し）

作成: 2026-09-02（司令塔） ／ 状態: **v1.0確定（2026-09-02 ユーザーが改善Q1〜Q4回答・§8参照）→ Phase 0発進（`実装指示書_脱GAS移行_Phase0-1_2026-09-02.md`）**
発端: ユーザー「読み込みが遅い・定期的なエラーでストレス。他のレジシステムのようにサクサク動き、数字のエラーが起きない設計に根本改善したい」

**前提**: これは新しい方針ではなく、**確定済みの設計判断（要件定義書§16「正本=Supabase＋BigQuery・シートは入力UIと出力先に降格」）の実行計画**。請求書・会計・予約（rsv_reservations）など新しい機能は最初からSupabase側で作られており速い。遅いのは`tori-dashboard`（経営D）だけがGoogle Sheets＋GASの古い作りで残っているため。

## 1. なぜ遅い・なぜ数字が狂うのか（現状の構造）

```
今:  ブラウザ(app.js) → GAS WebApp → Googleスプレッドシート/BigQuery
                         ↑ここが遅い・不安定
```

**遅さの原因（構造的）**: ①GASは呼び出しごとの起動が遅い（コールドスタート数秒）②スプレッドシートの読み書きが遅い ③GAS特有の実行時間・同時実行の上限で「定期的なエラー」が出る ④画面がタブごとに何度もGASを呼ぶ

**数字が狂う原因（実例ベース）**: ⑤正本がシートに分散し、表記ゆれ・空行・列ズレがそのまま数字に化ける（じんべぇ問題・入金DB空行事故）⑥**同じ数字を画面ごとに別ロジックで計算している**（明細分析vs.ダッシュボードの客数不一致は、データ源からして別だった）⑦「全部揃わないと反映しない」型のガードが月中は静かに推定値を出し続ける（bqDetailのmaxDateガード）

## 2. 目指す姿（ゴール）

```
これから:  ブラウザ(app.js) → Supabase（PostgREST/Edge Function・0.1〜0.3秒）
                              ↑ 日次/リアルタイムに集計済みのデータを読むだけ
           入力もWeb管理画面 → Supabase正本 → シートへは自動書き出し（見る用に残す）
           GAS → 段階的に引退（最後はシート書き出し係だけ残すか、ゼロに）
```

- **速度**: 初回表示2〜3秒以内・タブ切替は体感ゼロ（先読み＋キャッシュ）・エラー時は自動リトライ＋分かるメッセージ
- **正確さの設計原則（全Phase共通・新規実装にも適用）**:
  1. **1つの数字に正本は1つ**（同じKPIを2箇所で別計算しない。共通の集計ビュー/関数から全画面が読む）
  2. 店舗名・媒体名は**必ずマスタ（store_aliases/tpl_media_alias）経由**（直書き禁止）
  3. **部分反映＋出典表示**（「実績◯日分＋推定◯日分」のように、どこまでが確定値か画面に出す。all-or-nothing禁止）
  4. **毎日の自動突合**（bq-sales-reconcile・見張り番を全主要テーブルへ拡張。新旧の数字がズレたらLarkに出る＝人が気づく前に機械が気づく）

## 3. 段階移行の計画（Strangler方式＝動いているものを止めずに1本ずつ差し替える）

| Phase | 内容 | 効果 | 目安 |
|---|---|---|---|
| **0. 計測と安定化** | GAS呼び出しの遅延・エラーを自動記録（どの画面・どのactionが遅い/落ちるかのランキング）。直近の不具合3件（目標入力消え・権限タブ・明細分析データ源統一）のホットフィックス | 敵の正体を数字で掴む・目先のストレス軽減 | 2〜3日 |
| **1. 即効チューニング（GASのまま速くする）** | ①タブ切替時の再取得を止めキャッシュ優先＋裏で更新（stale-while-revalidate）②複数GAS呼び出しの1回化（バッチaction）③失敗時の自動リトライ＋読み込み中表示の統一④初回に全タブ分を先読み | **体感は最も大きい**（何もデータを動かさないので安全） | 3〜5日 |
| **2. 読み取りの脱GAS** | よく見る画面から順に、データ源をGAS経由→**Supabaseの集計済みテーブル直読み**へ差し替え。日次ミラー（stg_*・fact_daily_store）は既にあるので、①BQ→Supabaseへ「画面用の集計結果」を毎朝＋日中数回書き出す②画面はSupabaseから0.1秒で読む。差し替えのたびに**新旧の数字を自動突合してから切替**（BQ切替=A-3でやった実績ある手順） | GASコールドスタート・上限エラーが読み取りから消える | 画面ごとに1〜2日×主要5画面（2週間程度） |
| **3. 入力の脱シート** | 手入力（PL販管費・目標・単価設定・広告費入力など）をWeb管理画面→Supabase正本に移行。**シートへは自動で書き出し続ける**（Excel的に見る用途は残す＝運用の見た目は変えずに正本だけ引っ越す） | 表記ゆれ・空行・列ズレ事故が構造的に消える | 入力面ごとに2〜3日×数面（2〜3週間） |
| **4. GAS引退・仕上げ** | 残ったGAS（シート書き出し係・精算/PL管理システム連携）を棚卸しし、Edge Function/GitHub Actionsへ移すか「書き出し専用」として最小化。ロールバック手順書更新 | 保守対象が1系統に | 1週間 |

**やらないこと**: 一括置き換え（事故リスク大）／フロント（app.js）のフレームワーク刷新（速度の主因はデータ層なので今回はやらない。将来の別テーマ）

## 4. 体制（縄張り）

- **新レーンP（プラットフォーム移行専任）を新設**: Supabase側の画面用集計テーブル（接頭辞`kd_`）・Edge Function（`keiei-api-*`）・突合監視の拡張を所有。**app.js/GASは一切触らない**
- **担当A**: app.js側の接続切り替え（Pが用意したAPIへの差し替え・キャッシュ/先読み実装）とGAS縮小。Phase 0のホットフィックス3件も担当Aの現行キューに入っている
- **担当D**: 日次ジョブ・突合監視の拡張（見張り番の対象追加）
- Sync: P が画面用APIを1本用意→WORKLOGで宣言→Aが差し替え→**新旧突合OKを確認してから旧経路を止める**（画面ごとに繰り返す）

## 5. 「定期的なエラー」への即応（Phase 0の中身）

- GAS呼び出し全部に「所要時間・成否」の記録を仕込み、コックピット/Larkに日次ランキングを出す（どのactionが犯人か特定）
- エラー時のUX統一: 白画面や無言の0表示を禁止し、「⚠️読み込みに失敗しました（自動で再試行中）」＋手動再読み込みボタン
- すでに特定済みの3件（目標入力が消える・チーム長の予約タブ・明細分析のデータ源不一致）は担当Aが最優先で修正

## 6. リスクと安全策

- 各Phaseで**新旧並行→自動突合→ユーザーOK→切替**（A-3のBQ既定化と同じ実績ある手順）
- 切替ごとにロールバック手順を`手順書_ロールバック`へ追記（1操作で旧経路へ戻せる状態を維持）
- 移行中はtori-dashboard系の**新機能追加をスローダウン**するのが安全（§7のQ3）

## 7. ユーザーへの質問（回答→Phase 0開始）

- **改善Q1**: 一番ストレスな画面トップ3を教えてください（例: ダッシュボード初回表示／PL／明細分析／予約タブ／広告管理…）。「定期的なエラー」は、どの画面でどんな表示が出ますか？（スクショ1枚あると特定が速いです）
- **改善Q2**: 体感の合格ラインは「初回2〜3秒・タブ切替は瞬時」でよいですか？
- **改善Q3**: 移行期間中（3〜6週間目安）、経営ダッシュボード系の**新機能追加をスローダウン**してよいですか？（バグ修正はやります。並行で新機能を積むと事故リスクが上がるため）
- **改善Q4**: Phase 3で、PL販管費・目標・単価設定などの**手入力の場所がスプレッドシートからWeb管理画面に変わる**ことはOKですか？（シートには自動で書き出し続けるので「見る」用途はそのまま残ります）

## 8. 確定（2026-09-02 ユーザー回答）

| Q | 回答 |
|---|---|
| Q1 ストレス画面 | **①ダッシュボード→PL等のタブ移動が毎回更新で長すぎる ②精算書の切り替わり ③全体が重く止まってしまう**。あわせてスクリーンショットで**予約管理の「取得エラー（Failed to fetch）」**の実例を受領（Phase 0の最初の調査対象） |
| Q2 合格ライン | **2〜3秒でOK（現状は5〜10秒）**。タブ切替は瞬時 |
| Q3 スローダウン | **OK**（スピード改善を優先。バグ修正は継続） |
| Q4 入力のWeb移行 | **OK** |

**Q1から確定する重点順**: ①タブ移動の高速化（Phase 1のキャッシュ・先読みで最大効果の見込み）②**精算ダッシュボードも高速化の対象に含める**（別GASプロジェクトのため精算D用の対策を明記）③フリーズ級の重さ（Phase 0の計測でGAS律速かフロント律速かを特定）。

**スクリーンショットからの追加発見（Phase 0で調査）**: 予約管理の「取得エラー Failed to fetch」に加え、**2026-09-02の予約リストが手動1件のみ**（前年同曜日657名）＝**9月分の自動取込が動いていない疑い**（月替わり後の初取込。I-1の対象月ロジックか食べログ側の「当月」ボタンの月替わり挙動）→担当Dへ緊急確認を指示。

## 9. 外部AIレビューの反映（2026-09-02受領。本計画v1.1として以下を追加・全レーン必須）

**レビュー結論**: 遅さの主因は「画面が必要以上に大きいデータを読み、アプリ側で集計し、GAS/シート/BQ/Supabaseが混在していること」。現行計画（計測→キャッシュ→Supabase直読み）は方向性良し、と裏付け。そのうえで以下を追加する。

### 9.1 原則の強化（「数字が狂わない4原則」→**6原則**へ）
- **原則5「店舗はIDで持つ」**: 全テーブルに`store_id`を持たせ、**店舗名は表示専用**にする（名前でのJOIN・絞り込みを段階的に廃止。ここが数字ズレ対策の本丸）。**未知の店舗名は「書き込まない」から一歩進めて「隔離テーブル（例: `kd_quarantine_rows`）に入れて警告」へ**（店舗名ゲートウェイ原則の強化。データを失わず、混ぜもしない）
- **原則6「画面は集計済みだけ読む」**: 初期表示で明細（行データ）を返さない。画面ごとに「KPI・月次PL・店舗別サマリ」など**集計済みの軽いデータだけ返す専用API**を用意し、明細はドリルダウン時にだけ取得

### 9.2 Phaseへの反映
- **Phase 2に追加**: 画面別の**初期表示サマリAPI**（`keiei-api-dashboard-summary`等・集計済みのみ返す）。予約API（P-2a）は**用途別に分割**（予約一覧＝日別・期間必須／キャンセル集計／月次サマリ。「3年前〜1年後を全件返す」設計は禁止）
- **Phase 2.5（新設）: store_id化**: PL・入金・媒体まわりの絞り込み/JOINを`store_name`文字列→`store_id`へ移行（`store_aliases`は入口の変換にだけ使い、保存後はID）。移行は「列追加→二重書き→読み替え→名前列を表示専用化」の安全手順で
- **Phase 3に追加**: 入力データに`sync_status`を持たせ、**「保存済み／BQ同期待ち／PL反映済み／精算反映済み／失敗」を画面に表示**（"入力したのに反映されない"ストレスの構造的解消）
- **Phase 4に追加**: 巨大ファイル対策は全面刷新ではなく、**「API層」「店舗名正規化」「PL集計」「予約集計」から小さくモジュール分割**（app.js 8,500行・Code.gs 5,400行のAI並行開発リスク低減）

### 9.3 不動産（SK）の方針確定（レビュー採用）
**システムは分けない**。同じ統合ポータル・同じ認証・同じ法人/店舗/従業員マスタの上に**不動産専用モジュール**として追加する。条件（SK設計書§2.6に転記）: ①不動産画面を開いた時だけ不動産データを読む（飲食ダッシュボードの初期表示では読まない・重いJSに混ぜない）②マスタはID共通 ③テーブルは`re_`接頭辞（`re_deals`/`re_invoices`/`re_payments`/`re_remittance_tasks`/`re_incentives`）④本部タスクとは`task_type=入金/送金/請求書`で連携。**実装は速度改善後・設計のみ先行**（ユーザー合意済みのスローダウンと整合）

### 9.4 実行順（レビュー推奨をそのまま採用）
①新機能一時停止（不動産は設計のみ）→②遅いAPIトップ10を2〜3日計測（P-0）→③初期表示サマリAPI（目標: 初回2〜3秒）→④PL・入金・媒体のstore_id化→⑤sync_status見える化→⑥不動産を`re_`で追加
