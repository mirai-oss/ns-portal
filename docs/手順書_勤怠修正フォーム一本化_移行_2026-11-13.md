## 4. 一緒に直る不具合（修正申請の承認依頼）

- 原因: `slack-interact` の 1 行で、`dedupe_key` の後ろに `//` で始まるコメントがあり、同じ行の続き（`ref`・`username`・`icon_emoji`）がコメント扱いになっていた。
- 影響: Slack の入力画面から出した**修正申請の承認依頼**（マスターの DM）だけ。①通知の台帳（`notification_deliveries`）の「どの勤怠確認の通知か」（`ref_table`・`ref_id`）が空 ②送り主の表示名とアイコンが Bot の既定のもの。承認／却下・反映・リマインドの動きには影響なし（ボタンと勤怠確認の行に別の控えがあるため）。打刻削除・勤怠確認・フォーム申請の通知は、もとから正しい。
- 直し方: 承認依頼の中身を共通部品（`_shared/attendance-fix-notify.ts`）で組み立て、Slack の入力画面とフォームの両方が同じものを使う。
- すでに送った分の台帳は空のまま（さかのぼって埋めるなら別途 SQL が要る。動作には不要）。

## 5. 休憩の申告（フォームの「☕ 休憩の申告」）

- フォームの受付は入っているが、記録する側（`sf_break_exception_submit`。別の担当の `supabase/2026-11-13_break_autofill.sql`）が本番に入るまでは、押しても「この機能はまだ使えません」と出るだけ（ほかの申請には影響なし）。
- その SQL を本番に入れた時点から、そのまま使えるようになる（フォーム・関数の出し直しは不要）。
- 気になる場合は、その SQL を入れてから手順 3 を行う。

## 6. 戻し方

基本は **出したのと逆の順**。受け口（手順 2）とフォーム（手順 3）は「足しただけ」なので、戻すのは通常 手順 5 → 4 だけで足ります。

| 戻すもの | やること | 戻したあとの動き |
|---|---|---|
| 手順 5（毎朝の通知） | 変更前の `smaregi-attendance-anomaly-check/index.ts` に戻して、同じコマンドでデプロイ | 次の朝から古い形のボタン。すでに出た新しい形のボタンは、押せば引き続きフォームが開く |
| 手順 4（Slack の受付） | 変更前の `slack-interact/index.ts` に戻してデプロイ | 「× 修正する」で今までの入力画面が開く。**注意**: 新しい形のボタン（手順 5 以降に出たもの）は、フォームと入力画面の両方が開く。先に手順 5 を戻し、新しい形のボタンが残っている間は手順 4 を戻さないのが安全 |
| 手順 3（フォーム） | `kintai.html` を前のコミットに戻して push | 今までのフォーム。アラートからのリンクは、自動入力なしの通常のフォームとして開く |
| 手順 2（受け口） | 変更前の `attendance-request/index.ts` に戻してデプロイ | 新しいフォームでアラートから開くと「まだ使えません」→ 通常のフォーム |

- 「変更前に戻す」: コミット前なら `git show HEAD:<ファイル>` の内容、コミット後なら 1 つ前のコミットの内容を使う。変更前の写しは `<共有メモの kintai-tests/>before/` にもある。
- 申請中のデータ（承認待ちの修正）は、どの戻し方でもそのまま残り、承認できます（DB は変えていないため）。

## 7. 出したあとに実機で確かめること（まだ確かめていない点）

1. **スマホの Slack でボタンを押したとき、どのブラウザで開くか**。Slack アプリの中のブラウザで開くと、ポータルにログインしていない状態になることがあります（その場合「ログインが必要です」と出る → ポータルにログイン → ブラウザの「戻る」か、もう一度ボタン）。初回だけ手間が増える人がいないか確認。
2. 新しい形のボタン（url 付き）を押したとき、Slack に警告マーク（⚠）が出ないこと（押下の通知に、関数がすぐ返事を返していれば出ません）。

4. フォームから出したアラートの修正が、マスターの DM に「勤怠確認」（⏰）の名前で届き、承認 → 管理システム → スマレジまで通ること（テスト用の勤怠で 1 件）。
