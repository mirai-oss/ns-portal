# デリバリー「0円」と「未取得」の区別 ルール案（担当A・2026-11-11・司令塔へ）

## 調べた事実（本番の読み取り）
- 取込の実行記録は **`import_runs`**（ns-daily-import が記録）。ロケットナウの日次は `job='rocketnow-sales'`（source=playwright・毎朝 JST 6:27 ごろに前日分）。`status` = success／failed／partial／running。**対象日の構造化列は無い**（`target_ym` は空）。ただし `detail` に「sales-report(Multi)_YYYYMMDD_YYYYMMDD.xlsx: N件投入」と**ファイル名（＝対象日）が入る**。日次ファイルは全店舗×1日（Multi）なので、成功＝その日は全取扱店ぶん取れている。
- `kd_delivery_daily.sync_run_id` は `kd_sync_runs`（BQ→kd の反映ジョブ）の実行ID。**取込（ロケットナウ→BQ）の成否ではない**ので、取込成功の判定には使えない（反映の成否は別の確認になる）。
- 休業・臨時休業は **DBに表が無い**（経営ダッシュボード app.js に登録を直書きしている）。したがって「営業日か」は現状DBで判定できない。
- 取扱店は `delivery_store_map(channel, store_id, active, created_at)`。

## ルール案（店舗×日ごとの状態）
| 状態 | 条件 | 表示 |
|---|---|---|
| ok | その日の kd_delivery_daily に行があり net_sales>0 | 金額 |
| zero | **取込成功の記録がある日**（import_runs success で detail の日付＝その日）で、行なし or net_sales=0 | 「¥0」 |
| closed | 休業登録に当たる日（営業日ではない） | 判定の対象外（欠損にしない） |
| missing | 取扱店の営業日で、**取込成功の記録が無い**（failed／partial／未実行）、かつ行も無い | 「未取得」 |
- 判定の対象期間: 日次＝対象日1日／月間＝月初〜対象日。対象店舗は、取扱開始日（delivery_store_map.created_at）以降の日のみ。
- **月間**: 期間内に missing が **1日でも**あれば、F/L/FL は店内のみの「参考値」・4段階評価は「評価保留」（司令塔指示）。zero は欠損ではない（0円の日として合算）。
- 「最終行が3日以上前」の簡易ルール（v6に実装済み）は、**暫定**。上の import_runs 方式に置き換える。

## 実装に必要なこと（承認後）
1. **休業の表（新設）**: `store_closed_days(store_id, from_date, to_date, note)`。app.js の直書き登録の移行元（司令塔・担当Aで調整）。無い間は「休業なし」として判定（休業日が missing 扱いになる誤警告を避けるため、休業登録は表ができるまで画面登録と同じものを手で入れる）。
2. **取込成功日のビュー**: `delivery_ingest_days_v(biz_date, ok)` = import_runs（job='rocketnow-sales'・status='success'）の detail から正規表現で日付を取り出す。**detail の文言に依存するので、ns-daily-import（担当D）に「対象日を import_runs.items（例 {date_from,date_to,rows}）に構造化して記録」を依頼するのが本筋**（それまでは正規表現で暫定）。月次精算（rocketnow-settlement）で確定済みの月は、その月の行が確定行として揃うため ok 扱い。
3. VM v6 の `delivery.status` と `fl_reference_*`・評価 hold を上の判定に差し替え（SQL のみ・小さい差分）。

## 注意
- 日報の送信時刻より取込が遅いと、その日は「未取得」になる（取込は翌朝6時台）。日報の対象日＝前日分のため通常は取り込み済みだが、取込が遅延した日は未取得＝参考値になるのが正しい動き。
- 取込が partial の日は、行があれば ok、無ければ missing 扱い。
