2-2. 守りの仕組み（数字を守る6点）

  1. 原本の事実（日付・摘要・入出金額）は、訂正の手続きを通しても変えられない。直すときは「管理上の訂正値（adj_*）」を入れる（集計は訂正値があれば訂正値、無ければ原本の値）。訂正を取り消せば原本の値に戻る。
  2. 確定済みの明細の管理項目・訂正値は直接変えられない。直すには bank_tx_correct（理由必須）を使う。
  3. 明細は削除できない（誤りは訂正で直す）。
  4. どんな変更も、修正前・修正後・修正者・日時が自動で履歴に残る（手続きを通らない経路でも漏れない）。
  5. 履歴は追記専用（更新・削除できない）。
  6. 取得履歴の「原本のSHA-256・置き場所」は、入ったら変えられない。原本が置き場に無い取り込みは確定できない（保存に失敗したら確定の前に止まる）。
  7. 同じ取引は同じ「重複判定キー」で1行にまとまる（データベースの制約で二重登録を防ぐ）。

2-3c. 原本の保存確認（段階2の必須条件・DBで強制）

取得履歴（bank_import_files）は、次の順にしか進めません。どれかが欠けると、DBが拒否します（段階2の取込関数にバグがあっても、飛ばせない）。

  1. 保存：原本を置き場（Storage）へ保存 → 台帳（bank_csv_originals）に行を作り、取得履歴を stored にして original_id を結ぶ。
  2. 読み戻し：置き場から実ファイルを読み戻して、SHA-256とバイト数を計算し、取得履歴の original_verified_sha256・original_verified_size・original_verified_at に記録する（段階2の取込関数が行う）。
  3. 解析済み（parsed）・確定（committed）に進む条件（DBのトリガーが毎回確かめる）：
    • 置き場（storage.objects）に、その原本の実ファイルが実在する（バケット・パスが一致）
    • 置き場のファイルサイズが、台帳のサイズと一致する
    • 読み戻して計算したハッシュ・サイズが記録されていて、台帳の値と一致する
    • （確定のみ）取込途中の明細が0件
  4. 最初から parsed・committed で作ることはできない。確認結果の記録は、あとから変えられない。取得履歴の更新はサービスロール（取込ジョブ）だけで、社長でも画面からは書き換えられない。
正直な限界：DBの中ではファイルの中身を読めないため、「読み戻してハッシュを計算する」処理そのものは段階2の取込関数が行います。DBが強制するのは「その結果が記録されていて、台帳・実ファイルと一致していること」です。記録の偽装は、サービスロールの鍵を持つ処理にしかできません。

3-2. 移行のルール

  1. シート1行＝明細1行。同日・同額の行も、統合も削除もしません（行の並び順を legacy_seq に残す）。
  2. 各行に、元の6列（店舗・日付・入金額・摘要・取引時刻・取込日時）を legacy_payload にそのまま保存する（いつでも元に戻せる）。
  3. 状態は全行 「移行済み・照合待ち」（match_status='legacy_pending'）。確定状態は open。
  4. 店舗は、いまGASが使っている表記ゆれの表（store_aliases）で店舗IDに解決する。解決できない行は店舗IDを空のまま移し、一覧にして報告する（いまのSupabase集計も、店舗名が合わない行は集計から外れているので、数字は変わらない）。
  5. 同じ移行を2回流しても二重にならない（legacy_batch + legacy_seq の一意制約）。
  6. 入金DBは2つのシート（売上DBとダッシュボード）にあるため、両方を取り出して突き合わせ、違いがあれば先に報告する（片方が自動連携の数式のときは、その旨も）。

3-4. 移行後の確認（一覧にして報告します）

  • 行数：シートの行数＝移した行数。
  • 店舗別×日付別の件数と金額：シート＝正本の集計（店舗IDが空の行は別枠で件数と金額を報告）。

  • 差が出た店舗・日付は、原因を付けて一覧にします。

4. 重複判定の設計（旧シートの行と、新しいCSVの行をどう結ぶか）

4-1. PayPay銀行

  • CSVの「取引順番号」を使う。口座＋日付＋取引順番号で一意（実CSV 10口座・943行で、重複0を確認）。
  • いまのGASは、取引時刻を「分」までに切り捨てて判定するため、同じ分・同額の別取引を同じものとみなす恐れがあります（実CSVに1組あり。実際に取りこぼしているかは移行時に確認）。新しい方式では起きません。
  • CSVの「残高」でも鎖を確かめ、つながらない行は保留にする（GMOと同じ検証）。

4-2. GMOあおぞら（並び順に頼らない）

サンプルのCSV（じんべぇ川崎の口座・2026-06-01〜11-26・398行）の実測：
  • 列は「日付・摘要・入金金額・出金金額・残高・メモ」の6列。取引時刻も取引番号もありません。新しい日付が上。文字コードはShift-JIS。
  • 残高の鎖：398行すべてつながった（切れ目0）。
  • 「日付＋摘要＋入金＋出金」だけだと、同じになる組が19組ある（＝並び順や金額だけでは、別取引と見分けられない）。
  • 「日付＋摘要＋入金＋出金＋残高」にすると、同じになる組は0。残高が各取引に固有の指紋になる。

判定の流れ（段階2で実装）

  1. CSV内で残高の鎖を検証する（隣の行どうしで「古い行の残高＋入金−出金＝新しい行の残高」）。1か所でも切れたら、そのファイルは取り込まず「保留」（原本と取得履歴だけ保存）。
  2. 重複判定キー＝日付｜摘要｜入金｜出金｜残高（口座ごと）。取得期間が重なる2つのCSVでも、同じ取引は同じキーになり、二重に入らない。
  3. すでに入っている行と重なる範囲では、残高が食い違っていないかも確かめる（食い違えば「期間が重なる部分で鎖が合わない」として、そのファイル全体を保留）。
  4. 同じキーがCSV内に2行出たら（取引の中身が完全に同じ）、確実に識別できないのでその行は保留（理由つき）。
  5. CSVの一番古い行は、前の残高が分からない。すでに入っている行の残高と照らせるときは照らし、照らせないときは「起点」として扱い、取得履歴に印を付ける。
  6. 保留の行は、集計には入れず（保留の件数は画面に出す）、本部が理由を見て解除・訂正できる。

4-3. 旧シートの行との結び付き（「移行済み・照合待ち」→「照合済み」）

  • 新しいCSVを取り込むとき、キー（店舗の口座＋日付＋金額＋時刻 or 残高）が合う旧行を探し、1対1で結ぶ。結べた行は「照合済み」になり、口座・残高・原本との結び付きが入る。金額・日付は変えない（食い違えば保留）。
  • 同じキーの旧行がN個・CSV行がN個なら、順に1対1。数が合わないときは、余った旧行は照合待ちのまま残す（削除しない）。
  • GMOは、旧シートの取引時刻の欄に「残高…」の形で残高が入っているはず（手動取込のルール）。移行時に確かめ、合えば残高で確実に結ぶ。
  • 実測：じんべぇ川崎の旧シートは、サンプルCSVと192行が、日付・金額とも1行ずつ一致（シートにだけある行0・CSVにだけある行0）。
  • 銀行が返す範囲より古い旧行（PayPayは約3か月、GMOはサンプルで約6か月より前）は、CSVが無いので、照合待ちのまま残るのが正常です。

5. 数字が変わる問題の直し方（段階2〜7）

原因（確定）：いまは同じ入金が3つの道で画面に届き、更新の時刻がそろっていません。
道更新のタイミング
シートを直接読む14:00の取込で即反映
BigQueryミラー朝08:34と11:01の同期だけ（14:00の取込はどちらにも間に合わない）
Supabaseの集計（kd_deposit_daily）BigQueryから作るので、さらに遅れる

実測（11/27 夕方時点）：11/26と11/27の2日だけ、シートがBigQuery・Supabaseより件数・金額とも多い（14:00の取込分が未反映）。他の1,042日は一致。BigQueryの取得失敗でシート直読みに切り替わると、数字が急に変わる。

直し方

  1. 取込（取得→保存→確定）が成功した同じトランザクションの中で、集計を作り直す。時間差の道を作らない。
  2. 集計の作り直し中は「集計中」と表示し、古い数字を最新として出さない。エラー時に0で上書きしない（失敗は取得履歴に残し、直前の確定値のまま「最終取得日時」を出す）。
  3. 二重実行は、実行ロックと一意制約で防ぐ。
  4. 画面は bank_deposit_daily() だけを読む（BigQueryもシートも読まない）。BigQuery失敗時のシート直読みフォールバックは、段階6の切り替えと同時に廃止（＝移行完了後は存在しなくなる）。
  5. 14日並行比較は、同じ取得完了時点（as_of）までのデータだけを、店舗別×日付別に件数・金額で照合する。毎日自動で一覧にして出し、14日連続で不一致0件が、切り替えの条件。
