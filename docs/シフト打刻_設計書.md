# シフト・打刻 設計書 v1.0（機能④⑤）

対象読者: この機能を実装する実行スレッド（またはレビューする人）。仕様の正は`要件定義書.md`§8・§9・§19（責任分界）。このドキュメントはその具体化。

## 1. スコープと責任分界（おさらい・§19）

| 領域 | 担当 |
|---|---|
| シフト提出・未提出管理・通知・シフト公開・必要人数シミュレーション・管理画面 | **自社システム（ハブ、現場アプリ=nippo）** |
| 正式な勤怠記録・打刻の正本・有給・給与計算に必要なデータ | **スマレジ・タイムカード** |
| 給与・会計・振込 | **マネーフォワード**（対象外） |

つまり、うちのシステムは「シフトの**予定**を作る・公開する・人数を見る」ところまでが本体。実際の出退勤打刻・給与計算はスマレジ側の正式機能にそのまま任せる。ただし、**シフトを作った時点でスマレジ・タイムカードにも予定として反映する**（ユーザー要望）ことで、二重入力を避け、スマレジ側の画面でも同じ予定が見える状態にする。

- 契約: スマレジ・タイムカート、契約ID `sez093z1`（本番のみ、サンドボックス環境は無し）
- 既存の`smaregi-sync` Edge Function（v2.6.14）が`SMAREGI_CONTRACT_ID`/`SMAREGI_CLIENT_ID`/`SMAREGI_CLIENT_SECRET`を使い、従業員同期（登録・退職・一覧取得）で本番稼働中

- 追加後、実際に本番環境で**シフト作成→削除の実機テストに成功**（テストデータは即削除・残留なしを確認）
- 認証: OAuth2クライアントクレデンシャル方式（`POST https://id.smaregi.jp/app/{contract}/token`、Basic認証＋`grant_type=client_credentials&scope=...`）
- 既存のマッピング列がそのまま使える: `employee_profiles.smaregi_staff_id`（12/12人が連携済み）・`stores.smaregi_store_id`
- **打刻**（`timecard.attendances:write`）のスコープはまだ未確認・未申請。⑤打刻の実装に着手する際に同様の手順（開発者コンソールでスコープ追加→実機テスト）が必要

### 使用エンドポイント（`https://api.smaregi.jp/{contract}/timecard`配下）
- `POST /shifts/{store_id}/{staff_id}` — シフト/実績登録（`division`="schedule"で予定、"result"で実績）
- `PUT /shifts/{shift_result_id}` — 更新
- `DELETE /shifts/{shift_result_id}` — 削除（**JSONボディに`{"division":"schedule"|"result"}`が必須**。忘れると400）
- （⑤で使用予定）`POST /shifts/attendance/{store_id}/{staff_id}`・`PUT /shifts/leaving/{shift_result_id}`・`PUT /shifts/break_start_time/{shift_result_id}`・`PUT /shifts/break_end_time/{shift_result_id}`

## 3. ヒアリング結果（2026-08-19・ユーザー回答）

### 3.1 入力単位
- 基本は**時間帯プリセットから選択**（店舗ごとに「ランチ」「ディナー」「終日」等の時間帯プリセットを用意）
- ただし**プリセットの時間帯自体をその場でカスタマイズできる**（例: 「ディナー」を選んだ後、開始時刻だけ30分ずらす、等）
- シフトを作成した時点でスマレジ・タイムカードにも反映されること（§1参照）

### 3.2 対象者
**全役職が提出対象**: AL（アルバイト）・SHAIN（社員）・TENCHO（店長）・TEAM以上（本部・部長級）

### 3.3 提出サイクル
**月2回・固定日**:

| 対象期間 | 提出期限 | 公開日 |
|---|---|---|
| 当月16日〜月末 | 当月5日 | 当月10日 |
| 翌月1日〜15日 | 当月20日 | 当月25日 |

つまり「公開日の5日前が締切」「公開日は毎月10日と25日」というルール。**祝日・土日の考慮は今回のヒアリングでは未確認**（10日/25日が休日に当たった場合の扱いは実装前にユーザーへ再確認する）。

## 4. データモデル（新規テーブル案・`sf_`接頭辞）

既存の`checklist_*`・`hq_*`と同じ考え方で、シフト専用テーブルを新設する（既存テーブルへのALTERはしない）。

```sql
-- 店舗ごとの時間帯プリセット（本部・店長が管理画面から編集）
create table sf_time_presets (
  id uuid primary key default gen_random_uuid(),
  store_id uuid not null references stores(id),
  label text not null,              -- 例: "ランチ" "ディナー" "終日"
  start_time time not null,
  end_time time not null,
  break_minutes int not null default 0,
  sort_order int not null default 100,
  is_active boolean not null default true,
  created_at timestamptz not null default now()
);

-- シフト本体（1人・1日・1エントリ）
create table sf_shifts (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references users(id),
  store_id uuid not null references stores(id),
  work_date date not null,
  start_time time not null,
  end_time time not null,
  break_minutes int not null default 0,
  preset_id uuid references sf_time_presets(id),  -- どのプリセットから作ったか（カスタマイズ後も記録）
  period_key text not null,          -- 提出サイクルのキー。例 '2026-09-A'(1-15日) '2026-09-B'(16-末日)
  status text not null default 'draft' check (status in ('draft','submitted','published','cancelled')),
  submitted_at timestamptz,
  published_at timestamptz,
  smaregi_shift_result_id text,      -- スマレジ側の shiftResultId（作成成功時に記録。連携失敗時はnull）
  smaregi_sync_status text default 'pending' check (smaregi_sync_status in ('pending','synced','error')),
  smaregi_error text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique(user_id, work_date)         -- 1人1日1シフト（休憩を挟む複数勤務は将来拡張）
);
create index sf_shifts_store_date_idx on sf_shifts(store_id, work_date);
create index sf_shifts_period_idx on sf_shifts(period_key, store_id);

-- 必要人数（店舗×曜日×時間帯、または店舗×日付の個別上書き）
create table sf_required_headcounts (
  id uuid primary key default gen_random_uuid(),
  store_id uuid not null references stores(id),
  preset_id uuid references sf_time_presets(id),
  weekday int,                       -- 0-6。null=個別日付指定と併用
  specific_date date,                -- 特定日の上書き（繁忙日等）。nullなら曜日ベース
  required_count int not null,
  created_at timestamptz not null default now()
);
```

**設計判断のメモ**:
- `period_key`は「2026-09-A」（当月1-15日）「2026-09-B」（16日-末日）のような文字列にして、締切・公開日の計算をアプリ側の関数1つに閉じ込める（DBに複雑な日付演算をさせない）
- スマレジ連携は**シフトごとに成功/失敗を記録**する設計にする（スマレジ側が落ちていても、シフト自体の提出・公開は止めない。連携失敗分は管理画面に「⚠️ スマレジ未反映 N件」のように出して後から再送できるようにする）
- 削除・変更時はスマレジ側も`PUT`/`DELETE`で追従させる（`smaregi_shift_result_id`があれば更新、無ければ新規作成）

## 5. 画面設計（現場アプリ=nippo）

### 5.1 シフト提出画面（全役職）
- カレンダー形式（対象の提出期間=`period_key`の日付範囲のみ表示）
- 日付タップ→時間帯プリセットのボタン一覧（店舗の`sf_time_presets`から）＋「休み」ボタン
- プリセットタップ後、時刻を微調整できる（±30分刻み等の簡易UI。自由入力ではなくスマレジのラウンド設定=15分単位に寄せる）
- 「この内容で提出する」→該当期間の全シフトを`status='submitted'`に一括変更
- 締切後は編集不可（表示のみ）。締切前なら再提出（上書き）可能
- 未提出者への通知は既存の`hq_notifications`基盤を使う（店長・本部向けに「未提出者リスト」表示、締切前日にリマインド）

### 5.2 シフト管理・公開画面（店長・本部）
- 店舗×期間を選んで、全員のシフトを一覧（縦=日付、横=人、というガントチャート風、または既存チェックシートのような表形式）
- **必要人数シミュレーションを同じ画面に同時表示**（別画面にしない、が確定要件）: 時間帯ごとに「必要人数 vs 現在の提出人数」を色分け表示（不足=赤、充足=緑）。**`sf_required_headcounts`が未設定の時間帯は「未設定」表示のみで判定はしない**（初期リリースでは必要人数データの入力は後回し。表の骨組みだけ実装し、後から店長が管理画面で入力できるようにする）
- 「公開する」ボタン→対象期間の全シフトを`status='published'`にし、この時点で**スマレジへのAPI同期をまとめて実行**（1件ずつ`smaregi_sync_status`を更新、失敗分だけエラー表示）
- 個別の手動追加・修正も可能（店長がバイトの代わりに入力するケース）
- **公開後の変更**: 店長・本部どちらも編集可能（確定）。変更時はスマレジ側も同時に`PUT`/新規`POST`で追従させる

### 5.3 マイページ・確認画面
- 自分の確定シフト一覧（`published`のみ）をカレンダーで見る（既存の「今日のタスク」的な導線に追加）

## 7. 提出サイクル・締切の自動計算

アプリ側（JS）またはSupabase関数で以下のロジックを1箇所に集約する:

```
今日が1〜9日  → 対象期間=当月16日〜末日（period_key=YYYY-MM-B）, 締切=当月5日(既に過ぎている場合は次回の当月20日締切分を案内)
今日が10〜24日 → 対象期間=翌月1〜15日（period_key=YYYY-MM+1-A）, 締切=当月20日
今日が25〜末日 → 対象期間=翌月16日〜末日（period_key=YYYY-MM+1-B）, 締切=翌月5日
```

**確定（2026-08-19ユーザー回答）**: 5日・10日・20日・25日が土日祝でも**日付は動かさない**（固定）。祝日カレンダーとの突き合わせは不要。

## 9. 確認事項（2026-08-19・全て解消済み）

1. **10日/25日が土日祝の場合**: 日付は動かさない（固定）
2. **時間帯プリセットの初期データ**: 各店の店長が管理画面から自分で入力する運用（Claudeによる一括投入はしない）
3. **必要人数の初期設定**: 初回リリースでは後回し。シミュレーションのUI（表の骨組み）だけ実装し、「未設定」表示にしておく。データ投入は別途
4. **公開後のシフト変更**: 店長（自店舗）・本部（全店舗）どちらも編集可能。変更時はスマレジ側も同時追従
