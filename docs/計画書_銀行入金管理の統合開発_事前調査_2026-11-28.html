2. GMO自動取得の実現方法と、規約・認証上の制約

調べたこと結果
公式API公開されている仕様書は個人・個人事業主口座編（2021年版・入出金明細照会あり）。法人口座は、会計ソフト（マネーフォワード・弥生）が「参照系API」で明細を取得している。自社の法人口座を自社のプログラムから直接使う申込方法は、公開資料から確認できない。「銀行APIパートナープログラム」は開発企業向け（開発実績2サービス以上など）で、当社の用途には当てはまりにくい
規約取引規定に、自動操作を明示で禁止・許可する条文は見つからない。ID・パスワードを第三者に知られない管理責任・誤入力が続くと利用停止の規定あり。法人向けのインターネットバンキング規定は未入手（銀行への確認が必要）
認証ログイン画面はID・パスワードの入力と、パスキー（WebAuthn）の部品。法人は電子証明書方式・口座ごとの認証の可能性。ログイン後の追加認証は、人が手でログインしないと分からない（私は認証情報を入力できない）
既存の別ルート当社が使っているマネーフォワードで、すでにGMO口座が銀行連携されていれば、その仕組みの明細を使うのが、規約上いちばん安全な選択肢（要確認：MFにGMO口座を連携済みか／MFから明細を取得できるか）
結論：ご指示の条件（規約に適合・認証制限の回避をしない・実データの検証）のすべては、今日の時点では満たせません。手動CSV取込（原本保存・読み戻し・重複判定・取得履歴）は、すでに完成・検証済みです（1口座のCSVで398行を取込・再取込で増えない）。自動ログインの本番稼働は保留とし、次の2つが揃ったら、実装・検証に進みます：①あなたがMac miniで手動ログインし、認証方式と8口座の切り替え操作を確認（観察ツール gmo-observe.js は用意済み）②GMOに「法人口座の明細を自社プログラムで定期取得してよいか／法人向けの明細取得手段はあるか」を確認、またはマネーフォワード経由の取得の可否を確認。

4. 店舗ID未設定の明細を保存するために必要な変更

すでにできること：店舗ID・法人ID未設定の口座・明細を、原本・取得履歴つきで保存できる（試験済み）。未確定の明細は店舗別入金実績（日次集計）に入らない（店舗がnullの行は集計から除外）。法人・店舗が決まらない行は、本部・社長・マスターだけが見られる。

5. 法人マスタ・運営会社の紐付け方法

  • 法人の対応表：public.corporations.legacy_info_id が info.corporations.id を指す（4法人すべて確認済み・正式名も一致）。名前の文字列一致には頼らず、このIDの対応を正とする。対応が欠けた法人が増えたときは、台帳側で「対応なし＝全法人管理者だけ」に倒す。
  • 区別する4つのID：corporation_id（入金が帰属する法人）＝明細・口座に取込時点の値を保存（店舗マスタの法人を変えても、過去の銀行入金の法人は変わらない。現状の作りで既に満たす）／store_id／bank_account_id／contractor_id（業務委託先・新設）。
  • 運営法人の履歴（新設 store_corporation_periods：店舗ID・法人ID・適用開始日・終了日）。現在の stores.corporation_id から初期データを作る。取込時は「入金日に有効な法人」を引いて明細に保存する（既存の明細は変えない）。M&Aで店舗の運営法人が変わったら、新しい期間を足す（過去の期間は残る）。
  • 口座の名義・法人：corporation_bank_accounts（現在0件・有効期間・名義カナ・確認者つき）を、台帳の口座の「名義確認の記録」として使う（台帳の口座に corporation_bank_account_id を足す）。法人ID未確定の口座は、名義を確認してから確定（社長判断どおり）。

6. 業務委託先の精算書画面と入金管理を統合する方法

6-1. 既存の精算書システムの認証・権限

  • 画面＝GitHub Pages（seisan-dashboard）／API＝GAS／データ＝Googleスプレッドシート。権限はスプレッドシートの「権限_精算ダッシュボード」で管理（マスター＞本部＞委託先）。委託先は、Supabaseのユーザーではない（統合ログイン＝Supabase認証の対象外で、サーバー側で拒否されている）。委託先は、自分の担当店舗だけ閲覧（売上のN-style収益は非表示・編集不可）。
  • 委託先と店舗・契約期間の対応は、いまはSupabaseに無い（スプレッドシートの権限シートのみ）。

6-2. 統合の方法（新しいログインは作らない）

  1. 認証は精算書のまま。精算書のGASが、ログイン済みの委託先からサーバー側で「担当店舗」を決める（画面から送られたURL・パラメータの店舗IDは信用しない）。
  2. Supabaseに contractors（委託先）と contractor_store_contracts（委託先・店舗・契約開始日・終了日・閲覧可能期間・過去分の閲覧の明示設定）を新設。精算書GASは、委託先の識別（contractor_id）だけをSupabaseの専用の読み取り関数に渡す。
  3. 専用関数 vendor_deposit_view(contractor_id, 月)（サービスロール専用・精算書GASからだけ呼べる）が、契約で許可された店舗・期間だけを、公開してよい項目だけで返す：店舗名・日付・入金額・件数・入金日・入金差額・未入金。返さない項目：口座番号・残高・原本CSV・他法人／他店舗・内部承認・差異・訂正履歴。契約終了後は自動で空（過去分は明示設定のあるときだけ）。
  4. 画面：精算書の画面に「入金管理」タブを足す（閲覧専用）。売上・入金予定は、元の数字・算出方法が検証できるまで出さない（現状は kd_deposit_daily_v に現金売上があるが、レジ照合の確認状況との対応を確かめてから）。
  5. 検証：URL・APIパラメータの店舗ID・委託先IDを書き換えても、他店舗が取れないこと（関数が契約から店舗を決めるため、引数に店舗IDを受け取らない設計）／契約終了日の前後／過去分の明示設定／他法人／N-style収益の非表示。
