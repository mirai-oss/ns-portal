## 3. 既存コードで再利用できる部分

1. **CSV生成の共通パターン**（BOM付きUTF-8 Blob・`<a download>`）は4箇所で完全に同一実装。Export ServiceのCSV出力もこの慣例（BOM必須＝Excel誤文字化け防止）を踏襲すべき。
2. **exceljsの実績**（`excel-tools.tsx`）はあるが、**「既存テンプレートを読み込んでデザインを保持したまま値だけ差し込む」実装ではない**。実態はコードでゼロから書式を組み立てる方式（ヘッダー色・列幅・データ検証・セルノートをJSで指定）。指示書§5が求める「テンプレートの罫線・数式・条件付き書式を維持」は**未実証**（exceljs自体は`workbook.xlsx.load()`→既存セルの`.value`だけ書き換えれば理論上可能だが、この社内での実績はゼロ＝Phase 1のPoCで検証必須）。
3. **監査ログのAI対応スキーマが既に先例あり**: `invoice_audit_logs`（`2026-08-23_invoices.sql` 87〜98行目）に`actor_type text not null default 'human' check (actor_type in ('human','ai'))`列が存在。指示書§13（将来のHermes連携）・§15（利用ログ）の設計はこれをそのまま踏襲できる。
4. **機密情報の「メタ情報とシークレットの分離＋RPC経由アクセス＋監査ログ必須」パターン**（`info.credentials`／`info.credential_secrets`／`info.reveal_secret()`／`info.export_credentials()`、`ns-info-system/supabase/migrate-info/info_ddl.generated.sql` 90〜152行目）は、指示書§11（ID・パスワード関連の別扱い）が要求する設計そのもの。新規に考案する必要はなく、Export Service内の「ID・パスワード一覧」的な出力があれば直接流用可能。
5. **BQ→サーバー間ブリッジの前例**: `labor-allocation-compare` Edge Function（D-2）が、BigQueryへの新規サービスアカウントを用意せず、**既存GAS WebApp（`bqDailyStore`等）をHTTP fetchで呼び出す**方式を採用済み（後述§6で最重要の再利用ポイント）。

## 4. Excelテンプレートの最適な保管場所

**推奨: Supabase Storage 非公開バケット`export-templates`（指示書の第一候補どおり）。**

既存の直近の類似実装（`invoice-files`バケット、`2026-08-23_invoices.sql` 644〜656行目）が最良の参考パターン:
```sql
insert into storage.buckets (id, name, public, file_size_limit, allowed_mime_types)
values ('invoice-files', 'invoice-files', false, 20971520, null);
```
- `public=false`＋RLSで`invoice_can_access()`のようなアクセス関数を通す（署名URL閲覧）。**`allowed_mime_types`は絞りすぎない**（同ファイルのコメントに実際の事故例あり：MIME判定が環境依存で静かに失敗した）。
- テンプレートファイル自体はサイズが小さい（数百KB程度）ため、`report-photos`のような大容量向けの仕組みは不要。
- パス規約は`{template_code}/{version}.xlsx`のような形にし、`template_versions`的な発想はDBの`version`列で管理し、Storage側はバージョンごとに別ファイルとして保持（上書きしない＝指示書§4「過去バージョン」要件）。

## 5. Google Sheetsテンプレートの管理方法

**結論: Phase 1では「担当A経由のGAS方式」を推奨。Edge Function＋サービスアカウント方式は現時点で技術的にブロックされている。**

理由（最重要の発見）: WORKLOG 2026-08-22のエントリに記録の通り、**このGoogle Cloud組織では`iam.disableServiceAccountKeyCreation`ポリシーによりサービスアカウントの鍵作成自体がブロック**されており、過去に「dash-syncをGCPサービスアカウント方式でBigQuery直接クエリに変える」試みが同じ理由で断念に追い込まれている（代替としてGASブリッジ方式に切り替えた実績あり）。Google Sheets/Drive APIをEdge Function（Deno）から呼ぶ場合も同じ認証手段（サービスアカウントの鍵ファイル）が必要になるため、**同じ壁に当たる可能性が高い**。

一方、GAS側は「Advanced Service」経由でBigQueryやDrive/Sheetsにアクセスしており、これは**Apps Script自身のOAuth**（Googleアカウントの権限委譲）であり、サービスアカウント鍵を必要としない。`tori-dashboard/gas/appsscript_注意.md`にBigQuery Advanced Serviceの設定が明記されている通り、この経路は今後も安定して使える。

**比較表:**

| 方式 | 実現性 | 備考 |
|---|---|---|
| GAS方式（担当A経由で新規WebAppまたは既存GASへのアクション追加を依頼） | ◯（既存の認証基盤を再利用できる） | 担当A専任領域のため実装は依頼制。テンプレートコピー(`SpreadsheetApp.copy`)→データ流し込み→指定Driveフォルダ保存、という指示書§7の要件はGASで実装すること自体は技術的に難しくない（既存実績は無いが`DriveApp`/`SpreadsheetApp`はGASの基本API） |
| Edge Function＋サービスアカウント方式 | △〜×（現状ブロック中） | Workload Identity Federation等の鍵レス認証で回避できる可能性はあるが、Supabase Edge Function（Deno/非GCPランタイム）からのWIF設定は前例が無くハードルが高い。**組織ポリシー変更（ユーザーによる）が先に必要** |

Phase 1のPoC（§11）でGoogle Sheets出力を含める場合は、担当Aへの依頼（WORKLOGでの正式依頼）が発生する前提でスケジュールに織り込む必要がある。**PoCの3形式（Excel/CSV/Google Sheets）のうちGoogle Sheetsだけ担当Aの手が空くまで遅延するリスクがある**点を承認時にご認識いただきたい。

## 6. Export Serviceの推奨アーキテクチャ

```
export.html（新規・iframe埋め込み想定）
   │ Supabase Auth JWT
   ▼
export-preview / export-run / export-templates-* / export-history（Edge Functions・新規）
   │
   ├─ Supabase由来データ（経費・シフト・勤怠・従業員等）
   │    → 呼び出し元JWTでのRLS読み取り、または service_role＋アプリ層権限チェック関数
   │
   ├─ BigQuery由来データ（PL・売上・入金・媒体）
   │    → 【重要】新規サービスアカウントを作らず、既存tori-dashboard GAS WebApp
   │      （bqGetPL/bqDailyStore/bqGetDeposit/bqGetMedia）をHTTP fetchで呼ぶ
   │      （labor-allocation-compare Edge Functionの前例をそのまま踏襲）
   │
   ├─ Google Sheetsテンプレート由来（広告費用対効果_管理シート等）
   │    → 同様にGASブリッジ経由（新規アクション追加は担当A依頼）
   │
   ▼
テンプレートエンジン（exceljs、Deno npm:specifier経由）
   │
   ├─ Excel: Supabase Storageからテンプレート取得→値だけ差し込み→署名URL or ダウンロード
   ├─ CSV: 既存4箇所と同じBOM付きUTF-8生成
   └─ Google Sheets: GASブリッジへコピー・書き込みを依頼（担当A経由）
   │
   ▼
export_history（監査ログ・新規）
```

**設計判断の根拠:**
- BQへの新規直接クエリ経路（新サービスアカウント）は§5と同じ理由で避ける。既存のGASブリッジ（`bqGetPL`等）を「Export Serviceの実質的なBQデータAPI」として扱う。
- Deno Edge Function内で`npm:exceljs`が動作するかは**未検証**（Supabase Edge FunctionsはDeno上でnpm互換レイヤーを持つが、exceljsのZip/Buffer処理がフル互換かはPhase 1で実機検証が必要な項目）。動作しない場合は「サーバーはデータJSON生成のみ→ブラウザ側（export.html）でexceljs実行」という現行`excel-tools.tsx`と同じクライアント生成方式にフォールバックする設計にしておく。
- Edge Functionの実行時間制限（過去にtori-dashboardのレポート生成でタイムアウト事故がありPuppeteer方式を廃止した前例、WORKLOG参照）を踏まえ、**重い集計・大量データはBQ/GAS側で完結させ、Edge Functionは薄いオーケストレーション層**に留める。

## 7. テンプレートマッピング方式

指示書§6の「設定DB化で複雑になる場合は代替案を提案」を受けた推奨:

**ハイブリッド方式を推奨（フルDB化は避ける）:**

1. **単純な「勘定科目→セル」「列→セル」対応**（PLの60科目×行、店舗一覧の1行1店舗など、行が規則的に並ぶ帳票）は`template_mapping`テーブル（`template_id / source_field / target_cell_or_column / display_format`程度のシンプルな列構成）で管理。指示書のtransform_ruleのような「変換ロジックをDB内に持つ」設計は避け、**変換が必要な場合はコード側の小さな関数（テンプレートコードごとに1つ）に閉じる**。
2. **合計・比率などの計算列はDB化せず、Excelテンプレート自身の数式を温存**（exceljsで値セルだけ書き換え、数式セルには触れない）。これにより指示書§5「毎回AIがデザインを生成する方式にしない」「数式を可能な限り維持」を最も素直に満たせる。
3. 複雑な帳票（明細行数が可変、条件付き書式が複雑等）が将来出てきた場合のみ、テンプレートごとの専用マッパー関数を追加する（コードでの管理＝レビュー・テストがしやすい）。

理由: 「DB上の`transform_rule`に変換ロジックを持たせる」設計は、結局それを解釈する汎用エンジンをコードに書くことになり、複雑さがDBとコードの両方に分散するだけで指示書が懸念する「複雑になる」を招きやすい。シンプルな座標マッピングだけをDB化し、ロジックはコード（テンプレートコード単位で疎結合）に残す方が保守しやすいというのが実務上の判断。

## 8. 権限/RLSとの整合性

### 8-1. 既存の権限パターン
- ハブ本体（`public`スキーマ）の判定は「役職ロール（CEO/HQ/TEAM/TENCHO/SHAIN/AL）＋`is_master`」が主流（`expense_can_manage()`型、`2026-08-18_expenses.sql` 109〜112行目）。
- 店舗単位の絞り込みが必要な機能は`user_stores`テーブルを併用（`sf_can_manage()`、`2026-08-19_shifts.sql` 9〜21行目）。
- **法人（`corporation_id`）単位でSupabase本体データを絞るRLS実装パターンはハブにまだ存在しない**（`info`スキーマの`can_access_corp()`が先行実装のみ）。指示書§2「対象法人▼」フィルタの権限チェックは、Export Service向けに**新規に整備が必要**。

### 8-2. BigQuery側は「RLSではなくアプリ層」
既存GASの`bqGetPL`等は、BigQuery自体に行レベルセキュリティは掛かっておらず、**GASコードが`session.stores`（ログイン時に取得した店舗名の文字列リスト）をSQLのWHERE句へ文字列連結**することで権限境界を実現している（`gas/Code.gs` 1216行目ほか）。Export ServiceがこのGASブリッジ経由でBQデータを取得する場合、**Export Service側で「このユーザーがアクセスできる店舗ID一覧」を確定させたうえで、GASへ渡す店舗名リストを生成する**必要がある（GAS側のセッション権限をそのまま信用してはいけない＝GASログインとExport Serviceのログインは別セッション）。

### 8-3. 推奨実装方針
1. `public.corporations`＋`stores`＋`user_stores`を使い、`export_allowed_stores(user_id)`のようなsecurity definer関数を新規に整備（`sf_can_manage`型を法人対応に拡張）。
2. Export Serviceはこの関数の結果（許可店舗IDリスト）を**BQ側にはUUIDではなく店舗名として渡す**（現行GASブリッジがUUIDを受け付けないため）。店舗名の変換は`stores.name`を正とし、`store_aliases`は使わない（表記ゆれの原因になるため、正本の店舗名のみ）。
3. 給与・個人情報系（`info.employee_salaries`等）は`info.has_perm()`系の既存関数を利用しつつ、**指示書§10が要求する「通常より厳しい制御」として、Export Service側では追加のマスター限定ゲートを重ねる**（既存の`info`側RLSに法人チェックが無い既知の穴＝R11をそのまま信用しない）。

## 9. 大量データ出力時の性能対策

既存の前例から3つのパターンが確立している。Export Serviceもこれに準じる。

1. **期間ウィンドウ制限**: `bqDailyStore`等の`months`パラメータ（既定13ヶ月）、`bqGetMedia`は明示的に直近3ヶ月に制限（`gas/Code.gs` 2004行目コメント）。Export Serviceの「対象期間▼」も、無制限期間の一括出力は既定で拒否し、大きい範囲は非同期ジョブ扱いにする。
2. **キャッシュ**: BQ結果は`CacheService`で10分キャッシュ済み（GASブリッジ側で既に効いている）。Export Service側で二重キャッシュする必要は薄いが、同一条件での連続プレビューは呼び出し回数を抑える工夫が要る。
3. **タイムアウト回避の教訓**: tori-dashboardのレポート生成（Puppeteer方式）が過去にタイムアウトで機能不全に陥り、ブラウザレス方式（BigQuery直読み`capture-bq`）へ全面的に作り替えた実績がある（WORKLOG 2026-08-22）。Export Serviceも「Edge Function内で重い処理を長時間実行する」設計は避け、**指示書§9の`export_history.status`（pending/processing/completed等）を使った非同期パターン**（受付→バックグラウンド生成→完了時にfile_path/sheet_url確定）を既定にすることを推奨。
4. **CSV生成のストリーミング**: 大量行のCSVはEdge Functionのメモリに全件展開せず、可能ならチャンク単位でStorageへ追記する設計にする（件数が数万行を超える出力＝媒体別売上21,000行超のような帳票が対象になった場合に必須）。

## 10. 既存機能を壊さない移行方法

- **新規ファイルのみ**（`export.html`・`export-*`・`export_`/`tpl_`接頭辞）が縄張りのため、既存機能への直接的な影響は原理的に無い。
- ただし以下は**既存資産への「依存」であり「改変」ではない**点に注意して進める:
  - GASブリッジ利用（§6）は既存の`bqGetPL`等アクションを**呼ぶだけ**（GAS本体は担当A専任のため一切変更しない）。新しいBQ集計が必要になった場合は担当Aへ新規アクション追加をWORKLOG経由で依頼する（既存アクションの改変ではなく追加）。
  - `app_secrets`テーブルからの`dash_id`/`dash_pw`読み取り（GASログイン用、`labor-allocation-compare`と同じ手段）は**共有テーブルの読み取りのみ**で書き込みは発生しない。
- 段階的展開: 指示書§16の順序（設計→テンプレート管理設計→権限監査ログ設計→UI→1帳票実装→実機テスト→横展開）をそのまま踏襲。既存メニュー（経営D CSVボタン等）と機能重複するが、**既存ボタンを置き換えない**（Export Serviceは並行稼働の新経路とし、指示書に明記の「局所実装にしない」方針を「既存の局所実装を廃止する」意味には取らない。廃止判断は横展開後にユーザー判断で）。

## 11. PoCとして最初に実装すべき帳票

**推奨: 「月次PL」（指示書が示す第一候補）を継続推奨。**

理由:
1. データ経路が実測済みで安定（`stg_pl`←`DB_PL`←`✍販管費入力`＋自動同期、`bqGetPL`アクション実績あり、`売上ダッシュボード_データ設計仕様書_2026-08-23.md`で読み込みシーケンスまで検証済み）。
2. 既に`mfExportCsv()`という「PLをCSV形式で書き出す」前例があり、列構成（60科目×店舗）の期待値がコード上に既に存在する＝テンプレートマッピング設計の練習台として最適。
3. Excel帳票としての体裁（罫線・小計行・書式）が経営者にとって最も「PDFで役所や銀行に出す」ような公式感のある帳票であり、指示書§5（デザイン維持）の検証価値が高い。
4. 法人・店舗フィルタ、期間フィルタの両方を自然に使う帳票であり、§8の権限モデル（法人×店舗）を最初から鍛えられる。

**次点候補（PL処理中に問題が出た場合の代替）**: 「売上実績」（`fact_daily_store`、正本はまだシートだが読み出し実績が最も豊富＝5画面で使われている安定データ）。「経費申請一覧」（Supabase本体データのみで完結・BQ/GASブリッジ不要のため技術的には最も簡単だが、指示書が想定する「Excel帳票としての完成度」の検証にはやや不向き＝件数一覧のCSV的な出力になりがち）。

**Google Sheets出力は§5の制約により、月次PLのPoCでは「Excel/CSV先行→Sheetsは担当A依頼後に追いつく」2段階での完了報告も許容いただきたい**（指示書の完了条件「3形式で実機出力」を一括達成できない場合はその旨を明示して個別確認する）。

## 12. 想定されるセキュリティリスク

1. **BQクエリの文字列連結（既知リスクR17の継承リスク）**: 既存GASブリッジは店舗名をエスケープのみでSQLに連結している。Export Serviceが同じ関数を叩く分には新規リスクではないが、**Export Service側で新たにBQクエリを直接組み立てる実装をした場合は同じ穴を作らないこと**（許可リストをアプリ側で厳密検証してから渡す）。
2. **法人単位RLSの不在（§8-1）**: 「対象法人▼」フィルタを画面上の絞り込みだけに頼ると、指示書§10「画面で選択肢を隠すだけでなくサーバー側でも権限チェック」に反する。新規のsecurity definer関数を用意するまでは、Export Service Edge Function内でのアプリ層チェックを必須にする。
3. **給与データRLSの既知の穴（R11）**: `info.employee_salaries`のRLSに法人チェックが無い。Export Serviceが誤ってこの権限モデルをそのまま信用すると、他法人の給与を出力できてしまう可能性がある。**給与関連データの出力機能はPhase 1スコープ外にすることを推奨**（§1参照。従業員IDの紐付けも未整備のため技術的にも時期尚早）。
4. **サービスアカウント鍵の新規作成試行**: §5・§6の制約を認識せずにGoogle Sheets/Drive APIの実装を進めると、組織ポリシーでブロックされて手戻りになる（過去に同じ壁で1回失敗した実績あり）。設計段階でこの制約を前提にしておくことでリスクを回避。
5. **Storageの公開バケット誤用（既知リスクR5の再発防止）**: `report-photos`が公開バケットである教訓を踏まえ、`export-templates`・出力ファイルの保存先は**必ず非公開バケット＋署名URL**とする（指示書自体が第一候補として明示済みだが、実装時に既存の`invoice-files`パターンを踏襲することで確実にする）。
6. **監査ログの実効性**: `export_history`を作るだけでなく、**「誰が・いつ・どの条件で」出力したかを検索可能にする**（`invoice_audit_logs`の`entity_type/entity_id`インデックス設計を踏襲）。特に給与・個人情報を含む出力は、`info.reveal_secret()`のように呼ぶたびに個別レコードを残す粒度が必要。
7. **AI経由アクセスの将来リスク（§13）**: `actor_type`列の前例はあるが、「AIが依頼者本人の権限を超えて取得できない」保証は、Export Service API自体がAI用の別ロール・別トークンを発行し、**呼び出し時に「依頼者のuser_id」を必須パラメータにして毎回権限を再検証する**設計にしないと形骸化する。要件定義書§18のDBアクセス厳格化6原則（353〜360行目）をExport Serviceの内部APIにもそのまま適用すること。
