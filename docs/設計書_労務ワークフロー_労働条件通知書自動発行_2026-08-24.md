# 設計書: 労務ワークフロー（労働条件通知書の自動発行）

作成: 2026-08-24／担当C（設計のみ・**実装はしない**）
参照元: `実装指示書_並行開発の担当分け_2026-08-24.md` C-3／`実装指示書_勤怠月またぎ再取込と新規要望4件_2026-08-24.md`タスク2／`要望まとめ_2026-08-24_複数システム.md` G3

**確定した前提（2026-08-24 ユーザー回答）**:
①テンプレートは**一般的な雛形**（厚生労働省の労働条件通知書標準様式ベース）を使う。特定の自社雛形PDFは無い
②送信経路は**メール・LINEの両方**（本人が選択できるようにする）
③**電子交付の同意取得**を送信前フローに含める（労働基準法上の要件を満たすため）

対象読者: 実装スレッド（担当未定。§7参照）。着手前に本書と最新のWORKLOGを確認すること。

## 0. 現行構造（このワークフローが橋渡しする既存要素）

| 要素 | 場所 | 補足 |
|---|---|---|
| 社員台帳 | `info.employees`（ハブSupabase・社内情報管理システム=`ns-info-system`） | 氏名・住所・雇用形態・入社日・電話番号など。**時給・月給の列は無い**（`info.employee_salaries`は月給ベースの4項目のみで時給列なし＝本ワークフロー専用の入力項目として新規に持つ必要がある） |
| ポータルログイン | `public.users` | `info.employees.user_id`で紐付く（Day1で追加）。**ただし在籍社員でも`user_id`がnullな人が存在する**（2026-08-22時点で3名＝ポータル未使用者。原因は自動一致0件・目視対応中）。この3名は本人へのメール/LINE自動送信ができない |
| メールアドレス | `auth.users.email`（Supabase Auth） | nippoの入社登録フォーム（`j-email`欄）でログインID兼メールとして登録される。`user_id`が無い社員はこの経路自体を通っていないため、メールアドレスも存在しない可能性が高い |
| LINE連携 | `public.users.line_user_id` / `line_linked_at` | nippoの「LINEと連携する」フロー（合言葉方式）で登録。入社登録と同時に案内される運用のため、新規入社者は比較的揃いやすい |
| 書類保管 | `info.documents`（`corporation_id`・`store_id`・`title`・`kind`・`file_path`・`mime_type`） | 非公開Storageバケット`documents`。既存の拡張パターンとして`info.loans`向けに`2026-08-19_loan_documents.sql`が`loan_id uuid references info.loans(id)`を追加した実績があり、本ワークフローも同じ形で`employee_id uuid references info.employees(id)`を追加する想定 |
| メール送信の参考実装 | `ns-portal/supabase/functions/invoice-send`＋GAS`gas/invoice-intake/` | Edge Functionが送信対象をキューから取り出し→GAS WebApp（共有シークレット認証）へPOST→GAS側`GmailApp`で実送信→成否をDBへ書き戻し。5分おきのGASトリガーが`queued`のまま残った分を再送する保険ルートも持つ。**本ワークフローの送信経路もこの型をそのまま踏襲する** |
| LINE送信の参考実装 | `line-webhook`Edge Function（`push_user`アクション）／`smaregi-payroll-reconcile`等のバッチ系LINE送信 | `app_secrets.line_channel_token`を使いLINE Push APIを直接叩く方式 |
| ⚠️LINE送信の既知の制約 | WORKLOG（2026-08-22系のエントリ） | LINE公式アカウントが**月間送信上限に到達し送信失敗した実績がある**（`You have reached your monthly limit.`）。シフトリマインド等と共有アカウントのため、対応方針はユーザー判断で保留中。**本ワークフローのLINE送信もこの共有枠を消費する**ため、実装時に上限状況を再確認すること |
| PDF生成 | **既存実装なし** | リポジトリ横断でPDF生成ライブラリ（pdf-lib・Puppeteer等）の使用実績は無し。新規に用意する必要がある（§3） |
| 同意取得の記録 | **既存パターンなし** | DB上に「同意済み」を表す列・テーブルは他機能にも存在しない。本ワークフローで新規に設計する（§5） |

## 1. 全体フロー

```
①本部が対象社員を選ぶ（info.employees一覧・社内情報管理システム）
  ↓
②本部が労働条件項目を入力（時給/月給・雇用形態・契約期間・就業時間 等）
  ↓
③プレビュー画面で通知書PDFの内容を確認（テンプレートへ差し込んだ結果を表示）
  ↓
④「送信」ボタン
  ↓
⑤送信経路を選択（メール／LINE／両方）＋電子交付同意チェック必須
  ↓
⑥PDF生成 → info.documentsへ保管 → 本人へ送信キュー投入
  ↓
⑦GAS（送信専用）が5分おきに拾って実送信 → 成否をDBへ書き戻し
  ↓
⑧本人側: 受信したリンク/添付から通知書を確認 → （同意ステップ済みのため）追加操作は不要
```

一度送信した通知書は「確定版」として保管し、内容を訂正する場合は**新しいバージョンとして再送**する（既存の`invoice_email_outbox`の`queued/sent/failed`ステータス運用と同型。上書き編集はしない＝監査証跡を残す設計）。

## 2. データモデル（すべて追加のみ・既存を壊さない）

| 変更 | 内容 |
|---|---|
| `info.employees`に時給/月給列を追加 | `hourly_wage numeric`・`monthly_wage numeric`（どちらか一方を使う想定・両方nullは不可のCHECK）。**給与情報を`info`スキーマに置くことは`要件定義書.md`の「給与情報はinfo金庫の分離を維持」方針と整合**（`employee_salaries`と同じ隔離レベルで守る） |
| 新テーブル`info.labor_notices`（仮称） | `id`・`employee_id`（→`info.employees`）・`corporation_id`・`status`（`draft`/`pending_consent`/`queued`/`sent`/`failed`）・`terms`（jsonb＝雇用形態・契約期間・就業時間・休憩・休日・賃金等の入力値スナップショット）・`pdf_document_id`（→`info.documents.id`）・`created_by`・`created_at`・`sent_at` |
| 新テーブル`info.labor_notice_consents`（仮称） | `id`・`notice_id`（→`labor_notices`）・`consented_at`・`consent_ip`（任意）・`consent_method`（`email_link`/`line_button`）。§5参照 |
| `info.documents`にリンク列追加 | `employee_id uuid references info.employees(id) on delete set null`（`loan_id`追加時と同じALTERパターン）。本ワークフローが生成したPDFは`kind='労働条件通知書'`で登録 |
| 送信キュー | 請求書と同型の`labor_notice_outbox`（`notice_id`・`channel`=`email`/`line`・`status`・`sent_at`・`error`）を新設し、GAS側の5分トリガーが拾う設計にする |

## 3. PDF生成

- テンプレートは**厚生労働省の労働条件通知書標準様式**をベースにしたGoogle Docsテンプレート（プレースホルダー差し込み）とし、GAS側で`DocumentApp`または`Slides`のテンプレート複製→差し込み→PDFエクスポートという、Google Workspace標準機能だけで完結する方式を推奨（新規ライブラリ・外部サービス不要でリスクが低い）
- 差し込み項目: 氏名・住所・雇用形態・契約期間・就業場所・業務内容・始業終業時刻・休憩・休日・賃金（時給/月給）・支払方法・退職に関する事項　等（労基法15条の明示事項に準拠。項目の過不足は実装時にユーザーへ最終確認）
- 生成したPDFは`info.documents`バケットへアップロード→`info.labor_notices.pdf_document_id`に紐付け

## 4. 送信（メール・LINE両方・本人選択）

- 送信直前の画面で**受信方法を選ばせる**（メールのみ／LINEのみ／両方）。実際の選択はUIの本部側入力ではなく、**本人が受け取れる経路が複数ある場合に本部が代理選択**する運用でよいか、または本人へ事前アンケートするかは実装時に要確認（今回のユーザー回答「本人が選択」は方針確認であり、UI上の主体＝本部代理か本人自身の事前登録かまでは未確定）
- メール送信は`invoice-send`と同型（GAS `GmailApp`経由）。LINEは`line-webhook`の`push_user`パターンを流用
- **本人がメール・LINEどちらも持たない（`user_id`がnullな在籍社員）場合の代替経路**（例: 印刷して手渡し＋システム上は「手渡し」ステータスで記録）を設計に含める必要がある（§0の3名がこれに該当）

## 5. 電子交付の同意取得（新規パターン）

労働基準法上、労働条件通知書の電子交付には本人の希望・同意が前提となる。本ワークフローでは以下のステップで対応する:

1. 本部が送信する前に、まず「電子交付の同意確認」メッセージ（本文のみ・PDF無し）を本人へ送る
2. 本人がメール内リンク／LINEのボタンをタップ→同意ページで「同意する」を押す→`labor_notice_consents`に記録（`consented_at`・`consent_method`）
3. 同意が記録されて初めて、本体のPDF付き通知が送信可能になる（`labor_notices.status`が`pending_consent`→`queued`に遷移する条件を「同意レコードが存在すること」にする）
4. 同意が一定期間（例: 3日）得られない場合は本部へリマインド表示（実装時にリマインド要否を確認）

この同意フローはDB上に前例が無い**完全新規のパターン**であるため、実装時は労務・法務的な確認事項（同意文言・保存期間・書面交付とのどちらを既定にするか）をあらためてユーザーに提示すること。

## 6. 保管（info.documents連携）

- 送信済みPDFは`info.documents`（`kind='労働条件通知書'`・`employee_id`紐付け）へ自動登録。手動アップロードと同じ一覧に混在して表示される
- `info.deadlines`との連携（契約更新日等のリマインド）は本ワークフローのスコープ外（必要なら別途要望として起票）

## 7. 権限・所有権（実装時の注意）

- 本部入力フォーム・送信ボタンの置き場所は**社内情報管理システム（`ns-info-system`リポジトリ）が自然**（`info.employees`の詳細画面に追加する形）。このリポジトリは**担当Fが専任**（`実装指示書_並行開発の担当分け_2026-08-24.md`所有権マトリクス）のため、**実装フェーズでは担当Fとの調整（または担当割当の変更）が必要**。担当Cの縄張り（`invoices.html`・`invoice-*`）には無い作業範囲であることに注意
- 送信用GAS新規プロジェクトのデプロイは、既存ルールどおり**GASデプロイ権限を持つ担当Aのみ**が実施可能（他担当はデプロイ禁止）
- RLS方針は`info.employees`の既存権限関数（`info.can_access_corp()`等）を踏襲。時給等の給与情報を含むため、閲覧権限は`employee_salaries`と同等以上に絞る

## 8. 未解決・実装前にユーザー確認が必要な事項（まとめ）

- 労基法15条の明示事項のうち、本テンプレートに含める項目の最終確認（雇用形態別に必須項目が変わる可能性）
- LINE公式アカウントの月間送信上限問題が実装時点で解消しているか（未解消なら、本ワークフローのLINE送信は影響を受ける前提で設計を調整）
- ポータル未登録（`user_id`null）の社員への代替送付方法（印刷手渡し等）の運用フロー
- 「本人が選択」の主体が本部代理か本人事前登録かの具体化
- 同意リマインドの要否・タイムアウト日数
- 実装担当（`ns-info-system`は担当F専任のため、担当割当の調整が必要）
