# 設計書: 従業員情報の変更と関連システムの連動（現状調査と提案）

2026-11-10 作成。**調査と設計のみ**（本番 SQL・EF デプロイ・画面公開・外部システムへの書き込みは行っていない。実装は別途承認）。
調査対象: nippo `index.html`、ns-portal の SQL / Edge Functions / `requests.html` / `invoices.html`、ns-daily-import、本番 DB の構造（テーブル・関数・トリガー・件数のみ。個人情報は読んでいない）。

## 0. 結論（先に）

- 変更の「申請→承認」は 3 系統が別々に作られている: 個人情報（`profile_change_requests`）／退職・移籍・兼務（`hr_change_requests`）／入社時の賃金・交通費・扶養（`onboarding_*`・`post_join_*`）。
- 同じ項目を **承認なしで直接書き換えられる経路** が並んでいて、そちらが実際に使われている（`profile_change_requests` は本番 0 件）。直接編集は変更前後・操作者が残らない項目が多い。
- **住所・最寄り駅・所属店舗・雇用形態が変わっても、交通費の再確認は始まらない。** 銀行口座は「いつの給与から新口座か」を扱う仕組みが無い。
- 提案: 既存の表は残したまま、その上に **共通の「変更イベント → 影響判定 → 承認 → 同期履歴」** を 1 つ足す。最初の一歩は「記録するだけ（挙動は変えない）」＋「住所・駅・所属の変更で交通費の再確認を本部へ出す」。

## 1. 住所変更と交通費の連動（ご質問 ① への回答）

| 確認事項 | 現状 | 根拠 |
|---|---|---|
| 住所変更の承認後、通勤経路の再確認が自動で始まるか | **始まらない** | `review_profile_change_request`・`update_my_profile` に交通費の処理なし。`employee_commute` に住所を見るトリガーなし |
| 最寄り駅の変更を検知できるか | **できない** | `employee_commute.home_station` は経路申請（`onboarding_save_commute`）のときだけプロフィールから写す |
| 駅すぱあとで新しい交通費を再計算できるか | **手動ならできる** | 本人が通勤カードから再申請 → 本部が Slack「🔁 再検索」。EF `commute-route` は動く |
| 本部に交通費の再承認依頼が届くか | **届かない** | 承認済みの人は再申請しても `judgement='approved'` のまま（再承認を求めない作り） |
| 承認された交通費が適用開始日からスマレジに反映されるか | **部品はある（未有効）** | `employee_commute_settings.effective_date` → UI ジョブ（Playwright）。スイッチ OFF・入社ワークフローがある人だけ |
| 旧住所・旧経路・旧交通費と変更履歴が残るか | **一部だけ** | 住所: 申請経由のみ残る（直接編集は残らない）。経路: `onboarding_events`（ワークフローがある人だけ）。確定値: `employee_commute_settings` は行が積み重なるので残る |

4 つの日付の扱い: 現状は **適用開始日（交通費設定・賃金）だけ** がある。住所の変更日（引越日）・申請日・承認日は、申請経由のときに申請日・承認日が残るだけで、引越日の欄は無い。

提案（ご希望どおり）: 住所変更を **契機** に通勤経路の再確認を必須にする。駅が変わったかどうかは自動で決めつけず、①本人に「最寄り駅・経路は変わりますか」を必ず答えてもらう → ②駅すぱあとで再検索 → ③金額が変わる／変わらないを表示 → ④本部が承認（変わらない場合も「変更なしで確認済み」を記録）。

## 3. 既に連動できている項目

入社手続き／賃金（適用開始日つきでスへ・差分検出あり）／退職・移籍・兼務（承認→期日に自動反映→本部タスク）／扶養・年末調整の提出→承認→反映指示／所属の日次照合（報告）／給与計算結果と勤怠の取込。

## 4. 連動していない項目と実務上のリスク

1. **住所・最寄り駅が変わっても交通費が旧経路のまま**（過払い・不足が続く）。本人の住所変更はスにも届かない（本部が保存したときだけ届く）。
2. **所属店舗が変わっても交通費が再計算されない**（勤務先の駅が変わる）。経路検索は「所属の先頭の店舗」を使う。
3. **雇用形態が変わっても交通費の月額上限が変わらない**（アルバイト 6,000 円／社員なし）。変更に適用開始日が無く、過去月の再計算が「今の区分」で行われるおそれ。スの従業員区分にも届かない。
4. **銀行口座**: 適用開始（何月支給分から）の概念なし。本部の直接編集は上書きで旧口座が残らない。振込 CSV は出力した瞬間の口座を読むため、出力直前の誤変更・出力後の変更を検知できない。「どの口座に振り込んだか」の記録が支給回ごとに残らない。退職後も口座が残る。
5. **賃金（入社後の変更）**: 申請・承認が無く、同じ適用日は上書き、削除は物理削除で、変更前後・操作者が残らない。
6. **氏名**: スに届かない（給与明細・源泉徴収票の氏名、口座名義カナとの不一致）。本人が承認なしで変更できる。
7. **役職・権限**: 承認も履歴も無い（誰がいつ権限を上げたか追えない）。
8. **源泉区分（甲乙・扶養人数）**: 既存従業員は仕組み上変更できない（入社ワークフロー必須）。扶養に適用開始日が無い。
9. **退職**: 口座・賃金行・交通費設定・未完了の自動操作ジョブが残る。直接の無効化は記録が残らない。
10. **休職**: 概念が無く、月額（定期代）支給や社保の停止につながらない。
11. **勤務条件**: データが無く、変更を検知する対象が無い。
12. 直接編集の多くは **誰がいつ何を変えたか残らない**（`users`・`employee_profiles`・`user_stores`・`payroll_bank_accounts` に履歴の仕組みなし）。

## 5. 推奨する共通設計（ご質問 ④⑤）

既存の表・RPC・Slack ボタンは作り直さない。上に 3 つの共通部品を足す。

```
変更（申請 or 直接編集 or スからの取込）
  → ① 変更イベント（何が・誰が・いつ・変更前後・4 つの日付）
  → ② 影響判定（ルール表: この項目が変わったら何を起動するか）
  → ③ 承認（重要項目は承認まで確定しない）→ 正本を更新
  → ④ 影響ごとの処理を起動（既存の仕組みを呼ぶ）→ 同期 → 読み戻し照合
  → ⑤ 同期状況（済／未／エラー／競合）を一覧表示。失敗は本部タスク＋Slack
```

**① 変更イベント `employee_change_events`**（新規・追記のみ）
項目グループ、変更前後、変更元（本人申請／本部直接／スから取込）、申請者・申請日、承認者・承認日、**変更日（事実が起きた日: 引越日・改姓日など）**、**適用開始日**、状態。
- 申請経由: 既存の `profile_change_requests`・`hr_change_requests` の承認時に 1 行書く。
- 直接編集: `users`・`employee_profiles`・`user_stores`・`payroll_bank_accounts`・`employee_wage_settings` に **記録用トリガー** を付けて必ず 1 行残す（挙動は変えない）。これで「承認を通らない変更」も漏れなく拾える。
- 個人情報の値そのもの（住所・口座番号）は本部だけが読める列に入れ、Slack・通常ログには項目名だけ出す。

**② 影響判定ルール `employee_change_rules`**（新規・設定表）
項目グループ → 起動する影響・承認の要否・承認者。初期値:

| 変わった項目 | 起動する影響 |
|---|---|
| 住所・最寄り駅 | 交通費の再確認（必須）、スの住所更新 |
| 所属店舗 | 交通費の再確認、スの所属照合 |
| 雇用形態 | 交通費の月額上限の再判定、扶養・年調ルール切替（既存）、スの従業員区分（本部タスク）、給与対象の確認 |
| 賃金 | スの賃金同期（既存）、人件費の見込み |
| 氏名 | スの氏名更新、口座名義カナの確認タスク |
| 銀行口座 | 適用する支給回の決定、振込前の再確認 |
| 扶養・税務 | スの源泉・扶養（既存） |
| 退職・休職 | 交通費設定の終了、未完了ジョブの取り下げ、口座の扱い、ス退職処理（既存） |

**③ 影響の実行と同期履歴 `employee_change_effects`**（新規）
変更イベント 1 件につき影響 1 行。状態は「未着手／承認待ち／同期待ち／同期済み／エラー／競合／対応不要」。実体は既存の行を指す（`employee_commute`・`employee_commute_settings`・`employee_wage_settings`・`ui_automation_jobs`・`hq_tasks`・`notification_deliveries`）。読み戻し照合の結果（スの値と一致したか）もここに残す。

**重要項目の扱い**: 給与・交通費・権限・口座は、承認前に確定・書き込みしない（既存のスイッチと 3 点照合はそのまま）。自動で起動するのは「再確認の依頼」「再計算の表示」まで。

**例 1: 住所変更**
本人が申請（引越日を入力・「最寄り駅や経路は変わるか」に回答）→ 本部承認 → 住所を更新（スの住所へ API）→ 交通費の再確認を起動（承認済みを「再確認待ち」に戻す・本人へ経路の再申請依頼）→ 駅すぱあと再検索 → 旧経路・旧金額と新を並べて Slack に表示 → 本部が承認（変更なしも記録）→ 適用開始月を決めて交通費設定 → スへ反映 → 読み戻し照合 → 完了。

**例 2: 時給変更**
店長または本部が申請（適用開始日つき）→ 承認 → `employee_wage_settings` に登録（既存 `hr_save_wage`）→ スへ API 同期（既存）→ 読み戻し（既存 `wage_pull`）→ 人件費の見込みに反映 → 完了。足すのは「申請・承認」と「変更イベントの記録」だけ。

**例 3: 銀行口座変更**（給与は末日締め・翌月 15 日払い）
本人申請 → 本部承認（2 人目の確認）→ **「何月 15 日支給分から新口座か」を明示して確定** → 振込 CSV の出力時に、その支給回で使った口座を控えとして保存（出力後の変更はその回に影響しない）→ 出力済みの回に間に合わない変更は「次回から」と表示。旧口座は履歴に残す。

**⑤ 同期状況の画面**
本部向けの一覧（従業員 × 項目 × 状態）。未同期・エラー・競合だけを絞り込める。エラー・競合は本部タスクを自動作成し、Slack の人事チャンネルに通知（既存の仕組みを使用）。

目標: 「従業員情報を変更したら、関連する処理が自動的に洗い出され、必要な承認・同期が完了するまで追跡できる」。新しい連動は、ルール表（`employee_change_rules`）に影響を足し、影響の処理を 1 つ書くだけで増やせる（申請フォームごとに連動を個別実装しない）。

## 7. 未確認・前提

- 氏名や従業員区分をスの API で更新できるかは未検証（できなければ画面自動操作か本部タスク）。
- 雇用契約・就業規則との整合（交通費の上限・支給方法、口座変更の締切）は未確認。
- 調査はコードと DB 構造にもとづく。運用上の例外（紙・口頭での変更）は把握していない。

## 12. 将来の「Slack の DM で AI に話しかけて申請」に向けて（2026-11-10 構想の共有を受けた指摘。実装はしていない。★2026-11-11: 下の 6 点を、今後の共通基盤の要件として採用）

構想: 従業員と AI アプリの 1 対 1 の DM で自然文の申請 → AI は理解・不足の質問・整理だけ → 本人が「申請する」を押して登録 → 承認者だけに依頼 → 承認後は既存の処理 → 結果を DM へ。最初の対象は退職申請。AI は低コストのモデルを差し替え可能にし、必要のないところには入れない。

**いまの作りで、そのまま使えるもの**: 申請・承認・履歴・同期はすべて DB の関数で行い、画面や AI は関数を呼ぶだけ（AI に直接の更新権限は要らない）／承認の関数は Slack の操作者を受け取れる／申請した本人は自分の申請を承認できない／変更履歴は共通／通知は口座番号・金額を持たない／AI を使わずに動く。

**妨げになりうる点（今後の設計で直す。大きな作り直しは不要）**

1. **本人申請の入口が「画面にログインしている本人」前提**。Slack 経由（サービス経由で「この申請者は本人」と渡す）だと、口座の本人申請は通らない。入口の関数に「Slack で本人確認済みの申請者」を受ける口を足す必要がある（承認側は対応済み）。
2. **「差し戻し」の状態が無い**（承認待ち・承認・却下・取り下げだけ）。差し戻し → 本人が直して再申請、の流れを足す必要がある。
3. **承認者・通知先が固定**。承認できる人は役割（本部・社長・マスター）で決め打ち、本部タスクの担当は氏名 3 名の固定、通知先は人事チャンネル固定。申請の種類ごとに承認者・通知先を設定する表が無い（最終承認を社長に集約する運用もいまは設定できない）。既存のポータルの承認関数は社長を承認者に含まない、という不揃いもある。
4. **申請者への結果通知が無い**。いまの通知は本部向けだけ。本人の DM に結果・差し戻しを返す仕組みは未実装。
5. **申請の入れ物が種類ごとに別**（個人情報・口座・賃金／退職・移籍・兼務／交通費／社内情報管理システムの申請）。種類ごとの「必要な項目・Slack に出してよい項目・承認のルール」を定義する共通の受付口を 1 枚かぶせる形がよい（各表はそのまま使う）。
6. **Slack に出してよい項目の制限**は、いまは通知の文面ごとに作り込んでいる。種類ごとの定義にまとめると、DM・承認依頼の両方で同じ制限を使える。

**構想の確定内容（2026-11-11）**
- 窓口は、従業員本人と AI アプリの 1 対 1 の DM（公開チャンネルは使わない。他の従業員に会話・申請内容が見えない）。
- 従業員の流れ: 文章で伝える → AI が申請の種類を判断して整理 → 足りない情報だけ質問 → 内容を本人に表示 → 本人が「申請する」を押した時点で正式に登録 → 進捗・承認結果・差し戻しも同じ DM で確認。
- 本部・社長の流れ: 通常の申請は本部の承認権限者へ通知／賃金は本部確認のあと社長へ最終承認の依頼／Slack 上で承認・却下・差し戻し／結果は管理システムに反映し、本人へ通知。Slack からの承認にも、管理画面と同じ権限判定と監査履歴を使う（承認ルールは §14）。
- AI の役割は、文章の理解・不足の質問・内容の整理だけ。本人照合・権限判定・申請登録・承認・データ更新・スマレジ同期は、管理システムの決まった処理で行う。AI の判断だけでデータを更新しない。
- Slack のユーザーと従業員の紐付け（既存の表 `user_slack`）で本人を特定し、他人の情報を取得・変更できないようにする。口座・給与・住所は Slack 上に必要最小限しか出さない。AI のモデルは差し替え可能にし、文章の理解には低コストのモデルを使える構造にする。
- 最初の実装対象は退職申請。

## 14. 申請・承認権限の正式ルール（2026-11-11 ユーザー確定）と、いまの作りとの差分

### 14.4 社長本人の賃金変更（例外ルールの案。★承認されるまで実装しない）

| A. 代理の最終承認者 | あらかじめ設定表に「社長本人の賃金変更の最終承認者」を 1 名指定しておく（社長以外。例: 本部の責任者や他の役員）。本部確認 → その人の最終承認 | 仕組みが単純。2 人の目が必ず入る | 指定された人に権限が集まる。その人自身が本部確認もしてしまうと実質 1 人になる |
| B. 本部 2 名の承認 | 本部の承認権限者 2 名（申請者と別の 2 人）の承認で確定 | 特定の 1 人に依存しない | 本部の人数が少ないと回らない。社長の報酬を本部だけで決める形になる |
| C. 根拠書類つきの確認 | 役員報酬の変更を決めた記録（株主総会・取締役会の議事録など）の添付を必須にし、本部はその書類どおりかを確認して登録する | 決定そのものは会社の正式な手続きに置ける。システムは「書類どおりに登録されたか」を確かめる役になる | 書類の用意が必要。従業員としての賃金（役員報酬でない場合）には合わない |

**推奨: A ＋ C の組み合わせ**
1. 申請は本部が起こす（社長本人は申請も承認もしない）。
2. 根拠書類（決定の記録）の添付を必須にする。
3. 段階 1: 本部確認（書類どおりの金額・適用開始日か）。
4. 段階 2: 設定表で指定した「代理の最終承認者」が承認（段階 1 と別の人であること）。
5. 確定と同時に、社長本人へ結果を通知（事後の確認。本人が異議を出せる）。
6. 申請・書類・各段階の承認者・日時・変更前後・適用開始日・同期結果を記録。
代理の最終承認者をだれにするかは、決めていただく必要がある。

## 15. 確認済みの同期差異を安全に管理する設計案（未実装）

ねらい: 同期状況の一覧で、「まだ誰も見ていないエラー」と「見たうえで、意図して許容している差異」を区別する。ただし、確認済みにしても、給与への影響や未同期の事実は隠さない。

- **確認の記録**（例 `employee_sync_acknowledgements`）: どの差異か（一覧の項目の印）／確認した人・日時／理由（必須）／見直す日（必須。既定は次の給与締めの前）／確認した時点の中身の印（差異の内容が変わったら確認を無効にするため）。
- **一覧での見せ方**: 3 つに分ける。①未確認（従来どおり上に出す）②**確認済み・許容中**（消さない。別の段にまとめ、理由・確認した人・見直す日を出す）③解消済み（出さない）。件数も「未確認 ○件／確認済み ○件」と分けて出す。
- **給与に関わる差異は必ず見える**: 賃金・交通費・源泉・口座に関わる項目は、確認済みでも「給与に影響」の印を付け、給与の締め前（振込画面・月次の確認）に「確認済みで許容中の差異が ○件あります」と必ず出す。確認済みにできるのは表示の区分だけで、未同期という状態そのもの（`sync_status`）は変えない。
- **確認が自動で外れる条件**: 差異の中身が変わった（金額・開始日・対象が確認時と違う）／見直す日を過ぎた／確認した人が取り消した。外れたら「未確認」に戻る。
- **本部タスクとの関係**: 確認済みのあいだは、まとめのタスクのチェック項目からは外す（対応不要と判断したため）。見直す日が来たら、また載る。
- **だれが確認できるか**: 本部・社長・マスター。自分自身に関する差異は、別の人の確認を必須にする（申請の自己承認禁止と同じ考え方）。給与に関わる差異の確認は、承認ルール（§14）に合わせて社長の確認を必要にするかを決める。
- **履歴**: 確認・取り消し・自動で外れた、をすべて残す。

### 17.3 新しく必要なもの

**DB**
- 承認ルートの設定表（例 `approval_routes`）: 申請の種類ごとに、段階の並び（段階の名前・承認できる役割または指定の人・通知先のチャンネル・期限の時間）、自己承認を許すか、Slack に出してよい項目、リマインドの設定（何時間後から・何時間おき・最大回数・夜間は送らない）。
- 承認の案件表（例 `approval_cases`）: 申請 1 件につき 1 行。どの申請か（既存の表と行への参照）・対象の従業員・申請者・いまの段階・状態（承認待ち／差し戻し／承認／却下／取り下げ）・段階の期限・Slack の親メッセージの控え・最後にリマインドした時刻と回数。**既存の申請の表は作り替えず、この表が「共通の見出し」になる。**
- 承認の操作履歴（例 `approval_actions`）: 案件・段階・操作（申請／本部確認／承認／却下／差し戻し／再申請／取り下げ／リマインド）・操作した人・どこから（管理画面／ポータル／Slack／自動）・コメント・日時。
- 既存の表への追加は最小限（賃金・口座の申請に「差し戻し」の状態を足す程度）。

**API（DB の関数と Edge Function）**
- 権限判定の関数 1 つ（その人が、その案件の、いまの段階を操作できるか。自己承認の禁止・社長の役割の確認・マスターでも省略不可、をここだけで判定）。
- 操作の関数 1 つ（確認／承認／却下／差し戻し／再申請／取り下げ）。最後の段階の承認のときだけ、種類ごとの既存の確定処理（賃金登録・口座の反映・退職の承認など）を呼ぶ。
- 一覧の関数（段階ごとの未処理件数・経過時間・期限超過）。同期・承認の状況の一覧（ステップ 4）に統合する。
- 承認カードの送信・更新（`onboarding-notify` と同じ作りの関数。送信は `notify-slack` 経由）。Slack の操作の受付は `slack-interact` に `approval.*` の操作を足す。
- リマインド（既存の毎時の `pending-reminders` に、期限を過ぎた案件の確認を足す）。送れなかった通知の再送（台帳で失敗になっているものを、同じ重複防止の鍵で送り直す）。

**画面**
- nippo: 承認カードを 2 段階に対応（本部確認／社長の最終承認／差し戻し）。未承認の一覧（段階ごとの件数・期限超過）。
- ポータルの承認画面: 差し戻しと再申請。
- 設定の画面は後回し（最初は設定表を SQL で入れる）。

### 17.4 共通承認基盤の推奨設計

1. **正本は管理システム**。案件・段階・履歴は DB に先に書き、Slack への通知はそのあと。通知が失敗しても案件は残り、一覧とリマインドで拾える。
2. **判定は 1 か所**。管理画面・ポータル・Slack のどこから操作しても同じ関数を通る。Slack のボタンは「だれが押したか」を管理システムの従業員に照合してから判定する。
3. **既存の確定処理を包む**。新しい基盤は「だれが・いつ・どの段階で」を担当し、確定の中身（賃金登録・適用開始日・スマレジ同期・口座の支給回・振込の安全対策・変更履歴）は既存の関数をそのまま呼ぶ。
4. **種類ごとの初期ルート**: 口座・住所・最寄り駅・交通費・所属店舗・退職＝本部の 1 段階。賃金・手当＝本部確認 → 社長の最終承認の 2 段階（本部確認だけでは確定しない。マスターでも省略不可）。
5. **入社時の初期賃金登録は別扱い**。入社手続き中の人・その契約の初回の登録は、いまの入社フロー（Slack の賃金設定）のまま通す（判定は既存の「初期登録・入社手続き中」の関数を使う）。
6. **社長本人の賃金・役員報酬**は例外ルートを別途設計（§14.4。正式な決定手続きの証跡を必須にし、代理の承認者を単純に固定しない）。方針が決まるまで実装しない。それまで、対象が社長本人の賃金申請は「受け付けず、案内を出す」にしておくのが安全。
7. **段階ごとの期限とリマインド**: 期限は設定表から。期限を過ぎたものだけ、設定した間隔でリマインド（同じ親メッセージのスレッドに投稿し、承認できる人に知らせる）。承認・却下・取り下げで止まる。回数の上限あり。
8. **重複防止**: 案件×段階×出来事ごとに 1 つの鍵。同じ通知は 2 回作らない。親メッセージは案件ごとに 1 件で、状態が変わるたびに更新。

### 17.5 2 チャンネルでの通知・承認の流れ

**通常の人事申請（1 段階）**
1. 申請（本人: ポータル／将来は DM。本部: 管理画面）→ 案件を登録。
2. #本部-人事 に承認カード（親メッセージ 1 件）: 種類・対象の従業員・所属店舗・申請日・適用開始日・いまの段階・期限・状態。ボタン: 承認／却下／差し戻し／管理画面で確認。
3. 本部の承認権限者が操作 → 権限判定 → 既存の確定処理 → 親メッセージを「承認済み（だれが・いつ）」に更新 → 本人へ結果を通知（DM。未紐付けなら既存の連絡手段）。

**賃金変更（2 段階）**
1. 申請 → #本部-人事 に「本部確認の依頼」カード。
2. 本部が確認（申請者と別の人）→ この時点では賃金は変わらない。#本部-人事 のカードを「本部確認済み（だれが・いつ）・社長の承認待ち」に更新。
3. **#本部-重要承認 に親メッセージ 1 件**（同じ項目＋本部確認者。金額は載せない）。ボタン: 最終承認／却下／差し戻し／管理画面で確認。
4. 社長が最終承認 → 権限判定（社長の役割の本人だけ）→ 既存の賃金登録 → スマレジ同期 → 親メッセージを「承認済み（社長・日時）」に更新、同期結果をスレッドに追記 → 申請者へ結果を通知。
5. 却下・差し戻しは理由が必須。差し戻しは申請者へ戻り、直して再申請すると同じ案件のまま本部確認からやり直し（履歴は残る）。

**共通**: 期限超過 → 該当スレッドにリマインド。通知の失敗 → 案件は残り、台帳から再送。Slack で押した人に権限が無いときは、その人だけに「権限がありません」と返す。

### 17.6 実装の順序と規模（目安。1 単位＝これまでのステップ 1 つぶん程度）

| 段階 | 内容 | 規模 | まとめて作るもの |

| 第 1 段階 | 共通承認基盤（設定表・案件・操作履歴・権限判定・操作の関数）と、賃金変更の 2 段階承認（nippo の承認カード対応・未承認の一覧の最小版・入社時の初期登録の区別・社長本人は受付停止） | 大（1.5〜2 単位） | 差し戻しの状態・期限の列・リマインドの設定欄は、最初から表に入れておく（あとで作り直さない） |
| 第 2 段階 | #本部-重要承認 への通知・承認（親メッセージ・更新・スレッド・ボタン）と、#本部-人事 の承認カードの整理 | 中（1 単位） | カードの組み立ては種類共通の 1 つにする。重複防止・再送もここで |

### 18.3 承認期限と、給与の締め前の注意（設計）

- 給与は末日締め・翌月 15 日払い。賃金変更の「締め日」は、適用開始月の末日。

## 21. スマレジ側の賃金の直接変更への対策（設計。2026-11-11。★未実装・別途承認）

### 21.0 前提: 「検知できること」と「給与への反映を防げること」は別

- 給与計算はスマレジの賃金で行われる。管理システムが取り込みを保留しても、スマレジに行が残っているかぎり給与計算には効く。
- 管理システムにできることは 3 つの段階に分かれる。

| 段階 | 中身 | 給与への反映を防げるか |
|---|---|---|
| ① 検知 | スマレジと管理システムを比べて、違いを見つけて知らせる | 防げない（気づくだけ） |
| ② 是正 | 締めの前に、スマレジを承認済みの値に戻す（または、正式に申請して社長の承認を取る） | 締めの前に済めば防げる。スマレジへの書き込みなので、人の操作で行う |
| ③ 関所 | 給料確定の前に「未解決の未承認変更」があれば止める・警告する | 間違った金額のまま確定・振込に進むのを防げる（スマレジの計算結果そのものは変えない） |

- 根本の予防は、スマレジ側の権限の制限（21.5）。管理システムからは防げない。

### 21.1 未承認の行を、自動で正式な賃金にしない

いま: 取り込み（一括・1 人ずつ）は、管理システムに無い行を「同期済み」としてそのまま追加する。

変更案
- 自動で追加するのは**初期投入だけ**にする。条件: その人のその契約の賃金が管理システムに 1 件も無い、かつ（入社手続き中、または、その契約へのスマレジ連携が出来てから 14 日以内）。入社時の初期賃金登録と、移籍・兼務で新しい契約に入った直後の取り込みは、これまでどおり通る。
- それ以外で見つかった「スマレジにだけある行」は、正式な賃金にせず、**外部変更の控え**（新しい表。案 `wage_external_changes`）に「未承認」として記録する。記録するもの: 従業員・契約・区分・店舗・適用開始日・見つけた日時・スマレジの値・管理システムの値（あれば）・種類（新しい行／金額の違い／行の削除）・状態。
- 状態と出口は 3 つ（どれも本部の操作。自動では決めない）。

| 出口 | 中身 | そのあと |
|---|---|---|
| 正式な申請に載せる | 控えから賃金変更の申請を作る（金額・適用開始日は控えから入る）→ 本部確認 → 社長の最終承認 | 承認されたら、管理システムに正式な行として登録（スマレジには既に同じ行があるので、送り直さずに結び付けるだけ）。却下されたら「スマレジを戻す」へ |
| スマレジを戻す | 新しい行は削除、金額の違いは管理システムの値で上書き（既存の修正・削除の処理を使う。スマレジへの書き込み） | 控えを「是正済み」に。履歴に残す |
| 対象外として閉じる | 過去の履歴の行など、給与に関係しないもの。理由が必須 | §15 の「確認済みの差異」と同じ扱い |

- 承認済みの賃金のスマレジ同期（管理システム → スマレジ）は変えない。管理システムが送った行は、スマレジ側の番号で結び付いているので、未承認とは区別できる。送信待ち・送信エラーの行は、これまでどおり「未同期」「同期エラー」で、外部変更にはしない。

### 21.2 定期の照合

- 毎日 1 回（朝）、全契約の在職者ぶんを読み取りだけで照合する（スマレジには書かない）。既存の一括取り込みと同じ読み方を使い、人数を小分けにして処理する。
- 給料確定の画面を開いたとき・締め日の前日にも照合する（21.4）。
- 照合の記録（いつ・何人・違いが何件）は、既存の照合の記録に残す。照合が 2 日以上できていないときは「照合が古い」を要対応に出す。

### 21.3 検知できる範囲

| スマレジ側の操作 | 検知 | 補足 |
|---|---|---|
| 時給・月給の金額の書き換え（適用開始日は同じ） | できる（いまも可。定期化する） | 「金額の違い」 |
| 時給・月給の新しい適用開始日の行の追加 | できる（21.1 で保留に変える） | 「新しい行」 |
| 時給・月給の行の削除 | できる（追加が必要） | 管理システムで同期済みの「いま有効・これから適用」の行が、スマレジに無い |
| 日給 | できる（追加が必要） | 読み方は同じ。一括の照合の対象に足す |
| 営業時間帯別の賃金・固定残業代 | 変化は検知できる（追加が必要） | 管理システムに正本が無いので「承認済みと違う」ではなく「前回の照合から変わった」として出す。前回の控えを持つ |
| 過去の適用開始日の行（履歴）の書き換え | 一部（追加が必要） | 管理システムにある行は比べられる。無い行は「前回から変わった」で出す |
| 各種手当の金額 | **設定の段階では未確認**（スマレジの読み取りで手当の設定が取れるかを調べる必要あり） | 取れない場合の代わり: 給与計算の結果（毎月の取込に、手当の合計・固定残業代・通勤手当が入っている）を前月と比べ、変わった人を出す。これは給与計算のあとの検知になる |
| だれがスマレジで変えたか | できない | スマレジの読み取りでは分からない。スマレジ側の操作履歴で確認する運用 |

### 21.8 給与確定・振込の停止（★2026-11-11 夕方 ユーザー確定の方針による設計）

方針: 未承認の賃金変更が見つかったら、原則として給与確定・振込を止める。ただし全員を止めるのではなく、影響する従業員と対象の月を特定して、その人だけを保留する。安全に分けられないときは全体を止める。例外の解除は、社長の承認・理由・操作履歴が必須（本部担当者が理由を入れるだけでは解除できない）。

**だれを・どの月を保留するか**
- 対象の人: 外部変更の控え（§21.1）に、未解決の行がある従業員。
- 対象の月: その行が効く月。新しい行・金額の違い＝適用開始日が月末以前の、まだ支給が済んでいない月すべて／行の削除＝まだ支給が済んでいない月すべて。
- 保留の記録: 既存の「振込データからの除外」の仕組み（人×月の保留・本部タスク・振込漏れの防止）を、理由つきで使えるように広げる（理由: 口座変更の承認待ち／未承認の賃金変更）。

**保留された人に起きること（管理システムで制御できる範囲）**

| 処理 | 単位 | 保留中の動き |
|---|---|---|
| 振込データ（CSV） | 人ごと | その人を入れない。本部タスク（振込漏れ防止）と「対応が必要」を出す。既存の除外と同じ動き |
| 現金手渡し | 人ごと | 一覧に「保留中」と出し、手渡しの完了（サイン）を受け付けない |
| 給料確定 | 法人×月（人ごとには分かれていない） | 確定は進められるが、保留の人は「未確定」として残す（確定の記録に保留の人数、作られる本部タスクの項目に「保留」）。保留が解けたら、その人の分だけ追って確定する。**この「人ごとに残す」作りが既存の給料確定・給与仕訳に安全に入れられるかは、実装の前に確認する。入れられない場合は、その法人の給料確定を止める** |

**全体を止める場合（安全に分けられないとき）**
- その法人の契約の照合が、給料確定の前 24 時間以内に成功していない（照合の失敗・古い）。だれに影響があるか分からないため。
- 見つかった違いを従業員に結び付けられない（スマレジのスタッフと管理システムの従業員の対応が無い・店舗の対応が無い）。
- 照合で読めなかった人が多い（目安: 対象の 2 割を超える）。少数なら、読めなかった人だけを保留する。
- 止めるのは、その法人のその月の給料確定と、その月の振込データの出力。ほかの法人・ほかの月は止めない。

**解除**

| 解除のしかた | 条件 |
|---|---|
| 正式な申請が最終承認された | 賃金変更の申請（本部確認 → 社長の最終承認）が通り、正式な賃金として登録された |
| スマレジを戻した | 本部が「スマレジを戻す」を行い、そのあとの照合で一致を確認できた |
| 対象外として閉じる | **社長の承認が必須**（理由つき）。本部だけでは閉じられない |
| 例外の解除（未解決のまま、その月だけ進める） | **社長の承認が必須**（理由つき）。共通承認基盤に種類を 1 つ足す（1 段階・社長の役割だけ・マスターでの代用なし・申請した本部の人と理由・承認者・日時が履歴に残る）。解除はその人のその月だけ。未解決の控えは残り、次の月はまた保留になる |

**どこまで制御できるか**

| もの | 管理システムで止められるか |
|---|---|
| 給料確定の印・給料の本部タスクの作成 | 止められる |
| 振込データ（CSV）への掲載 | 止められる（人ごと） |
| 現金手渡しの一覧・完了 | 止められる（人ごと） |
| 給与仕訳の作成 | 給料確定のあとに動くので、確定を止めれば止まる。人ごとに外せるかは実装の前に確認 |
| **スマレジの給与計算そのもの** | **止められない**。スマレジの賃金で計算される |
| **スマレジの Web 給与明細（本人が見る金額）** | **止められない**。スマレジ側の公開の操作・設定による |
| スマレジから出したデータを使った別の経路の振込・銀行での手作業の振込 | 止められない |

- つまり、管理システムの停止は「間違った金額のまま、管理システムの確定・振込・手渡しに進まない」ための関所。スマレジの計算結果と明細を正しくするには、締めの前にスマレジ側を是正する（戻す・または正式に承認して一致させる）しかない。
- 運用で補うこと: スマレジで給与を締める・明細を公開する前に、管理システムの「締め前の確認」が 0 件であることを見る手順にする。
