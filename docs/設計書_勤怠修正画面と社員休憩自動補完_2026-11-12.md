## 1. いまの作り（調査の結果）

勤怠修正の入口は 2 つあります。どちらも「申請 → マスターの承認 → 管理システムに反映 → スマレジへ書き戻し」の同じ流れです。

| 入口 | どこ | 並び | 休憩 |
|---|---|---|---|
| Slack の入力画面 | #勤怠確認 の「× 修正する」で開く（`slack-interact` の `attendance.fix.modal`） | **縦 1 列**（出勤・退勤・休憩 1 開始・休憩 1 終了・休憩 2 開始・休憩 2 終了・休憩なし・理由） | 開始と終了の日時を 2 組まで |
| ポータルのフォーム | `kintai.html` | **すでに 2 列**（出勤｜退勤、休憩 1 開始｜終了、休憩 2 開始｜終了） | 時刻だけ入力。出勤より早い時刻は翌日とみなす |

- 「縦に並んで見づらい」のは Slack の入力画面です。
- Slack の入力画面は、入力欄を横に並べられません（Slack の仕様。入力欄は 1 つずつ縦に積まれます）。
- 休憩は、管理システム（`labor_cost_daily`）もスマレジも「開始・終了の時刻を 2 回まで」で持っています。
- 承認されると、Edge Function `smaregi-attendance-fix` がスマレジへ書き戻します（出勤・退勤・休憩 1・休憩 2 を 1 回で送る）。
- スマレジ側で直接直された勤怠は、毎朝の取り込みで検知して #勤怠確認 に出します。

調査で見つけた不具合（今回は直していません）: `slack-interact` の修正申請の通知で、コメントの書き方のミスにより `ref`・表示名・アイコンの指定が送られていません（177 行目。動作には影響が小さいが、通知と申請の結び付けが台帳に残らない）。

## 2. 勤怠修正画面の変更案

### 2.1 方針（おすすめ）

**修正の入力は、ポータルのフォームに一本化し、そこを新しい 2 列レイアウトにします。** Slack の「× 修正する」は、対象の勤怠が選ばれた状態でフォームを開くボタンにします。

| 案 | 中身 | 良い点 | 弱い点 |
|---|---|---|---|
| A（おすすめ） | Slack の「× 修正する」→ フォーム（2 列）を開く。入力はフォームで | 希望どおりの 2 列。修正前後を並べて見せられる。スマホでも見やすい | Slack から画面が切り替わる。ポータルへのログインが要る |
| B | Slack の入力画面のまま、見やすく整理する | Slack の中で完結 | 2 列にはできない（縦 4 行＋理由になる） |
| C | A ＋ B の両方を残す | 好きなほうを使える | 2 つの画面を保守する |

### 2.2 画面の仕様（A 案のフォーム）

- 1 行目: 出勤｜退勤。2 行目: 休憩開始｜休憩終了。スマホでも 2 列のまま。
- 入力は時刻だけ。日付は対象の勤務日から決めます。
- 日付またぎ: 出勤より早い時刻を入れると、自動で「翌日」のしるしが付きます。しるしは押して切り替えられます（出勤が前日になる場合にも対応）。
- 各欄の下に「修正前」の値を小さく出します。変えた欄は色を付け、「修正前 → 修正後」を出します。
- 休憩 2 回目は「休憩をもう 1 回」を押したときだけ出します。「休憩なしにする」も 1 押しで。
- 下に「勤務 − 休憩 ＝ 実働」と、修正前の実働を出します。
- 理由と「修正を申請する」。

### 2.3 変えるところ・変えないところ

| もの | 扱い |
|---|---|
| 申請・承認・履歴の関数（`sf_attendance_fix_request`・`sf_attendance_request_submit`・`…_decide`） | 変えない。検査（退勤は出勤より後・24 時間以内・休憩は勤務の内側など）もそのまま |
| スマレジへの書き戻し（`smaregi-attendance-fix`） | 変えない |
| フォーム `kintai.html` | 並びと入力欄を作り替える（翌日のしるし・修正前後の表示・実働の計算） |
| 受け口 `attendance-request` | 「異常値アラートからの修正」をフォームから出せるように、アラートの番号を受ける口を 1 つ足す |
| Slack の「× 修正する」 | フォームを開くボタンに変える（A 案）。ボタンの名前（`action_id`）は変えない方針に合わせ、開く先だけ変える |
| 規模 | 1 単位弱（フォーム 0.5・受け口と Slack の差し替え 0.3・テスト） |

## 3. 社員の休憩時間の自動補完

### 3.1 先に確かめたこと: スマレジの API

**休憩の開始・終了の時刻は、API で登録・更新できます。**

| 項目 | 結果 |
|---|---|
| 使う API | 勤怠更新 `PUT /timecard/shifts/{勤怠の番号}`（実績）。休憩は `breakStartTime1`・`breakEndTime1`・`breakStartTime2`・`breakEndTime2` |
| 権限（スコープ） | 取得済みの `timecard.shifts:write` で足りる |
| いまの利用 | 勤怠修正の書き戻しで、同じ API を本番で使っている |
| 休憩の回数 | 1 勤務 2 回まで。分数だけの指定はできない（時刻が要る） |
| 出勤・退勤 | 必須（退勤前の勤務には使えない）。休憩だけ足すときも、出勤・退勤を送り直す |
| 締め済みの月 | 更新できない（409）。締めの解除はスマレジの管理画面だけ |
| 回数の制限 | 更新は 1 秒 20 回まで（1 日数件なので問題なし） |
| 代わりの方法 | 不要（Mac mini の自動操作に勤怠を直す操作は無く、作る必要もない） |

実機で確かめる必要が残る点（実装の最初に、テスト用の勤怠で確認。承認が要る）:
- 休憩つきの更新が本番で通った明示の記録がない（勤怠修正 2 件は成功しているが、休憩を含んでいたか不明）。
- 休憩が日付をまたぐとき。
- **スマレジ側の「休憩時間の自動設定」がいま有効かどうか**（有効だと二重に休憩が引かれるおそれ。管理画面で確認が必要）。

参考: スマレジには標準の「休憩時間の自動設定」（勤務 n 時間以上で m 分など）があります。設定だけで済みますが、過去の実績には効かず、推定と実績の区別・例外の申告・履歴は管理システムで持てません。今回の要件（区別・履歴・例外）は、管理システム側の補完で満たす設計にします。

### 3.2 いまの勤務の実態（直近 90 日・社員と店長 10 人・359 勤務）

| 出勤から退勤まで | 勤務数 | 休憩の登録あり | 休憩の登録なし |
|---|---|---|---|
| 8 時間超 | 341（95%） | 38 | **303（89%）** |
| 6 時間超〜8 時間以下 | 14（4%） | 0 | 14 |
| 6 時間以下 | 4（1%） | 1 | 3 |

- 登録されている休憩は平均 53 分。45〜59 分が 27 件、60 分以上が 7 件、45 分未満が 4 件。
- 2 回に分けた休憩の登録は 0 件。
- 自動補完の対象は、1 日あたり 3〜4 件の見込みです。

### 3.3 補完のルール

| 項目 | 決めること |
|---|---|
| 対象の人 | 役割が社員・店長。アルバイトは対象外 |
| 対象の勤務 | 退勤まで済んでいる／休憩が 1 つも登録されていない／当月でスマレジの締め前 |
| 8 時間超 | 60 分を補完 |
| 6 時間超〜8 時間以下 | **45 分を補完（提案）**。法定の最低が 45 分で、取っていない休憩を多く引かないため。「60 分にする」「補完せず本部に確認を回す」も選べます（4. の確認事項） |
| 6 時間以下 | 補完しない |
| 補完しない場合 | すでに休憩がある（上書きしない）／休憩を取っていない・短かったという申告がある／その勤怠に修正の申請・異常値の確認が出ている／人が直した勤怠／すでに補完済み |
| 社員ごとの分数の設定 | 作らない |

休憩時刻の決め方（推定）:
1. 実際の時刻が分かっていれば、それを使う（打刻・修正の申請・本人の申告）。
2. 分からないときは、勤務時間の中で 1 つ作る。置き場所は「勤務の中央」。ただし、出勤から 1 時間以内・退勤まで 1 時間以内・深夜（22 時〜翌 5 時）には置かない（深夜の割増が減るのを避けるため）。
3. 作った時刻は「推定」として記録し、実際の時刻と区別する。

### 3.4 持つデータ

| もの | 中身 |
|---|---|
| 休憩の出どころ（勤怠ごと） | 打刻／修正の申請／本人の申告／自動補完（推定） |
| 補完の履歴（新しい表） | 勤怠の番号（1 勤怠 1 行＝二重登録を防ぐ）・補完の前後・使ったルール・処理の種類・日時・同期の状態（未同期／同期済み／エラー／競合）・スマレジの応答 |
| 例外の申告（新しい表） | 人・勤務日・種類（休憩なし／短縮）・実際の分数や時刻・理由・だれがいつ申告したか |

### 3.5 処理の流れ

1. 毎朝の取り込みのあと、対象の勤務を選ぶ（3.3 の条件）。
2. スマレジの最新の勤怠を読み直す。休憩が入っていた・時刻が変わっていたら、補完しない（競合として記録）。
3. スマレジへ、出勤・退勤はそのまま、休憩 1 に推定の時刻を入れて更新する。
4. 読み直して、入ったことを確かめる。
5. 成功したら、管理システムの勤怠にも同じ値を入れ、出どころを「自動補完（推定）」にする。**ここまで通知も承認もなし。**
6. 失敗・競合・締め済みのときだけ、本部タスクに 1 件まとめて出す（Slack には個別に出さない）。

- 5. で管理システムにも同じ値を入れるので、次の取り込みで「スマレジ側で直接直された」という通知は出ません。
- あとから実際の時刻が分かったら、勤怠修正（2. のフォーム）で直します。出どころは「修正の申請」に変わり、補完の履歴には「置き換えられた」と残ります。
- スマレジ側で休憩が直されたら、次の取り込みで検知します。補完の履歴は「競合」になり、スマレジの値を正とします。

### 3.6 給与計算との関係

- 給与はスマレジが計算します。休憩を入れると実働が減り、残業・深夜の時間が変わります。
- そのため: 締め前の当月だけを対象にする／深夜には置かない／取っていない休憩を引かない（申告を優先）／過去の月の一括修正はしない（別途承認）。
- 303 件の未登録（過去 90 日）のうち、10 月以前の分は給与の計算が済んでいます。さかのぼるかどうかは、労務の判断が要ります。

### 3.7 規模

| 段階 | 中身 | 規模 |
|---|---|---|
| 1 | 実機の確認（テスト用の勤怠で、休憩つきの更新・日付またぎ・スマレジ側の自動設定の有無） | 0.2 |
| 2 | 表 2 つ・補完の判定と推定（試し実行＝何も書かずに候補だけ出す）・例外の申告の入口 | 0.7 |
| 3 | スマレジへの同期・読み直し・競合の検知・本部タスク | 0.6 |
| 4 | 毎朝の自動実行（スイッチで有効化）と、1 週間の並行確認 | 0.3 |

## 5. 決めていただきたいこと

1. 勤怠修正画面は A 案（フォームに一本化）でよいか。Slack の入力画面は残すか。
2. 6 時間超〜8 時間以下の勤務は、45 分の補完でよいか。
3. 推定の休憩の置き場所は「勤務の中央（深夜を避ける）」でよいか。店舗ごとの決まった休憩の時間帯があれば、それを優先できます。
4. 過去の月（締め済み・給与計算済み）は対象外でよいか。
5. 例外の申告の入口はどこにするか（フォームに「休憩を取っていない／短かった」を足す案）。
6. スマレジの管理画面で「休憩時間の自動設定」がいま有効かどうかの確認（こちらからは見えません）。


## 6. 確定した仕様と実装: 社員の休憩の自動補完（2026-11-11 夜。実装・テスト済み。★本番未適用・未デプロイ・設定は無効）

ユーザーの決定: 45 分と 60 分に分けない。**6 時間を超える勤務で休憩が未登録なら、60 分を補完する。** 対象は社員・店長。

### 6.1 作ったもの

| もの | 中身 |
|---|---|
| SQL `supabase/2026-11-13_break_autofill.sql`（戻し `…_rollback.sql`） | 補完の履歴（1 勤怠 1 行）・例外の申告・対象の判定（1 か所）・記録の関数・置き換えの検知・本部タスク・状況。既存の表と関数は作り替えない |
| 判定と推定の部品 `_shared/break-autofill.ts` | 推定の時刻の決め方／スマレジのいまの実績を見た可否の判断／送る中身／書いたあとの確認 |
| Edge Function `attendance-break-autofill`（新規） | 対象を選ぶ → スマレジを読み直す → 既存の勤怠更新の API で休憩 1 を入れる → 読み直して確認 → 管理システムにも同じ値を入れる |
| 設定 `app_settings.attendance_break_autofill` | `enabled`（既定 false）・対象の役割・6 時間・60 分・さかのぼる日数 35・1 回の上限 30・再試行 3 回・`smaregi_auto_break_confirmed_off`（既定 false） |

### 6.2 補完する・しない

| 条件 | 扱い |
|---|---|
| 社員・店長／6 時間を超える／休憩が 1 つも無い／きのうまでの勤務 | 60 分を補完 |
| 休憩が登録されている | 補完しない（上書きしない） |
| 休憩を取っていない・短かったという申告がある日 | 補完しない |
| 人が直した勤怠・確認待ちの申請やアラートがある勤怠 | 補完しない |
| 給与確定済みの月 | 補完しない |
| スマレジ側で勤務時間が引かれている疑い（休憩の時刻は無いのに、勤務時間が 30 分以上短い） | 補完しない（二重控除の防止）。本部タスクへ |
| 深夜（22 時〜翌 5 時）を避けて休憩を置けない | 補完しない。本部タスクへ |
| スマレジの勤怠が締め済み（409） | 補完しない。本部タスクへ |
| アルバイト・6 時間以下・今日の勤務 | 対象外 |

推定の時刻: 勤務の中央（5 分きざみ）。出勤から 1 時間以内・退勤まで 1 時間以内には置かない。深夜にかかるときは、深夜の前（〜22 時）か後（5 時〜）に寄せる。

### 6.3 二重登録・二重控除・同期の繰り返しを防ぐしくみ

| 心配 | 防ぎ方 |
|---|---|
| 同じ勤怠に 2 回入る | 履歴は 1 勤怠 1 行。始めるときに勤怠の行をロックして条件を確かめ直す。書く直前にスマレジを読み直し、休憩があれば書かない |
| スマレジ側の自動休憩と二重に引く | 実行のたびにスマレジの設定（事業所・従業員区分）を読み、有効なものがあれば止まる。読めないときは、人が確認した印が無ければ動かない。勤怠ごとにも、勤務時間が引かれていないかを見る |
| 補完 → 取り込みで「スマレジ側で直された」と検知 → 通知、の繰り返し | 成功したら、管理システムの勤怠にも同じ値（スマレジの読み直しの勤務時間・概算人件費）を入れるので、次の取り込みで違いが出ない |
| 途中で止まった同期 | 30 分後に失敗として扱い、再試行（3 回まで）。スマレジに入っていた場合は、次の取り込みで休憩が入り、対象から外れる |

### 6.4 推定と実際の区別・あとからの訂正

- 補完した休憩は、履歴に「推定」として残る（補完の前の値・使ったルール・日時・同期の結果つき）。関数 `attendance_break_source` で、その勤怠の休憩が「推定／実際の値／なし」のどれかが分かる。
- 実際の時刻が違うときは、勤怠修正のフォームで直す（社員本人・権限のある人）。直されると、履歴は「置き換えられた」になる。スマレジ側で直された場合も同じ。
- すでに補完した日に「休憩を取っていない」と申告があったときは、自動では消さず、勤怠修正を案内する。

### 6.5 通知

通常の補完は、Slack にも本部タスクにも出さない。同期の失敗（3 回）・競合・例外だけを、その日の分 1 件にまとめて本部タスクに出す（本部と社長にだけ見える・金額なし）。

### 6.6 テスト

- 判定と推定の部品: 5 件 OK（6 時間ちょうどは対象外・中央・端の 1 時間・深夜の回避・スマレジの実績による可否・送る中身）。
