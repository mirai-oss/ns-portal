# 調査レポート: D-8 AIエージェント窓口（LINE・Mac mini常駐）候補A/B比較

作成: 2026-08-31 ／ 担当D ／ 状態: **調査完了・候補B（自作LINE bot）を推奨**

## 0. 重要な訂正（要件定義書§18の参照先について）

**`要件定義書.md`§18が参照している`hermes-agent.org`は、Nous Researchの公式サイトではない**（同サイト自身が利用規約に「Nous Researchとは提携していない独立した非公式情報サイト」と明記）。

- Hermes Agent本体は実在・活発なプロジェクト（GitHub `NousResearch/hermes-agent`・MIT・★238,688・Fork 48,633・2026-08-31時点でも直近コミットあり）
- **正しい公式サイトは`hermes-agent.nousresearch.com`**。今後Hermes Agentを検討する際は、この公式ドメインから直接情報・インストーラーを取得すること（非公式サイト経由の案内は鵜呑みにしない）

この訂正を踏まえ、以下は公式ソースに基づき調査し直した内容。

## 1. 候補A: Hermes Agent（公式情報に基づく再調査）

| 項目 | 内容 |
|---|---|
| MCP対応 | **対応**（stdio/HTTP両対応・OAuth対応のネイティブMCPクライアント標準搭載） |
| LINE連携 | **公式に対応**（`LINE Setup`ドキュメントあり）。ただし**Webhook方式が前提**（後述） |
| 権限制御 | 3段階認可（許可リスト→ペアリング承認）＋危険コマンド承認フロー＋Dockerコンテナ隔離の多層防御 |
| モデル自由度 | Claude/OpenAI/Gemini/OpenRouter/Bedrock/Ollama等、極めて広い |
| コスト | 本体無料（MIT）。裏側で使うLLMのトークン課金は別途発生（候補Bと同条件） |
| サブエージェント・Cron | 両方標準搭載 |
| 懸念点 | Open Issues 38,000件超（発展途上）。日本固有サービス（マネーフォワード・GBP等）の標準連携は未確認 |

**最大の技術的制約**: LINE連携はLINE公式仕様どおり**Webhook必須**（後述§2）。Mac miniは公開URLを持てないため、**Cloudflare Tunnel/ngrok等で外部公開する仕組みが別途必要**になる（既存の`lark-listener.js`が採用している「トークンでポーリング」方式は、Hermes AgentのLINE連携には用意されていない）。

## 2. LINE Messaging APIの基本仕様（確認事項）

| 論点 | 結果 |
|---|---|
| Webhook必須か | **はい**。LINEはHTTPS POSTで配信するプッシュ型のみで、受信用のポーリングAPIは無い |
| Mac miniでの受信方法 | 公開URLが無いため、①トンネル(Cloudflare Tunnel/ngrok)を張るか、②**既に公開HTTPSを持つ`line-webhook`（Supabase Edge Function）を中継役にし、Mac mini側はSupabaseへポーリングする**、のいずれかが必要 |
| 複数アカウント | 1事業者で最大100個まで作成可・プラン/無料枠もアカウントごとに独立 |
| 無料枠 | Push APIは月200通まで無料。Webhook受信後すぐ返す「Reply API」は無料枠を消費しない（今回のような少人数運用なら実務上枠超過は考えにくい） |

## 3. 既存LINE窓口（応募者・シフトリマインド用）との分離

**新しい別のLINE公式アカウントを新設し、AIエージェント専用窓口として分離することを推奨**。理由:
1. 応募者対応・シフトリマインドの会話と、社長・本部のMac mini操作指示が混線する
2. 既存の本番稼働中`line-webhook`（`ns-portal/supabase/functions/line-webhook/index.ts`）へ手を加えると、応募者対応・リマインド機能への回帰リスクがある
3. 管理者専用の高権限操作窓口と、公開性の高い窓口を分けるのが最小権限の原則に沿う

複数アカウントはコスト・技術的障壁がほぼ無いため、分離のデメリットは小さい。

## 4. 比較表

| 比較軸 | 候補A: Hermes Agent | 候補B: 自作LINE bot（既存Mac mini基盤の拡張） |
|---|---|---|
| 接続性 | 公式LINE対応だがトンネル必須 | 既存`line-webhook`を中継にすればMac miniは非公開のまま実現可 |
| セキュリティ | 標準で多層防御 | ゼロから設計だが要件を絞れる。署名検証は既存コード流用可 |
| MCP・API対応 | ネイティブ標準搭載 | 自前実装（Claude Agent SDKなら比較的容易） |
| モデル自由度 | 非常に広い | Claude API固定を想定（要件通り） |
| コスト | 本体無料＋LLM課金 | 開発工数はかかるが既存基盤（Supabase）を流用しやすい |
| 保守性 | 開発は活発だがIssue多数・非公式情報が混在しがち | 社内で全コード把握・`lark-listener.js`と同じ設計パターンを流用可能 |
| スケジュール実行 | Cron内蔵 | 自前実装だが既存タスク運用のノウハウあり |
| サブエージェント | 標準対応 | 自作コスト増だが実装可能 |
| 権限制御 | 標準で3段階認可 | 自前実装だが範囲を絞れる |

## 5. 結論・推奨

**候補B（自作LINE bot・既存Mac mini基盤の拡張）を推奨。**

1. **既存資産との親和性**: `lark-listener.js`の設計（ポーリング／コマンド解析／タスクメニュー／結果返信）をほぼ流用できる。既存の`line-webhook`をLarkの窓口役に見立て、Webhook受信→Supabaseテーブル書き込み→Mac miniがポーリング、という構成にすれば、**Mac miniを公開URL化しない方針を崩さずに実現できる**（Hermes Agentのトンネル必須構成より社内方針に沿う）
2. **Claude Code環境との親和性**: 既に慣れているClaude Agent SDK/APIをそのまま使え、Hermes Agentという別エコシステム（Python製・独自設定体系）を新たに学習・保守するコストを避けられる
3. **将来拡張性**: Supabase中心の設計にすれば、他システム（nippo等）と同じデータ基盤にAIエージェント窓口も自然に統合できる。マネーフォワード等日本固有連携がHermes AgentのMCPカタログに標準搭載されている確証は無く、結局自作連携が必要になる可能性が高い
4. **運用負荷・情報の信頼性**: 参照元だった`hermes-agent.org`が非公式サイトだった事実（§0）は、情報の裏取りコストと運用リスクの両面で無視できない

一方でHermes Agentのサブエージェント・多層防御・Cron内蔵は魅力的であり、**将来AIエージェント窓口の対象が大きく増え自作の保守が追いつかなくなった場合の「次の選択肢」として、公式版Hermes Agentを再評価する価値はある**。
