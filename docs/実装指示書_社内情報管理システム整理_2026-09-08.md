## 2. C-1 期限の強化と自動生成（担当F）

### 2.1 マイグレーション `ns-info-system/supabase/2026-09-XX_deadlines_v2.sql`

```sql
alter table info.deadlines
  add column if not exists kind text not null default 'other'
    check (kind in ('lease_renewal','lease_notice','business_license','late_night_liquor',
                    'fire_manager','fire_inspection','food_hygiene_manager','lease_end',
                    'loan_end','loan_grace_end','visa','insurance','domain','other')),
  add column if not exists severity text not null default 'normal' check (severity in ('critical','normal')),
  add column if not exists remind_days int[] not null default '{30,7,0}',
  add column if not exists source_table text,      -- 'properties' | 'loans' | 'employees' | 'suppliers' | null(手入力)
  add column if not exists source_id uuid,
  add column if not exists document_id uuid references info.documents(id),
  add column if not exists done_at timestamptz,    -- 更新手続き完了
  add column if not exists employee_id uuid;
create unique index if not exists deadlines_source_uniq on info.deadlines(source_table, source_id, kind) where source_table is not null;
```

- 種類ごとの既定値: `lease_renewal`/`lease_notice`/`business_license`/`late_night_liquor`/`fire_manager`/`visa` → `severity='critical'`。`visa` は `remind_days='{90,30,7}'`。
- 既存行の `kind` は現在の `guessKind(title)` と同じルールでUPDATE（「許可」→business_license、「更新」→lease_renewal）。

### 2.2 自動生成（トリガー関数 `info.sync_deadlines_from_source()`）

| 元 | 生成する期限 |
|---|---|
| `properties` INSERT/UPDATE | `lease_renewal`（due=renewal_date）。`notice_months`（新列・既定6）があれば `lease_notice`（due=renewal_date − notice_months） |
| `loans` | `loan_end`（完済月末）、据置期間があれば `loan_grace_end` |
| `employees.visa_expires_on`（新列） | `visa` |
| `suppliers.contract_end_month`（D-1で追加） | `lease_end`（種別=リースのとき） |

- 元の日付がNULLになったら該当期限をDELETE。`done_at` が入った期限は元日付が変わるまで再生成しない。
- 手入力の期限（営業許可・深夜酒類・防火管理者・消防点検・食品衛生・保険）は `deadline-form.tsx` の「何の期限？」を**選択式（kind）＋任意タイトル**に変更し、`business_license` は書類添付必須。

### 2.3 ポータル向けRPC `public.info_alerts_for_portal()`

```sql
create or replace function public.info_alerts_for_portal()
returns table(kind text, title text, store_no text, store_name text, due_date date, days_left int, severity text, url text)
language sql stable security definer set search_path = info, public as $$
  select d.kind, d.title, s.store_code, s.name, d.due_date, (d.due_date - current_date), d.severity,
         '/stores/' || d.store_id || '?tab=deadlines'
  from info.deadlines d left join info.stores s on s.id = d.store_id
  where d.done_at is null and d.severity = 'critical'
    and d.due_date <= current_date + 60
    and ( public.portal_is_master() or public.portal_role() in ('CEO','HQ')
          or d.store_id in (select store_id from public.user_stores where user_id = auth.uid()) )
  order by d.due_date;
$$;
revoke all on function public.info_alerts_for_portal() from public, anon; grant execute on function public.info_alerts_for_portal() to authenticated;
```

- `portal_role()` 相当の関数名は `ns-portal/supabase/` の既存関数に合わせる（無ければ `portal_permissions` の判定を流用）。店舗IDの対応は `info.stores.hub_store_id` を使う。
- **受け入れ条件**: マスターで全店の期限が返る／店長で自店のみ／`severity='normal'` と61日以上先は返らない／anonで実行不可。

### 2.4 通知

- 既存の社内情報の通知（`/notifications`・Lark/Chatwork）に `remind_days` の日付で通知を出す。本部タスクの `hq_check_alerts()` と同じ「読み込み時判定＋通知テーブルINSERT」の型で可（日次バッチが無いため）。

### 4.1 マイグレーション `2026-09-XX_store_investments.sql`

```sql
create table info.investment_categories (
  id text primary key, name text not null, default_treatment text not null
    check (default_treatment in ('deposit','asset','expense')),
  default_dep_years int, sort_order int not null default 100, is_active boolean not null default true);
insert into info.investment_categories(id,name,default_treatment,default_dep_years,sort_order) values
 ('deposit','敷金・保証金','deposit',null,10),('key_money','礼金','expense',null,20),('brokerage','仲介手数料','expense',null,30),
 ('deposit_amort','償却（保証金の償却分）','expense',null,40),('interior','内装工事','asset',15,50),('kitchen','厨房機器','asset',8,60),
 ('fixtures','什器・備品','asset',6,70),('signage','看板・サイン','asset',10,80),('pos_network','POS・通信工事','asset',5,90),
 ('recruit','求人費用（開業前）','expense',null,100),('pre_labor','開業前人件費','expense',null,110),('pre_rent','開業前家賃','expense',null,120),
 ('license','許認可・登記費用','expense',null,130),('other','その他','expense',null,900);

create table info.store_investments (
  id uuid primary key default gen_random_uuid(),
  corporation_id uuid not null references info.corporations(id),
  store_id uuid not null references info.stores(id),
  property_id uuid references info.properties(id),
  category_id text not null references info.investment_categories(id),
  amount numeric not null, tax numeric not null default 0,
  paid_on date, supplier_id uuid references info.suppliers(id),
  treatment text not null check (treatment in ('deposit','asset','expense')),
  depreciation_years int, depreciation_start date,   -- 資産計上のみ。開始は既定=開業月
  document_id uuid references info.documents(id), memo text,
  created_at timestamptz not null default now(), created_by uuid);

create view info.v_store_investment_summary as
select store_id,
  sum(amount) as total,
  sum(amount) filter (where treatment='deposit') as refundable,
  sum(amount) filter (where treatment='asset') as assets,
  sum(amount) filter (where treatment='expense') as opening_expense,
  sum(case when treatment='asset' and depreciation_years>0 then amount/(depreciation_years*12) else 0 end) as monthly_depreciation
from info.store_investments group by store_id;

-- 店舗×年月（経営PL連携用）: 減価償却は定額・月割・耐用年数まで。開業費用は支払月に計上
create view info.v_store_investment_monthly as
with m as (select generate_series(date '2024-04-01', date_trunc('month', current_date)::date, interval '1 month')::date as ym)
select i.store_id, s.store_code as store_no, to_char(m.ym,'YYYY-MM') as year_month,
  sum(case when i.treatment='asset' and i.depreciation_years>0
            and m.ym >= date_trunc('month', coalesce(i.depreciation_start, i.paid_on))
            and m.ym <  date_trunc('month', coalesce(i.depreciation_start, i.paid_on)) + (i.depreciation_years||' years')::interval
           then i.amount/(i.depreciation_years*12) else 0 end) as depreciation,
  sum(case when i.treatment='expense' and date_trunc('month', i.paid_on)=m.ym then i.amount else 0 end) as opening_cost
from info.store_investments i join info.stores s on s.id=i.store_id cross join m
group by 1,2,3 having sum(1)>0;
```

- RLS: `store_investments` は `properties` と同じポリシー（カテゴリ `property` の権限）。`investment_categories` は全員read・マスターのみwrite（**設定画面で追加・並び替え・無効化**できるUIを `/settings` に追加＝§9-2）。
- 経営D向けの読み取り経路は F-8（`loan-repayment-feed`）と同じ: `/api/store-investment-feed`（Bearerトークン、`{rows:[{storeNo,yearMonth,depreciation,openingCost}]}`）を追加。

### 4.2 画面（店舗カルテ「初期投資」タブ）

- 明細の一覧・追加・編集・削除（区分を選ぶと treatment と耐用年数が既定値で入る。変更可）。
- 上部に4つの数字: **初期投資合計／うち戻る分（預け金）／月々の償却額／回収見込み**（回収見込み＝合計 ÷ 直近3ヶ月の月次営業利益平均。営業利益は経営Dの `kd_pl_monthly_summary` を `keiei-api-dashboard-summary` 経由で取得。取れないときは「経営Dに未接続」と表示し、空欄にしない）。

### 7.2 `public.vendors` への連動トリガー

```sql
create or replace function info.sync_vendor_from_supplier() returns trigger language plpgsql security definer set search_path = public, info as $$
begin
  if new.is_accounting then
    insert into public.vendors (info_supplier_id, name, default_account, default_sub_account, payment_method, payment_rule, frequency, amount_type, monthly_estimate, updated_at)
    values (new.id, new.name, new.default_account, new.default_sub_account, new.payment_method, new.payment_rule, new.frequency, new.amount_type, new.monthly_estimate, now())
    on conflict (info_supplier_id) do update set name=excluded.name, default_account=excluded.default_account, default_sub_account=excluded.default_sub_account,
      payment_method=excluded.payment_method, payment_rule=excluded.payment_rule, frequency=excluded.frequency, amount_type=excluded.amount_type, monthly_estimate=excluded.monthly_estimate, updated_at=now();
  end if;
  return new;
end $$;
create trigger trg_sync_vendor after insert or update on info.suppliers for each row execute function info.sync_vendor_from_supplier();
```

- `public.vendors` に無い列（`default_account` 等）と `info_supplier_id` の unique 制約は **担当Cが追加**（D-2）。担当FはWORKLOGで依頼し、追加後にトリガーを本番適用する。
- 移行手順（ユーザー確認後・1回）: ①既存 `vendors` を名称で `suppliers` に突合し `info_supplier_id` を埋める ②突合できない `vendors` は `suppliers` に新規作成（`is_accounting=true`） ③取引先ルール一覧CSV（ユーザーのデスクトップ `取引先ルール一覧_トーホーエージェンシー.xlsx` の「取引先一覧」シート。ユーザーから受領してリポジトリ `docs/` に置く）を `suppliers` へ取込（列対応: 頻度→frequency、金額の性質→amount_type、月額目安→monthly_estimate、勘定科目/補助科目→default_*、支払方法→payment_method、支払口座→payment_account、支払タイミング→payment_rule）。
- 画面: `/suppliers` を「一覧（種別・取引状況・店舗でフィルタ）→ 取引先カルテ（基本／担当者／契約・支払ルール／書類（名刺・契約書）／振込先口座（ポータルの `vendor_bank_accounts` を参照表示のみ））」に変更。

## 10. E-2 従業員カルテ（担当F）

- `/employees/[id]` タブ: **基本（nippo参照・読み取り専用）／給与体系（既存 `employee_salaries`）／給与明細／年末調整書類／書類／申請履歴**。
- 基本タブ: `v_employee_basics` を表示。社内情報側 `employees` の重複列（氏名〜国籍）は **切替日**（データ移行完了後）に画面から外し、列は読み取り専用で残す（削除しない）。移行: `employees` にあってnippoに無い値（雇用形態・国籍・在留期限）を nippo へ移すSQLを用意し、ユーザー確認後に実行。
- 給与明細タブ: `sf_payroll_sync`（`user_id`＝ポータルアカウント紐付け済みのID）を年で切り替えて月別に表示（支給合計・固定給・通勤手当・控除合計・差引支給額）。年別推移の小さな棒グラフ（色は基本色1色）。各月の📎は `payroll-pdfs` バケットの署名URLで開く（Storageポリシー `payroll_pdfs_read` に「本人 or マスター or 給与権限」の条件があるか確認し、無ければ担当Bへ依頼）。
- 年末調整書類タブ: 新テーブル `info.tax_documents(id, employee_id, year int, kind text check (kind in ('withholding_slip','dependents_form','insurance_form','withholding_ledger','other')), document_id, created_at)`。**一括アップロード**（複数PDFを選択→ファイル名の「氏名」「年」で自動振り分け→確認→保存）。閲覧は本人・マスター・給与権限者のみ。スマレジAPIで取得できることが確認できたら `smaregi-payroll-sync` と同じ型で自動化（本指示書では対象外）。
- 書類タブ: `documents.employee_id` を追加し、労働条件通知書・雇用契約書・在留カードを従業員に紐付けて表示。
- **受け入れ条件**: 本人ロールで自分の給与明細だけ見える／店長で部下の給与が見えない／マスターで全員。
