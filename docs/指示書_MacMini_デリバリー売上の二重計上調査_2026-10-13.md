# 指示書（Mac miniセッション用）: デリバリー売上（`stg_delivery_order`）の二重計上の疑いを調べる【読み取りのみ・調査まで】

発行: 担当D（MacBook）2026-10-13。依頼元: 担当A（経営ダッシュボードPLの売上高にデリバリーを合算表示。ユーザー報告「二重計上されている」）。
実行する人: **Mac miniのClaudeセッション**（ダッシュボードのログイン情報`DASHBOARD_LOGIN_ID/PW`が`.env`にあり、`bqGetDeliveryOrders`等を呼べるため）。MacBookにはBigQuery・ログイン情報が無く、データを見られない。
**この指示書の範囲は「調査と報告」まで。BigQueryの削除・更新、再取込、コード修正は、報告を見たユーザーの了承を得てから（別途）行う。**

## 1. 背景（担当Aの根拠）
`bqGetDelivery`（店舗×日の集計）で 鳥一代 本店: 2026年9月=**827注文・¥2,455,012**（日平均27件・約8万円）／8月=63件・¥132,511／10月(12日)=97件・¥166,680（日平均8件・約1.4万円）。1注文あたりも9月≒¥2,970・10月≒¥1,720。9月だけ突出。9月分は10/4〜10/5に月次精算（`rocketnow-settlement`）を取り込んだ時期と重なる。

## 2. 担当Dが読んだコードからの見立て（検証してほしい仮説）
- 取込口: `tasks/delivery-sales.js`（日次速報=`parseWorkbook`・月次精算=`parseSettlementWorkbook`）→GAS `bqLoadDeliveryOrders`。BQの`MERGE`キーは **(channel, order_no, txn_type, txn_at)**。同じ注文が日次(速報・`is_settled=false`)と月次(確定・`is_settled=true`)で**order_no／取引タイプ／取引日時の表記・時刻が少しでも違うと別行として二重に入る**。日次の`txn_at`は文字列(`toDatetime`)、月次はExcel日付をUTCゲッターで整形(`settlementDatetime`)で、組み立てが別。取引タイプの文言も日次(取引タイプ列)と月次(同名列)で一致している保証が無い。
- 集計側: `bqGetDelivery` は `COUNT(DISTINCT order_no)`・`SUM(sales)` を `txn_date`×`store_id`で集計し、**`is_settled`や`txn_type`で絞らず、同一注文の重複排除もしない**。重複があれば売上がそのまま二重になる。`order_no`が同じで`txn_at`だけ違う重複なら、注文数は変わらず売上だけ増える（9月の1注文あたり単価が1.7倍なのはこの形と整合）。
- もう1つの仮説: 月次精算の`sales`（注文金額・idx9）と日次の`sales`（売上高）で**列の意味が違う**（金額の定義差）。この場合は二重ではなく定義違いで、単純合算は両者を混ぜない設計が必要。
- 別の仮説: 月次精算の店舗名→`store_id`解決（`delivery_store_map`の`channel_store_name`）で他店の注文が本店に寄っている（精算ファイルが複数店舗を含む等）。
- 実数の確認が必要: 8月が63件と少なく、9月が突出なのか、10月（日次のみ）が少なすぎるのか（日次速報が一部しか拾えていない可能性）。**どちらが実態に近いか**を、ロケットナウの管理画面の実績（ユーザーの画面）と照合する材料も出す。

## 3. 調査手順（読み取りのみ）
ローカルの使い捨てスクリプト（コミットしない・`logs/`か`/tmp`相当に置く）で、`.env`のログイン情報を使い、既存のGASアクションを**読み取りで**呼ぶ。
1. **注文明細の取得**: ダッシュボードにログイン（`lib/gas.js`の`gasPost({action:'login',…})`）→ `bqGetDeliveryOrders`（`months=3`）。返る列=店舗名・日時(txn_at)・取引タイプ・注文番号・注文内容・売上・媒体。
2. **本店の日別推移**: 8月〜10月で、日別に 行数・distinct注文数・売上合計・取引タイプ別件数。9/1〜9/13（日次の自動取込が始まる前）／9/14〜9/30／10月で平均を出し、**10/4〜10/5前後（月次精算の取込日）に段差が無いか**を見る。
3. **重複の検出**:
   - 同じ`order_no`で行が複数あるもの。そのうち「同じ取引タイプで`txn_at`だけ違う」「取引タイプが違う（例: 速報側と確定側の表記違い）」を分けて件数・売上差を出す。`txn_at`の差が一定（例: ちょうど9時間）なら時刻の組み立て違いが原因。
   - `order_no`が違っても、同じ日・同じ売上額・同じ注文内容(`items_text`)の行が2つ並ぶもの（`order_no`の表記違いの疑い）。
4. **order_noの形式**: 9/1〜9/13・9/14〜9/30・10月で、`order_no`の長さ・先頭の文字・桁数の分布を比べる（日次と月次で形式が違うかを見る）。
5. **確定行の合計**: `diagDeliverySettlementBreakdown`（管理者権限・既存の読み取り診断）で、`source_file`ごとの確定(`is_settled=true`)の 売上合計・行数を取る。**9月分の本店の確定ファイルの売上合計と行数**を、手順2の9月の合計と比べる（9月の大半が確定ファイル由来かどうか）。
6. **店舗の寄り**: 9月の確定ファイルの`store_id`別の行数・売上を見て、本店に他店舗ぶんが混ざっていないかを確認（精算ファイル1つに複数店舗の行が含まれていないか）。
7. **金額の定義**: 日次と月次の同じ注文（`order_no`が一致するもの）が両方あれば、`sales`を並べて同額か。違う場合は差の理由（注文金額と売上高の違い等）を推定。

## 4. 報告に含めること（`ns-portal/docs/調査結果_デリバリー二重計上_2026-10-1x.md`に書き、WORKLOG冒頭にも要約）
- 二重計上は「ある／ない」。ある場合、**どの形か**（①order_no同一でtxn_at違い ②取引タイプ違い ③order_no表記違い ④店舗の寄り ⑤金額の定義差）と、重複行の件数・過大な売上額（月別・店舗別）。
- 10月（日次のみ）が過少でないか。実績（ロケットナウ管理画面）と合わせるために、ユーザーに確認してほしい数字（本店の9月の注文件数・売上）。
- **修正案**（実行はしない）: 担当Dの案=①集計側で重複排除（同じ`order_no`×`txn_type`に確定行がある場合は速報行を除外＝確定優先。`ROW_NUMBER() OVER (PARTITION BY channel, order_no, txn_type ORDER BY is_settled DESC, imported_at DESC)=1`）を`bqGetDelivery`/`bqGetDeliveryOrders`に入れる ②`MERGE`キーを見直し（`txn_at`を外す等。副作用を検討）③既に入った重複行の掃除（BQ側で`DELETE`・要ユーザー了承）。再取込が必要か、必要なら対象月とやり方。
- 担当Aへ渡す要点（`kd_delivery_daily`は取込完了ドリブンで自動追従するので、BQ側が直れば表示も追従する）。
