# バックアップと復旧（ハブ Supabase / nippo プロジェクト）

作成: 2026-08-18 ／ Supabase Pro化（実装指示書_第3期実装フェーズ §A）に伴う確認・文書化。
対象: ハブプロジェクト `uuvsxzhpxtghojoubjcc`（ref）＝ポータル・本部タスク・チェックシート・日報・社内情報(infoスキーマ)すべてが載っている統合DB。

## 1. 今のバックアップ状態（2026-08-18 時点で確認済み）

- **プラン**: Pro（`organization.plan = "pro"` をManagement APIで確認済み）
- **日次物理バックアップ**: 有効（`walg_enabled: true`）。直近7日分（2026-08-11〜08-17）が`COMPLETED`で揃っていることを確認済み
- **PITR（Point-in-Time Recovery、秒単位の巻き戻し）**: **無効**（`pitr_enabled: false`）。Proプランの基本機能ではなく別料金のアドオン。今回は未加入（必要になったら追加検討）
- **保持期間**: 7日分（Proプランの標準）。8日以上前の状態には戻せない
- **リージョン**: ap-northeast-1（東京）

## 2. 何がバックアップされるか

DB本体（`public`・`hq_*`・`portal_*`・`info`スキーマなど、プロジェクト内の全スキーマ）が対象。
**含まれないもの**:
- Storageのファイル（`report-photos`バケットの写真・`info`のdocuments等）はDBバックアップとは別物。Supabase StorageはS3互換の冗長ストレージ上にあり個別のバックアップ機構は無い（誤ってファイルを消すと戻せない。**Storageの削除操作は特に慎重に**）
- Supabase Auth自体の設定（メールテンプレート等）
- Vercel・GitHub Pages側のデプロイ設定

## 3. 復旧の手順（バックアップから戻す）

**⚠️ 復旧はDB全体を指定時点の状態に巻き戻す操作。復旧後は「バックアップ取得〜復旧実行までの間に入った新しいデータ」が失われる。実行前に必ずユーザーの判断を仰ぐ（Claudeが単独で復旧操作を行うことはしない）。**

1. https://supabase.com/dashboard/project/uuvsxzhpxtghojoubjcc/database/backups を開く
2. 一覧から戻したい日付のバックアップを選ぶ（直近7日分のみ選択可）
3. 「Restore」を実行 → 確認ダイアログが出る（プロジェクトが一時的にオフラインになる旨の警告が出る）
4. 復旧には数分〜数十分かかる（DBサイズによる）。完了までポータル・本部タスク・日報などすべてのシステムが使えなくなる
5. 復旧完了後、主要画面（ポータルログイン・本部タスクボード・日報）が正常に表示されることを確認

**代替手段（DB全体を戻さず、特定テーブルだけ調べたい場合）**: Management APIの`database/query`で、バックアップを実際に復元せずとも、直近の変更履歴を`hq_task_activity`等の履歴テーブルから追う方が早いことが多い。DB全体の復旧は「データが壊れた／誤って大量削除した」など他に手段がない場合の最終手段。

## 4. 起きやすい事故と対処の目安

| 事故 | 対処 |
|---|---|
| 特定のテーブルを誤って`DELETE`した（WHERE漏れ等） | 影響範囲が小さければ、その日のバックアップから**該当テーブルだけ**を別プロジェクトへ一時復元してデータを拾い出す方が、DB全体を戻すより安全（本番の他のデータを巻き戻さずに済む） |
| RLS/マイグレーションSQLの実行ミスで整合性が壊れた | まず新しい修正SQLで直せないか検討（追加のみの原則）。直せない規模なら復旧を検討 |
| Storageのファイルを誤って削除した | **バックアップ対象外のため復旧不可**。日頃から「削除は慎重に」を徹底する以外の防御策が無い |

## 5. 旧・社内情報管理プロジェクト（`wciefkpooncglahqdtmu`）について

社内情報の本番切替（フェーズC）完了後も、**しばらくは削除しない**（実装指示書§C-5の方針どおり）。切替後2週間、問題が出ないことを確認してからユーザーの判断で削除する。それまでは旧プロジェクト側にも元データがそのまま残っているため、実質的な二重のセーフティネットになっている。
