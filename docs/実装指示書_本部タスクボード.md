## 0. 最重要の注意（並行セッション対策）

**別のClaudeセッションが同時期に他のテーブル・他のコードを触っている。** 衝突させないため以下を厳守:

1. **作業開始時と push 直前に必ず `git fetch` → リモートが先行していたら `git pull --rebase`**。上書きpush（force）は厳禁。過去に並行セッションとの上書き事故が起きている。
2. **DBは `hq_` で始まる新規テーブル・関数だけを作る**。既存テーブル（users / stores / store_aliases / portal_* / checklist_* / reports / tasks / attendance_records / info.* など）への **ALTER・DROP・UPDATE・RLS変更は一切禁止**。読むのは自由。
3. **既存ファイルの編集は最小限に**。新規ファイルを作るのが基本（下記 §3）。特に `ns-portal/index.html` への変更は「本部タスクへのリンク追加」だけに留める。
4. **`supabase/` の既存SQLファイルは編集禁止**。新しいマイグレーションは新規ファイル `supabase/2026-08-XX_hq_tasks.sql` として追加（冪等に書く: `create table if not exists` / `drop policy if exists` → `create policy`）。
5. 日報アプリ（nippo）・経営D（tori-dashboard）・精算（seisan-dashboard）の**リポジトリは触らない**（今回のスコープ外）。

## 4. データ設計（設計書 第6章のとおり）

テーブル: `hq_task_templates` / `hq_tasks` / `hq_task_steps` / `hq_task_links` / `hq_task_photos` / `hq_task_alerts` / `hq_task_activity` / `hq_notify_channels` / `hq_notify_rules` / `hq_task_members`（公開範囲指定者）

実装上の要点:
- 人は `public.users(id)`、店舗は `public.stores(id)`（店舗番号は`store_no`列）を参照。**文字列で持たない**
- `hq_tasks.target_date`（対象日）を必ず持つ。「期限内」は保存せず、対象日×完了日時×出勤日から都度計算（設計書 第5.5章）
- 出勤日の暫定ソース = `attendance_records`（スマレジ勤怠。読み取りのみ）
- 管理権限判定は既存の `portal_can_post()` と同型の **専用関数 `hq_can_manage()`**（is_master or role in CEO/HQ）を新設（既存関数は変更しない）
- 公開範囲: `visibility='all'`（本部全員）/`'members'`（`hq_task_members` に載る人＋工程担当者のみ）。**RLSで強制**（画面出し分けだけにしない）
- チーム長(TEAM)は閲覧＋自分の担当工程の完了のみ。店長以下はRLSで「自分が工程担当のタスク」だけ見える
- 写真は既存バケット `report-photos` を使う。**ストレージポリシーの制約: パスの第1フォルダは必ず `auth.uid()`**。例: `{uid}/hqtask_YYYYMMDD_xxx.jpg`（バケット・ポリシーの変更禁止）
- Lark Webhook URLは `hq_notify_channels` テーブルに入れる。**公開リポジトリなのでコードへのハードコード厳禁**

## 5. 実装手順（この順で。各ステップでE2E検証→コミット）

**3d-1: 基盤＋ボード＋詳細**
1. SQLマイグレーション作成→Management APIで適用→確認クエリで検証
2. `tasks.html`: ボード（かんばん3列: 未着手/進行中/完了）・サマリー信号（期限超過/今日期限/停滞/今月完了）・絞り込み（法人×頻度×👤自分・掛け合わせ）・フリーワード検索（過去分含む）
3. タスク詳細: 工程（担当・期限・完了記録・「いまここ」停滞表示）・⚠️注意事項・リンク（url/manual/credential種別。credentialは値を持たずラベルのみ）・写真・履歴
4. 単発タスクの作成UI（テンプレなしで直接作る）

**3d-2: 繰り返し＋毎日タスクUI**
5. テンプレートCRUD（頻度: 毎日/毎週[曜日]/毎月[日]、工程ひな形[+n日オフセット]、公開範囲、アラート既定）
6. 自動生成: 当日分のタスクをテンプレから生成。**サーバーレスで実現する**: tasks.htmlを誰かが開いたときに「今日の生成が済んでいるか」をチェックして未生成なら生成（`hq_generation_log`テーブルで日次1回を保証・競合はunique制約で防ぐ）。← GAS時計トリガーでもよいが、まずはこの方式が追加インフラ不要
7. 毎日タスクのシンプルUI（設計書 第2.5章）: 行を開くと手順/注意/リンク、子チェック（種類: ふつう/店舗別/2択[OK・異常あり→異常メモ必須]/写真必須）。**全子チェック完了までタスク完了にならない**
8. 休み明けのたまり表示（第5.5章のバナー＋日付ラベル）

**3d-3: 通知＋過去タスク**
9. `hq_notify_channels`（Lark Webhook登録UI）＋`hq_notify_rules`（対象×出来事×宛先）
10. 判定はタスク画面ロード時＋日次生成時に実行: 期限アラート（-3/-1/0/超過）・停滞（3日）・異常あり→ルールに従いLark送信（`UrlFetchApp`は無いので`fetch`でWebhookへPOST。Larkカスタムボットは**本文にキーワードが必要な場合がある**—チャンネル登録UIにキーワード欄を設ける）＋アプリ内通知（既存`notifications`テーブルは日報のものなので触らず、`hq_notifications`を新設してポータルにベル表示）
11. 📁過去タスクタブ（月別・無期限・検索対象）

**3d-4/3d-5（今回はここまでやらなくてよい・準備だけ）**
- credential/manualリンクの実接続はそれぞれのシステム完成後
- 期限内完了率の集計ビュー `hq_ontime_stats_v`（担当者×月）だけ作っておく（評価制度が後で読む）

## 6. テストの流儀（このプロジェクトの標準・必ずやる）

1. **一時ユーザーでE2E**: service_roleで `*-test@example.com` ユーザーを作成（HQ役・TEAM役・AL役）、ブラウザ実機でログインして操作検証。**RLSの敵対テスト**（権限のない書き込み・他人のデータ削除をAPI直叩きで試み、403/RLS拒否を確認）まで行う
2. **テスト後は完全削除**: authユーザー削除（public.usersはトリガーでcascade）、作ったテストデータ・写真も削除。`select count(*) from users where email like '%test@example.com'` が0（既存の `ceo@example.com` は消さない）
3. 構文チェック: HTMLのscriptブロックを抜き出して `node -c`
4. デプロイ確認: push後 `until curl -s https://mirai-oss.github.io/ns-portal/tasks.html | grep -q '<目印>'; do sleep 10; done`
5. ローカル確認は launch.json の `portal`（8891）。**シークレットでなく通常リロードはキャッシュに注意**
