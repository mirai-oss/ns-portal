# 調査・実装案: Uber Eats 売上の取込（鳥一代 本店・はなれ・芝の3店）

担当D・2026-11-11／依頼元: 司令塔（店舗日報v2・FL比率の分母に入れる）／状態: **調査と実装案のみ（本番実装は別承認）**
調べ方: Uber公式の開発者ドキュメント・ヘルプの確認＋既存のデリバリー取込（ロケットナウ）の実コード・DBの実査。**日本の Uber Eats Manager の実画面は私は見ていない**ため、画面・列の細部は「要実機確認」と明記（末尾にユーザーへ頼むスクリーンショット一覧）。

## 結論（先に6行）
1. **取得方法の本命は「Uber Eats Manager の定期レポート（メール）→ 自動取込」か「Mac mini の Playwright」**。APIは**Uberの書面承認（NDA・API利用契約・担当者の承認）が必要**で、3店の事業者が通る保証もなく、時間がかかる。**APIは並行して申請だけ出す**のが妥当。
2. **どれを選ぶかは、日本の Uber Eats Manager に「日別・注文単位」のCSVがあるかで決まる**（私は未確認）。無い場合、取れるのは**週次の支払いCSV（月曜4時〜翌月曜4時・注文別の売上・税・調整・純支払）**で、**FL比率の分母に入る前日値が間に合わない**（確定は週1・最大72時間遅れ）。→ 最初にスクリーンショットで確認するのが最優先。
3. **データの置き場は既存の仕組みにそのまま乗る**: `stg_delivery_order`（channel='ubereats'の行を追加）→ `kd_delivery_daily`（channel列あり）。`delivery_store_map` に3店×channel='ubereats' を追加。MERGEキー（channel×注文番号×取引タイプ×日時）で速報→確定の置換も同じ。
4. **既存コードに直さないといけない箇所が2つある**（見落とすと二重・誤集計になる）: ①GASの `bqGetDelivery` は**媒体名を「ロケットナウ」と固定**し、**チャネルでグループ化していない**ため、Uber Eatsを入れると**ロケットナウに合算されて見える** ②同関数の「**確定行がある店舗×月は速報を使わない**」規則は、**Uber Eatsの週次確定だと月の後半の速報が消える**ため、チャネル別（できれば注文単位）に直す必要がある。
5. **税込・税抜に注意**: 既存の `kd_delivery_daily`（ロケットナウ）は**税込のまま**で、FL計算用売上は「店内＋デリバリー÷1.08」。Uberのレポートの「売上」は**税抜**（ヘルプの説明。日本版は要確認）の可能性があり、**税込（売上＋税）に揃えて保存**しないと分母が約8%ずれる。
6. **工数の目安: 実装2〜4人日（取得方法が決まってから）＋既存コード改修1人日＋遡及取込0.5人日**。取得方法の確定（スクリーンショット確認）に0.5日。

## 実装設計（案B/Cのどちらでも共通の部分）
### データの置き場（既存を再利用）
- **BigQuery `stg_delivery_order`**: channel='ubereats' の行を追加。列の対応: `store_id`=当社店舗（`delivery_store_map` 経由）／`channel_store_id`=UberのストアUUID（または店舗名）／`txn_date`=注文日（現地）／`txn_at`／`txn_type`=PAY（通常）・CANCEL（返金・調整のマイナス）／`order_no`=Uberの注文ID／`items_text`=商品（取れれば）／`sales`=**売上＋税（税込）**／`coupon_store`=店舗負担の値引き／`fee_total`=Uberサービス手数料／`tax`=税額／`payout_expected`=純支払／`is_settled`=週次の確定CSVで true・日次の速報は false。
- **重複排除（MERGEキー）**: 既存と同じ `(channel, order_no, txn_type, txn_at)`。速報→確定は同じキーで上書き（72時間後・週次確定で置換）。
- **`delivery_store_map`** に3行追加（channel='ubereats'・本店／はなれ／芝）。未登録の店舗は既存の店舗名ゲートウェイ（kd_unresolved_names）へ隔離し、**status='partial'** ＋ items.skipped_stores（ロケットナウと同じ）。
- **`kd_delivery_daily`**: `(store_id,biz_date,channel)` で channel='Uber Eats' の別行（キー列は既にある）。

### ジョブ設計
- ジョブ名 `ubereats-sales`（ns-daily-import・毎朝・前日＋直近3日を再取得して72時間の確定を反映／週1で確定レポートを取り直し）。取得（B or C）→ パーサー（Uber用CSV→上記の列）→ 既存の `processBuffer` 相当（店舗ID解決→BQ upsert）→ `import_runs` に `items{date_from,date_to,rows,stores,skipped_stores}` と status。

### 既存コードの修正（必須・見落とし注意）
1. **GAS `bqGetDelivery`（tori-dashboard/gas/Code.gs）**: ①SQLに `T.channel` を追加して**チャネル別にグループ化**、②出力の媒体名を固定の「ロケットナウ」から**チャネル→媒体名の対応（rocketnow→ロケットナウ、ubereats→Uber Eats）**に変更、③「確定行がある店舗×月は速報を使わない」規則を**チャネル別**にする（Uberは週次確定のため、月の後半の速報が消えないよう、**注文単位のMERGE置換に一本化**するか、確定の最終日以降の速報を残す）。これを直さないと、Uber Eatsが**ロケットナウに合算**される／月後半が消える。
2. **`keiei-kd-refresh` の delivery_daily**: 行の3列目（媒体名）をそのままchannelに入れる作りなので、1.②が直れば変更不要（要テスト）。
3. **FL計算用売上**: デリバリー÷1.08は**税込で保存されている前提**。Uberも税込（売上＋税）で入れれば同じ式で足りる。チャネルごとに税率が違う場合（Uberは8%で同じはず）は`fl_delivery_tax_divisor`を確認。
4. **注文明細（デリバリー分析タブ）**: `stg_delivery_order` の明細を返す別のGAS関数が、チャネルを絞っているか未確認 → 確認が必要。

### 日報の欠損判定（担当Aのルール案）との整合
- 判定を**チャネル別**にする: 店舗×日×チャネルで、`import_runs`（job='ubereats-sales'・status success／partial・items.date_from〜date_to）に当日が含まれれば「取込済み」。その日に行が無ければ「Uber Eats注文なし（0円）」、取込成功の記録が無ければ「未取得」。**Uberの確定遅れ（72時間）**: 直近3日は速報値として表示し、確定後に置換される旨を日報の注記に出す。
- 日報の「デリバリー」金額は、ロケットナウ＋Uber Eatsのチャネル別行の合計（税込）→ ÷1.08 を店内売上に加える。

### 資格情報（値は扱わず種類だけ・ユーザーが用意）
- 案B/C: **Uber Eats Manager のログイン（ユーザー名・パスワード・4桁のセキュリティPIN）**、ログイン時の**端末認証コードの受け取り先（メール／SMS）**、3店の**ストア名またはストアUUID**。Playwrightの場合は専用のログインアカウントを作ることを推奨（本部の個人アカウントと分ける）。
