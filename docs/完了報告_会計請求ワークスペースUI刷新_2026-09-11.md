## 3. SoTから変更した箇所と理由

- **5タブの並び・名称（請求書｜売上入金｜自動取込｜自動化｜設定）は完全にSoTどおり**。逸脱していない。
- **inbox/sent/notApplicable/important/history/transfersは、SoTのような単純な合体ではなくナビゲーション橋渡し方式にした**：これらは`invoice_emails`起点（メールにひもづくが`invoices`の行を持たない場合がある）で、統合請求書一覧（`invoices`起点）とデータモデルが根本的に異なると判明したため（Step3調査）。データモデルを無理に統合するとバグの温床になるため、各タブの中からワンクリックで開ける導線を追加する方式にした。
- **契約書一覧（contractList）は5タブ構成の外に残した**：ユーザー判断「メールで来た契約書を社内情報管理システムに入れる場合があるため」（Step1確認事項）。
- **会計設定はSoTの「4カードが全て同時に中身を表示する」レイアウトを文字通りには再現していない**：既存8サブタブそれぞれが独立したCRUD画面（テーブル・フォーム）を持ち、実データ量も可変のため、全カード同時展開だと情報過多・スクロール過多になると判断。「4グループのナビ＋選択したグループの中身を表示」という、Step2のAC_GROUPSと同じ実証済みパターンを採用した（指示書§9-16「情報量削減禁止」を優先した判断）。
- **会計ダッシュボードはSoTの新規ピクセル単位レイアウトではなく、既存の①〜⑦セクション構成に⑧セクションを追加する形にした**：既存ダッシュボードが既にSoTの「1画面サマリー・KPIクリックで絞り込み遷移」という要求を満たす実装だったため、作り直さず拡張した（指示書§9-20「新UIが安定するまで旧UIコードを削除しない」の精神に沿う判断）。

## 18. 本当に残っている課題

1. **実機E2E未実施**：本セッションはログイン認証情報を持たないため、実際のHQ/master権限ユーザーによる本番環境での動作確認が一度もできていない。特に本部タスク例外連携（Step9）は、実際にタスクが正しく発行・自動完了することを本番で確認する必要がある。
2. **売上入金の実データが0件**：担当DのPayPay加盟店明細取込ジョブ（PayPay for Business管理画面からの新規Playwrightジョブ）が未着手のため、`ar_receivables`にデータが入っていない。データが入り次第、実際の集計・消込ロジックの検証が必要。
3. **`import_paypay_settlement`（担当D）→`ar_receivables`（担当C）の自動連携が未実装**：現状`ar_receivables`は空のテーブルとしてのみ存在し、担当Dの生データを正規化して投入するバッチ・ジョブはまだ無い。次フェーズで担当Dと連携して実装が必要。
4. **本部タスク例外連携の対象は意図的に4種類に限定**（重複疑い・口座変更・MF登録エラー・入金差異）：指示書§9-13が例示する「未取得」「AI確信度不足」「勘定科目/法人/店舗不明」「振込エラー」は、既存のダッシュボード表示で十分カバーされている・detection ロジックが未実装、等の理由で対象外にした。将来的に本部タスク化が必要と判断されれば追加できる設計にはなっている。
