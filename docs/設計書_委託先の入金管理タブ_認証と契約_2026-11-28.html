残る安全上の問題（入金タブの有無に関係なく既存の認証にある）
  • 【事実】委託先 3 件のうち 2 件はまだ「塩つき SHA-256 1回」のハッシュ（総当たりに弱い形。次にそのアカウントがログインした時に PBKDF2 へ置き換わる）。DB は service_role だけが読めるので直ちに漏れる形ではないが、入金タブを有効にする前に、この2件を置き換える（本人にログインしてもらう／パスワード再設定）。
  • 【事実】セッションは固定14日・アイドル切れなし・ブラウザの localStorage に保存。入金タブだけは短い条件（12時間）を RPC で追加する（§1）。
  • 【事実】失敗回数の制限は入力したID文字列ごと（ID と メールは別枠）で、IP ごとの制限はない。他人が連続で失敗させると本人が15分ロックされる（締め出し）。分散した推測には弱い。通知もない（ログのみ）。
  • 【事実】DB 側の判定（settle_can_view）は、委託先でも担当店舗が空欄または「全店」だと全店が見える。空欄は保存画面（saveAccount）で拒否しているが、DB の関数は拒否しない（現在は該当 0 件）。入金の RPC では DB 側でも拒否する。
  • 【事実】旧セッションの経路が残っている：settle_whoami は新しいセッションのほか、旧GAS時代のログイン（sd_dash_grant ＋共通の ds_sessions）も受け付ける（11件・うち委託先4件・2026-12-10 にすべて期限切れ）。入金の RPC はこの経路を使わない。
  • 【事実】旧GASのWebアプリはまだ応答する（ping は v5.41-ready）。コード上は、切替後は PDF・メール係（合言葉つき）以外の関数を全て断る設計（SEISAN_FROZEN）。【未確認】本番でその旗が実際に on か（読み取りで確かめる方法がない）。旧シートの平文パスワード列が残っているか／誰が開けるかも【未確認】。
  • 【事実】共通の ds_sessions（他のダッシュボードと共用・トークンが平文の主キー・134件有効・最長約78日）。RLS で直接は読めないが、anon に表の SELECT 権限が付いたまま（RLS 任せ）。精算の入金タブとは別件（別担当の判断）。

1. MVP（最小構成）— 現在の本番の認証の上に足す

1-1. MVPの範囲

出す自店舗（その委託先アカウントの担当店舗）の入金日・入金額（日ごとの合計と件数）。既存の精算書画面に「入金」タブを1つ足す（閲覧専用・月を選ぶ）。
出さない口座番号・残高・CSV原本・摘要（振込人名等が入り得る）・他店舗／他法人の情報・訂正や承認の履歴・保留中の金額。売上・入金予定額・差額はMVPの後（§5-3）。
再利用する
（作らない）		ログイン画面・ログイン方式・パスワードのハッシュ・セッション（settle_sessions・ハッシュ保存）・ログイン失敗の制限（settle_login_fails）・記録の表（settle_audit・settle_auth_logs）・店舗の対応（settle_stores.store_id：5店舗すべて設定済み）・利用申請→本部承認で個人別アカウント（-01形式）を作る既存の流れ・Edge Function seisan-api・精算画面。
新しく要る
（足す）		①アカウント別の入金スイッチ表 settle_deposit_access（既定OFF・閲覧期間つき）②入金RPC settle_client_deposits ③seisan-api に読み取りの動作 sd_getDeposits を1つ ④画面の「入金」タブ。

1-2. MVPの構成（これだけ作る）

  1. DB（追加のみ）
    • 新表 settle_deposit_access（login_id 主キー／enabled 既定 false／view_from date 必須／view_to date 空可／approved_by・approved_at・note）。他の settle_* と同じく RLS 有効・service_role のみ。行が無い＝見えない（既定OFF）。契約の開始日・終了日は、この表の閲覧期間として本部が登録する（初版の契約6表の代わり。委託先は3件・5店舗なので、表を増やさない）。
    • 新関数 settle_client_deposits(p_token text, p_month text)（security definer・search_path 固定・revoke … from public, anon, authenticated・grant execute … to service_role。店舗IDも委託先IDも引数に無い）。中の判定を順に：
      1. トークン → settle_sessions の行（新しいセッションだけ。旧GAS経路は見ない）→ アカウント（有効・役割＝委託先）。
      2. セッションの発行から12時間以内でなければ「再ログインが必要」を返す（settle_sessions.created_at を使う。既存の列で足りる）。
      3. settle_deposit_access に有効な行があり、今日（JST）が閲覧期間内であること。
      4. 担当店舗 stores_raw が空欄・「全店」なら空を返す。それ以外は settle_stores の店舗に対応づけ、store_id の集合を作る。
      5. 要求の月と閲覧期間を交差させる（範囲外は空）。
      6. 入金の集計は既存の bank_deposit_daily(p_from, p_to) をそのまま呼び、手順4の店舗IDだけに絞る（§5-2：この関数は service_role の呼び出しなら全店を返す作り。これで本部の画面と同じ集計規則を使える＝ロジックの二重持ちが無い。呼び出しの中で auth.role() が service_role のままか、実環境のリハーサルで確認する）。
      7. 返すのは 店舗の表示名・入金日・合計・件数・状態（入金あり／確認中の有無）・最終更新時刻だけ。entries（摘要）・保留金額・各種IDは返さない。
      8. 閲覧を settle_audit に記録（誰が・何月・何店舗・何行。金額は記録しない）。
  2. Edge Function（既存 seisan-api に追加）：読み取りの動作 sd_getDeposits（引数は [トークン, 月] だけ。月は YYYY-MM の形式検査。他は無視でなく拒否）。トークンは既存の sd_getDashboard と同じ扱い（Cache-Control: no-store・POSTのみ・CORS固定は既存のまま）。入金タブ専用の回数制限（ログインIDごとに1時間60回まで・既存の settle_add_fail を流用）。新しい関数・新しいシークレットは作らない。
  3. 画面（seisan-dashboard/index.html）：「入金」タブ（委託先アカウントにだけ表示）。スイッチOFFや期間外は「この機能はまだご利用いただけません」を出す。12時間を過ぎたら既存のログイン画面へ戻す。DB_FNS_ に sd_getDeposits を足す。スマホ幅で確認。

1-3. MVPの認証の流れ（利用者目線）

  1. 本部が、入金を見せる委託先アカウントにスイッチを入れる（対象アカウント・閲覧期間・理由。MVPでは本部が承認つきでSQLを実行。管理画面は後）。
  2. 委託先は今までどおりログインする（ID／メール＋パスワード、またはGoogle）。精算書のタブは今までどおり。
  3. 「入金」タブを開く。ログインから12時間を過ぎていたら、もう一度ログインを求められる。
  4. 自店舗の月の入金日・入金額・件数が出る。他の店舗は出ない（ブラウザから店舗を指定する入力口が無い）。
  5. 契約終了：本部が閲覧期間の終了日を入れる（または enabled を false）。次のリクエストから空になる（毎回、今日と期間を計算するため。ジョブに頼らない）。アカウント自体の停止は既存の「無効化」（セッションも削除される）。

委託先の店舗の絞り込み【事実】サーバー側（settle_whoami が持ち主を確定 → settle_can_view が店舗の担当を確認 → 店舗名を正規化して settle_stores と一致）。ブラウザから店舗ID・委託先IDを信用して受ける作りではない。ただし DB 側の判定は担当店舗が空欄または「全店」なら全店を許す（保存時の検査で空欄を拒否しているが、DB関数自体は拒否しない。現在、該当する委託先は0件）。委託先3件の担当店舗は計5エントリで、5件とも settle_stores に対応し、5件とも store_id（正本の店舗）が設定済み。概ね良い。空欄・全店の拒否をRPCに入れる
旧セッションの経路【事実】settle_whoami は、新しいセッションが無い時に旧GAS時代のログイン（sd_dash_grant＋共通の ds_sessions）でも持ち主を確定する。sd_dash_grant 11件（委託先4件）・sd_dash_snapshot 25件（最終更新 11/26）。全て2026-12-10 に期限切れ。画面の写し（sd_dash_get・sd_dash_logout）は anon から呼べるが、トークンが無ければ何も返らず、中身は精算の写しで入金は含まない。12/10 に自然に消える。入金RPCは使わない
DBの権限【事実】sd_dash_*・settle_* の全表：RLS有効・ポリシー0件・anon／authenticated に権限なし・service_role のみ。関数：settle_* は全て service_role のみ実行可。bank_* 表：RLS有効・anon 権限なし。kd_deposit_daily：RLS有効・ポリシーは ai_reader と認証済みの本部系／店長のみ（anon は表の権限だけ付いているがポリシーが無く0行）。良い
CORS・メソッド・秘密【事実】CORS は https://mirai-oss.github.io だけ（* ではない）。POSTのみ（それ以外は405）。応答は Cache-Control: no-store。エラーは理由を詳しく返さず、トークン・パスワードをログに出さない。サービスキーは環境変数。機械間の合言葉（PL_SYNC_TOKEN・SEISAN_WORKER_SECRET）はハッシュ同士で比較。良い
監査ログ【事実】settle_auth_logs（ログイン・Googleログイン・再設定・申請・承認却下。13件。入力されたID文字列が残る）。settle_audit（明細・設定・添付の操作。54件）。閲覧（読み取り）の記録は無い。入金の閲覧は新しく記録する
委託先アカウントの実態（件数のみ）【事実】全体6件：マスター1・本部2・委託先3（全て有効）。委託先：メール登録あり3／メール空欄0／担当店舗が空欄0／「全店」0／メールの重複0／-NN 形式の個人別アカウント0／パスワード未設定0。【推測】3件が会社ごとの共有アカウントで、1件に複数人が入っている可能性（実態は【未確認】）。共有のままなら入金は出さない
旧GAS【事実】旧GASのWebアプリは今も応答する（ping＝v5.41-ready）。コード上、呼び出せるのは許可リストの関数だけで、SEISAN_FROZEN が on なら PDF・メール係以外は全て断る。11/26 の WORKLOG は「旧GAS：停止（凍結）」と記録。【未確認】本番の旗の実際の値。旧シート（権限_精算ダッシュボード）に平文パスワードが残っているか・誰が開けるか。GAS が持つサービスキーの有無。PDF・メール係の URL は Edge Function のソースにも書かれている（URL自体は秘密ではないが、合言葉は環境変数）。要確認（別件）

評価の結論：現在の本番の認証は、パスワードのハッシュ化・トークンのハッシュ保存・失敗の制限・CORS固定・サーバー側の店舗確定・自己承認の禁止を備え、初版が懸念した状態（平文パスワード・制限なし・平文トークン・URLに引数）は解消している。入金日・入金額・件数だけを見せる MVP には流用できる。足りないのは、入金のような銀行情報に対する追加の条件（アカウント別スイッチ・短いセッション・全店／空欄の拒否・閲覧の記録・許可リスト）であり、§1 でそれだけを足す。売上・予定・差額・口座等へ広げる段階では、§3 の完全版（IP制限・TOTP・招待）を再検討する。

3. 完全版の構成（MVPの後・範囲を広げる場合）

この章は、MVPでは作らない。入金情報以外（売上・予定・差額・口座に近い情報）へ広げる、またはログイン全体を強化する段階の設計として残す。現在の本番の認証（§2）で既にある部分（トークンのハッシュ保存・失敗の制限・CORS固定・サーバー側の店舗確定）は、そのまま使う。足りないもの（IP制限・アイドル切れ・TOTP・招待型の初回本人確認・契約表）を、以下の案で足す。sd_dash_grant は旧GASの画面の写し用で、2026-12-10 に空になるため、トークンの入れ物としては使わず、既存の settle_sessions（created_at・expires_at あり）に列を足す形が自然（§3-2 の sd_dash_grant の記述は、この意味に読み替える）。

3-1. 経路

  • ブラウザ（精算画面・GitHub Pages）→ Edge Function contractor-portal（独自トークンの検証・回数制限）→ DB関数（service_role 専用）→ 許可リストの項目だけ返す。
  • ブラウザはサービスキーを持たない。GASは入金タブの経路に入れない（GASの侵害・鍵の保管を避ける）。
  • 委託先は Supabase Auth のユーザーにしない。【推測】Supabase の認証済みトークン（authenticated）は PostgREST から直接テーブルに届く。既存のポリシーは to authenticated を前提にしたものが多く、11/26 にも匿名の露出を閉じる作業があった。委託先が authenticated になると、既存表の取り違えのリスクを背負う。独自トークンなら、DB関数以外には届かない。
  • CORSは精算画面のオリジンだけ許可（既存関数は * が多いが、これは新規なので絞る。CORSは認証の代わりではない）。

3-6. サーバー側の確定（パラメータに委託先ID・店舗IDを受けない）

  1. 入力は Authorization のトークンと「月（YYYY-MM）」のみ。それ以外のフィールドは無視ではなく拒否（400）。
  2. トークンのハッシュ → sd_dash_grant の行（失効なし・最大期限内・アイドル内）→ contractor_user_id。
  3. 担当者 → 委託先（状態＝有効）→ 今日（JST）有効な契約（valid_from ≤ 今日 ≤ valid_to）→ contractor_contract_stores。
  4. 見える範囲＝契約の閲覧可能期間 ∩ 店舗の適用期間 ∩ 要求された月。範囲外は空（エラー文で理由を詳しく言わない）。
  5. DB関数も同じ導出を自分でもう一度行う（Edge Functionが誤っても関数側で防ぐ二重化）。応答の店舗は、画面用の表示名だけ（内部のUUIDは返さない）。

5-2. 専用のRPCの形（MVP）

  • settle_client_deposits(p_token text, p_month text) → (store_label text, deposit_date date, amount numeric, deposit_count int, day_status text, data_as_of timestamptz) の表（または同じ中身のjson）。security definer・search_path 固定・revoke all from public, anon, authenticated・grant execute to service_role。判定の中身は §1-2。
  • 【事実】集計は既存の bank_deposit_daily(p_from, p_to) を呼んで使う（初版の「service_role からは使えない」は誤りだった）。この関数は、見える範囲の判定 bank_store_visible() が「呼び出しの役割が service_role なら全店を可」と定義されているため、Edge Function（service_role）から呼べば全店分が返る。集計の条件は本部の画面と同じ（counts_as_sales_deposit・store_id 確定・訂正値があれば訂正後・legacy_pending と verified のみ合算）。RPC はその結果を担当店舗の store_id だけに絞り、entries（摘要）・保留金額・各種IDを捨てる。ロジックを二重に持たないので、本部の画面との食い違いが構造上起きない。【推測】RPC の中から呼んでも auth.role()（リクエストの設定値を読む）は service_role のままのはず。実環境のリハーサルで必ず確認する（そうならない場合の代替：同じ条件の集計を RPC に書き、台帳側の変更時に合わせる＋数字一致のテストを常設）。
  • テーブルへの直接のSELECTは委託先の経路に一切つけない（anon・authenticated に新しい権限を出さない）。

5-3. 売上・入金予定額・差額（MVPの後の条件）

  • 元は kd_deposit_daily_v（現金売上・入金額・差額）。kd_deposit_daily は台帳と別の表（BigQuery 経由の写しで、更新が遅れる／明細は50件で切れる等の既知の問題がある）。本調査で、5店舗の日別の入金を台帳と突き合わせた結果（件数のみ）：台帳と kd_deposit_daily が同じ日・同じ金額・同じ件数 818 日／金額か件数が違う日 1／台帳にだけある日 2（うち1日は kd の最終日より後の 11/28＝更新の遅れ）／kd にだけある日 0。入金に関しては、ほぼ一致している。売上・予定・差額（現金売上のレジ照合の確認状況）は未検証のまま。
  • 公開の条件：①同じ店舗・同じ期間で kd_deposit_daily_v と台帳の入金が一致（差の理由を説明できる）②現金売上がレジ照合の確認済み ③契約ごとのスイッチ show_sales_expected（既定false）を本部がONにする。

7. 既存利用者への影響・移行・テスト・承認

7-1. 既存の精算ダッシュボード利用者への影響と移行手順

  1. 段階0（影響なし）：事実確認（承認A。実施済み）。
  2. 段階1（影響なし）：新表1・RPC1を追加（承認B）。既存の表・関数・ポリシー・画面は変更しない。スイッチ表は空＝誰にも出ない。
  3. 段階2（影響なし）：Edge に sd_getDeposits、画面に入金タブを追加（承認C・D）。スイッチOFFの間は、タブを開いても「まだご利用いただけません」だけ。本部の担当者を使い捨ての「テスト委託先」として登録し、使い捨ての店舗・データで通す（終了後に完全削除）。
  4. 段階3（パイロット1社）：個人別アカウントの確認・古いハッシュの置き換え→スイッチON（承認F）。既存の精算書のログインと画面はそのまま。
  5. 段階4：他の委託先へ展開。売上・予定・差額（§5-3の条件後）。
  6. 段階5（別承認）：ログイン全体の改善（アイドル切れ・IP制限・通知・古いハッシュの一斉置き換え）。必要なら §3 の完全版（TOTP・招待）。
  7. 段階6（別承認）：旧GASの凍結の旗・サービスキー・旧シートの平文パスワードの有無を確認し、不要なら除去。

影響を受けるのは「入金タブを使う委託先」だけで、現行のログインは止めない。

7-2. テスト項目

  • 契約外の店舗・日付・月が取れない／契約終了日の前日・当日・翌日／閲覧可能期間の延長あり・なし／店舗が途中で外れる。
  • 他社の担当者のトークンで他社の店舗が出ない／失効後・期限切れ・アイドル切れのトークンが拒否される。
  • （完全版 §3 を作る場合のみ）招待・ログインリンクの再使用の拒否／確認コード5回失敗で無効／同時に2回引き換えても1回だけ成功。
  • （MVP）スイッチ行なし・enabled=false・期間外・担当店舗が空欄／「全店」・旧経路のトークン・12時間超のセッション・役割が委託先以外、のどれでも空（または再ログイン）になる。他の委託先のトークンで他社の店舗が出ない。ログアウト・パスワード変更後のトークンが拒否される。
  • DB上にトークン・コードの平文が無い（ハッシュのみ）／匿名・認証済みのキーから新規表と関数を直接呼べない。
  • 未知のフィールド（store_id・contractor_id など）を付けると拒否される（sd_getDeposits は [トークン, 月] 以外を受けない）。
  • 応答に許可リスト以外の項目が無い（キー一覧の完全一致テスト）。
  • 本部の画面（bank_deposit_daily）と店舗・日付ごとに数字が一致。保留・未確定の行が合算されない。
  • ログ（監査・Edge）に平文のトークン・メール・金額が無い。スマホ幅・ライト／ダークの表示。
  • 本番でのテストは使い捨ての委託先・店舗・契約で行い、終了後に完全削除して0件を確認。

7-3. 承認が必要な点（まとめ）

§1-5の承認B・C・D・F（Aは取得済み）。そのほか：委託先に入金情報を見せることの契約上・銀行規約上の扱い（承認Fに含む）／売上・予定・差額の公開（MVPの後に別承認）／旧GASの鍵・旗・シートの確認と除去（段階6）／ログイン全体の改善（段階5）。

8. 未確認事項（今回の調査でも分からなかったこと）

初版で【未確認】だった次の項目は、今回の読み取り調査で確認できた：sd_dash_grant・sd_dash_snapshot の定義と件数／本番 seisan-api のソースと認証／委託先アカウントの数・メール有無・担当店舗の空欄／verify_jwt・CORS／kd_deposit_daily と台帳の一致度／台帳段階1〜4の本番適用（bank_deposit_daily は存在し、service_role で実行可）。

  1. 旧GAS：本番で凍結の旗（SEISAN_FROZEN）が on か／GAS が service_role の鍵を持っているか／旧シート（権限_精算ダッシュボード）に平文パスワードが残るか・誰が開けるか。読み取りでは確かめられない（GASの設定画面か、凍結を確かめる実行が要る）。
  2. 委託先アカウント3件が、会社ごとの共有か、個人か（共有なら、入金は個人別アカウントにしてから）。
  3. auth.role() が、settle_client_deposits（security definer）の中から呼んだ bank_deposit_daily でも service_role と判定されるか（実環境のロールバック付きリハーサルで確認。そうでなければ代替案：§5-2）。本調査では、書き込み・役割の切り替えを伴うため試していない。
  4. Supabase Edge のクライアントIPのヘッダの信頼性／プラットフォーム側の回数制限（完全版・IP制限を入れる場合に必要）。
  5. 委託先の店舗の入金が、店舗ごとの専用口座か複数店舗の共用口座か（共用なら、店舗への割り当てが正しいかをパイロットで必ず突き合わせる）。台帳の集計対象（店舗確定済みの入金）は全体で 5,673 行、うち legacy_pending（旧データの移行分・照合待ち）4,666 行／verified（照合済み）1,007 行で、5店舗の集計にも両方が含まれる。数字は本部の画面と同じ規則。段階5・6は本番未適用。
  6. 委託先に自店の入金情報を見せることが、委託契約・銀行（PayPay・GMOあおぞら）の規約に反しないか。
  7. 契約の実データ（開始日・終了日・閲覧に関する取り決め）の置き場と、store_operation_relations の網羅性（MVPはアカウント別の閲覧期間で代えるため、必須ではない）。

  9. メールの送信手段（再設定・利用申請の通知に使う旧GASのPDF・メール係。MVPでは新しいメールは送らない）。
  10. パスキー・TOTP の対応状況（完全版を作る場合）。
