## 2. 現在のシステム構成（要点）

### データモデル（hq_プレフィックス、全て `supabase/2026-08-10_hq_tasks.sql` + `supabase/2026-08-11_hq_v2.sql` で定義）
- `hq_task_templates` / `hq_task_template_steps`: 繰り返しタスクのひな形。`hq_generate_today()`が毎日1回（ページ読み込み時にどのクライアントからでも冪等に）実行され、当日分の`hq_tasks`/`hq_task_steps`を自動生成
- `hq_tasks` / `hq_task_steps`: タスク本体・工程（サブタスク）。店舗別チェックは`store_id`で店舗ごとに1行ずつ生成される
- `hq_task_links` / `hq_task_photos`: 添付（URL/マニュアル/写真）。owner列（`task_id`/`step_id`/`template_id`/`template_step_id`のいずれか1つ）で4種類のエンティティに紐付け可能
- `hq_task_comments`: コメント＋@メンション（`mentions`はuuid配列）
- `hq_notify_channels` / `hq_notify_rules`: 共有ルームへの一斉配信設定（管理者が設定。法人/頻度/テンプレ単位で絞り込み可）
- `hq_user_chatwork`: 個人のChatwork設定（`account_id`=共有ルームでの[To:]タグ用、`room_id`=個人専用ルームへの直接配信用。どちらも任意・併用可）
- `hq_corps`: 法人マスタ（追加・非表示切替可能）
- `hq_feature_permissions`: 機能ごとの利用可能レベル（`master`/`manage`/`team`）。マスターのみ変更可。`hq_feature_allowed(feature)`が通知設定・法人管理・テンプレート管理・タスク作成のRLSから参照される（**画面の出し分けだけでなくAPI直叩きにも効く**）

### RLSの基本方針
- 全テーブルRLS必須。`hq_can_manage()`（マスター/社長/本部）が実質的な管理者判定
- **既知の落とし穴**: あるテーブル自身のSELECTポリシーが自分自身への自己参照サブクエリを行うと、`INSERT ... RETURNING`時に新規行が見えずに失敗する。`hq_task_visible_self()`のように「行の値を直接渡す」パターンで回避すること

### Chatwork連携のアーキテクチャ
- サーバー側の秘密情報（`CHATWORK_API_TOKEN`）はSupabase Edge Function `notify-chatwork`（Deno）内でのみ保持。クライアントはroom_id/bodyだけを送る
- CORS対応済み（OPTIONS+Access-Control-Allow-*ヘッダ、version 2でデプロイ済み）
- 送信元は上記フェーズ2のBotアカウント
