作成 2026-11-13。**調査と設計の下書きだけ。** コード・DB・設定は何も変えていない。Slack・LINE・カレンダーへは何も送っていない。DB は SELECT だけ（定義と件数）。個人の値（氏名・電話・メール・LINE の ID・本文）は取り出していない。

前の計画: `ns-portal/docs/計画書_採用管理の共通APIとSlackからの操作_2026-11-12.md`（方針と大きな順番はそのまま生かす。このメモは、**面接確定を実際のコードで確かめた結果**と、**作り方の具体案**を足すもの）。

## 0. 先に結論（3 つ）

1. **依頼主の言う ①〜⑥ は、全部いまの管理システムに「ある」。** ただし、順番を決めて動かしているのは **画面の JS（ブラウザ）** で、サーバー側には部品（保存・送信）しか無い。だから、いまのままでは Slack から「同じ処理」を呼べない。
2. **作り直しは要らない。** 画面の JS がやっている「順番の制御」（カレンダー → 保存 → LINE → 送信済みの印）を、**サーバー側の入口 1 つ**（新しい Edge Function）に写し、部品（保存の RPC・LINE 送信・GAS のカレンダー）はそのまま使う。Slack が先にその入口を使い、画面は後から 1 か所ずつ同じ入口に寄せる。
3. **応募者からの LINE 返信が Slack のスレッドと管理システムの両方に出る仕組みは、もう動いている**（追加の実装は不要）。**スレッドのふつうの返信が応募者へ届く経路は、いま存在しない**（Slack の発言を読む仕組み自体が無い）。

## 2. 共通化の案

### 2.1 入口は 1 つ: 新しい Edge Function `recruit-action`

面接確定は「GAS（外）→ DB → LINE（外）」の 3 つをまたぐため、DB の関数 1 本では出来ない。**サーバー側で順番を持つ場所**として Edge Function を 1 つ足す。DB の変更は必ず RPC を通す。

```
管理システムの画面（ログインしている本人の JWT）─┐
                                                   ├─▶ recruit-action（入口 1 つ）─▶ RPC（権限・照合・保存・記録）
Slack（slack-interact が押した人を特定して渡す）──┘                               ─▶ GAS（カレンダー・Meet）
                                                                                  ─▶ LINE（_shared/line.ts の linePush）
                                             DB が変わる ─▶ いまのトリガー ─▶ recruit-notify ─▶ Slack のスレッド
```

| op（操作） | 中身 | いまの何を使う／写す |
|---|---|---|
| `interview_confirm`（確定・変更） | 日時・方法・場所・「案内を送るか」 | GAS `meet`（そのまま）／`set_interview` の中身（そのまま）／`interviewText` を写す |
| `interview_cancel` | 予定を消す・面接の列を空に・（選べば）応募者へ連絡 | GAS `delete_event`／画面の直接 update を RPC に |
| `message_send` | 応募者へ LINE 1 通 | `linePush`／`line_log_out` の中身（送った人を最初から入れる） |
| `assignee_set` | 担当者の変更 | 画面の直接 update を RPC に |
| （次の段階）`handled_set`・`status_set`・`hire` | 対応済み・状態・採用 | `mark_applicant_handled`・`hire_applicant` の中身 |

どの op も同じ約束（前の計画書 §2 と同じ）: **だれの操作か**（画面＝JWT の本人／Slack＝`actor_id`。`onboarding-notify` と同じ渡し方）・**権限**（`has_feature(actor,'recruit')` かつ `can_see_applicant(actor, 店舗)`。どちらも既存）・**依頼の鍵**・**見ていた値**・**結果を DB に残す**。処理の中から Slack は呼ばない（DB の変化を、いまの通知が拾う）。

### 2.2 足す表（2 つ）と関数

| 足すもの | 役目 |
|---|---|
| `applicant_ops`（操作の記録） | 1 操作 1 行: 応募者・op・だれが・どこから（画面／Slack／自動）・依頼の鍵（**一意**）・中身・状態（処理中／完了／一部失敗／失敗）・**段ごとの結果**（カレンダー: 成功・予定の番号／LINE: 送信済み・失敗理由／保存: 済み）・日時。これが「送受信と操作の履歴・失敗理由」の共通の置き場になり、アラートと再同期の元にもなる |
| `applicant_outbox`（送信箱） | 応募者あての 1 通 1 行: 宛先の媒体・本文・だれが・状態（**送信待ち／送信中／送信成功／送信失敗／結果不明**）・失敗理由・LINE の応答・重複防止の鍵（**一意**）・試しかどうか・できた `applicant_messages` の id |
| `recruit_op_begin` / `recruit_op_step` / `recruit_op_finish`（RPC） | 権限の確認・鍵の重複の確認・**応募者ごとの順番待ち**（同じ応募者の面接操作は一度に 1 つ）・見ていた値の照合・段の結果の保存 |
| `recruit_interview_save`（RPC） | `set_interview` と同じ保存＋予定の番号も **同じ 1 回の update** で（いまは別々）。操作者を引数で受ける。サービス役だけが呼べる |
| `recruit_set_assignee`（RPC） | 担当の変更（前の担当を照合して入れ替える） |

既存の RPC（`set_interview` など）と `line-webhook` は **最初は触らない**（`line-webhook` は本番の重要な関数で、書き換えには「本番から復元して差分確認」の決まりがある）。新しい入口は `_shared/line.ts` の `linePush` を直接使う。

### 2.3 面接確定の中身（画面の JS と同じ順番をサーバーで）

1. `recruit_op_begin`（鍵・権限・順番待ち・見ていた値の照合）
2. 方法が変わるなら古い予定を消す → GAS `meet`（予定の番号があれば同じ予定を直す）。**返ってきた予定の番号を、すぐ操作の記録に控える**（このあと失敗しても、やり直しが同じ予定を使う＝予定が 2 つ出来ない）
3. `recruit_interview_save`（日時・URL・方法・場所・住所・予定の番号・確定した人）
4. 「案内を送る」かつ LINE 連携済みなら、送信箱へ 1 通 → 送る → 成功したら `applicant_messages` に **送った人つき**で記録し、`interview_sent_at` を入れる
5. `recruit_op_finish`。カレンダーだけ失敗・LINE だけ失敗は「一部失敗」として残す（**確定そのものは取り消さない**。いまの画面の動きと同じ）

GAS の URL と合言葉はサーバー側で `app_secrets` から読む（いまはブラウザへ渡している。画面を寄せ終えたら、渡すのをやめられる）。

### 2.4 二重防止（3 つの二重を、それぞれ別の仕組みで）

| 防ぐもの | 方法 |
|---|---|
| 同じ操作の再実行（Slack の再送・二度押し・読み込み直し） | **依頼の鍵**（一意）。Slack＝モーダルの番号（`view.id`）／画面＝確認の窓を開いたときに作る番号。同じ鍵の 2 回目は、前の結果を返すだけ |
| 同時押し（2 人が同時に確定） | **応募者ごとの順番待ち**（`recruit_notice_lock` と同じ作り）＋**見ていた値の照合**（下の 2.5）。後の人には「先に ○○ さんが △△ で確定しました。内容を確かめてください」と返し、何も変えない |
| 面接の二重確定 | 上の 2 つ＋「いまの日時・方法・場所と同じ内容の確定」は、保存も送信もせず「確定済みです」と返す |
| LINE の二重送信 | 送信箱の鍵＝`応募者＋用途＋内容の印`（面接の案内なら 日時・方法・場所・URL の印）。**同じ内容は 1 回だけ**。［送り直す］は、別の鍵をわざと作る明示の操作にする。さらに、LINE の公式の「再送の鍵」（`X-Line-Retry-Key`。同じ鍵の push は LINE 側で 1 回になる。**実装時に公式の説明で再確認**）に送信箱の id を使う |
| 結果不明（LINE の返事が来ない） | 「結果不明」で止める。**自動では再送しない**。再送は同じ「再送の鍵」で行う（LINE 側で二重にならない） |
| カレンダーの二重登録 | 予定の番号の再利用（いまの作りを生かす）＋番号を先に控える（2.3 の 2）＋順番待ち |
| 移行のあいだ（画面は古い経路・Slack は新しい経路） | 新しい入口は送る前に「直近 10 分に、同じ本文の『こちらから』が `applicant_messages` にあるか」を見て、あれば送らない（古い経路には鍵が無いため、その分をここで受ける） |

### 2.5 古いデータでの上書きを防ぐ

- **「押した人が見ていた値」を一緒に送り、サーバーが保存の直前に照合する。** 面接＝見ていた `interview_at`・`interview_mode`・`interview_place`／担当＝見ていた `assignee_id`。違っていたら保存せず、いまの値を返す。
  - `applicants.updated_at` は使わない。理由: 画面が自分の時計で入れている所が多い／LINE を受信しただけでも変わる（関係のない変更で「古い」と判定されてしまう）。
  - 別案: 面接の列が変わるたびに増える番号（`interview_rev`）をトリガーで持つ。照合が 1 つの数で済むが、列が 1 つ増える。→ どちらにするかは §5 で判断。
- Slack 側: ボタンとモーダルに「見ていた値」を持たせる。カードは DB が変わるたびに書き換わるので、古いカードのボタンを押しても、照合で止まる。
- **注意（いまの画面にある上書きの元）**: 詳細の［保存する］（`saveApplicant`・6288〜6303 行）は、**開いたときの面接日時と担当者を、変えていなくても毎回送る**。画面を開いているあいだに Slack で担当や面接を変えると、［保存する］で元に戻ってしまう。→ 画面を「変えた項目だけ送る」に直す（小さな修正・nippo の公開が要る）。Slack からの操作を本番で使い始める前に入れる。
- Slack の表示更新に失敗しても DB は正しいまま: 処理の中で Slack を呼ばないため、失敗は表示だけ。いまの見回り（5 分ごと・`retry` の印）が合わせ直す。**追加の仕組みは不要。**

### 2.6 既存の動きを変えない移し方（順番）

1. **足すだけ**: 表 2 つ・RPC・`recruit-action` を配置。スイッチ（新しい設定 `recruit_actions`: `enabled=false`・`line_mode='dry'`）は OFF。既存の RPC・`line-webhook`・画面は 1 文字も変えない。
2. **Slack から使い始める**（テスト用の応募者だけ → 承認のあと本番）。
3. **画面を 1 か所ずつ寄せる**: 面接確定（詳細）→ 一覧の確定 → 取り消し → 返信欄 → 担当。入口が使えないとき（未配置・スイッチ OFF）は今までの処理に落ちる書き方にする（nippo の今までのやり方と同じ）。寄せた所から、2 つの入口の違い（§1.1 の表）も無くなる。
4. **抜け道を閉じる**（最後）: `set_interview` を新しい保存の関数を呼ぶだけの薄い形にする／［保存する］で「採用」を選んだら `hire_applicant` を通す／GAS の合言葉をブラウザへ渡すのをやめる。

文面（`interviewText`）は画面の JS から TypeScript へ写す。**同じ入力で、いまの画面の関数と 1 文字も違わないこと**をテストで確かめる（オンライン・対面・URL なし・場所の注意書きあり、の 4 通り）。

## 3. Slack の画面の案

### 3.1 スレッドのカード（1 通目。いまのカードに足す）

```
【採用管理】（氏名）
状態：面接調整中
応募店舗：○○店　／　応募媒体：Indeed（ホール）　／　応募日時：11/13 10:05
面接：未定
  本人の希望：① 11/20（木）14:00〜16:00　② 11/21（金）18:00　③ いつでも（平日の夜）
  希望の形式：オンライン
担当：（担当者名）
LINE：連携済み（ここから送れます）        ← 未連携なら「未連携（ここからは送れません）」
[面接を確定] [応募者へ LINE 返信] [担当者を変更] [管理画面で開く]
```

- 面接が決まったあと: 「面接：11/20（木）14:00・オンライン（確定: ○○）／案内: 送信済み 11/13 10:20」＋ `[面接を変更] [面接を取り消す] [応募者へ LINE 返信] [担当者を変更] [管理画面で開く]`。
- 失敗が残っているとき: カードに「⚠️ LINE の案内を送れていません（理由）」「⚠️ カレンダーに登録できていません」＋ `[もう一度送る]` `[もう一度登録]`。
- 希望日時は最大 3 件まで出す（`interview_prefs` の順）。電話・メール・回答の中身は今までどおり出さない。
- 親（1 行）は変えない。

### 3.2 ［面接を確定］（変更も同じ窓）

1. **入力の窓**
   - 日時: 希望日時から選ぶ（`exact`＝その時刻／`range`＝開始時刻を初期値に／`any`＝選べない）＋「別の日時」（日時の入力欄）。どちらか 1 つ。
   - 方法: オンライン／対面（初期値＝いまの値。無ければ本人の希望）。
   - 場所: 対面のとき必須（設定の面接場所から選ぶ。いま 3 か所）。オンラインで場所が入っていても無視する。
   - 応募者への案内: ☑ LINE で送る（連携済みのときだけ。初期値 ON）。**未連携のときは欄を出さず、「LINE 未連携のため、ここからは送れません。確定のあと、案内文をスレッドに出します（Indeed などで送ってください）」と書く。**
2. **確認の窓**（次へ進む形）: 「（氏名）さん・11/20（木）14:00・オンライン」「カレンダー: 登録します（Meet の URL を発行）」「LINE: 下の文面を本人に送ります」＋ **送る文面の全文**（URL は確定後に入る旨を書く）。変更のときは「前: 11/19 15:00 → 後: 11/20 14:00」。
3. ［確定する］→ 窓を閉じる（3 秒以内）→ 裏で `recruit-action`。
4. 結果: スレッドに「📅 面接の日程が決まりました：…（確定: ○○）」「↩️ こちらから（LINE・○○）…」（いまの通知がそのまま出す）。失敗は「⚠️ カレンダーに登録できませんでした（理由）」「⚠️ LINE を送れませんでした（理由）」を担当にメンションして出す。押した人には、本人だけに見える結果も返す。
5. 競合: 「先に ○○ さんが 11/20 14:00 で確定しました」と本人だけに返し、何も変えない。

### 3.3 ［応募者へ LINE 返信］

1. 入力の窓: 「宛先: （氏名）さん／LINE（連携済み）」（変えられない表示）＋本文（複数行・1,000 文字まで）。
2. 確認の窓: 「**この内容が、応募者本人の LINE に届きます**」＋宛先＋本文の全文。
3. ［送信する］→ 送信箱 → LINE。成功: スレッドに「↩️ こちらから（LINE・送った人・日時）」と本文の冒頭。失敗: 「⚠️ 送信できませんでした（理由）」。結果不明: 「⚠️ 送れたか確認できていません。もう一度送る前に、管理画面で確かめてください」。
4. **LINE 未連携（Indeed など）**: ボタンは出すが、押すと「この応募者は LINE と連携していないため、ここからは送れません」と本人だけに返す＋［管理画面で開く］。入力の窓は開かない（送れたように見せない）。
5. スレッドのふつうの返信は、どこにも送られない（読む仕組みが無い）。カードの下に「このスレッドの返信は社内の連絡です。応募者には届きません」と 1 行出す。

### 3.4 ［担当者を変更］

- 窓: いまの担当＋選ぶ欄（採用の権限がある有効な利用者）。確認の窓は付けない（外へ何も送らないため）。
- 保存: `recruit_set_assignee`（前の担当を照合）。スレッドに「👤 担当：A → B（操作: ○○）」（いまの通知が出す）。新しい担当へのメンションは、未対応・日程待ちのときだけ（いまの決まり）。
- **予備担当への通知は、担当の変更とは別**（予備へ知らせても `assignee_id` は変えない）。

### 3.5 ［面接を取り消す］

- 窓: 「（氏名）さんの 11/20（木）14:00 の面接を取り消します。カレンダーの予定も消します」＋応募者への連絡（☐ LINE で知らせる。**初期値 OFF**＝いまの画面と同じ。ON のときは文面を確認の窓に出す）。
- 取り消したあとの状態（`interview_set` のままにするか、`contacted` に戻すか）は §5 で判断。

### 3.6 `action_id` の案（いまの決まり「領域.対象.操作」に合わせる）

`recruit.interview.open`／`recruit.interview.modal`／`recruit.interview.cancel`／`recruit.interview.cancel.modal`／`recruit.line.open`／`recruit.line.modal`／`recruit.assignee.open`／`recruit.assignee.modal`／`recruit.retry`。ボタンの値は `{applicant_id, 見ていた値}` だけ（個人の値は入れない）。

## 5. 確かめられなかったこと・決めてもらうこと

### 確かめられなかったこと

1. **GAS の中身**（Meet の発行・予定の削除・毎日の点検を呼ぶ時計）がリポジトリに無い。未確認: 既にある予定の番号で方法（オンライン⇔対面）を変えたときの動き／担当者を予定に招待しているか／失敗の返し方の全種類。サーバーから同じ GAS を呼ぶ案は、GAS が「合言葉つきの POST をだれからでも受ける」作りである前提（画面からの呼び方を見るかぎり、その作り）。
2. LINE の月の上限と、いまの使用数（LINE を呼ぶ確認はしていない）。
3. LINE の「再送の鍵」の細かい仕様（有効な時間・対象の API）。実装時に公式の説明で確認する。
4. `applicants` の行ごとの権限（RLS）の式の中身（方針の名前だけ確認）。画面からの直接 update が通っていることは、コードから分かる。
5. 面接前日のリマインドは、最後の記録が 10/9。毎日の点検そのものは 11/12 に動いているので、対象がいなかっただけと見ている（推測。直近 30 日で LINE 連携済みの面接は 2 件）。
