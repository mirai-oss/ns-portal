# 指示書（Mac miniセッション用）: `infomart-invoice` に取込口 `invoice-auto-ingest` への送信を追加

発行: 担当D（MacBook）2026-10-13。実行する人: **Mac miniのClaudeセッション**（`.env`のSupabaseサービスキーと、取得済みのCSV/PDF（`ns-daily-import/logs/infomart-invoice/`）がMac miniにあるため）。
前提: `infomart-invoice`（取得＋4段検算）は完成済み。取込口（担当C）は本番デプロイ済み（`invoice-auto-ingest` version 1）。
**必ず先に読む**: 取込口の仕様 [仕様_invoice-auto-ingest_インフォマート請求書の取込口_2026-10-13.md](仕様_invoice-auto-ingest_インフォマート請求書の取込口_2026-10-13.md)（URL・認証・本文・戻り値・注意）／全体の確定事項 [報告_担当D_インフォマート請求書PDF自動取得案_2026-10-13.md](報告_担当D_インフォマート請求書PDF自動取得案_2026-10-13.md) §8。

## 0. やること（範囲はこれだけ）
`infomart-invoice.js`で **「取得OK」（CSV＋PDFが両方あり4段検算が通った）の取引先だけ**を、取込口へ**取引先1社×1か月につき1回**送る。送ると、受け側が下書きの請求書＋明細＋PDF証憑を作り、仕訳下書き→検算→「承認待ち」に流す（**MFには何も登録されない**）。
**範囲外（やらない）**: MFへの登録、PLへの反映、本部タスクの作成、プレコフーズの納品書の取得、24社への拡張、取込口側の変更。指示にない機能は追加しない（先に止めた「振込タスク作成」のような追加は、必ずユーザー確認の後）。

## 1. 送信の作り方
- **機能フラグ**: 環境変数 `INGEST_ENABLE=1` のときだけ送信する（**既定は送らない**）。`INGEST_DRY=1` は送らずに送信予定の内容（取引先・明細行数・合計・PDFのサイズ/sha256）だけをログに出す（シークレット・PDFの中身は出さない）。
- **認証**: 本文の`secret`は `app_secrets` の `invoice_intake_secret`（キー名は取込口の仕様どおり）を**サービスキーでDBから読む**。コード・ログ・WORKLOG・チャットに値を書かない。
- **本文**（仕様どおり）: `source:'infomart'`／`vendor_hint`=取引先名（正式名）／`target_ym`／`infomart_invoice_no`=PDFの請求No／`due_date`=PDFの支払予定日／`pdf:{file_name, base64, sha256}`（sha256は**base64を戻したバイト列**の小文字hex）／`lines`／`totals:{gross,tax}`。
- **`lines`の作り方**: 会計データ出力CSVのうち、**「借方取引先」列がその取引先の行**を、`dept_code`（借方部門の先頭の数字2桁＝インフォマートの部門コード 01〜08）×`tax_category`（借方税区分。`課税仕入 10`→`課税仕入10%`、`課税仕入 軽8`→`課税仕入8%（軽減）`、対象外・非課税はその文言）で集計し、`gross`=借方金額（税込）の合計、`tax`=借方税額の合計、`sub_account`=借方補助科目（参考）。**貸方金額は使わない**（取引先が増えると同じ取引Noに複数取引先が載ってずれる）。
- **店舗はコードのまま送る**（店舗名に変換しない）。`store_no`との06/08の逆転は受け側が`resolve_store('infomart', code)`で解決する。
- **科目・貸方はこちらで決めない**（受け側が`vendor_line_rules`を優先。CSVの科目列は送らなくてよい）。
- 送信前の自己チェック: Σ`gross`＝`totals.gross`、Σ`tax`＝`totals.tax`、PDFの御請求額と一致（4段検算が通っていれば一致するはず。ずれたら送らず「要確認」）。
- **送信先**: `POST https://uuvsxzhpxtghojoubjcc.supabase.co/functions/v1/invoice-auto-ingest`（JWT不要・`Content-Type: application/json`）。
- **戻り値の扱い**:
  - `success:true`（新規）→ `result.json`のその取引先に `ingested:{invoice_id, at}` を記録。
  - `success:true, duplicate:true`（重複）→ エラーではない。`ingested`として記録（`duplicate:true`も）。
  - `vendor_resolved:false` → 送信は成功扱いだが、実行結果に「取引先を確定できず（承認画面で人が確定）」と残し、Larkに1行通知。
  - 422（`pdf_required`/`hash_mismatch`/`totals_mismatch`）→ その取引先を「要確認」にして理由を記録（再送しても直らない＝内容の修正が必要）。
  - 5xx・通信エラー → 次回の実行（翌日10:30）で再送（受け側が二重を防ぐので安全）。同じ実行内の連続リトライはしない。
- **二重送信の抑止**: `result.json`に`ingested`がある取引先は、同じ月は再送しない（受け側でも防ぐが、無駄な呼び出しを避ける）。
- 実行結果（`import_runs.items`・`detail`）に、取引先ごとの「取得OK／送信済み／重複／要確認」を出す。10社すべて送信済みで「月次完了」。

## 2. 進め方（本番に書き込むので段階を踏む）
1. **試走（DRY）**: 2026年9月分で `INGEST_DRY=1 TARGET_YEAR_MONTH=2026-09 node run.js infomart-invoice`。10社ぶんの送信予定（行数・合計・sha256）を確認し、合計がseedの請求額と一致することを確認（例: アールエスエス ¥105,923・伊勢五本店 ¥447,272・シモヤマ ¥608,364）。
2. **1社だけ本番送信**: **ユーザーの了承を得てから**。金額が小さい **アールエスエス**だけ `INGEST_ENABLE=1`＋対象取引先を絞る（例: `INGEST_ONLY=アールエスエス`）で送る。ユーザーに「会計・請求の請求書タブ『承認待ち』にアールエスエスの9月分が出ているか、明細（店舗別・税区分別）とPDF添付を確認」してもらう。同じ内容をもう一度送って`duplicate:true`になる（二重にならない）ことも確認。
3. **残り9社を送信**: ユーザーの確認後に `INGEST_ENABLE=1` で全社。
4. **定期実行に組み込む**: `INGEST_ENABLE=1`を本番の実行環境（`.env`等）に設定してよいかユーザーに確認してから有効化する（毎日10:30の実行で、承認が済んだ取引先から自動送信される）。

## 3. 完了の定義
1. 9月分の10社が、取込口を通して請求書タブの「承認待ち」に出る（MF登録はされていない）。ユーザーが明細・PDF添付を確認済み
2. 二重送信しても1件にまとまる
3. 変更をコミット・push、`ns-portal/WORKLOG.md`冒頭「📍現在の状況」に結果を追記してpush
4. 失敗・要確認があれば原因と対処を結果に書く

## 4. 注意
- 本番に請求書の下書きが作られる操作は、各段階でユーザーの了承を取る（上記2・3・4）。了承なしに全社送信や常時有効化をしない。
- PDF・金額・取引先の情報をログ・WORKLOG・チャットに必要以上に出さない。シークレットは絶対に出さない。
- 想定外の応答（4xxの未知のコード等）があれば、再送せず内容を記録して止める。
