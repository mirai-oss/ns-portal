### 入口をトリガーにした理由（`notifications` を見る形にしなかった理由）
- `notifications` は受信者ごとに行が増える（1 つの応募で人数ぶん）。状態の変更・面接の確定・採用・辞退は入らない。応募フォームの通知文には電話番号が入る（`apply_submit`）。
- 既存の `trg_lark_notify`・`notifications`・`lark_routes` には触れない＝Chatwork はそのまま出続ける（並行できる）。
- 弱点: 「同じ求人への Indeed 再応募」で列が何も変わらない場合は拾えない（求人・勤務地・返信用の宛先のどれかが変われば拾える）。

## 3. 親 1 件を保証する仕組み（三重）
1. **控えの一意制約**: `notice_cases` の (type_key, ref_table, ref_id)。応募者 1 人に控えは 1 行しか入らない。
2. **先に権利を取る**: `recruit_notice_claim(応募者)` が true を返した実行だけが親を投稿する。同時に呼ばれても、行のロックで 1 つだけが true。親の ts が控えに入ったら、二度と true にならない。
3. **notify-slack の重複防止**: 親は `dedupe_key = recruit:parent:<応募者ID>`、台帳の番号も応募者 ID から決まる固定の UUID。送信済みなら notify-slack は送らずに「送信済み」と ts を返す。

加えて、**応募者ごとに処理を 1 つずつ**にする（`recruit_notice_lock`／`unlock`）。採用→招待の送信のように出来事が続けて起きても、スレッドへの書き込みが重ならない。処理中に次の知らせが来たら「やり直しの印」を付け、処理中の実行がもう一周する。

### 途中で失敗したとき
| どこで止まったか | どうなるか |
|---|---|
| 親の送信に失敗（Bot 未参加など） | 控えに ts は入らない。5 分後から権利を取り直せる。見回りが 5 分ごとに再試行（応募から 3 日まで）。同じ番号・同じ鍵で送る |
| 親は出たが、カード・控えの保存の前に止まった | 取り直した実行が同じ鍵で親を送る → notify-slack が「送信済み」と ts を返す → 親は増えず、カードから続ける |
| スレッドへの返信に失敗 | 「前回の状態」を進めない＋やり直しの印。次の知らせか見回りで同じ行をもう一度出す（出せた行は台帳が覚えているので二重にならない） |
| pg_net の呼び出し自体が失敗・取りこぼし | 見回り `recruit_notice_sweep`（5 分ごと・1 回 30 人まで）が、控えより新しい応募者・親の無い新規応募を拾う |
| Webhook の重複受信 | やり取りは既存の一意制約（source_ref）で行が増えない＝トリガーも動かない。届いても、台帳で「出した」と分かるので書かない |

**残る穴（正直に）**: Slack が投稿を受け付けた直後、notify-slack が台帳に「送信済み」と書く前に落ちた場合だけ、やり直しで親が 2 件になりうる（ごく短い瞬間）。そのときは、控えが指していないほうの親を手で消す。

## 4. 統合（同じ人の応募をまとめる）
- 調べた事実: 取り込みの時点で `applicant_match(氏名, 電話, メール)` が既存の応募者を探し、いれば新しく作らずその人に足す（自動）。管理画面では `applicant_similar` が候補（ほぼ確実／同姓同名／似ています）を出し、人が［まとめる］（`merge_applicants(残す, 消す)`）か［別の人です］（`mark_applicants_not_same`）を押す（手動）。**この通知は、統合の判定を一切しない。既存の判定の結果に従うだけ。**
- 自動で足された場合: 応募者の行は増えない＝親も増えない。スレッドに「再応募」「フォームの回答」の行が出る。
- 人がまとめた場合（消える側の行が無くなったことを確かめてから、`recruit_notice_merge(残す, 消す)`）:
  - 残る側に親が無い → 控えの ref_id を残る側へ付け替える。**同じ親・同じスレッドが残る側のものになる**（新しい親は作らない）。
  - 両方に親がある → 残る側を正にする。消える側の親は `｜統合済み`＋［統合先のスレッド］にして閉じる（Slack のメッセージは別のスレッドへ移せないため。消さない）。残る側のスレッドに `🔀 まとめました`＋統合前のスレッドへのリンク。
- 「あやしい場合は確認待ち」: 管理画面の候補表示のまま（人が押すまで別々の親）。Slack 側で勝手に 1 件にしない。
- **要確認**: `indeed_intake` は氏名だけを渡して `applicant_match` を呼んでいる（電話・メールは渡していない）。`applicant_match` が氏名の一致だけで「同じ人」とするなら、決定「氏名が同じだけでは統合しない」と食い違う（Indeed の同姓同名が、既存の人のスレッドに「再応募」として出る）。中身はリポジトリに無く未確認。直すなら `applicant_match`／`indeed_intake` の側で、この通知の側では直せない。

## 6. 過去の応募者の扱い
- 過去分をまとめて流し込む処理は作っていない。スイッチを入れた時刻（`since`）より前からいる応募者は、**動きがあったときだけ**スレッドを作る: 応募者から返信が来て未対応／これから面接がある／切り替え後に採用が決まった／切り替え後にフォームの回答が届いた。古い応募者を不採用に整理しただけでは作らない。

## 7. メンションの決め方（既存の `notice_mention_rules`・`notice_mention_targets` に種類を足す）
- `recruit`/`assignee`: 担当者（applicants.assignee_id）がいれば、その人。
- `recruit`/`open`: 担当者がいなければ、応募店舗の店長＋その店舗の担当チーム長。
