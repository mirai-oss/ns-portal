# 設計メモ: 店舗カメラの人流・店内オペレーション分析（構想段階・質問事項）

作成: 2026-08-27（司令塔） ／ 状態: **構想段階＝§4の質問に回答をもらってから設計書を作る**（実装割当なし）
発端: 2026-08-27ユーザー要望「監視カメラから人流データを測って、何人通って・何人が看板を見て・何人入店したかをデータ利用したい。店内カメラからは注文から提供までの時間、どのお客様がリピーターか、注文の相関、ランチで注文から5分以内に提供されていなければアラートを出してプリンターから印刷したい」

---

## 1. 要望の整理（やりたいこと一覧）

| # | やりたいこと | 場所 |
|---|---|---|
| ① | 店頭の通行人数 → 看板を見た人数 → 入店した人数（ファネル） | 店頭カメラ |
| ② | 注文から商品提供までの時間の計測 | 店内 |
| ③ | どのお客様がリピーターか | 店内 |
| ④ | 何を注文した人が次に何を頼むか（注文の相関） | 店内 |
| ⑤ | ランチで注文から5分以内に未提供ならアラート＋キッチンプリンター印刷 | 店内 |

## 2. 重要な提案: 「カメラでやること」と「diniiのデータでやれること」を分ける

②③④⑤は、**カメラ映像よりも、既に導入済みのモバイルオーダー（dinii）の注文データの方が正確・低コストで実現できる可能性が高い**。dinii注文データは毎朝BigQueryへ自動取込済み（`bqLoadOrders`・明細分析タブで稼働中）のため、新しいハードウェアなしで着手できる。

| # | カメラ案 | dinii案（提案） |
|---|---|---|
| ② 提供時間 | 映像から料理到着を画像認識（開発難度高） | 注文時刻はdiniiにある。**提供時刻がdiniiのステータス（提供済み操作）に残っているかが鍵**（要調査） |
| ③ リピーター | 顔認識（**個人情報保護法上の本人同意・店頭掲示など法的ハードルが高い**） | diniiの会員ID・電話番号ベースの再来店判定（利用規約の範囲内で。要調査） |
| ④ 注文相関 | 映像からは不可能 | **dinii明細データだけで今すぐ可能**（同一伝票内の組み合わせ分析） |
| ⑤ 5分アラート | 映像判定＋プリンター連携 | dinii注文時刻＋「提供済み」操作時刻の差分でアラート判定→**印刷はキッチンプリンターのAPI/連携方法次第** |
| ① 店頭人流 | **カメラでしかできない**（本命） | 不可 |

→ **提案する進め方**: Phase 0=dinii側の調査（提供時刻・会員データが取れるか）→ Phase 1=④注文相関と②提供時間をdiniiデータで先行 → Phase 2=①店頭人流のカメラPoCを1店舗で → Phase 3=⑤アラート印刷。

## 3. カメラ側の技術方式（回答待ちのため概要のみ）

- 既設カメラの映像を取り出せるか（機種依存: RTSP対応/クラウドAPI/取り出し不可）で方式が全く変わる
- 取り出せない場合は「人流カウント専用のAIカメラ・センサーを店頭に1台追加」する方が既設流用より安く済むことが多い
- 顔認識によるリピーター判定は法的配慮（利用目的の掲示・同意）が必要なため、**やるとしても最後**。人数カウント（個人を特定しない）とは要件が別物

## 4. ユーザーへの質問

- **Q1. カメラの現状**: 今付いている監視カメラのメーカー・機種名（またはスマホで見るときのアプリ名）と、台数（店頭向き・店内向きの内訳）を教えてください
- **Q2. 映像の保存先**: 映像は今どこに残っていますか？（レコーダー本体／SDカード／クラウド契約）
- **Q3. PoC店舗**: まず1店舗でお試しするならどの店舗ですか？（店頭の通行量が多く、看板がカメラに映っている店舗が向いています）
- **Q4. diniiの操作実態**: キッチン・ホールで料理を提供したときに、diniiで「提供済み」のような操作をしていますか？（していれば②⑤はカメラなしで実現できる見込みが高くなります）
- **Q5. キッチンプリンター**: ⑤で印刷したいプリンターは何ですか？（diniiの伝票プリンター／別のレシートプリンター。機種名が分かれば連携可否を調査します）
- **Q6. 予算感**: 店頭人流のPoCにハードウェア追加（数万円〜）が必要になった場合、1店舗分の投資は許容範囲ですか？
