# N-Styleグループ ダッシュボード統合・アカウント1本化 要件定義書

作成日: 2026-08-05 ／ 版: 3.2（2026-08-17: 外部レビュー反映＋旧記述の矛盾解消・法人マスタ統一の前倒し・AIアクセス厳格化）

## 1. 背景と目的

グループ内に4つのシステムが並立し、URL・アカウント・店舗の呼び名がバラバラになっている。

| システム | 画面 | データ | ログイン方式（現状） |
|---|---|---|---|
| 経営ダッシュボード (tori-dashboard) | GitHub Pages | GAS + スプレッドシート + BigQuery | 独自ID/PW（アカウントシート） |
| 精算ダッシュボード (seisan-dashboard) | GitHub Pages | GAS + 精算書スプレッドシート | 独自ID/PW（権限シート） |
| 社内情報管理システム (ns-info-system) | Vercel (Next.js) | Supabase `wciefkpooncglahqdtmu` | Supabase Auth（メール+PW） |
| 日報・週報システム (nippo) | GitHub Pages | Supabase `uuvsxzhpxtghojoubjcc` | Supabase Auth（メール+PW） |

目的:
1. **アカウントの1本化** — 1人につき1つのメールアドレス+パスワードで全システムに入れる状態にする
2. **入口の1本化** — ポータル1ページから権限に応じて各システムへ遷移
3. **店舗マスタの1本化** — 社内店舗番号（01〜12）を全システム共通の正準キーにする

### ハブを日報プロジェクトにする根拠

- 日報システムには決定した役割体系がほぼそのまま実装済み（`CEO=社長 / HQ=本部 / TEAM=チーム長 / TENCHO=店長 / SHAIN=社員 / AL=アルバイト`）。マスターのみ追加
- 従業員全員（アルバイト含む）のアカウントが既に存在する唯一のシステム
- stores（8店舗）の店舗名が経営ダッシュボードの正式名と完全一致
- 招待リンク・スマレジ連携・Lark通知・権限マトリクスなどアカウント管理機能が既に揃っている
- 社内情報管理システム側のSupabaseは利用者が少数（社長・本部中心）なので、後からハブへ寄せる方が移行が小さい

## 5. 認証アーキテクチャ

### フェーズ1（今回）
- **ポータル** (GitHub Pages / `mirai-oss/ns-portal`): ハブのSupabase Authへメール+PWでログイン → `users`テーブルから役割を取得 → マトリクスに従いシステムのタイルを表示
- **日報**: 既にハブ直結。同じメール+PWでそのまま入れる（=1本化済み）
- **経営D・精算D・社内情報**: タイルからリンク遷移（ログインは当面それぞれの方式）

### フェーズ1b（経営ダッシュボードのSSO）
- app.jsのログイン画面に「統合アカウントでログイン」を追加
- 流れ: ポータル/経営DでSupabaseログイン → `access_token`をGASへ送信 → GASが`GET {SUPA_URL}/auth/v1/user`で検証（公開キーのみで可・秘密鍵不要） → メールアドレスをアカウントシートの新設「メール」列と突き合わせ → 従来のセッショントークンを発行
- 既存ID/PWログインは並行稼働（削除しない）。GAS再デプロイ1回必要

### フェーズ2
- 精算D本部ユーザーのSSO（委託先は対象外・従来どおり）
- 社内情報管理システムをハブプロジェクトへ移設（テーブルは`info`スキーマ等に分離して衝突回避）し、アカウントを完全統合
- 独自ドメイン（例: `portal.ns0314.com`）+ 配下パスに集約 → **同一オリジンになるためログインセッション自体も共有可能になる**

### フェーズ3（脱スプレッドシート）
- 経営ダッシュボードのデータ基盤をGAS+シートから移行する。**売上系のRaw・時系列データの移行先はBigQuery**（Raw→Staging→日次Fact→集計テーブル。§16参照）。**RawをSupabaseへ全面移行することはしない**。ダッシュボード表示に必要な集計結果のみSupabaseへ同期することは可
- 現状の初回表示28秒はGAS往復が原因（実測済み）。移行前の暫定策としてGAS側の無駄取り（setupIfNeeded毎回実行の停止等）で5〜7秒まで短縮可能

## 6. 非機能要件・制約

- 稼働中の自動処理（Lark自動日報 毎日12:00 / 精算トリガー 1日・5日・18日 / ns-daily-import 毎朝 / PL取込）を止めない。既存テーブル・シートの列削除や改名はしない（追加のみ）
- 公開リポジトリに秘密情報を置かない（Supabaseのpublishableキーは公開前提の設計なので可。service_roleキー・PATは絶対に不可）
- ハブのRLSポリシーは今回変更しない（列追加・行追加のみ）
- 委託先がハブのアカウントを持たないこと（精算の分離要件）

## 6.5 データ横断の方針（2026-08-05 追記）

ユーザー要望: **「どの管理システムからでも横断して情報がやりとりできる状態にしたい」**。
具体例として、従業員の給与情報・評価項目・評価点数を社内情報管理システムか日報のどちらかで見たい。

そのための原則:

1. **同じ人・同じ店舗は同じIDで指す** — 人＝ハブ `public.users.id`、店舗＝`store_no`（01〜12）。
   新しいテーブルを作るときは、氏名や店舗名の文字列ではなく必ずこのIDを外部キーにする。
2. **評価データはハブに置く** — 評価は「日報の提出状況・売上実績・勤怠」と突き合わせて意味を持つため、
   日報と同じデータベース（ハブ）に置くのが最も自然。社内情報管理システム側から見せる場合も、
   ハブの `info` スキーマへ移設後であれば単純なJOINで済む。
3. **給与は分離した金庫に置く** — 社内情報管理システムは既に `employee_salaries` を
   別テーブル＋RLSで保護している。移設後も同じ分離を維持し、閲覧は役割ベースで絞る。
4. **どのシステムから書いても正は1箇所** — 例: 評価点数を日報から入力しても社内情報から入力しても、
   保存先は同じ `info.employee_evaluations`（仮）1テーブルとする。

この方針により、後から「日報側で評価を見る」「社内情報側で見る」のどちらにも対応できる。

# 第2期（フェーズ3）: 機能拡張の配置地図 — v2.0

## 8. 大方針: 4つの「家」の役割を固定する

判断基準は **「誰が毎日触るか」** と **「機密かどうか」**。**業務データはハブ（Supabase）に、売上・POS・広告等の分析データはBigQueryに置き**（正本の分離は§16）、画面だけを適切な家に配る。同じ人・同じ店舗を同じIDで指すことで、どの画面から見ても同じ情報になる（横断要件の土台）。

| 家 | 役割 | 対象者 |
|---|---|---|
| ポータル (ns-portal) | 入口・お知らせ・検索・本部タスクボード | 全員（機能は役割で出し分け） |
| 日報・週報 → **現場アプリ** | 現場が毎日触る場所（チェックシート・マニュアル・シフト・打刻・発注） | 全従業員 |
| 経営ダッシュボード | 数字を見る場所（分析・KPI・シミュレーション結果） | 店長以上 |
| 社内情報管理 | 機密金庫（給与・評価・契約書・口座・ID/PW） | 権限者のみ |

| ⑮ | **AI窓口（エージェント型に格上げ）** | 従来の「マニュアル回答ボット」構想を拡張し、**Supabase・BigQuery・スプレッドシートから実データを取得して、抽象的な質問にも正確な数字・内容で答えるエージェント**へ。例:「先月の恵比寿の売上は？」「精算書の締めっていつだっけ？」 | 窓口UI=ポータル＋現場アプリ。中継サーバー（Edge Function等）経由でAI APIを呼ぶ（キーはサーバー側） |

### ⑬経費申請の要件詳細（初期案・質問回答で確定）
- 申請項目: 金額／日付／店舗／科目（プルダウン）／写真（レシート・複数可）／メモ
- 承認フロー: フロー定義を画面で作成（例: 店長申請→チーム長→本部。金額による分岐は要確認）
- 状態: 申請中→承認済み→（差戻し）。履歴と承認者・日時を全部記録
- 承認完了時: 指定した本部タスクテンプレートから自動でタスク生成（例:「経費精算の振込処理」）→既存のhq_タスク基盤に接続
- 経理連携: 承認済みデータはCSV出力可（PL管理システムへの自動連携はフェーズ2）

### ⑭役職テストの要件詳細（初期案・質問回答で確定）
- テスト作成: 役職ごとに問題セットを作成（選択式中心。記述式の扱いは要確認）
- 受験: 現場アプリから受験。制限時間・合格点は問題セットごとに設定
- 結果: 点数・合否・受験履歴を保存。評価制度（⑪）のKPIと並べて閲覧できるようにする
- 権限: 問題と正答は受験者から見えない（RLSで強制）。成績の閲覧=本部以上＋本人

# 第3期補強: データ基盤・保存先・AIエージェント方針 — v3.1（2026-08-17）

外部レビュー（他AI・エンジニア）の指摘10項目とユーザー回答を反映。**既存の要件・ロードマップは維持**し、以下を追加・明確化する。

## 16. データの正本（Source of Truth）の明確化 — Supabase と BigQuery の分離

「データはすべてハブ（Supabase）」という従来の表現を改め、**業務系=Supabase／分析系=BigQuery**に正本を分離する。

| データ | 正本 | 備考 |
|---|---|---|
| ユーザー・従業員・役割・権限 | **Supabase** | users / info.employees ほか |
| 法人・店舗マスタ | **Supabase** | store_no 01〜12。⚠️法人マスタは現在 `hq_corps` と `info.corporations` が並存→**§16.5の方針で経費申請より先に一本化する** |
| 日報・週報／タスク／チェックシート／経費／テスト／評価／シフト提出／通知・チャット | **Supabase** | 業務トランザクション |
| POS売上Raw・売上明細・広告実績Raw・大量時系列・分析用勤怠 | **BigQuery** | 既にDinii明細はBQが正本（tori-analytics） |
| 売上の日次集計（現在） | スプレッドシート `分析_日別店舗`（暫定の正本） | 脱スプシ時にBQの日次Factへ移行 |

**売上パイプラインの目標形（脱スプシ時に適用）:**
`Raw → Staging（店舗ID・媒体ID・日付を正規化）→ 日次Fact → 用途別集計テーブル → ダッシュボード`
- ダッシュボードからRawへ直接重いSQLを打たない。日付パーティション＋店舗/媒体クラスタリングを設定
- SupabaseへBQの全データを複製しない。**アプリに必要な集計結果だけ**をSupabaseへ同期（例: 日次店舗売上サマリー）
- どのテーブルも「正本はどちらか」を必ずこの表に追記してから作る

## 16.5 法人マスタの一本化（経費申請より先に実施・v3.2で確定）

現在、法人マスタが `hq_corps`（本部タスク用）と `info.corporations`（社内情報管理）に二重化している。**経費申請の実装前に一本化する。**

| 論点 | 方針 |
|---|---|
| 正本テーブル | **`public.corporations` を新設して正本にする**（id uuid＋`corp_code`（'nstyle'等の短いコード）＋名称＋表示順＋有効フラグ） |
| 共通法人ID | 以後の全機能は `corporation_id`（public.corporations.id）で法人を参照。文字列名やコード直書きで持たない |
| 既存2テーブルの扱い | データはinfo.corporations（4社・codeあり）を種にして正本へ投入。`hq_corps`・`info.corporations` は**削除せず**、正本へのID対応列（or 同一IDの引き継ぎ）を持たせて互換維持→参照側（tasks.html等）を順次正本へ切替→切替完了後に旧テーブルを読み取り専用化 |
| 店舗マスタとの関連 | `stores` に `corporation_id` を追加（既存列は削除しない）。店舗→法人が引ける状態にする |
| 壊さない移行 | 追加のみ（新テーブル・新列・ビュー）。既存機能のRLS・列は変更しない。切替は画面ごとに段階的に行い、都度E2Eで確認 |

## 17. ファイル保存先の方針（写真・動画・数字・文章の切り分け）

**原則: 「数字と文章はDB、画像はSupabase Storage、視聴用動画はYouTube、大容量アーカイブは将来GCS」。無意味に分散させない。**

| 種類 | 保存先 | 理由 |
|---|---|---|
| 数字（売上・件数・点数…） | DB（Supabase/BQ。§16の正本表に従う） | ファイルに数字を入れない。集計・検索・権限制御のため |
| 文章（マニュアル本文・お知らせ・メモ・注意事項） | DBのテキスト列 | 全文検索・AI窓口の知識ソースになる。WordやPDFで持たない（既存書類のPDF保管は可） |
| 業務写真（チェック証拠・タスク添付・レシート・日報写真・プロフィール） | **Supabase Storage** | 稼働実績あり・RLSでアプリの権限とそのまま連動・Pro化で100GB |
| 業務PDF（契約書・精算書控え等） | Supabase Storage（機密は非公開バケット＋info.documents） | 同上 |
| 視聴用動画（マニュアル・研修・社長発信） | **YouTube限定公開**＋DBにURL | 配信・画質変換・通信量をYouTubeに任せる。Storageへの動画直置きは原則禁止 |
| 大容量・長期アーカイブ・バックアップ・AI分析用大量データ | **Google Cloud Storage（将来導入）** | **今は導入しない**。移行判断は容量・転送量・長期保管ニーズ・バックアップ用途・コストを総合的に見て行う（「Storage使用量が数十GB規模に達したら検討開始」はあくまで**目安**であり絶対条件ではない） |
| 既存のGoogle Drive運用（精算書添付など） | 現状維持 | 動いているものは移さない |

**業務写真の保管にSupabase Storageを選ぶ理由（ユーザー案への回答）:** ①Supabase Auth/RLSと権限を統合しやすく、システムの役割・公開範囲の制御がそのまま効く ②user_id・store_id等とファイルを直接紐付けて管理できる ③Private Bucketでアプリの権限と一体化できる ④アップロード・表示・削除がアプリ内で完結する。Google Driveは「人が手で管理する書類置き場」として優秀なので、既存のDrive運用（精算書添付など）はそのまま維持する。

## 18. AIエージェント方針（⑮の具体化）

**最終像:** Supabase（業務）＋BigQuery（売上・広告）＋スプシを横断して「昨日売上が悪かった店舗と原因仮説」「社長が今週確認すべき問題を重要度順に」などに答えるエージェント。

**候補と選定方法（現時点で採用は確定しない）:**
- 候補A: **Hermes Agent**（Nous Research製・MIT・完全セルフホスト・MCP対応・モデルはOpenRouter/カスタムエンドポイント/ローカルまで自由・テレメトリなし）
- 候補B: **Claude API等で独自エージェント**（Edge Function/小型サーバー上に自作。面は最小・完全制御）
- 比較軸: 接続性／セキュリティ／MCP・API対応／モデル選択自由度／コスト／保守性／スケジュール実行／サブエージェント／権限制御（AIフェーズ着手時に調査レポートを作成して決定）
- **モデルは特定ベンダー固定にしない**（Claude/OpenAI/Gemini等を切替・併用できる抽象化を挟む）

**権限は段階開放（絶対原則）:**
| Phase | できること |
|---|---|
| 1 Read Only | データ取得・分析・異常検知・報告・提案のみ |
| 2 Draft | タスク案・通知文案・改善案の下書き作成（実行は人間） |
| 3 低リスク操作 | 明示的に許可した範囲のみ自動実行 |
| 4 重要操作 | 常に人間承認必須 |

- **給与変更・振込・経費承認・評価確定・ユーザー削除・権限変更をAIが無承認で実行できる設計は禁止**

**DBアクセスの厳格化（v3.2追加・必須要件）:**
1. **AIエージェントにSupabaseのservice_role/secretキーを直接渡さない**（いかなるPhaseでも）
2. **AI専用の最小権限アクセス経路**を用意する: AI専用DBロール（PostgresのGRANTで物理制限）＋中継API経由のみ
3. AIに公開するのは**明示的に許可したView・RPC・APIだけ**（テーブル直アクセスを許さない）
4. **AIが取得できる範囲（どの法人・どの店舗・どの従業員のデータか）を設定で明示**し、範囲外は物理的に取得不可にする
5. **AI監査ログ必須**: 「どのAIが・誰の権限で・いつ・何を読んだ/変更した/実行したか」を `ai_audit_logs`（仮）に全件記録
6. **給与・口座・契約書等の機密情報は、AIが必要とする場合でもデフォルト参照不可**（個別に明示許可した場合のみ・許可も監査ログに残す）
7. AIが重要操作を実行する場合（Phase 3以降）は、**操作のたびに「依頼したユーザー本人の権限」と「人間の承認」の両方を検証**する

## 19. シフト・勤怠・給与の責任分界（⑤の具体化）

**給与計算・法定勤怠管理は自作しない。** スマレジAPI調査の結果を踏まえ、次の分界で設計する。

| 領域 | 担当 |
|---|---|
| シフト提出・未提出管理・通知・シフト公開・必要人数シミュレーション・管理画面 | **自社システム（ハブ）** |
| 正式な勤怠記録・打刻の正本・有給・給与計算に必要なデータ | **スマレジ・タイムカード** |
| 給与・会計・振込 | **マネーフォワード** |

## 20. 経費申請の確定仕様（⑬・ユーザー回答反映）

- **初期版: 申請者→承認者の1段階承認**。承認者は申請者の役職・所属から自動設定（変更も可）
- データ構造は**多段フローに拡張できる形**で最初から作る（`expense_flows`=フロー定義、`expense_approvals`=承認ステップ記録。金額分岐・追加承認は定義追加だけで対応）
- 初期対象=**立替経費**。会社カードは `payment_type` 列で後から追加
- 管理項目: 申請者／利用日／金額／用途／勘定科目候補／店舗・部門／領収書写真（複数）／備考／承認者／ステータス／申請日時／承認日時
- 承認完了→**指定した本部タスクテンプレートからタスク自動生成**（既存hq_基盤に接続）
- 将来拡張の設計余地: 領収書OCR/AI読取→金額・日付・取引先抽出→科目/店舗の自動候補→人間確認→**マネーフォワード連携**（CSV出力から開始）
- UI最重要要件: 申請=3タップ級（金額・写真・用途）、承認=通知から1タップ（承認/差戻し）

## 21. 役職テストの確定仕様（⑭・ユーザー回答反映）

- 問題形式: **選択式＋記述式の両対応**（初期は選択式中心）
- 合格ライン: 役職・テストごとに本部が設定
- 再受験: 可能。**再受験ルール（即時／◯日後）はテストごとに設定**
- 記述式のAI採点は将来機能（最初は人間採点）
- 問題・正答は受験者から見えない（RLS強制）。成績閲覧=本部以上＋本人

## 22. 共通ID・権限設計の原則（全機能共通・最優先）

- ID: user_id（users.id）／法人=共通法人マスタ（§16のTODO完了後）／store_id（store_no連動）／役割。**機能ごとにバラバラのIDを持たない**
- 権限の基本形: **役職 × 法人 × 担当店舗 × 本人** に対して **閲覧・作成・編集・承認・削除・出力** を制御
- 既存実装（portal_permissions・hq_の公開範囲・checklistの管理関数）はこの原則の部分実装。**経費申請の実装時に共通の権限判定関数群として整理し、以後の新機能はそれを使う**
