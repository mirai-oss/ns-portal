## 3. 共有ハブDBの「持ち主」整理（最重要）

同じSupabaseプロジェクトの中に、複数システムが自分のテーブルを持ち寄っている状態。**接頭辞でおおよその持ち主がわかる**が、例外もあるので下表で確認すること。

| テーブル群 | 持ち主 | 他システムからの扱い |
|---|---|---|
| `hq_*`（`hq_tasks`/`hq_task_templates`/`hq_task_steps`/`hq_notify_*`/`hq_feature_permissions`など） | **本部タスクボード（ns-portal）** | 他システムは**触らない**。読むことも基本ない |
| `portal_*`（`portal_permissions`/`portal_posts`など） | **ポータル（ns-portal）** | 他システムは触らない |
| `checklist_*`（`checklist_templates`/`items`/`checks`） | **日報（nippo）の機能**（SQL定義だけns-portalリポジトリ内にある） | nippoが自由に使ってよい。今のところ他システムからの参照なし |
| `manual_items` | **日報（nippo）のマニュアル機能** | nippoが自由に使ってよい。**ただし本部タスクボードが`id`/`label`/`url`/`category`/`is_active`/`sort_order`列をFK参照・SELECTしている**（`category='本部マニュアル'`の行を一覧取得）。この5〜6列の意味・型を変える場合は本部タスクボード側の実装にも影響するので要連絡 |
| `users` | **共有（両方が使う）** | 列追加は基本安全。**`role`の取りうる値**（`CEO`/`HQ`/`TEAM`/`TENCHO`/`SHAIN`/`AL`）と**`is_master`/`is_active`の意味**は本部タスクボードのRLS・権限判定が直接依存しているため、値の意味を変えたり列を消したりしない（詳細は4章） |
| `stores` | **共有（両方が使う）** | `id`/`is_active`/`sort_order`/`store_no`列は本部タスクボードの店舗別チェック機能が直接参照。列追加はOK、既存列の削除・型変更はNG |
| `report-photos`（Storageバケット） | **共有** | 両システムとも `{uid}/....` の形でパスを切っている（先頭フォルダ＝アップロードした人の`auth.uid()`必須というRLSポリシーに従う必要がある）。このパス規約を崩すとアップロードがRLSで弾かれる |
| それ以外の日報既存テーブル（`reports`/`attendance_records`/`teams`など） | **日報（nippo）専有** | 本部タスクボードは一切触っていない・参照もしていない。自由に変更してよい |

## 4. 日報（nippo）を別PCで修正するときに絶対にやってはいけないこと

1. **`hq_`で始まるテーブル・関数・RLSポリシーを ALTER / DROP / RENAME しない**。本部タスクボードが全面的に依存している。読むだけなら実害はないが、通常は読む必要もないはず
2. **`portal_`で始まるテーブルも同様に触らない**
3. **`users.role`が取りうる値を増減・変更しない**（`CEO`/`HQ`/`TEAM`/`TENCHO`/`SHAIN`/`AL`の6種。本部タスクボードのRLS関数（`hq_can_manage()`/`hq_feature_allowed()`/`hq_task_visible()`など）がこの値で分岐している）
4. **`users.is_master`・`users.is_active`列を削除したり、意味を変えたりしない**（同上、権限判定の土台）
5. **`stores.id`/`is_active`/`sort_order`/`store_no`列を削除・型変更しない**（本部タスクボードの店舗別チェック機能が直接参照。特に`store_no`は社内の店舗番号統一の要でもある。詳細は記憶ファイル「店舗番号の採番と突き合わせの現状」参照）
6. **`manual_items`の`id`/`label`/`url`/`category`/`is_active`/`sort_order`列を削除・リネームしない**（変更したい場合は本部タスクボード側で`ensureManualItems()`〔`tasks.html`内〕を合わせて直す必要がある）
7. **`report-photos`バケットのRLSポリシー（先頭フォルダ=`auth.uid()`）を変更しない**。パスの先頭を`{uid}/...`以外にすると、両システムの写真アップロードが軒並み失敗する
8. **既存のマイグレーションSQLファイルを編集しない**。新しい変更は日付入りの新規ファイルを追加する（ns-portal側の運用ルールと同じ。nippo側にSQL置き場が無ければ`nippo/supabase/`を新設するか、ns-portalの`supabase/`に日付ファイルを足す形でも可＝実際に`checklists.sql`はその形で運用されている）
9. **SQL実行はManagement API経由・curl必須**（Pythonのurllib等はCloudflareにブロックされる）。実行前後で`git fetch`、他スレッドが同時に本部タスクボードを触っていないか意識する
10. **本番データを直接テストに使わない**。テストは一時ユーザー（Auth Admin APIで作成→削除）で行い、hq_/portal_以外のテーブルであっても実ユーザー・実店舗のデータは変更しない

### 触ってよいもの（nippoの管轄）

- `checklist_templates`/`checklist_items`/`checklist_checks`（自由に拡張可。ただし変更したらSQLファイルを残すこと）
- `manual_items`のデータ本体（行の追加・編集）、列追加（削除・リネームでなければ自由）
- 日報既存のテーブル群（`reports`/`attendance_records`/`teams`/`chat_rooms`など、本部タスクボードが触れていないもの全部）
- `nippo/index.html`自体
