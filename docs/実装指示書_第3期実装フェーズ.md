## B. 法人マスタ統一（要件定義書§16.5）

**目的: `hq_corps` と `info.corporations` の二重化を解消し、正本 `public.corporations` を作る。経費申請はこの共通法人IDを使う。**

1. 現状調査: 両テーブルの中身（件数・名称・コード・使用箇所）を確認。`tasks.html` 内の `hq_corps` 参照箇所を洗い出す
2. 設計判断（推奨・調査結果で不合理なら報告して相談）: **`public.corporations` のidは `hq_corps` のidを引き継いで作る**（hq_tasks等の既存FKと画面改修を最小化）。`info.corporations` 側は対応列 `legacy_info_id`（または対応表）で紐付け。名称・`corp_code` は info.corporations（4社・code持ち）を正とする
3. 新規SQL `supabase/2026-08-XX_corporations.sql`（冪等）:
   - `public.corporations`（id uuid PK・corp_code unique・name・sort_order・is_active・legacy_info_id）
   - `stores.corporation_id uuid references corporations(id)` を**追加**（既存列は触らない）。値は `info.stores`（corporation_idを持つ・00〜05）と店舗の実態から埋められる分を埋め、**不明な店舗はnullのまま残してユーザーに一覧を提示して確定してもらう**（勝手に推測で確定しない）

4. 参照側の切替: `tasks.html` の法人参照を `corporations` に変更（idを引き継ぐ設計なら表示名の取得元変更が中心）。`hq_corps` は残すが新規書き込みを止める（テンプレ作成UIの法人選択を corporations 起点に）
5. E2E: タスクボードの法人フィルタ・テンプレ作成・既存タスクの法人表示が全部正しく動くこと（既存データで確認）。RLS敵対テスト（TEAM役でcorporationsへPOST→403）
6. 完了報告に「店舗×法人の対応表（確定分＋要確認分）」を含める

## D. 経費申請（要件定義書§20・§22の仕様で実装）

### D-1. データ設計（新規SQL `supabase/2026-08-XX_expenses.sql`・冪等）

- `expense_categories`（勘定科目候補: id・name・sort_order・is_active）— HQが画面で編集
- `expense_requests`（id・applicant_id→users・use_date・amount・purpose・category_id・store_id→stores・**corporation_id→corporations（§Bの共通ID必須）**・payment_type（既定'tatekae'。会社カードは将来値追加）・memo・status（draft/pending/approved/rejected）・approver_id・applied_at・decided_at・reject_reason・task_template_id（承認時に生成するhq_タスクテンプレ）・created_at）
- `expense_photos`（request_id・path・created_by）写真は既存 `report-photos` バケット `{uid}/expense_...` パス（第1フォルダ=auth.uid()の既存ポリシー準拠・変更禁止）
- `expense_flows`（将来の多段用フロー定義。v1では「1段」の既定フロー1行を置くだけ）＋`expense_approvals`（ステップ実績: request_id・step_no・approver_id・action・acted_at・comment）— **v1から多段化できる構造で作るが、UIは1段のみ**
- `expense_approver_rules`（申請者の役職→承認者の決め方: 例 AL/SHAIN/TENCHO→所属店舗のTEAM、TEAM→HQ、HQ→CEO。HQが画面で編集可・個人指定の上書きも可）
- RLS: 申請者=自分の申請のCRUD（pending以降は編集不可）／承認者=自分宛のpendingの閲覧+承認/差戻し／マスター・CEO・HQ=全件閲覧＋CSV出力。**全部RLSで強制し敵対テストする**

### D-2. 画面（新規 `expenses.html`。ポータルと同じ素fetch・`nsportal_session_v1` 流用）

- **申請（全員）**: 「金額→写真→用途」の3ステップ縦1画面（迷う要素を置かない・§20のUI最重要要件）。科目と店舗は自動推定の初期値（所属店舗）＋プルダウン。下書き保存
- **自分の申請一覧**: 状態バッジ（申請中/承認済み/差戻し）・差戻し理由表示・再申請
- **承認（承認者）**: 承認待ち一覧→1タップで「✅承認 / ↩️差戻し（理由必須）」。写真はその場で拡大表示
- **管理（HQ/CEO/マスター）**: 全件一覧（月・店舗・法人・状態で絞り込み）・CSV出力（会計取込用・BOM付きUTF-8）・科目マスタ編集・承認ルート設定・タスクテンプレ紐付け設定
- ナビ: `index.html` のサイドバー「各システムへ」の下に「💴 経費申請」を追加（**最小行数の追記のみ**）。日報側は触らない

### D-3. 連携

- 申請提出時: 承認者へ通知（既存 `hq_notifications` ＋通知チャンネルのLark/Chatwork。既存のhq_notify基盤を流用し、経費用の出来事タイプを追加）
- **承認完了時: `task_template_id` のテンプレから本部タスクを自動生成**（既存の生成関数を流用。タスクのメモ欄に申請番号・金額・申請者を入れる）→担当者へ通知
- 差戻し時: 申請者へ通知

### D-4. 受入チェックリスト（完了報告に結果を書く）

```
[ ] AL役: 申請作成（写真つき）→承認者に通知が届く
[ ] TEAM役: 承認待ちに表示→1タップ承認→申請者に通知→指定テンプレから本部タスクが自動生成される
[ ] 差戻し: 理由必須・申請者側に理由表示・再申請できる
[ ] pending以降の申請を申請者が編集できない（RLS敵対テスト）
[ ] 他人の申請が見えない（AL役で全件SELECT→自分の分のみ）
[ ] 承認者でない人が承認APIを直叩き→拒否
[ ] HQ: 全件一覧・CSV出力・科目/ルート/テンプレ設定
[ ] corporation_id が共通法人マスタ（§B）を参照している
[ ] スマホ幅(375px)で申請3ステップが快適に操作できる
[ ] テストデータ・一時ユーザー完全削除／WORKLOG追記／Pages反映確認
```
