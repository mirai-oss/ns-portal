## 0. 先に結論（7 つ）

1. **管理システムには、固定残業代を入れる場所がありません。** 表 `employee_wage_settings` に列が無い。申請・承認・履歴・CSV・Slack も「基本の金額 1 つ」だけです。
2. **スマレジへ送る処理（`wage_push`）は、月給を「区分・適用開始日・金額」の 3 つだけで送ります。** 固定残業代（`fixedWage`）は送りません。月給の行も送る対象です。
3. **定期実行（pg_cron・launchd・GitHub Actions）で賃金をスマレジへ送るものは、ありません。** 送るのは、人が画面や Slack で操作したとき（7 つの入口）だけです。
4. **「既存社員の月給の同期を止める」専用のスイッチは、今はありません。** 今あるスイッチでは止まりません（§2.5）。止めるには、新しい見張りを 1 つ足す必要があります（§2.6）。
5. **スマレジの API は、固定残業代の「適用する／金額／含める 6 つ」を読めて、書けます。** 「計算方法」と「時間数」は API にも CSV にもありません。画面の「固定残業時間から算出」は、金額を計算して入れるだけのボタンです（スマレジは時間数を保存しません）。
6. **月給を固定残業代なしで更新（PUT）したとき、スマレジ側の固定残業代が消えるか残るかは、仕様書に書かれていません。** テスト従業員での確認が要ります。
7. **既存の月給の人は 13 人。基本給は、比べられた 12 人すべてでスマレジの給与結果と同じでした。** 10 月の給与結果で固定残業代があった人は 4 人。うち 1 人（A さん）は、管理システムから 11 月開始の月給を登録したあと、11 月の給与結果から固定残業代が無くなっています（§5.4。意図した変更かどうかの確認が要ります）。

### 2.6 止め方の案（影響の小さい順。どれも未実施）

**案 0: 何も変えず、運用で止める**（影響: なし・確実さ: 低い）
- 本部に「社員の月給は、確認が終わるまで管理システムで触らない」と伝えるだけ。
- 今の状態: 月給の行 17 行はすべて `synced`（送る待ちは 0 行）。賃金の申請 0 件。入社手続き中の社員 0 人。**何もしなければ、月給は 1 行も送られません。**
- 弱点: だれかが保存・修正・「管理システムに合わせる」・契約コピーを押すと送られます。

**案 1: DB に「月給の止め」の見張りを 1 つ足す**（SQL 1 本・Edge Function の配置なし・おすすめの第一歩）
- 新しい設定 `employee_change.monthly_wage_sync_hold`（true で止める）と、表 `employee_wage_settings` の新しいトリガー。
- 止めるもの: 月給（`division=2`）の行の、新規・金額や適用開始日の変更・「送る待ち」への変更・削除。入社手続き中の人と、確認が終わった人（解除の一覧に入れた人）は除く。
- 効き方: 送る処理は「送る待ち（`pending`／`error`）の行」しか送りません。月給の行が送る待ちになれないので、§2.1 の入口 1〜7 がすべて止まります（承認の途中で止まった場合は、承認ごと取り消されて理由が出ます）。`wage_update` はサービスの権限で書きますが、トリガーは権限に関係なく働きます。
- 時給・日給には影響しません。スマレジからの取り込み（`synced` で入る行）も通します。
- 弱点: 入口 8 の「削除」は、先にスマレジを消してから表を消す作りなので、DB の見張りでは防げません（案 2 か、画面のボタンを隠す対応が要る）。
- 戻し方: 設定を false にするだけ。

**案 2: `smaregi-sync` の中で月給を送らない**（Edge Function の修正と配置が必要・いちばん確実）
- `wage_push`・`wage_update`・`wage_delete` の先頭で、止めの設定が true・月給・対象の人なら、スマレジを呼ばずに「確認待ちのため送っていません」と返す。
- 利点: 削除も止まる。画面に分かりやすい理由が出る。
- 手間: 本番のソースの復元と差分の確認・配置（リポジトリの決まり）。固定残業代の送信を作るときに、どのみち同じ場所を直します。

**案 3: 既存の `wage_approval_required` を ON にする**（おすすめしない）
- 理由は §2.5 のとおり。月給だけを止められず、止めても承認後に基本給だけが送られます。

**おすすめ**: 今日は案 0（事実として送る待ち 0 行）。承認をもらえたら案 1。固定残業代の送信を作る段階で案 2 を同じ配置に入れる。

### 3.5 ヘルプで分かったこと（「月給を設定する（基本給／固定残業代）」記事 360000000208 ほか）

- 固定残業代の欄は、給与形態が月給のときだけ使えます。
- 「適用する」にチェック → 金額の欄と「固定残業代に含めるもの」が入力できます。
- **「計算方法」という選択肢は、ありません。** 金額は直接入れる欄です。横の【固定残業時間から算出】は、計算用の小窓を開くボタンです。【適用】を押すと、計算した金額が欄に入ります。
- 小窓の入力は 4 つ: 割増計算に含める手当など（金額）／所定労働時間（時間・分。従業員 ＞ 従業員区分 ＞ 基本設定の順で自動で入る）／固定残業時間（時間数）／割増率（%。基本設定の時間外の倍率が自動で入る。変えられる）。
- 式（画面の画像に表示）:（月額賃金＋割増計算に含める手当など）÷ 所定労働時間 ＝ 1 時間あたりの賃金。1 時間あたりの賃金 × 固定残業時間 × 割増率 ＝ 固定残業代。
- 端数: 画像の例（350,000 円・160 時間・30 時間・125% → 82,032 円）から、丸める前の単価で計算して最後に切り上げていると**推測**（説明文は無い）。
- 「固定残業代に含めるもの」: 画面の文は「時間外労働の他、固定残業代に含めるものに…」の趣旨。**ふつうの時間外労働（法定時間外の残業）は、いつも含まれます。6 つは追加で含めるもの**です。
- 超過分: 固定残業代を超える残業をしたときだけ、追加の残業代が出ます。明細の項目名は「固定残業代」と「固定残業代超過分」。
- CSV の一括更新（記事 14390641438105）: 賃金の列に「固定残業代」（金額）と、含める 6 つ（0／1）があります。計算方法・時間数の列はありません。

### 3.6 仕様書・ヘルプに書かれていなかったこと（テスト従業員での確認が要る）

1. **固定残業代のある月給の行を、`fixedWage` なしで PUT したら、固定残業代は消えるか・残るか。**（今の `wage_push` はこの形で送ります。いちばん大事な確認）
2. 固定残業代を**外す**には、どう送るか（`fixedWage` を省く？ `rules` を空に？）。`rules: []` は通るか。
3. 書く側の `statutoryOvertime`（説明は「法定時間外」）が、読む側の `fixedWageStatutoryOvertimeFlag`（説明は「法定内残業」）と同じものか。仕様書の中で言い方が違います。
4. 超過分の正確な式（「残業代小計 − 固定残業代」で 0 より小さければ 0、と**推測**）。10 月までの給与結果では、固定残業代のある人の超過分は 0 件でした（DB で確認。式を実データで確かめる材料は無い）。

## 7. 分からなかったこと

1. §3.6 の 6 点（とくに「`fixedWage` なしの PUT で固定残業代が消えるか」）。テスト従業員での実測が要ります（スマレジへの書き込みなので、別途の承認が要る）。
