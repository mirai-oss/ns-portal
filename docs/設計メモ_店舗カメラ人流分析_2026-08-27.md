作成: 2026-08-27（司令塔） ／ 状態: **構想段階＝§4の質問に回答をもらってから設計書を作る**（実装割当なし）

## 1. 要望の整理（やりたいこと一覧）

| # | やりたいこと | 場所 |
|---|---|---|
| ① | 店頭の通行人数 → 看板を見た人数 → 入店した人数（ファネル） | 店頭カメラ |
| ② | 注文から商品提供までの時間の計測 | 店内 |
| ③ | どのお客様がリピーターか | 店内 |
| ④ | 何を注文した人が次に何を頼むか（注文の相関） | 店内 |
| ⑤ | ランチで注文から5分以内に未提供ならアラート＋キッチンプリンター印刷 | 店内 |

## 2. 重要な提案: 「カメラでやること」と「diniiのデータでやれること」を分ける

②③④⑤は、**カメラ映像よりも、既に導入済みのモバイルオーダー（dinii）の注文データの方が正確・低コストで実現できる可能性が高い**。dinii注文データは毎朝BigQueryへ自動取込済み（`bqLoadOrders`・明細分析タブで稼働中）のため、新しいハードウェアなしで着手できる。

| # | カメラ案 | dinii案（提案） |
|---|---|---|
| ② 提供時間 | 映像から料理到着を画像認識（開発難度高） | 注文時刻はdiniiにある。**提供時刻がdiniiのステータス（提供済み操作）に残っているかが鍵**（要調査） |
| ③ リピーター | 顔認識（**個人情報保護法上の本人同意・店頭掲示など法的ハードルが高い**） | diniiの会員ID・電話番号ベースの再来店判定（利用規約の範囲内で。要調査） |
| ④ 注文相関 | 映像からは不可能 | **dinii明細データだけで今すぐ可能**（同一伝票内の組み合わせ分析） |
| ⑤ 5分アラート | 映像判定＋プリンター連携 | dinii注文時刻＋「提供済み」操作時刻の差分でアラート判定→**印刷はキッチンプリンターのAPI/連携方法次第** |
| ① 店頭人流 | **カメラでしかできない**（本命） | 不可 |

→ **提案する進め方**: Phase 0=dinii側の調査（提供時刻・会員データが取れるか）→ Phase 1=④注文相関と②提供時間をdiniiデータで先行 → Phase 2=①店頭人流のカメラPoCを1店舗で → Phase 3=⑤アラート印刷。

## 3. カメラ側の技術方式（回答待ちのため概要のみ）

- 既設カメラの映像を取り出せるか（機種依存: RTSP対応/クラウドAPI/取り出し不可）で方式が全く変わる
- 取り出せない場合は「人流カウント専用のAIカメラ・センサーを店頭に1台追加」する方が既設流用より安く済むことが多い
- 顔認識によるリピーター判定は法的配慮（利用目的の掲示・同意）が必要なため、**やるとしても最後**。人数カウント（個人を特定しない）とは要件が別物

| Q | 回答 |
|---|---|
| Q1 機種 | おすすめ希望（別AIはReolink推奨・自動転送できるため）。台数は1店舗5台程度 |
| Q2 保存先 | 推奨プラン希望・コスト最小で |
| Q3 PoC店舗 | **鳥一代 本店** |
| Q4 dinii | **「提供済み」操作はしていない** → 提供時刻がデータに残っていないため、5分アラートには運用変更か別の仕掛けが必要（§5.3） |

| Q6 予算 | プリンター以外で1店舗10万円以内が目安 |

### 5.1 推奨構成案（コスト最小・月額ゼロ方針。※発注前に実機・価格の最終確認をする）

- **カメラ: Reolink のPoE有線モデル**（RLC-520A／RLC-810Aクラス。1台1万円前後・RTSP/ONVIF対応＝映像を標準規格で取り出せる・屋外対応モデルあり）。ユーザーが聞いていた「別サーバーへ自動転送」もFTP/RTSPで可能
- **保存・分析: クラウド契約ではなく店内ミニPC1台**（Intel N100クラス・3万円前後）に無料のオープンソースNVR「**Frigate**」を入れる構成を推奨。人物検知・人数カウント・録画保存が店内で完結し、**月額費用ゼロ・映像が外部に出ない**（プライバシー・通信量とも安全）。BigQueryへは「時間帯別の通過人数・入店数」など**集計値だけ**を日次送信
- **概算（PoC 1店舗）**: カメラ5台 約5万円＋PoEスイッチ 約1万円＋ミニPC 約3万円 ＝ **9万円前後**（予算内・プリンターは既存TM-m30II-Hを流用）
- 既設の監視カメラの機種が分かれば流用可否も判断できる（RTSP対応なら買い足し不要の可能性あり）

### 5.2 リピーター分析はカメラより先に「予約データ」でできる（新発見）

食べログノートCSVに**顧客No**が入っており、予約データ基盤（レーンI）が動けば**予約客の再来店・来店頻度の分析はカメラなしで可能**。顔認識は法的配慮（掲示・同意）が必要なため引き続き後回しを推奨。

### 5.3 「5分アラート」の実現方式（ユーザーに選んでほしい）

- **案A（推奨・追加費用ゼロ）**: ランチ帯だけ、料理を出したときにdiniiで「提供済み」を押す運用に変える → 注文時刻との差分で判定し、5分超過でTM-m30II-Hへ自動印刷
- **案B**: キッチンに「提供したらタップ」する安いタブレット/ボタンを置く（運用は同じ・dinii操作を変えたくない場合）
- **案C（非推奨）**: カメラ映像で料理提供を画像認識（開発難度・誤検知率が高い）

### 5.4 次の一歩（Phase 0・発注前の残確認）

1. ユーザー確認: ①5分アラートは案A/Bどちらでいくか ②鳥一代本店の**店頭（屋外側）にカメラを付けられるか**（電源・取付場所）③店舗のネット回線の種類（光ならOK）④既設カメラの機種名（分かれば流用判断）
2. 回答後: 司令塔が機材リスト（型番・価格・購入リンク付き）を確定 → ユーザー発注 → 設置後にPoC実装レーン発進
