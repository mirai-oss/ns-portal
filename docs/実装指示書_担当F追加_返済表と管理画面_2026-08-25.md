## F-5: 社内情報システム・返済表（借入金）の機能改善

対象: `ns-info-system`の`/loans`（既存: 元金均等/元利均等・返済予定表自動計算・銀行提出CSV・添付=`info.documents.loan_id`）。**すべて追加のみ・既存データは変換しない。**

### 仕様（2026-08-25 ユーザー要望）

1. **金利タイプ**: `rate_type`列を追加（**固定／変動**のプルダウン）。既存行は「固定」を既定値に
2. **借入種別**: `loan_category`列を追加（プルダウン: **プロパー／保証協会／制度融資**／その他。選択肢はマスタ化せず定数でよいが、追加しやすい実装に）
3. **返済開始月**: `repayment_start_month`列を追加。**返済予定表はこの月から元金返済がスタートする計算にする**（借入実行月と返済開始月が異なる=据置期間があるケースに対応）。既存行は現在の開始月をそのままコピーして初期化
   - 実装時にユーザーへ1点確認: 据置期間（借入月〜返済開始月の間）の**利息のみ支払い行**を予定表に表示するか、返済開始月から表を始めるだけでよいか
4. **添付した返済票の削除**: 借入詳細の添付ファイルに削除ボタンを追加（`has_edit_perm('loan')`権限者のみ・Storage実体と`info.documents`行の両方を削除・確認ダイアログ必須・削除を監査ログへ）
5. **年利の途中変更（履歴付き）**: 変動金利対応の核心
   - 新テーブル`info.loan_rate_history`（id／loan_id／annual_rate／**effective_from**（この年月から適用）／memo／created_by／created_at）
   - 既存の`loans.annual_rate`は残し（互換）、初期データとして各借入の現在年利を`effective_from=返済開始月`で履歴に1行移行
   - **返済予定表の計算を期間別金利対応にする**: 各月の利息は「その月に適用されている年利」で計算（元金均等・元利均等の両方式とも。元利均等は金利変更月以降の毎月返済額を残元本・残期間で再計算）
   - UI: 借入詳細に「年利の変更」ボタン→新しい年利＋適用開始月＋メモを入力→履歴一覧を詳細画面に表示（いつ・誰が・何%→何%）。**履歴の削除は不可**（マスターのみ訂正可・訂正も履歴に残す）
6. 検証: 既存の固定金利の借入で**変更前と返済予定表が1円も変わらない**こと（回帰）／変動テストケース（途中で年利変更）の予定表が手計算と一致すること

### 注意

- ns-info-systemは本番稼働中の機密金庫。SQLは`info`スキーマへの追加のみ・RLSは既存の`has_perm('loan')`/`has_edit_perm('loan')`を踏襲
- ローカル環境は必ず`git pull`＋ハブ向け`.env.local`を確認してから（過去に旧DB向きのまま開発しかけた事故あり）

## F-6: マスター管理系の「管理画面」整理（提案確定版）

**ユーザーの困りごと**: 権限・アカウント・テンプレート編集・通知先などの管理機能が各所に散らばっている。別途管理画面を設けるか、タブで分けるか整理したい。

### 採用する整理方針（提案→この形で実装。変えたい場合はユーザー確認）

**別サイトは作らず、統合ポータルシェル内に「⚙️ 管理」グループを新設し、タブで集約する**（マスター/社長/本部のみ表示）。既存の管理画面は作り直さず、iframe/リンクで再利用する=既存を壊さない。

| タブ | 中身 | 実体（再利用元） |
|---|---|---|
| 👤 アカウント・権限 | 従業員アカウント／役割×システムの権限マトリクス／個人上書き | 既存: nippo管理画面＋ポータルの権限設定タブ |
| 🔔 通知先 | Lark/Chatworkの配信グループ管理（レポート配信matrix）／通知ルート | 既存: 配信グループ管理（Day6③）＋nippoのLark通知設定 |
| 🏢 マスタ | 店舗管理（1箇所化済みの店舗管理画面）／法人管理 | 既存: nippo店舗管理＋tasks.htmlの法人管理 |
| 📄 出力テンプレート | Export Serviceのテンプレート管理（担当Gが作る画面を埋め込み） | 新規（担当G） |
| 📊 システム利用 | AI利用料ウィジェット（F-1.5）／出力履歴／将来のコストダッシュボード | 新規（データはD-4等） |

- 理由: ①ログイン・権限基盤を二重に持たない（別サイト案の欠点）②「管理はここ」という1箇所の入口ができ、今後の管理機能（テンプレート・通知先・APIコスト等）の置き場が明確になる③各機能の実体は既存画面のままなので工数最小・リスク最小
- 実装: portal.htmlのサイドバー最下部に「⚙️ 管理」グループ（権限で出し分け）。タブ構成は上表。**新規に作るのは枠だけ**で、中身の新画面（出力テンプレート等）は各担当の成果物が埋まる
