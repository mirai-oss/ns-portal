### 2.2 横断的な仕組み（画面に紐づかない基盤機能）

- **`hq_generate_today()`**: 画面を開くたび毎日/毎週(該当曜日)/毎月(該当日)のテンプレートから当日分のタスクを自動生成。工程内チェックリストのコピーもここで実施（2026-08-25追加）
- **`hq_create_from_template()`**: 「テンプレートから追加」の即時生成。チェックリストコピーも同様に対応済み
- **`hq_check_alerts()`**: 期限3日前/前日/当日/超過の通知判定・送信
- **`hq_can_manage()` / `hq_task_visible()` / `hq_feature_allowed()`**: 権限・可視性の中核関数
- **通知**: アプリ内通知＋Chatwork（チャンネル・ルール設定に応じて）
- **写真**: Supabase Storage非公開バケットへの署名URL方式アップロード・表示
- **CSV**: テンプレート一括登録／登録済み一覧エクスポート
- **URL深リンク**: `?task=<id>`でタスク詳細への直接遷移（通知タップ等で使用）

**上記すべてが「壊してはいけないもの」の一次リスト。実装時はこの表の各行にチェックを入れながら進める。**

## 4. 技術方針（現時点の推奨・§8で確定させる）

1. **DB構造は極力維持**。`hq_task_templates`/`hq_task_template_steps`/`hq_tasks`/`hq_task_steps`/`hq_task_links`/`hq_task_photos`/`hq_step_checklist_items`/`hq_task_members`/`hq_task_alerts`/`hq_task_activity`/`hq_generation_log`/`hq_notify_*`/`hq_feature_permissions`は変更しない前提で進める。列追加が必要になった場合のみ、日付入り新規SQLで追加（既存ルールどおり）
2. **画面の作り方は2案**:
   - **A. 既存`tasks.html`を段階的に改修**（サイドバー導入→工程UI刷新→添付UI刷新の順に、既存ロジックを流用しながら書き換え）。リスクが低く、途中で止めても既存機能が壊れない
   - **B. 新規ファイルで作り直し、完成後に切り替え**（`tasks-v2.html`等で並行開発→検証OKで`tasks.html`を置き換え）。デザインの自由度は高いが、DBアクセス層（RLS・RPC呼び出し）を丸ごと再実装する必要があり工数が大きい
   - **現時点はA案を推奨**（担当Fの統合ポータルシェルも既存資産を活かしつつ段階移行した実績があるため）。§8でユーザー確認
3. **サイドバーの導入方法**: `tasks.html`単体にサイドバーを実装するか、統合ポータルシェル（`portal.html`・担当F管轄）のiframe埋め込み前提でサイドバーは持たずヘッダーのみにするか、要確認（§8）。統合ポータルシェルは`?embed=1`でヘッダー非表示に対応済みのため、tasks.html側に独自サイドバーを作ると二重ナビになる可能性がある
4. **段階分け（Phase）案**:
   - Phase 0（今回のスコーピング）: 本書の作成・§7調査・§8確認
   - Phase 1: ナビゲーション刷新（サイドバー or ポータルシェル連携方式の確定＋「管理」グループ新設）。既存の全画面遷移をそのまま新ナビに繋ぎ変えるだけで、中身の画面は変更しない
   - Phase 2: ボード画面（かんばん/リスト/カレンダー）のビジュアル刷新
   - Phase 3: タスク詳細・工程UIの刷新（担当・期限の常時編集化・リソースカード化）
   - Phase 4: テンプレート編集画面の刷新（従業員側プレビュー常時表示化）
   - 各Phaseごとに実機確認→ユーザー承認→次Phaseへ、の順（一度に全部作り替えない）

## 5. 「管理」グループの設計案（ユーザー指示への直接回答）

現行の上部ボタン列にある以下5項目を、サイドバー（or ヘッダーのドロップダウン）の「⚙️ 管理」サブメニューへ集約する:

- 🔑 権限設定（`renderPerms`・isMasterのみ）
- 🏢 法人管理（`renderCorps`・canFeature "corps"）
- 🔔 通知設定（`renderNotify`・canFeature "notify"）
- 📁 過去タスク（`renderPast`・全員閲覧可）
- （検討）⚙️テンプレート管理自体も「管理」グループに含めるか、独立ナビ項目のままにするか→デザイン案では独立ナビ項目（🗂️テンプレート）なので、**テンプレート管理は独立のまま・上記4つだけを「管理」グループにまとめる案を推奨**（テンプレート管理は日常的に使う頻度が高く、権限/法人/通知/過去タスクは低頻度のため）

表示条件（誰に「管理」メニュー自体を見せるか）は、既存の`canFeature`/`isMaster`判定をそのまま踏襲（4項目のうち1つでも見える権限があれば「管理」メニュー自体を表示、全部見えない一般ユーザーには「管理」メニューごと非表示）。
