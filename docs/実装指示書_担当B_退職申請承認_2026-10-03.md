## 1. 作るもの（最小）

1. **テーブル `hr_change_requests`**（将来の異動・休職にも使えるよう`kind`を持つが、今回は`kind='retirement'`固定。汎用エンジンは作らない＝要望19章）
   - `id uuid pk`・`kind text not null default 'retirement'`・`store_id uuid→stores`・`user_id uuid→users`（＝employee_id）・`effective_date date not null`（＝retirement_date）・`status text check in (pending,approved,rejected) default pending`・`requested_by uuid`・`requested_at timestamptz default now()`・`approved_by/approved_at`・`rejected_by/rejected_at`・`reject_reason text null`・`sync_status text check in (none,synced,unsynced,error) default none`・`sync_result jsonb`・`synced_at`・`created_at/updated_at`
   - **部分ユニーク索引**: `(user_id) where status='pending' and kind='retirement'`（同一従業員の承認待ち重複をDBで防止＝要望11章）
   - RLS: 申請者本人の店舗の行は店長/チーム長が読める・本部/社長/マスターは全件。書き込みはRPC経由のみ
2. **RPC `hr_request_retirement(p_store uuid, p_user uuid, p_date date)`**（security definer・既存`set_employee_termination`と同じ作法）: 呼び出し者の役職チェック（Q2）→対象が`user_stores`でその店舗に所属・`is_active=true`・`termination_date is null`→未来日チェック（当日以降・Q1次第で過去日も可）→insert。違反は例外で返す（フロント任せにしない＝要望17章）
3. **RPC `hr_approve_retirement(p_request uuid)`**（security definer・**1トランザクション**）: `select ... for update`で行ロック→`status='pending'`でなければ例外（承認連打・二重承認防止）→**対象従業員の最新状態を再取得して再検証**（所属・在籍・退職済みでない＝要望12章）→**既存`set_employee_termination(p_user, effective_date)`を関数内から呼ぶ**（退職日の一致は列の値をそのまま渡すことで保証＝要望7章）→`status='approved'・approved_by/at`。途中失敗は全体ロールバック（要望16章）
4. **RPC `hr_reject_retirement(p_request uuid, p_reason text)`**: 同様にロック→`rejected`
5. **画面①「退職申請」**（店長・チーム長向け。シフト管理や日報の既存タイル群に1つ追加）: 店舗（既存の店舗選択。本人の所属店舗だけ）→従業員（その店舗の在籍者。氏名の一部で絞り込み。内部は`user_id`）→退職日。送信前に「○○さんの退職申請を送ります（退職日 YYYY/MM/DD）」確認。承認待ちがある人は選択肢から除外＋注記
6. **画面②「退職申請一覧」**（本部/社長/マスター。既存の従業員管理の中）: 申請日時・店舗・従業員・退職日・申請者・ステータス・操作。承認＝確認ダイアログ「○○さんを2026年10月31日付で退職処理します。よろしいですか？」→`hr_approve_retirement`→成功後に**既存`smaregiTerminate(user_id, date)`**→結果を`sync_status/sync_result/synced_at`に保存（`skipped`=未連携も記録）。失敗時は行に「⚠️スマレジ未同期・再同期」ボタン（同じ`smaregiTerminate`を再実行＝リトライはこの1個だけ）。却下＝理由任意
7. 既存の従業員編集「退職日」カードは**そのまま残す**（本部が直接処理する経路。申請を経ない退職も従来どおり可能）

## 4. 既存同期の制約（司令塔確認済み・要望9章への回答）
- スマレジ・タイムカードAPIは`PATCH /staffs/{id}`の`terminationDate`で退職日を、`PUT /staffs/{id}/active`で打刻の利用ON/OFFを更新できる（既に本番稼働）。**即時同期**（画面からの呼び出し）・定期同期は無し・失敗時はトースト表示のみ→今回`sync_status`で見えるようにする
- スマレジ未連携の従業員は`skipped`で正常終了（nippo側だけ退職処理）
- 既存は「退職日を入れた瞬間に打刻OFF・ログイン不可」。要望8章（退職日までは在籍扱い）と食い違う→**Q1**
