## 1. 第1弾: 共通定義と評価基準（SQL・未適用で司令塔レビュー）
1. `fl_metrics_*`（名称は担当A案）: 店舗×期間（日／月初〜当日／月）の **FL計算用売上（店内＋デリバリー）・人件費・食材原価・L率・F率・FL比率** を返す共通関数またはビュー。デリバリーは `kd_delivery_daily.net_sales` を Q11 の決定どおり税抜換算（既定 ÷1.08・換算率は1か所の定数）。店内売上（`net_sales`/`sales`）の値・列は一切変えず、分母は新列 `fl_sales` として持つ。`kd_store_monthly_summary` には `delivery_sales`・`fl_sales` を追加列で持たせ、labor_rate/cost_rate/fl_rate の分母を `fl_sales` に切替（keiei-kd-refresh の計算箇所）。`kd_home_kpi` も同じ関数を使う
2. `fl_rating_thresholds` / `fl_rating_threshold_history`（トリガー）/ `daily_report_card_snapshots` と RPC 6 本（list/upsert/copy(dry_run)/missing/history/me_is_master）。RLS: anon/PUBLIC なし、authenticated は RPC 経由のみ、RPC 内で `users.is_master` を判定（偽なら 403 相当の例外）。適用後に権限表（aclexplode）を出す SELECT を同梱
3. `daily_report_card_vm` v6: 既存キー維持＋追加（`fl_sales_today`/`fl_sales_mtd`、`labor_ratio_*`/`food_cost_ratio_*` の分母を共通定義へ、`fl_ratio_today`/`mtd_fl_ratio`、`is_holiday_eve`/`days_to_holiday`、`delivery{enabled,sales,orders,status,budget_ratio}`、`dinii_low_count`、`ratings{labor,food,fl}`、`mtd_status='暫定'`）
4. 経営ダッシュボード側の F/L/FL（日次・月次）を共通定義に合わせる変更点を列挙（§0 で承認を得た範囲だけ）
→ 司令塔レビュー → ユーザー承認 → 適用（ユーザー実行）

## 2. 第2弾: 画像 v2（tori-dashboard `scripts/daily-report-card.mjs`）
- 確定デザイン（ユーザー提供画像）どおり。配置: 上段左 本日の売上／上段右 本日のイベント／中段 本日のKPI（客数・客単価・L率・F率・FL比率）／月間累計（売上・予算進捗・L率・F率・FL比率＋4段階バッジ・FL強調・「暫定」）／下段左 口コミ・評価（口コミ増減・ダイニー低評価・ダイニー点数）／下段右 売上内訳（ランチ・ディナー・[デリバリー]＋予算比）／最下段 要確認（重要度順・最大2件・危険水準最優先）
- デリバリー: 取扱店は3行、0円は「¥0」、未取得は「未取得」、「FL計算用売上（店内＋デリバリー）」を小さく補足。非取扱店は2行
- 評価・判定は VM の値をそのまま表示（画像側で計算しない）。基準未設定は「基準未設定」。画像を極端に縦長にしない
- **プレビュー**: 通常店（例: 恵比寿）とデリバリー店（本店）の PNG をローカル生成し、ユーザー確認用に提出（Slack へは送らない）。`--vm-file` でテスト用 VM（計算検証例: 店内700万/デリバリー100万/人件費160万/原価200万 → L20.0%/F25.0%/FL45.0%）も1枚

## 3. 第3弾: 管理画面（tori-dashboard `app.js`）
