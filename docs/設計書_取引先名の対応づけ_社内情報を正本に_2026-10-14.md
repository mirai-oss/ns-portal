# 設計書 取引先の名前の対応づけ（社内情報を正本に）— 2026-10-14

担当C／ユーザー提案への回答。方針: **取引先の正本は社内情報（`info.suppliers`）。請求書・明細・会計(MF)・通帳での名前は、その1社にぶら下げて持つ。**

> ユーザーの提案: 「社内情報を正本にして、請求書での名前が違った場合は『請求書ではこの名前、明細ではこの名前』と紐付ける。三菱食品なら請求書は"リクエ"とあるので、社内情報の取引先に紐付け、MFでの取引先も紐付けていく」

## 1. 現状（調べた事実）

| 置き場所 | 持っているもの | 件数 | 備考 |
|---|---|---|---|
| 社内情報 `info.suppliers` | 取引先の連絡先台帳（名前・種別・電話・担当者・メール・状況） | 40（全件トーホー） | 39件が「要確認」。正式名・法人番号・口座の列は無い。名前は通称（「染谷商店」「下山」「トウキョウジョーカー」） |
| `public.vendors` | 請求書処理用の取引先マスタ（登録名・法人番号・MF取引先名・インフォマートの取引先ID） | 110 | 社内情報への紐付け `info_supplier_id` は**0件**（手動の軽い連携のみ） |
| `public.vendor_aliases` | 請求元の表記ゆれ（㈲染谷商店／染谷商店／リクエ…） | 47 | 請求書OCR・インフォマート送信の取引先判定に使用 |
| `public.vendor_line_rules` | 行ごとの科目ルール。**MFの補助科目名**（借方・貸方）を法人（tenant）ごとに保持 | 有効24 | MFの実名は総勘定元帳で確認済み（例: 買掛金/㈲染谷商店、リクエ） |

つまり名前はすでに4か所に散らばっているが、**「同じ会社」を結ぶ軸が無い**（社内情報との紐付けが0件）。

## 2. 目指す形

```
社内情報の取引先（正本）  info.suppliers
   │  vendors.info_supplier_id（1社＝1件で結ぶ）
   ▼
vendors（請求書処理側・会計に必要な項目）
   ├─ 登録名（vendors.name）          … Infomartの会計データ・請求書の正式名
   ├─ 請求書の名前（vendor_aliases.kind='invoice'）  … Infomart画面／メール／OCRの請求元表記
   ├─ 明細の名前 （vendor_aliases.kind='statement'）… 店舗別明細・CSV上の表記（請求書と違う場合）
   ├─ 通帳の名前 （vendor_aliases.kind='bank'）     … 振込・引落の摘要
   └─ MFの名前   （vendor_line_rules）              … 法人(tenant)×科目ごとの借方/貸方補助科目
```

- **1社＝社内情報の1件**。名前の違いは「別名」としてぶら下げる（名前を統一しようとしない。請求書の名前は先方が決めるため）。
- **MFの名前は法人×科目ごとに持つ**（同じ会社でも、トーホーは「買掛金/リクエ」、N-Styleは別名の可能性）。既存の `vendor_line_rules` がすでにこの粒度なので、そのまま使う。
- 判定は一方向: **請求書の名前 → 取引先（vendors）→ 社内情報／MFの名前**。新しい名前が来たら別名として足す（承認画面の「今後この内容で処理する」が既にこの入口）。

## 3. なぜ新しいテーブルを作らないか

- 既存の3つのEdge Function（`invoice-auto-ingest`・`invoice-auto-create`・`vendor-master`）は `vendor_aliases` から `(vendor_id, alias)` だけを読む。**列を足すだけなら影響しない**（`kind` の既定値は `invoice`）。
- MFの補助科目名は仕訳ルールが持つのが正しい（仕訳の生成に直接使うため）。別テーブルに複製すると二重管理になる。
- 足りないのは「どの用途の名前か」の区分と、**全部を1社ごとに並べて見る場所**だけ。

## 4. 段階（この設計書の範囲）

### 段階1のSQL
`supabase/2026-10-14_vendor_name_map.sql`（冪等・データ書換え無し）。ダッシュボードのSQL Editorで適用する。

- `vendor_aliases.kind`（`invoice`／`statement`／`bank`）を追加。既存の47件は `invoice` になる。
- `v_vendor_name_map`: 取引先×用途×法人×科目の長い一覧（登録名／MF取引先名／別名／MF借方・貸方補助科目）。
- `v_vendor_link_status`: 取引先ごとの紐付け状況（社内情報に紐付いているか・各名前の件数）。

## 5. 決めておくこと（おすすめ付き）

| 論点 | おすすめ | 理由 |
|---|---|---|
| 取引先の粒度 | **会社単位で1件**。「三菱食品」の中の「リクエ事業」は請求書の別名として持つ | 支払・口座・インボイス登録は会社単位。事業部で分けると請求書が2社に割れる。ただしInfomartが事業部ごとに別請求書を出す場合は、請求書ベースで見る（既存の方針と同じ） |
| 法人またぎ（トーホー／N-Style） | **会社1件にまとめ、MFの名前だけ法人ごとに持つ** | `vendor_line_rules.tenant_id` が既にその粒度 |
| 社内情報の名前（通称）と正式名 | 通称は残し、**正式名称・法人番号の列を社内情報に追加**（段階4・担当F） | インフォマートの会計データの名前＝正式名で突合できる |
| `info.suppliers` が法人別（corporation_id）の行である点 | 当面は全件トーホー。N-Styleでも同じ会社を使う場合は、社内情報に法人別の行が増える → `vendors` 側で複数行を1社に束ねる連携表が必要（段階4で設計） | 今は40件すべてトーホーのため先送りで問題無し |
| 社内情報の「要確認」39件 | 段階2の前に、24社分を「取引中」へ（担当F／ユーザー） | 状況が「要確認」のままだと正本として使えない |
