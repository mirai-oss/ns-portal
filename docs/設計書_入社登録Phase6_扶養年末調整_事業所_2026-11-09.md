# 設計書: 入社登録 Phase 6（v2）— 扶養家族・年末調整の入社後フォーム／源泉所得税の Slack 画面／スマレジ事業所の自動作成

作成 2026-11-09（立会い後）。**v2 2026-11-09 改訂**＝中山さんの最終方針（社員・アルバイト全員が対象、必須・リマインドは雇用区分の標準ルール＋個別上書き、履歴、年度、承認後反映、既存従業員）を反映。**本番未適用・未デプロイ**。ハブ側（ns-portal）の設計と実装。nippo 側・Mac 側は別担当が同じ契約（`scratchpad/phase6/CONTRACT2.md`）で作る。

> **大事な注記（方針①）**: この仕組みで「任意」にした提出は、社内運用上の扱いです。税法上の提出・申告の義務を免除するものではありません。法令上必要な手続きは別途、本部が管理します。

## 0. 何が変わるか（1 分で）

| 困りごと | こうなる |
|---|---|
| 入社フォームが長い | 入社フォームでは扶養・年末調整は入れない。「今入力する／後から入力する」を本人が選べ、後からでも入社登録は完了する |
| 誰が提出必須か分からない | **雇用区分の標準ルール**（社員＝扶養・年末調整とも必須＋リマインド／アルバイト＝利用できるが任意・リマインドなし）＋**本部の個別上書き**（必須・リマインド・期限・対象年度の対象判定・フォーム利用可否）。変更者・日時・理由は履歴に残る |
| 年末調整は毎年ある | 対象年度ごとに 1 行（`employee_year_end(user_id, target_year)`）。翌年は自動で「未提出」に戻る |
| アルバイト→社員になった | 標準ルールが社員に切り替わる（履歴 `class_changed`）。提出済みデータはそのまま再利用、未提出なら必須扱いになって本部の一覧に出る（自動通知はしない） |
| スマレジに勝手に書かれては困る | 提出 → **本部が Slack で承認** → その後だけスマレジへ（Mac の自動操作）。保存後は年末調整＝API で読み戻し、扶養＝画面を読み直して**氏名・続柄・生年月日**で照合 |
| 既存従業員 | スマレジの内容を **1 人ずつ**参考値として取り込み（年末調整＝API／扶養＝読むだけジョブ）、本人が確認・変更申請。取り込んだだけでは提出済みにしない。一括変更・一括通知はしない |
| 源泉所得税の Slack 画面 | スマレジの「源泉所得税設定を追加」と同じ 4 項目（社員・アルバイト共通） |
| スマレジに事業所が無い | 店舗管理の「スマレジにも事業所を作る」→ Mac が作成 → 対応表に自動登録 |

## 1. 流れ

```
入社フォーム（nippo）: 「今入力する／後から」→ RPC onboarding_post_join_choice（履歴 choice）
本人（nippo 設定ページ・既存従業員も）: 年末調整フォーム → RPC onboarding_save_year_end(user, data, via, actor, year) → employee_year_end（年度別）＋ status submitted
                                     扶養フォーム → RPC onboarding_save_dependents(user, rows, via) → employee_dependents（0 人＝none）＋ status submitted/none
本部（Slack 親メッセージ「入社後の提出」= 必須/任意・期限・状態）
  └ スレッド「📝 提出」→ ✅ 承認してスマレジへ（RPC onboarding_post_join_approve → enqueue）／↩️ 差し戻し（RPC onboarding_post_join_reject）／🔎 スマレジと比較（op post_join_compare）
      → ジョブ smaregi_year_end（payload に target_year・expected_contract_id・expected_staff_id・expected_stores）／smaregi_dependents（rows＋verify 氏名・続柄・生年月日）
      → Mac mini（Playwright）: 書き込み前に 契約ID・従業員ID・所属事業所 を画面で照合（1 つでも確認できなければ「事前確認: …」で中止＝screen_changed・再試行なし）
      → op ui_job_result: 年末調整＝API 照合／扶養＝rows_matched・rows_unmatched → status synced / error
cron（承認後）→ onboarding_post_join_remind_trigger → op post_join_remind → RPC onboarding_post_join_targets（必須かつ未完了だけ・期限前は n 日おき・期限後は毎日）→ Slack DM → LINE（既定 OFF）
既存従業員: op post_join_snapshot（年末調整＝API → employee_year_end_snapshot／扶養＝読むだけジョブ → employee_dependents(source=smaregi_snapshot, is_active=false)）。提出状況は pending のまま
```

## 4. 方針①〜⑨との対応

| 方針 | 実装 |
|---|---|
| ① 社員は必須＋リマインド、年末調整は年度ごと対象判定。アルバイトは利用可・任意・リマインドなし・個別に必須へ | `post_join_rules` 初期値／`post_join_overrides`／`post_join_effective`。「任意＝免除ではない」注記を overview・親メッセージ・本設計書に |
| ② 入社時に案内・「今／後から」・後からでも入社登録完了・既存従業員も設定ページから | `onboarding_post_join_choice`、入社登録の完了判定は従来の 10 項目のまま（別トラック） |
| ③ 独立した設定・標準ルール＋個別上書き・履歴 | rules / overrides / history（トリガー）。扶養と年末調整は track ごと |
| ④ アルバイト→社員 | users.role 変更トリガーで履歴。実効ポリシーは role から毎回計算（データは触らない）。`post_join_required_pending_v` で本部が案内 |
| ⑤ 必須かつ未完了だけリマインド・期限で間隔・完了で停止・自動送信は OFF | `onboarding_post_join_targets`（required∧remind∧status=pending∧target）、`post_join_remind_enabled=false` |
| ⑥ 既存従業員・1 人ずつ取り込み・未登録と断定しない・一括禁止 | `post_join_import_snapshot`（snapshot 表・source=smaregi_snapshot）、op post_join_snapshot は 1 人単位。status は変えない |
| ⑦ 承認後に反映・差分・再取得・扶養は氏名/続柄/生年月日 | approve → enqueue、`ui_job_result` の rows_matched/unmatched、`yearEndCompareText` |
| ⑧ 既存機能の維持 | 源泉モーダル・事業所作成・交通費・Phase 1〜5 は無変更（回帰テスト再実行） |
| ⑨ テスト | 下記 §6 |

## 7. 仮定・未検証（実機で確かめる）
- 扶養の照合（rows_matched / rows_unmatched）は Mac 側が詳細ページの表から氏名・続柄・生年月日を読める前提（表の列順は偵察で未取得）。
- 年末調整の API 照合項目（householdHeaderRelationship など）は公開リファレンスの要約由来。
- 書き込み前の 3 点確認（契約ID・従業員ID・所属事業所）は Mac 側の実装。契約ID が確実に取れない場合は未検証として中止する（推測しない）。ハブ側は結果の表示と手動工程だけ。
- 本人フォーム送信直後のスレッド投稿は nippo から EF を呼べないため、親メッセージは「🔄 表示を更新」で反映。スレッド投稿はリマインド／本部ボタンのとき。
- 事業所作成（v1 のまま）: フリガナは店舗名をそのまま、郵便番号が無い店舗は Mac 側で not_supported。
