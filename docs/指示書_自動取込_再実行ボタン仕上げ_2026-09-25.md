## 2. 仕組み（変更しないこと）

```
ブラウザ(未取得タブ) ─INSERT(status='pending')→ import_run_requests
                                                    ↑ 数分おき(dispatch.js)
Mac mini: lib/run-requests.js が pending を取得 → pending→running に「pendingのときだけ」更新して確保
   → node run.js <job>（NS_TRIGGER=portal）→ import_runs の実ステータスを取り直し → 同じ行へ success/partial/failed と要約を書き戻し
```

- ブラウザにGASトークン等の秘密情報を置かないため、GASのタスクキューではなくSupabase経由にしている。
- **対象ジョブは import_schedule の「月次・有効・kind∈deposit/purchase/sales」だけ**（現状: PayPay加盟店入金・ロケットナウ月次精算）。RLSとMac mini側の**両方**で検査する二重防御。
- 依頼できるのは `users.is_master` または `role in ('CEO','HQ')` の有効ユーザーのみ。同一ジョブは`pending/running`が残る間、部分ユニークindexで二重依頼不可（画面には409として表示）。
- 失敗時のLarkは`run.js`既存の失敗通知に任せる（重複通知を避けるため、依頼処理側では送らない）。
- 未取得判定とLarkアラート（期限超過）は別機能で実装済み（`lib/monthly-overdue-alert.js`）。再実行が成功すれば`import_runs`に成功が入り、未取得は自動で解消される。

## 4. 実機での動作確認（必ずこの順で）

> ⚠️ **本物のジョブは、いま押すと対象が「前月」＝2026年8月分になる。** ユーザーはPayPay加盟店の8月分を意図的に削除済み（元々手動で登録済みのため）。**8月分を復活させないこと。** 10/3の初回定期実行までは、実ジョブの再実行テストは行わない（ユーザーが明示的に望んだ場合のみ）。

**A. 実行を伴わない疎通テスト（先にこれ）**
1. ユーザー本人（マスター）でポータルを開き、会計・請求＞自動取込＞未取得に**「操作」列と「▶ 再実行」が出る**ことを確認（テーブルが無い間は出ない）。
2. 使い捨ての依頼で経路だけ確認する。サービスキーで`import_run_requests`に`{job:'__test__',status:'pending'}`をINSERT（サービスキーはRLSを迂回できる）→ 数分以内に`status='failed'`・`result='対象外のジョブ、またはタスクが見つかりません'`へ書き戻されること（＝拾う→確保→検査→書き戻しが動く）。確認後、そのテスト行を削除して0件を確認（CLAUDE.md「テストデータは作業後に完全削除」）。
3. RLSの確認: マスター以外（またはanon）のJWTで`INSERT`が拒否されること、対象外ジョブ名が拒否されること。

**B. 実ジョブの再実行（ユーザーの明示的な了承がある場合のみ）**
- 対象月を`TARGET_YEAR_MONTH`で指定する形にしたいなら§5-①を先に実装。指定なしで押すと前月分が再投入される点をユーザーに説明してから実施。
- 押下→「🕒依頼済み」→「▶実行中…」→完了で「前回の再実行: 成功/失敗 M/D HH:MM」に変わること、`import_runs`に`triggered_by='portal'`の行が入ること、失敗時にLarkへ通知が飛ぶことを確認。
