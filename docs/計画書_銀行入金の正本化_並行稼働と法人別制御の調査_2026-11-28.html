2. 既存GAS優先・正本は独立（ご指示2・3）

仕組み内容
順番口座ごとに「CSV取得 →（解析）→ GAS送信 → 正本への取込」。GAS送信が先に終わるので、正本側が遅くても待たされない
独立した枠正本側の例外・時間切れ（通信1回30秒・口座ごと2分）は、GAS送信の結果にも、他の口座にも影響しない。GAS側が失敗しても、正本側は実行される（GASの不調で正本を止めない）
失敗の通知正本側の失敗は、1回の実行につき1通にまとめて、別に通知（既存の通知の仕組み）。通知自体が失敗しても無視（ジョブの結果は変わらない）。実行結果の詳細にも「正本への取込は n 口座で失敗・GAS送信には影響なし」と残る
無効のときBANK_LEDGER_MODE が未設定なら、これまでと全く同じ動き（正本へは通信しない）

6-2. 既存の「法人別制御」の仕組み（法人情報システム・info）

  • info.can_access_corp(法人ID)：マスターは全法人／ユーザー個別の法人リスト（info.user_corporations）があればその法人だけ／なければ役割の法人リスト（info.role_corporations）／どちらも無ければ全法人。info.has_perm('カテゴリ') と組み合わせて、銀行口座・契約などの表のRLSに使われている（例：info.bank_accounts の閲覧＝権限カテゴリ「bank」かつその法人にアクセス可）。
  • この仕組みの対象ユーザー（info.profiles・9人）は、public.users と同じID。社長1・本部4（全員が info に登録済み）が含まれる。
  • 実際の設定：本部4人のうち、1人は2法人（LiveGate・トーホーエージェンシー）に限定されている。残りの本部3人・社長（マスター）は全法人。

6-3. 不足点

#不足影響
1銀行台帳の権限判定が、法人を一切見ていない法人を限定されている本部ユーザー（上の1人）が、台帳では全法人（N-Styleの口座・明細・原本まで）を見られる。既存の法人情報システムの設定より広い
22つの法人マスタのIDが別物（info.corporations と public.corporations。名前も「有限会社トーホーエージェンシー」と「トーホー」など表記が違う）そのままでは info.can_access_corp() を台帳に使えない。対応表（または public.corporation_aliases の別名）で結ぶ必要がある
3社長・マスターの「全法人」と、本部の「法人限定」を分ける属性が、public.users に無い（ユーザーの法人の持ち物は info 側にだけ）台帳の関数は info 側を参照する必要がある（info の更新が台帳の権限に効く）
4原本CSV（Storage）・取込ジョブ（サービスロール）・原本のパスに法人の概念がない法人別に原本を分ける場合は、パスに法人を含める／読み取りのポリシーで法人を判定する設計が要る。取込ジョブは1つのログインで2法人にまたがる
5bank_reconcile・差異・承認の記録も、法人で絞れない法人別の本部が承認する場合、他法人の差異を見て承認できてしまう
6GAS側（経営ダッシュボード）の役割（社長・本部）も法人を持たない画面切替のあと、画面側でも法人別の絞り込みが別途必要
