# 報告（司令塔宛）: インフォマート請求書PDFの自動取得案と、infomart-siireとの役割分担（担当D・2026-10-13）

対象: `seed_定期請求書10社_2026-10-11.md` §1／`設計書_請求書メール自動処理と仕訳承認フロー_2026-10-11.md` §8・§10・§11／`実装指示書_請求書自動処理_担当CFE_2026-10-11.md`（担当D分）。
調査したもの: `ns-daily-import/tasks/infomart-siire.js`・`config.js`・`lib/schedule-sync.js`・`lib/run-requests.js`・`import_run_requests`のSQL、D-9手順書、上記設計書。**実機（Infomart画面）はこのMacBookからは見られない**（認証情報がMac miniの`.env`のみ）ため、画面の操作手順は未確認。

## 0. 結論（先に）
1. **役割は別物。** `infomart-siire`は「店舗×日別の仕入見込（発注〜受領）の合計金額」＝速報。請求書PDFは「月1回・取引先×店舗×税率の確定金額」＝会計の正本。**seed §1の「請求明細（商品単位）は`infomart-siire`と同系統」は正確ではない**（siireは商品単位ではなく店舗別の日次合計。商品単位は発注明細＝D-9のAPI経路で、保留中）。
2. **Playwrightで自動取得は作れる見込み。ログインの部分は流用でき、画面の操作は新規。** 同じIDで入れる「請求書」サービスを使う想定（下記§3）。実機での確認が必要。
3. **⚠️最重要リスク: 仕入の二重計上。** 承認時にPLへ反映する設計（設計書§11-2）のままだと、請求書の仕入高が`infomart-siire`由来の原価と二重に載る恐れがある（§2）。実装前に方針の決定が必要。

## 1. 役割分担（確認結果）
| | infomart-siire（稼働中） | 請求書PDF（今回の対象） |
|---|---|---|
| Infomart側のサービス | 「受発注」→仕入日次推移（店舗別） | 「請求書」サービス（同じログインのサービス選択画面にある別サービス） |
| 中身 | 店舗×日の金額（発注〜受領の**見込**）。取引先別・商品別は無い（取引先別の誤レポートは中止する作り） | 取引先ごとの御請求書（店舗別・税率別の合計）。請求明細（商品単位）は別出力 |
| 頻度 | 毎日（朝7時前後）＋月初10日までは前月分も | 月1回（締め後に発行。9月分=10/1以降に取得可能な見込） |
| 行き先 | GAS「仕入れ」DB→経営ダッシュボードの原価（速報） | 請求書の自動処理（OCR→マッピング→仕訳下書き→承認→MF登録）→会計 |
| 性質 | 速報・店舗合計のみ | 確定・取引先別（仕訳の根拠・証憑） |
**併用が正しい**: 日々の原価の把握はsiire、月次の確定と仕訳は請求書。請求書が揃った月は、siireの月合計（店舗別）と請求書の店舗別合計を**突合**して差異を出すのが自然（siireは10社以外の取引先も含むので「請求書合計 ≦ siire合計」が目安）。

## 2. ⚠️二重計上の恐れ（要決定）
- 経営PLの原価(F)は `cost_auto（POS・仕入DB由来＝siireを含む）＋ cost_manual（DB_PL・精算書・請求書のPL直接反映）` で計算される（`refreshPlMonthly`）。
- 設計書§11-2は、承認時に`pl-fee-reflect`で勘定科目×店舗×月をPLへ反映する。10社の仕入高をこの経路で入れると、**同じ仕入がsiire（cost_auto）と請求書（cost_manual）で二重に載る**可能性が高い（cost_autoの`cogs`は日別分析シートの「仕入れ」列＝`infomart-siire`が書き込む仕入れDB由来であることをコードで確認済み。実際の数字の重なり方は担当A/Pの実データで確認してほしい）。
- 選択肢: **a=10社の仕入高は仕訳（会計）のみでPLへ直接反映しない**（PLの原価はsiire/POSのまま。請求書は突合に使う）／b=請求書確定月はsiireの該当分を置き換える（実装が複雑）／c=現状どおり二重を許容（不可）。**★おすすめはa**（PLの原価の主経路を変えずに済み、請求書の価値は会計の正確さと突合に出る）。なお衛生管理費（RSS・おしぼり）等の仕入高以外は従来どおりPL反映してよい。

## 3. 自動取得の案（Playwright）
### 3-1 流用できるもの／新規が要るもの
| 部品 | 流用 | 内容 |
|---|---|---|
| ログイン（`UID/PWD/Logon`）・専用プロファイル`withProfile('ns')`・`.env`の`INFOMART_ID/PASSWORD` | ✅そのまま | `infomart-siire.js`の`autoLoginIfNeeded` |
| サービス選択画面の通過 | △改造 | 現状は「受発注」を厳密に選び「請求書」を除外している。新ジョブは「請求書」を選ぶ版を追加（関数を引数化） |
| 請求書の一覧→PDF（＋請求明細CSV）ダウンロード | ❌新規 | 画面のセレクタは実機で確認が必要。ロケットナウ月次精算（`rocketnow-settlement.js`）と同じ作法（フォーム/ダウンロードイベント）で作れる見込み |
| 起動の仕組み | ✅ | `config.js`の`MONTHLY_SCHEDULE`に追加→`schedule-sync`で「自動取込ジョブ一覧」に自動表示（今日入れた仕組み） |
| 取得依頼の受け皿 | ✅ | `import_run_requests`（job・対象年月）をMac miniの`dispatch.js`が数分おきに拾って実行する既存の仕組み。ジョブは「月次・有効・kind∈deposit/purchase/sales」の条件に合わせて`kind=purchase`で登録すれば通る |

### 3-2 流れ
```
(A) 定期: 毎月1〜10日の朝（例 09:30）に新ジョブ `infomart-invoice` を実行
(B) 随時: 請求書メールが invoice_download と分類されたら、システム（Edge Function）が import_run_requests に
         { job:'infomart-invoice', target_ym } を追加 → Mac miniが数分以内に実行（同一ジョブのpending/runningは1件に制限＝重複依頼は自動で弾かれる）
ジョブ: ログイン→サービス選択「請求書」→対象月の請求書一覧→10社（取引先ごと）のPDFを取得
        →取得済み判定（請求番号 or SHA-256）で既存はスキップ→未取得分だけ取込口へ送信
        →10社すべて揃ったら「月次完了」、揃わない取引先は「未着」として結果に残す（Lark通知・自動取込ジョブ一覧に表示）
```
- 取込口（受け側）は**担当C側の新規**: サービスキー認証の取込エンドポイント（例 `invoice-auto-ingest`）。受け取る項目の案: `source='infomart'`・`vendor_hint`（取引先名）・`target_ym`・`infomart_invoice_no`・`file_name`・`file_data(base64)`・`sha256`。設計書§10の二重防止（SHA-256／業務キー=取引先×請求番号）をここで適用し、既存の読取（`invoice-ocr`）→マッピング→下書きの流れへ合流させる。`intake_source`は`auto`。
- 既存の`mf-journal intake_upload`はログイン中ユーザーのJWT前提なので、無人のPlaywrightからは使えない（新エンドポイントが必要）。
- 失敗時: 年月指定で再実行可（`TARGET_YEAR_MONTH`方式）／ポータルの「▶再実行」ボタンからも依頼可（月次・purchase条件に合うため）。

### 3-3 取引先ごとの対応（seedの10社）
10社は全て「インフォマート御請求書」形式（seed §1）なので、1つのジョブで全社を同じ手順で取得できる見込み。**ただしInfomartに無い取引先（紙・メール添付のみ）はこの経路の対象外**。`invoice_download`分類で依頼が来ても対応取引先でない場合は、設計書どおり例外（本部タスク）にする。
