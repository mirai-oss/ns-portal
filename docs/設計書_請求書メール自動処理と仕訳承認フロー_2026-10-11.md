## 8. 入口3経路と人・AIの分担（ユーザー補足・2026-10-11・確定）
対象文書: 請求書・売上入金・精算書など、支払いや売上を入力するときに来るもの。

| 入口 | 流れ | 既存の受け口 |
|---|---|---|
| 紙（郵送） | スキャン→管理システムへアップロード | 「アップロード請求書」（`intake_upload`・`intake_source=upload`） |
| メール | 自動取込→管理システム | `invoice-intake`（5分トリガー）→本書Phase1〜 |
| WEBダウンロード | AIが管理画面からダウンロード→管理システム | 自動取込ジョブ（`import_schedule`・Playwright。ロケットナウ・PayPay・インフォマート等＝担当D）＋`invoice_download`分類からの取得依頼 |

**人間がやること**: スキャン／会計入力の承認／振込。**それ以外はすべてAI・システム**（自動仕訳の会計入力=承認前まで・WEBからの請求書等のダウンロード・合っているかの確認=検算と異常検知）。
→ 入口が3つでも、**入口の直後からは同じ1本の流れ**（invoice生成→読取→マッピング→下書き→検算→承認待ち）に合流させる。`invoice_download`と判定したメールは、自動取込ジョブが対応していれば取得依頼を自動発行し、未対応の取引先だけ例外（本部タスク）にする。

## 9. 仕訳ルールの出どころと優先順位・仕訳辞書の位置づけ（2026-10-12 ユーザー確定・Sync11）

### 9-1 ルールの優先順位（取引先×明細の科目・補助・税区分・部門・貸方を決めるとき）
1. **過去の総勘定元帳（MF仕訳の実績）に履歴があるもの**を最優先の学習元にする（取引先×明細名→科目の実績。初期は`取引先ルール一覧_トーホーエージェンシー.xlsx`＝元帳分析の結果をseed。以後は`mf-journal`の実仕訳から定期的に再学習）
2. 履歴が無い／足りないものは、管理システムで**人が承認した自動仕訳**をルールとして保存
3. 人が**修正して承認**した場合は、**最後に修正した内容**を最優先のルールに更新（古いルールは履歴に残す・上書きで消さない）
4. **頻繁に修正される取引先×明細（例: 直近3か月で2回以上修正）は「ルール不安定」として毎回アラート**を出し、自動OKにしない（要確認に落とす）。安定したら自動OKに戻る
- 実装: `vendor_line_rules`に`source`（ledger/approved/corrected）・`version`・`corrected_count_90d`・`last_corrected_at`を持つ。承認画面で修正→保存時に新バージョンを積む

### 9-2 仕訳辞書（`mf_journal_templates`）の位置づけ
- **自動仕訳が稼働した取引先では、仕訳辞書は基本使わない**。取引先×明細の行ルール（9-1）＋取引先の既定（法人・貸方・計上日）で仕訳下書きを作る。承認画面に「辞書から選ぶ」は出さない（例外時の手動作成でのみ従来どおり）
- 給与（Sync8）の「法人×区分パターン」は内部的に辞書の行を使うが、人が選ぶ画面は無い＝同じ考え方
- 辞書は削除せず残す（手動作成・ロールバック・移行期の比較用）

## 10. 自動と人の二重処理防止（2026-10-12 ユーザー補足・確定）
前提: 同じ請求書が「インフォマート自動取得」「メール添付」「紙スキャンのアップロード」の複数入口から届きうる。人も自動も同じ1本の流れに合流させ、**請求書1枚＝invoice1件＝仕訳1本**を保証する。

| 二重の種類 | 防ぐ仕組み（既存＋追加） |
|---|---|
| 同じPDFが2回入る（入口違い・再送） | 既存: 添付SHA-256で`duplicate_suspected`。追加: **自動取得分も同じハッシュ登録**（Playwright取得＝`invoice-intake`と同じ受け口に流す） |
| 同じ請求書が別ファイルで入る（メールのPDFと紙スキャン等） | 追加: **業務キー `取引先×請求番号`**（請求番号が無ければ`取引先×対象年月×税込合計`）で`invoices`に部分ユニーク索引（cancelled除く）。2件目は作らず既存invoiceに「別経路からも到着」を記録 |
| 定期取引先の同じ月に2枚 | 追加: `vendor_line_rules`の取引先は「月1枚」が既定（`expected_per_month`）。2枚目は`duplicate_suspected`＋要確認 |
| 自動が下書き中に人が手で仕訳を作る | 追加: `current_stage`が`parsed〜ready_for_approval`の間は**請求書詳細の手動仕訳ボタンを無効化**し「自動処理中（AI）」バッジ。人が触りたいときは「手動に切り替え」ボタンで自動を止めてから（`current_stage=manual`・理由必須） |
| 人が処理中に自動が上書き | 既存: メールの`processing_user_id`/ロック。追加: invoiceにも同じロック列を使い、人がロック中は自動は`journal_draft`を書かない（次回の巡回で再試行） |
| 仕訳の二重登録（承認連打・別画面から再登録） | 既存: `payroll_journal_records`と同様に`invoices.mf_journal_id`を持ち、**登録済みなら再登録不可**（`mf-journal create`側でも`invoice_id`に既存journalがあれば拒否） |
| 本部タスクの二重 | 既存: `exception_reason`べき等 |
| PL・精算書・広告への二重反映 | 既存: `invoice_pl_reflections`の`source_key`単位upsert／精算書の`sourceKey`冪等。自動の下書き反映も同じキーを使う |

運用ルール: **自動取込が動いている取引先（10社〜）は、人は請求書を「アップロードしない・手で仕訳を作らない」。承認画面で確認するだけ**。紙で届いた場合も同じ請求書なら業務キーで吸収される。例外（自動が止まった請求書）だけ本部タスクに出て、そこから「手動に切り替え」で処理する。

## 11. 承認後のPL反映・精算書店舗の振り分け・入口の扱い（2026-10-13 ユーザー確認・Sync12・スコープ凍結）

### 11-1 入口はどれでも同じ扱い（確定）
自動取込（インフォマート等のダウンロード）／メール添付／人がスキャンしてアップロード、の3入口はすべて同じ流れ（invoice生成→読取→マッピング→下書き→検算→承認待ち）に入り、**承認したら同じ後続処理（MF登録→PL反映）が走る**。`intake_source`（auto/email/upload）は出所の記録であって処理の分岐ではない。メールで来た請求書も「自動取込扱い」として処理する。

### 11-2 承認時にPLへ反映する（§1「17」の「下書きまで」を更新）
承認＝人の確認が済んだ状態なので、承認時に**既存の`pl-fee-reflect`（勘定科目×店舗×月）をそのまま実行してPLへ反映する**（取り消しは既存`unconfirm`）。広告費は既存`ad-cost-reflect`、精算書は既存`seisan_confirm`で同様。「AI=下書き・人=承認」は維持（反映は承認後にしか起きない）。

### 11-3 業務委託精算書に入る店舗は精算書経由のみ（二重反映の禁止）
- 店舗を`resolve_store`で特定したあと、**その店舗が業務委託精算の対象か**（`v_store_current_relations`で運営主体が外部委託会社＝`vendor_roles.operator`／既存`stores.seisan_pl_categories_target`）を判定し、**行ごとにルートを1つだけ**決める:
  - 精算書対象店舗（じんべぇ 川崎／じんべぇ 新横浜／エース 本厚木／秋葉原 肉寿司）→ `reflection_route='seisan'`＝精算書へ登録。PLには**精算書の振込確定後に既存の`syncSeisanCategoriesToPl`で入る**（請求書側からPLへ直接は入れない）
  - それ以外 → `reflection_route='pl'`＝PLへ直接反映
- 同じ`source_key`（請求書ID×行）で両ルートに入れない制約（既存`invoice_pl_reflections`の`reflection_route`に加え、アプリ側で排他）。黒霧屋 新横浜はトーホー運営（グループ内・運営委託費なし）なので`pl`ルート（TK-126の方針どおり対象法人・運営関係で自動振り分け）
- 検算に「ルート判定」を追加: 1請求書の明細に精算書店舗と通常店舗が混在しても、行ごとに正しく振り分けられていること
