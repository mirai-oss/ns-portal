# 設計書ドラフト: 個人評価制度（個人評価タブ＋直属の部下からの非公開査定→ランク）

作成: 2026-09-01（司令塔） ／ 状態: **設計ドラフト＝§4の質問回答後に確定・着手**
発端: 2026-09-01ユーザー要望（項目2）。既存バックログ「評価制度の3層カデンス（毎月KPI／3ヶ月中間評価／6ヶ月給与・役職改定）」（要望まとめF1/F2・2026-08-24）と**同一テーマとして統合**する。

## 1. 要望の整理

1. **個人評価タブ**: その人の「現在の評価（ランク）」が見られる画面
2. **直属の部下からの査定**: 部下が定期的に上司を査定する（**本人には見えない**）。それをもとにランクを付ける
3. **ランクの定義は別設計が必要**（ユーザー明言）→ 本書がその設計書。§4の回答で確定させる

## 2. 実装案（回答前の骨子）

- **置き場所**: nippoの従業員管理まわりに「個人評価」タブ（本人向け=自分の現在ランクと推移／管理者向け=全員のランク一覧・査定状況）
- **査定の流れ**: ①査定期間になると、対象者の「直属の部下」に査定フォームが届く（nippo内・リマインドはLark/アプリ内の既存パターン）②部下が入力（本人からは誰が何を書いたか見えない）③管理者（社長・マスター）が査定結果＋KPI実績を見てランクを確定④本人の個人評価タブに「ランクと総評」だけ反映（個別回答は非公開のまま）
- **データ**: 新テーブル群（例: `ev_rank_master`=ランク定義／`ev_reviews`=査定回答（RLSで本人読取不可）／`ev_ratings`=確定ランク履歴）。**回答の生データは本人・一般には物理的に読めないRLS設計**（管理者と司令塔設計で決めた閲覧者のみ）
- **既存資産との接続**: 3層カデンス（毎月KPI=システム実績から自動・3ヶ月中間・6ヶ月改定）の「3ヶ月中間評価」の材料に部下査定を使う形が自然。KPI自動連携（チェック実施率・出勤強化日等）は要件定義書の既存原則どおり

## 3. 誰が誰を査定するか（データの持ち方）

「直属の部下」の定義が必要 → `employee_profiles`等に**上司（直属の上長）**を持たせる（店舗×役職からの自動推定＋手動修正）。この上司‐部下マップは入社・異動時にメンテナンスする前提（管理画面で編集可）。

## 4. ユーザーへの質問

- **評価Q1（頻度）**: 部下からの査定はどの周期でやりますか？（毎月／3ヶ月ごと=中間評価に合わせる／半年ごと）
- **評価Q2（ランク定義）**: ランクの段階と呼び方のイメージを教えてください（例: S/A/B/C/Dの5段階）。また**ランクが何に影響するか**（給与・役職・賞与・表彰など）
- **評価Q3（匿名性）**: 部下の査定は「本人に見えない」に加えて、**管理者（社長・マスター）にも誰が書いたか伏せますか？**（完全匿名か、管理者だけは見られるか）
- **評価Q4（査定項目）**: 部下が上司を査定する項目のイメージはありますか？（例: 指導力・公平さ・働きやすさ等を5段階＋自由記述。無ければこちらで叩き台を作って確認してもらいます）
- **評価Q5（対象者）**: 査定される側は誰まで？（店長以上／社員以上／本部も含む）。査定する側の「部下」はアルバイトも含みますか？
- **評価Q6（表示範囲）**: 本人の個人評価タブに見せるのは「現在ランク＋総評」まででよいですか？（部下査定の点数分布などは見せない前提）
