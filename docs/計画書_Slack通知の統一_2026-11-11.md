# 計画書: Slack 業務通知を「親 1 行＋詳細スレッド」に統一する

作成 2026-11-11 夜。**調査と計画まで。本番の変更はしていない（各段階の切り替え前に報告し、承認をもらう）。**
関連: [Slack 通知の共通フォーマット 設計書](設計書_Slack通知の共通フォーマット_2026-11-11.md) §16（勤怠確認で実装した形）・§17。

## 0. 決定事項（2026-11-11 夜 ユーザー最終決定）

- 原則すべての Slack 業務通知を、**親メッセージ 1 行＋詳細スレッド**にそろえる。
- 親メッセージ: 種類と対象者（必要なら日付と、短い状況「承認待ち・完了・要対応」）。操作は［詳細を確認］だけ。原因・詳細・理由・変更前後・長い説明は出さない。
- スレッド: その処理に必要な情報だけ（種類と原因・申請内容・変わった項目の差分・理由・状況・確認事項・操作・結果と履歴）。承認・却下・修正・再実行・中止のボタンはスレッドの中。済んだ案件のボタンは消す。
- 権限・承認の流れ・履歴は今のまま。賃金額・交通費額は Slack に出さない（スイッチ A を維持）。
- 通知を増やさない: 同じ案件で親を何度も出さない／状況は既存のメッセージを書き換える／リマインドは同じスレッド／自動処理の成功では通知を増やさない／人の判断が要るときだけ通知／同じエラーを短時間に繰り返さない／必要な担当だけにメンション。
- 進め方: 第 1 段階 勤怠確認 → 第 2 段階 入社登録・初期設定 → 第 3 段階 退職・賃金変更・店舗異動 → 第 4 段階 勤怠修正・休憩漏れ・その他。

### 1.3 調査で分かった重複・ばらつき

- Slack へ送る小さな関数が 7 か所に別々にある。承認依頼のブロックが 3 か所でほぼ同じ形。
- 入社の知らせが、最大 3 通重なりうる（従来の文面・DB からの別経路・親カード）。
- リマインドは、元のメッセージを複製して親を増やす作り（勤怠確認の新しい形だけ、スレッド内に直した）。
- 成功の通知を毎回出しているものがある（日次の取込 14 日で 40 件）。
- 期日超過は、解消するまで毎日、新しい親で出ている。

## 2. 共通の通知のしくみ（設計）

勤怠確認で作った部品（`_shared/attendance-alert-notice.ts`）から、種類によらない部分を取り出して共通部品にする。通知ごとに別の仕組みは作らない。

| 部品 | 中身 | もとになるもの |
|---|---|---|
| 案件の控え | 1 案件＝1 行。親・カードの控え、スレッドの位置、状態、対象者・店舗・日付 | `notice_cases`（作成済み・勤怠確認で使用中） |
| 種類の設定 | 種類の名前・絵文字・出す先・切り替えの版（今までの形／新しい形） | `notice_types`（作成済み。版の列あり） |
| 親 1 行 | `{印} {種類}｜{氏名}｜{日付}｜{短い状況}` ＋［詳細を確認］ | 勤怠確認の親 |
| カード | スレッドの 1 通目。「見出し・項目の行・変わった項目の差分・状況・いま押せるボタン」を受け取って組み立てる。状態が変わるたびに同じカードを書き換える | 勤怠確認のカード |
| スレッドへの返信 | 承認の依頼・リマインド・エラー（人の対応が要るときだけ。担当にメンション） | 勤怠確認の返信 |
| 送る処理 | 出す（親 → カード → 控え）／書き換える／返信する／リマインドする | `postAlert`・`renderAlert`・`remindInThread` |
| メンション | 種類ごとのルールで担当を決める。未連携・保留の店舗は広げない | `notice_mention_rules`・`notice_mention_targets`（作成済み） |
| 金額の守り | 文面で出さない → 出口で消す → 消し残りがあれば送信を止める | 既存の 3 段（そのまま通す） |

- 種類ごとに書くのは「カードに何を出すか」と「どのボタンを出すか」だけ。
- ボタンの名前（action_id）と、押したあとの処理（権限の判定・承認・履歴）は変えない。変えるのは「どこに表示するか」。
- 切り替えは種類ごとのスイッチ。進行中の案件は、始まったときの形のまま終わらせる（途中で形を変えない）。
- 大きな書き換えはしない。各関数の「文面を作る所」を共通部品の呼び出しに置き換える。

### 2.1 通知を増やさないための共通ルール

| ルール | しくみ |
|---|---|
| 同じ案件で親は 1 つ | 案件の控えで判定。2 回目以降は書き換え |
| 状況は書き換えで見せる | 親の印と短い状況／カードの状況の行 |
| 自動処理の成功は返信しない | カードの項目を「完了」に書き換えるだけ |
| 人の対応が要るときだけ返信 | 失敗・確認待ち・承認の依頼・期限切れ |
| 同じエラーは繰り返さない | 同じ案件・同じ内容は一定時間 1 回（金額の知らせと同じ作り） |
| リマインドは同じスレッド | 担当だけにメンション。間隔は今の 12 時間おきを基本にする |
| 完了したら静かに | 親を ✅ に書き換えるだけ。メンションしない |

## 3. 入社登録の変更案（第 2 段階）

### 3.1 形

親メッセージ（1 人に 1 つ）

```
👤 入社登録｜山田太郎
［詳細を確認］
```

状況の印: `👤`＝手続き中／`🔴 …｜要対応`＝止まっている項目がある／`✅ …｜完了`／`⛔ …｜中止`。

スレッド 1 通目（状況のカード。項目が進むたびに書き換える）

```
【入社登録】
氏名：山田太郎（アルバイト）
所属：鳥一代 本店
入社日：11/15

【登録状況】
入社フォーム：完了
スマレジ従業員登録：完了
Slack 連携：完了
賃金設定：確認待ち
交通費：確認待ち
源泉所得税：未
本人のスマレジアカウント：未
```

スレッド 2 通目（操作のカード。いま必要なものだけ）

```
［賃金を設定］［交通費を設定］［管理画面で開く］
（その他: 源泉所得税／本人へ連絡／スマレジ照合／表示を更新／中止）
```

- 金額は出さない（いまのスイッチ A の表示と同じ。「賃金設定済み」「交通費確認待ち」などの言葉だけ）。金額の確認と入力は、権限のある管理画面。
- 初回出勤日は、いまの入社フォームに項目が無いため出さない（項目を足すかは判断事項）。

### 3.2 いまのスレッドへの投稿（25 種類ほど）の整理

| いま | 変更後 |
|---|---|
| 成功の知らせ（賃金を反映した・交通費を設定した・照合した・源泉を保存した など） | 返信しない。状況のカードの項目を書き換える |
| 人の確認が要るもの（交通費の経路確認・適用開始日が変わった賃金・入社後提出の承認） | スレッドに 1 通（ボタンつき）。済んだらそのメッセージを書き換えてボタンを消す（今と同じ） |
| 失敗（賃金の反映失敗・スマレジ画面の自動操作の失敗 など） | スレッドに 1 通（再実行ボタン）＋親を「要対応」に。同じ失敗は繰り返さない。本部タスクは今までどおり失敗時だけ |
| 停滞のまとめ | スレッド内のリマインド（担当にメンション）に置き換え |
| 従来の文面・DB からの入社完了の知らせ | 出さない（親カードに一本化） |

### 3.3 欠けてはいけない処理（通知の変更では触らない）

入社フォーム送信／スマレジ従業員登録／Slack 招待と連携／人事チャンネルへの入社通知／賃金設定と承認／スマレジへの賃金反映と照合／交通費などの初期設定／本人アカウント登録案内／失敗時だけ本部タスク。

- これらは通知より前の処理（RPC・Edge Function・本部タスク）で動いている。変えるのは「文面を作る所」と「どのメッセージを書き換えるか」だけ。
- 切り替え前に、テスト用の入社登録 1 件で、上の 9 つが新しい形でも最後まで進むことを通しで確認する（賃金・交通費の実書き込みはしない・既存のテスト手順を使う）。
- 進行中の入社登録は、今までの形のまま終わらせる。

### 3.4 規模と影響

- 変更するのは `onboarding-blocks.ts`（親の組み立てを「親 1 行」「状況のカード」「操作のカード」に分ける）と `onboarding-notify`（親の書き換え → 3 つの書き換え、成功の返信をやめる）。`slack-interact` のボタンの処理は変えない。
- 規模: 1 単位ほど。稼働中のため、新しい入社登録から切り替える。

## 6. 時給の人の休憩漏れの確認（第 4 段階の一部。★有効化は別途承認）

|---|---|---|---|---|---|
| **鶏武者 新横浜（おすすめ）** | 28 | 3 件ほど | 12 | 2 人中 2 人 | 1 人（連携済み） |

### 6.2 通知の見本

親メッセージ（#勤怠確認・店舗ごと・1 日 1 つ）

```
🕒 休憩の確認｜鶏武者 新横浜｜11/10
［詳細を確認］
```

スレッド（人ごとに 1 通）

```
【休憩の確認｜休憩の打刻なし】
対象者：山田太郎
打刻：出勤 15:00／退勤 23:30／休憩 なし

［✏️ 休憩を入れる（フォームを開く）］［休憩は取っていない］
```

- 済んだ人のカードは「✅ 休憩を申請（申請者）」「✅ 休憩なしで確認（確認者）」に変わり、ボタンが消える。
- 親は、残りがあるあいだ `🕒 …｜残り 2 人`、全員済むと `✅ …｜完了`。
- リマインドはスレッド内（その店舗の社員・店長＋担当チーム長にだけメンション）。
- 未確認のままでも、勤務時間は打刻のまま（控除しない）。

### 6.3 実装の方法（規模 1 単位ほど）

- 検知: 毎朝の勤怠確認と同じ処理に足す。条件＝給与形態が時給（`attendance_pay_type`）・6 時間超・休憩の登録なし・「休憩を取っていない」の申告なし・給与確定前。対象の店舗は設定（`test_store_ids`）で絞る。開始日より前の勤務は出さない。
- 記録: 店舗×日の案件（`notice_cases`）と、人ごとの明細の表（新規）。
- ［休憩を入れる］: 勤怠修正フォーム（既存）。承認・スマレジ反映は今の勤怠修正と同じ。
- ［休憩は取っていない］: 既存の「休憩の申告」（`sf_break_exception_submit`）に記録。
- 同じ勤務に勤怠確認（打刻漏れなど）が出ているときは、そのスレッドに「休憩の登録なし」を足し、親を増やさない。

## 7. 未確認のこと・判断が必要なこと

1. 勤怠確認の実機確認（社長）。
2. 入社登録のカードに「初回出勤日」を出すか（いまの入社フォームに項目が無い。出すならフォームに項目を足す）。
3. 入社登録で、成功の知らせをスレッドに出さなくしてよいか（カードの書き換えだけにする案）。
4. 日次の取込の「成功」の通知（14 日で 40 件）をやめ、異常のときだけにしてよいか（第 4 段階）。
5. 時給の休憩漏れをテストする店舗（おすすめ: 鶏武者 新横浜）。
6. 本部タスクの通知を Slack に出すか（いまは出ていない）。
7. 承認の依頼を、DM ではなくスレッドのメンションだけにしてよいか（新しい形の勤怠確認はこの作り）。
