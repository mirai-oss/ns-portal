# 整理: Slack 通知の必要性の見直し（停止候補の調査）

作成 2026-11-11 深夜。**調査と提案まで。本番の変更・通知の停止・定期処理の停止はしていない（どれも承認をもらってから）。**
関連: [計画書 Slack 通知の統一](計画書_Slack通知の統一_2026-11-11.md)（形の統一と段階）／[棚卸し Lark・Chatwork 通知の解除計画](棚卸し_Lark_Chatwork通知の解除計画_2026-11-11.md)（別担当）。

## 0. 最上位ルール（2026-11-11 ユーザー決定）

Slack は「システムの動作報告の場所」ではなく、「人が判断・対応するための場所」。

| 分類 | 何か | Slack での扱い |
|---|---|---|
| **A 緊急・重大** | 給与・振込に影響するエラー／連携の継続的な障害／重要データの不整合／主要機能が使えない／期限の迫った重大案件 | 必要な担当へすぐ通知。解消までリマインド。同じ障害で親を増やさない。解消したら同じカードを更新 |
| **B 要確認・要対応** | 人の設定・承認・確認が要るもの／自動処理が失敗して手作業が要るもの | 必要な担当だけに通知。1 案件 1 親。詳細と操作はスレッド。未処理のときだけリマインド |
| **C 記録のみ** | 正常な取込・連携成功・正常稼働・通常の速度計測・照合成功・自動処理の完了・自動で復旧した軽いエラー・進捗 | Slack に出さない。記録は管理システムに残す。人の対応が要る状態になったときだけ通知 |

- 判断の基準は「数値が通常から外れたか」ではなく「人の対応が要るか」。
- 給与・個人情報・データの欠けに関わる異常は、自動で復旧しても「影響の確認が要るか」を判定する（要るなら B）。
- **監視・記録・通知は別もの。** 通知を止めても、監視と記録は止めない。

## 3. スプレッドシートとの照合（`bq-sales-reconcile`）

| 項目 | 調査結果 |
|---|---|
| 何を参照しているか | 経営ダッシュボードのスプレッドシートの「分析_日別店舗」シートと、BigQuery の日別店舗の表 |
| 何を照合しているか | 直近 35 日の純売上と仕入れの合計。差が 100 円以上で「差額あり」。人件費は 11/5 から対象外（BigQuery 側を勤怠の値に替えたため、毎日差が出ていた） |
| 処理の中身 | 1 つのジョブに 2 つの処理: ① シートの内容を BigQuery へ写す（同期）② 合計の照合 |
| 照合の結果の使われ方 | **通知だけ。** 他の処理は使っていない。DB にも保存していない |
| 同期の使われ方 | **使われている。** ダッシュボードの表示・集計・レポート・朝の監視が BigQuery の表を読む。ジョブの記録は、集計の更新のきっかけにもなっている |
| 正本への影響 | 照合は読むだけ。管理システムの正本は変えない |
| 止めると | **照合の通知だけ止める → 影響なし。** ジョブごと止める → 11:00 の同期が無くなる（朝と 16:00 の同期は残るが、反映が遅れる・集計の更新のきっかけが 1 つ減る） |
| 業務での利用 | このシートは、BigQuery へ写す元としてまだ使われている（「使っていないシート」ではなく、「照合の通知が不要」な状態）。完全に管理システムへ移した後で、同期ごと止められる |

- **止められるもの**: 照合の差額通知（記録だけにする）。
- **残すもの**: 同期（ジョブ本体）。朝の再生成と同期。
- ほかの照合:
  - 現金売上の月次照合（毎月 3 日・結果は仕訳候補に使う）＝残す。通知は Lark だけ・一致でも送っている → 一致は通知不要、不一致だけ B。
  - SMBC カードの入金（成功でも通知）＝取込は残す。成功の通知は停止候補（照合の結果を見る場所が通知だけ、という事情があるため、画面で見られるようにしてから）。
  - 人件費の按分の比較（毎週・表に保存だけ・通知なし）＝そのまま。
  - 給与明細と見積もりの月次の差（しきい値を超えたときだけ）＝残す。

## 4. 読み込み速度・監視の通知

実測（直近 15 日・1 日 1,200〜3,300 回の呼び出し）

| 指標 | ふだんの値 |
|---|---|
| 1 日の失敗率 | 0.4〜3.8% |
| 1 時間の失敗率が 10% を超えた回数（呼び出し 20 回以上の時間帯） | 15 日で 1 回 |
| ダッシュボードの主な読み込みの中央値 | 15〜19 秒 |
| 同 95% の値 | 21〜56 秒（まれに 180〜270 秒） |
| 集計の読み込みの中央値／95% | 4 秒／5〜17 秒 |

通知する条件（案）

| 条件 | 分類 | 通知 |
|---|---|---|
| 30 分のあいだ、主な読み込みの失敗率が 30% 以上（10 回以上の呼び出し） | B | 「システム障害｜経営ダッシュボード」1 件。続くあいだは同じカードを更新 |
| 上の状態が 60 分続く、または 1 時間すべて失敗 | A | 同じカードを「要対応」に。担当にメンション |
| 主な読み込みの中央値が、1 時間続けて 40 秒を超える（ふだんの 2 倍強） | B | 「著しい遅延」1 件 |
| 昨日の売上・勤怠の取込が欠けている（朝の監視） | A | 「データの欠け」1 件。解消で同じカードを更新 |
| 毎日の取込が、再試行しても残った | B | 「取込エラー」1 件 |
| 一時的な遅延・単発の失敗・自動で復旧したもの | C | 通知しない（記録だけ） |

- 計測は今のまま続ける（表に 14 日ぶん）。日ごとのレポートは Slack に出さず、必要なら管理画面で見る。
- しきい値は設定で持ち、運用を見て調整する。

## 5. 入社登録の重複の解消

いまの経路（1 人の入社で出うるもの）

| 経路 | 出す先 | いまの状態 |
|---|---|---|
| ① 入社登録の親カード | Slack #本部-人事 | 有効（これに一本化する） |
| ② 従来の文面（賃金を登録してほしい依頼） | Slack #本部-人事 | **停止済み**（11/9 に設定で停止） |
| ③ DB からの「入社登録を完了しました」 | Chatwork（Slack あての行は無効） | **Chatwork で有効** |
| ④ スマレジの事業所の自動作成の結果 | Slack #本部-人事（スレッドの外） | 有効（試行のたびに新しい投稿になりうる） |

- Slack の中では、いまは ① だけ（②は停止済み・③の Slack あては無効）。④ が外に出る点だけ残っている。
- 解消の方法: ③ は Chatwork の行を無効にする（通知だけの処理。登録・賃金・交通費・本人案内・本部タスクは別の呼び出しなので欠けない）。④ は入社のスレッドに入れ、失敗のときだけ出す。
- 注意: ③ の文面にある「スマレジの URL・メール登録の依頼」は、親カードには無い。新しい形のカードの「必要な設定を開く」に入れる。
- 止める順: 新しい形の入社通知（第 2 段階）を出してから ③ を止める（それまで Chatwork は止めない）。

## 7. 本部タスクの Slack への移行計画

いま: 本部タスクの通知は Chatwork だけ（共有の部屋 3 つ＋個人の部屋）。送るのはタスクの画面。期限の判定は、だれかが画面を開いた日だけ動く。

| 出来事 | いま（Chatwork） | Slack に移したあと |
|---|---|---|
| 次の工程の担当になった（＝新しく人の対応が要る） | 通知 | **B**: 担当にメンション。タスク 1 件につき親 1 つ（`✅ 本部タスク｜タスク名｜担当`）。工程が進んだら同じ親を更新 |
| 異常ありの報告 | 通知 | **B**（給与・振込に関わるタスクは **A**） |
| メンションつきのコメント | 通知 | **B**: そのタスクのスレッドに |
| 最重要の印 | 通知 | **A**: 親を「要対応」に |
| 期限の 3 日前・前日 | 通知 | **C**（出さない）。当日と超過だけ **B**（スレッドのリマインド） |
| 工程の完了・タスクの完了・自動処理の完了 | 一部通知 | **C**（親の更新だけ） |

移行の手順

1. 判定をサーバー側へ: 期限の判定を毎朝の定期処理にする（いまは画面を開いた日だけ）。
2. Slack に出す処理を足す（共通部品を使う・第 4 段階）。宛先の設定に Slack の行を足せる作りにする。
3. **並行期間**: Slack と Chatwork の両方に出す（1〜2 週間）。同じ人に二重で届くため、期間は短くする。
4. 確認のうえ、Chatwork の行を無効にする（行を消さず無効にするだけ＝すぐ戻せる）。**それまで Chatwork は止めない。**
5. 経費の申請・承認、精算の振込期限も同じ手順で（別担当の解除計画と合わせる）。

## 8. 月給の人の給与計算のテスト方法（★実施は承認後。実データは変えていない）

目的: 月給の人の勤務に休憩 60 分を入れたとき、スマレジの集計と給与計算がどう変わるかを確かめる。

- **対象: テスト従業員「テスト 立会い」（スマレジのスタッフ 380）だけ。** 実在の従業員の勤怠は変えない。スマレジに検証環境は無いため、本番の契約の中のテスト従業員で行う。
- 読む場所（どちらも読むだけの API）:
  - 日ごとの勤務実績: 拘束時間・休憩の時刻・概算人件費。
  - 月の給与明細: 総労働時間・残業時間・法定外残業・深夜の分・基本給・残業手当・深夜手当。
- 手順
  1. 準備: テスト従業員に月給の行を登録する（前回の実機テストと同じ。終わったら時給に戻す）。
  2. テスト勤務を 2 件作る（スマレジに作成）: ㋐ 日中の長い勤務（10:00〜19:30）㋑ 深夜を含む勤務（15:00〜翌 0:30）。
  3. 「休憩なし」の状態で、上の 2 つの API を読んで記録。
  4. 休憩 60 分を入れる（㋐ 13:00〜14:00 ㋑ 22:30〜23:30＝深夜の時間帯）。
  5. もう一度 2 つの API を読み、前後の差を表にする（拘束時間・休憩時間・実労働時間・残業時間・深夜労働時間・各手当）。
  6. 管理システムへ取り込み直し、スマレジと同じ値になることを確認。
  7. 復旧: テスト勤務 2 件を削除（スマレジの削除）→ テスト従業員の賃金を時給に戻す → 月の給与明細がテスト前と同じ値に戻ることを確認 → 管理システム側のテストの行・履歴を削除。
- 変わるもの: テスト従業員の勤務 2 件（作成 → 削除）と賃金の行（月給 → 時給に戻す）だけ。前回の実機テストで、作成・休憩の書き込み・削除・復旧は実績あり。
- 限界: テスト従業員の賃金の条件（固定残業の有無・所定の時間）が実在の月給の人と違うと、残業の出方が違う。金額ではなく「休憩の前後で、どの時間がどれだけ変わるか」を見る。実在の月給の人の設定の形（固定残業の有無など。金額は見ない）は、事前に読むだけで確認する。
- 給与の締めへの影響: テスト勤務は当日中に削除する。テスト従業員は給与の対象外。
