## 前提（DB の関数。SQL `2026-11-18_onboarding_wage_approval.sql`）
- `onboarding_wage_status(p_workflow, p_actor, p_only_open)` … 状況。ログインしている本部・社長・マスターには金額（`rows`）と却下の理由も返る。
  `p_workflow` を省くと全員ぶんの一覧。`requests[].can_decide`（承認・却下できるか）・`can_cancel`・`viewer.can_approve` は DB の答えをそのまま使う。
- `onboarding_wage_submit(p_workflow, p_rows)` … 入力。戻り値 `applied`（true＝その場で正式な賃金）・`rule`・`reason`・`request_id`。
- `onboarding_wage_decide(p_request, p_approve, p_note)` … 承認・却下（社長だけ。却下は理由が必須）。
- `onboarding_wage_cancel(p_request, p_note)` … 取り下げ。
- スマレジへの反映は、DB が Edge Function を呼んで行う。**画面からは wage_push を呼ばない**（二重に送らないため）。

## 変更点の一覧
1. 従業員ページの読み込み（8020 行付近。`loadWageRows` の次）: 本部・社長・マスターのときだけ `obWage=await loadObWage(adminDetail)` を足す。
2. 賃金カード `wageCardHtml`（8807 行〜）: 先頭の説明文のすぐ下に `obWageCardHtml()` を差し込む（承認待ち・却下・履歴）。
3. 賃金カードの「保存してスマレジに反映」（8858 行〜の `data-wagesave`）: `payWageNeedsRequest(c)` の分岐の**前**に、`obWageActive()` のときの分岐を足す（下の下書き A）。
4. 賃金カードの「修正 → 保存」（`data-wageeditsave`）と「◯◯の現在の賃金をコピー」（`data-wagecopy`・`copyWagesToContract` 8542 行）:
   `obWageActive()` のときは、同じく `onboarding_wage_submit` に回す（修正は 1 行ぶんを p_rows に入れる）。まず最小では「入社手続き中の人は、下の入力欄から入れ直してください」と案内して止めるだけでもよい（DB 側の制限が同じ内容のエラーを返す）。
5. 管理ページの「📝 承認待ちの申請」（`approvalCardHtml` 7242 行）: 既存の一覧の下に、入社時の賃金の承認待ちを並べる（下の下書き C。金額は出さない・名前を押すと従業員ページ）。既存のカードが出ない条件（ルートが無効で案件も無い）でも、入社時の賃金の承認待ちがあれば出す。
6. ボタンの結び付け `bindWageCard`（8846 行〜）の末尾に、承認・却下・取り下げを足す（下の下書き B）。
7. 文言: 承認待ちのあいだ、賃金カードの一覧（正式な賃金）には行が**出ない**のが正しい。カードに「承認されるまで、スマレジには反映されません」と書く。

## 確かめること（画面を直したあと）
- 設定が無効: 賃金カードの見た目・保存・反映が今までと同じ。
- 有効・アルバイト: 保存 → すぐ一覧に「⏳反映待ち」→ しばらくして「✅反映済み」（Slack のスレッドに結果）。画面からは wage_push を呼んでいないこと。
- 有効・社員: 保存 → 一覧に行が出ない・「社長の承認待ち」が出る → 社長以外には承認ボタンが出ない → 社長が承認 → 一覧に出て反映される／却下 → 出ない。
- `data-au` の行を押すと従業員ページへ移る（既存の一覧と同じ結び付けが効くか）。
- 承認の直後に画面を描き直した時点では、まだ「⏳反映待ち」のことがある（反映は裏で進む）。数秒後に描き直すか、「更新」を案内する。
