# 設計書ドラフト: 全社バックアップと復旧（「ここを見ればすべてのデータが回収できる」場所を作る）

作成: 2026-08-27（司令塔） ／ 状態: **設計ドラフト＝§5の質問にユーザーが回答してから確定・着手**
発端: 2026-08-27ユーザー要望「サーバーが壊れたときにバックアップされてる場所がわかるように、ここを見ればすべてのデータが回収できる場所を作りたい。ダッシュボードのデータが全部壊れたらそこだけに依存してしまうのは避けたい。数字だけでなく写真などのデータも含めリスクヘッジしたい」

**既存との関係**: `docs/バックアップと復旧.md`（2026-08-18・ハブSupabaseのみ）の全社版への拡張。2段階認証は**社内情報管理システムには導入済み**（ログイン時MFA・アカウント画面で管理）のため対象外とし、本書は「データを失わない」ことに集中する。

## 1. 現状の棚卸し（何がどこにあり、何に守られているか）

| データ | 正本の場所 | 今のバックアップ | 壊れたときのリスク |
|---|---|---|---|
| 業務データ（日報・シフト・タスク・請求書・応募者・経費 等） | ハブSupabase | ✅日次自動（直近7日・東京リージョン） | 8日以上前には戻せない。**7日間気づかない事故に弱い** |
| 機密データ（給与体系・借入・書類 等） | 社内情報Supabase（別プロジェクト） | 要確認（プラン次第） | 同上＋**バックアップ状態が未確認** |
| **写真・添付ファイル**（日報写真・請求書PDF・応募者写真・保管書類） | Supabase Storage（両プロジェクト） | ❌**無し**（DBバックアップの対象外と確認済み） | **誤削除・障害で永久に消える。現状最大の穴** |
| 売上・広告・PLの分析データ | BigQuery `tori-analytics` | ❌スナップショット無し | 大半はシートから再生成可能だが、手順を知らないと復旧に時間がかかる |
| 売上・PLの元データ（各種スプレッドシート） | Google スプレッドシート | ✅Google Drive標準（版履歴） | 比較的安全。ただし「どのシートが正本か」の一覧が無いと探せない |
| プログラム（各システムのコード） | GitHub 5リポジトリ | ✅Git自体が履歴 | 安全 |
| GASのコード（ダッシュボード・PL・精算・取込） | Google Apps Script | ✅`NStyle-AI/gas-backup/`に手動バックアップ運用 | 更新忘れがあると古い版しか残らない |
| 各種シークレット（APIキー・トークン類） | `app_secrets`テーブル・GitHub Secrets・GAS Script Properties | ハブDBバックアップに一部含まれる | **散在していて「何がどこにあるか」の台帳が無い** |
| Mac miniの取込ジョブ（ns-daily-import）と`.env` | Mac mini実機 | ❌`.env`は実機のみ | **Mac mini故障で取込が全停止**（2026-08-22に再起動だけで実際に停止した実績あり） |

## 2. 提案する対策（3本柱）

### 柱1: 「復旧の入口」1枚ドキュメント（すぐできる・費用ゼロ）
本書の§1の表を核に、**「◯◯が壊れたら→ここを開いて→この手順」**を1枚にまとめた`docs/復旧の入口.md`を作り、統合ポータルの⚙️管理グループからリンクする。全システム・全データについて「正本／バックアップ／復旧手順／所要時間」を1行ずつ。**これが「ここを見ればすべてのデータが回収できる場所」の本体**（データそのものではなく、確実にたどり着ける地図）。

### 柱2: 自動オフサイトバックアップ（Supabaseの外にもう1部置く）
週次（案）でGitHub Actionsが自動実行:
1. **ハブSupabase・社内情報Supabaseの全テーブルをエクスポート**（SQLダンプ or CSV一式）
2. **Storageの全ファイル**（写真・PDF・書類）を同期コピー
3. 保存先はQ1で決定（Google Drive共有ドライブ案が第一候補）。世代管理（例: 直近8週分保持）
- これで「Supabaseに何が起きても、最悪1週間前の全データ＋全ファイルが手元に残る」状態になる
- BigQueryは「シート・Supabaseから再生成できる」ことを復旧手順として文書化する方針（コピーを持たない。再生成コマンドは既存の`bqSyncSales`等がそのまま使える）

### 柱3: 単一障害点の解消（Mac mini対策）
- `ns-daily-import`の`.env`（設定・接続情報）の**暗号化した控え**をユーザーの安全な場所（パスワードマネージャ等）に保管する手順書を作る
- 重要ジョブから順にGitHub Actionsへ移す長期方針（スポット人件費の16:00保険同期で既に実績あり）。今回は方針の明文化まで

## 3. やらないこと（今回のスコープ外）

- PITR（秒単位の巻き戻し・別料金アドオン）への加入 → 週次オフサイトで足りるか見てから
- 旧・社内情報プロジェクトの扱い変更（既存方針どおり）
- 統合ポータル側への2段階認証追加 → Q3で希望があれば別タスク化

## 4. 実装の割り当て（案）

設計確定後、**担当D**（D-5として。GitHub Actions・cron・見張り番の実績があり同型）。「復旧の入口」ドキュメントは司令塔が下書き→Dが実手順を検証して仕上げ。バックアップ結果の成否は既存の「朝の見張り番」パターンでLark通知（失敗に気づける形にする）。

## 5. ユーザーへの質問

- **Q1. 逃がし先**: バックアップの保存先はどこがよいですか？
  - A: **Google Drive共有ドライブ**（今のWorkspace内・追加費用ほぼゼロ・容量上限に注意）← 第一候補
  - B: Google Cloud Storage（従量課金・大容量向き。要件定義書では「将来導入」扱いだった）
  - C: その他（外付けディスクをMac miniに挿す等）
- **Q2. 写真の範囲**: 写真・添付ファイルは**全量**バックアップでよいですか？（枚数が多いと初回コピーに時間・容量がかかります。「直近1年分だけ」等の絞りも可能）
- **Q3. 2段階認証の追加範囲**: 社内情報管理システムは導入済みです。**統合ポータル側（全員が使う側）にも2段階認証を広げたいですか？**（広げると全員のログインが一手間増えます。「役職が高い人だけ必須」等の折衷も可能）
- **Q4. 頻度**: 週1回の自動バックアップで十分ですか？（毎日にもできますが、保存先の容量消費が増えます。DBは日次バックアップがSupabase側に既にあるため、提案は「週次で外部へ」です）
