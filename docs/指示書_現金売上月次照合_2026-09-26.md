# 指示書: 現金売上の月次照合（レジ再取得 vs 管理システム）→ 一致すればMF仕訳候補／ずれればレジに合わせて修正

**発行**: Mac miniセッション（2026-09-26）／**依頼者**: ユーザー（「毎月3日に前月の現金売上が管理システムと合っているか確認し、合っていればMFへ仕訳できる状態に。
ずれていればどの店舗が何日いくらずれているか出して、レジの正しい方に管理システム側も修正できるように。業務委託精算書の対象店舗は精算書の現金売上にも反映」）
**状態**: コードは実装・push済み。**未デプロイ／未適用**: ①GAS2本の貼替 ②本番SQL2本 ③初回の実地確認（下記§5）。

## 1. 仕様（ユーザー確認済み）
- 対象は **12店舗**: Dinii(NS)8＋Dinii(N-Style)3＋ZeroRegi(秋葉原 肉寿司)。黒霧屋 新横浜を含む。
- 比較するのは**現金**。**1円でもずれたら「要確認」**。店舗×日で表示する（どの店舗が何日いくらずれているか）。
- **全店舗一致したときだけ**「登録可能」（仕訳候補を作る）。差異があれば作らない。
- 仕訳の中身は店舗（法人）ごとに違うので、**仕訳辞書**（`mf_journal_templates.receivable_source_name='現金売上'`）に**ユーザーが登録**する。
- 修正は「店舗×日の**その日の売上を丸ごとレジの値で書き換える**」方式（現金だけを直さない。売上DB・BigQueryの整合をシンプルに保つため）。
- 業務委託精算書の対象店舗は、修正後の正しい現金売上が精算書の「N月現金売上」行へ**自動で反映**される。

## 2. 全体の流れ
```
毎月3日 08:00 ns-daily-import: cash-sales-monthly-check
  ├ レジ(POS)を前月1日〜末日で取得: Dinii NS(8店)・Dinii N-Style(3店)・ZeroRegi(秋葉原)   … lib/pos-cash-month.js
  ├ 管理システムを読む: GAS cashReconRead → 売上DB「支払いDB」（店舗×日・数値16列）           … tori-dashboard/gas/Code.gs
  ├ 店舗×日で現金を比較 → cash_recon_runs / cash_recon_items へ保存 → Larkへ報告               … lib/cash-recon.js
  └ 全店舗一致 → ar_receivables に「現金売上」を店舗ごとに作成（＝売上入金の「仕訳を作成」へ）   … lib/cash-journal.js
ポータル 会計・請求＞売上入金＞💴現金売上照合（invoices.html）
  └ 「レジに合わせて修正」→ cash_recon_fix_requests に依頼 → Mac mini(lib/cash-fix.js)が
      ① 支払いDBの該当行をレジの値で書換（GAS paymentDailyReplace・修正ログ付き）
      ② rebuildAnalysis（分析_日別店舗）＋ bqSyncSales（BigQuery）
      ③ 精算対象店舗は精算書の現金売上行を更新（GAS seisanCashSync→精算GAS sd_apiCashSync。振込済みの月は更新しない）
      ④ 管理システムを読み直して再照合 → 全店舗一致なら仕訳候補を作成 → Lark
```

## 4. 実装上の決定と注意点
- **12店舗すべての現金は「支払いDB」に集約**されている（Diniiは支払い取込、秋葉原はZeroRegi日別売上取込が同じシートへUPSERT）。よって管理システム側の比較対象は支払いDBの1シートだけ。
- Dinii CSV・ZeroRegi CSVの列→支払いDB数値16列の対応は売上DB GAS（`支払いCSV Webアプリ取込.gs`/`日別売上取込.gs`）と同じにしてある。**ローカルのGASミラーは2026-08-22時点で本番と差がある**ため、初回の実地確認で「現金は一致するのに他の列が違う日」が無いか見ること（違うなら16列の対応を本番GASに合わせる）。
- 書換は既存行の3〜18列だけを更新し、店舗名・営業日セルは触らない。既存行は**シート上の店舗名×日**で探す（`matchStore`。「うお蔵 新横浜店」等の表記ゆれで二重追加しない）。同店舗×日が2行以上あれば最初の行だけ更新して報告（削除しない）。
- `missing_pos`（管理システムにだけある日）は自動では消さず「要手動確認」として報告する（レジ締め未処理でレジ側に行が無いだけの可能性があるため）。
- 月次ジョブの実行結果は、差異があっても`成功`で返す（`一部失敗`だと月次の未取得アラートが毎日鳴り続けるため）。取得失敗・照合不能は例外＝失敗（Lark通知）。1店舗でもレジ側が丸ごと取れなければ照合しない（「一致」と誤判定しない）。
- 再実行ボタン（自動取込＞未取得）用の`import_run_requests`（別SQL・`supabase/2026-09-25_import_run_requests.sql`）を適用すると、現金売上照合画面の「照合をやり直す」も使える。

1. **GAS 2本を貼替＋再デプロイ**（ユーザー手作業）: 経営ダッシュボード `Code.gs`（`?action=ping` → `token-336h-v1-a6p24`）／精算ダッシュボード `SeisanDashboard_コピー用.txt`（`v5.22-cash-sync`）。
2. **本番SQL適用**（ユーザー確認のうえ・Management API）: `2026-09-26_cash_recon.sql`（＋未適用なら`2026-09-25_import_run_requests.sql`）。
3. **読み取りの疎通**: `TARGET_YEAR_MONTH=2026-08 DRY_RUN=1 node -e "require('./tasks/cash-sales-monthly-check').run({log:console.log})"`（管理システム側はGAS `cashReconRead`。レジ側取得だけ先に確認済み: 8月＝Dinii NS/N-Style各31日・ZeroRegi 31日）。
4. **実書込なしの修正検証**: `paymentDailyReplace`を`dryRun:true`＋**既存行と同一の値**で呼ぶ（tori-dashboard CLAUDE.md §3の方針）→`unchanged`になることを確認。
5. 本番の照合→（差異があれば）ポータルから修正→再照合で全店舗一致→仕訳候補が売上入金に出ること。**実際のMF仕訳登録は人が確認して行う**。
6. ユーザーが**仕訳辞書に「現金売上」**を法人・店舗ごとに登録する（登録後、売上入金の「仕訳を作成」で自動適用される）。

## 6. 未実施・既知の限界
- 初回の実データ照合は、GAS未デプロイのため未実施（レジ側取得と照合ロジックの単体テストのみ完了）。
- 精算書への反映は、振込済み（`sd_isLocked_`）の月・店舗は更新しない（確定済みの精算書を自動で書き換えない）。その場合はLarkに出るので手動で確認する。
- 毎月5日の精算書自動取込（`sd_cashAutoTick`）は既存行をスキップする仕様のまま。3日に照合・修正→5日に取込、の順で正しい値が入る。
