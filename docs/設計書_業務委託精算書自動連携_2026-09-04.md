## 2. 調査結果②: 既存の精算書→PL連携の仕組み

`tori-dashboard/gas/Code.gs`の`syncSeisanCategoriesToPl`（[tori-dashboard/gas/Code.gs:2994](../../tori-dashboard/gas/Code.gs)）が本体。
呼び出しは**毎朝の時間主導トリガー**（Apps Scriptエディタで手動設定・コード上には見当たらないため
GAS UIの「トリガー」設定と推測。9-1章で実物確認を予定）。

| 質問 | 回答 |
|---|---|
| どの条件でPL対象になるか | 明細の`勘定科目`が空でも`対象外`でも`運営委託費`でもない（`運営委託費`は別の既存連携`syncSeisanFeeToPl`が担当・重複防止のため除外） |
| どのタイミングでPLへ入るか | **その店舗の属する法人・月が「振込済み」確定した後**、次の日次同期実行時（`sd_isLocked_`が`true`になるまでは`sd_apiCategorizedLines`が空配列を返す＝未確定の金額はPLに一切送られない） |
| どの店舗へ入るか | `store_directory_v`の`seisan_target=true`の店舗全部を毎回総当たり（新規追加店舗も自動的に対象になる） |
| どの対象月へ入るか | 呼び出し時の引数`ym`（単月）または`ymFrom〜ymTo`（さかのぼり一括、最大36ヶ月） |
| どのPL科目へ入るか | 明細の`勘定科目`・`補助科目`をそのまま使用（科目名の変換・マッピングはしていない＝精算書側で選んだ科目がそのままPL科目になる） |
| どの金額が入るか | 同一店舗・月・勘定科目・補助科目の明細を**税抜換算した上で合計**（個々の明細ではなく**集計値**としてDB_PLに書き込む。→5章で後述する制約の元） |
| PL対象外科目はどう判定しているか | `勘定科目 === '対象外'`（固定ロイヤリティ等、精算書はするがPLには乗せない経費用の特別値） |
| 反映済みをどう判定しているか | ❌**個々の明細単位では判定していない**。DB_PL側は「その月×その店舗×`自動｜精算書`というメモが付いた行」を**毎回全部消してから、その時点の集計値で丸ごと書き直す**方式（差分ではなく完全上書き） |
| 二重反映をどう防いでいるか | 上記の「自分のメモの行を先に削除してから書き直す」方式そのものが二重化を防ぐ仕組み。個々のリクエスト単位の冪等性チェックは無い（そもそも個別リクエストではなく日次バッチ） |

**重要な制約（今回の設計に直結）**: `sd_apiCategorizedLines`は明細を**勘定科目×補助科目で集計してから返す**ため、
DB_PL側は「どの個別明細（sourceKey）がその集計に含まれていたか」を突き合わせられない。
→ **「この1件のinvoice由来の明細がPLに反映されたか」を正確に追うには、集計前の情報を今より1段階多く
保持する必要がある**（5-3章で設計）。

## 5. API設計（提案）

共通: 認証は既存と同じ`PL_SYNC_TOKEN`（Script Properties）。エンドポイントはGAS Web AppのPOST 1本
（`{fn:'...', args:[...]}`形式、既存の`sd_apiCategorizedLines`等と同じ呼び出し規約）。

### 5-1. ①登録・③更新（統合）: 既存`sd_apiAddExternalLine`を拡張（**関数名・既存呼び出しは変更しない**）

**新しい関数は作らず、`sd_apiAddExternalLine(token, store, monthKey, line)`そのものを拡張する**
（ユーザー指示のとおり、既に稼働中のカード手数料等のMF仕訳自動反映=既存呼び出し元を壊さないことを最優先）。

```
POST {fn:'sd_apiAddExternalLine', args:[token, store, monthKey, {
  sourceKey,      // 必須。既存どおり。新形式 "invoice:<invoice_id>:<line_no>" を今回から利用
  item, amount, tax, account, subAccount,   // 既存どおり
  note,           // 【変更点】今回から「備考」列にそのまま書く（sourceKeyとは独立）
}]}
```

**後方互換性の保ち方**:
- 引数の型・順序・既存フィールド名は一切変更しない（追加のみ）
- 挙動の変更点は**「sourceKeyの保存場所」だけ**: 旧実装は備考列に`外部連携:<sourceKey>`と書いていたが、
  新実装は**新設の「外部参照ID」列**（`sd_ensureCategoryCols_`と同じ自己修復パターンで自動作成）に`sourceKey`を
  そのまま書き、備考列は`line.note`（無指定なら空）を書く
- **移行**: 外部参照ID列が無い既存シートには自動作成されるだけなので既存呼び出し元（MF仕訳連携）は無改修で
  動き続ける。ただし**過去に登録済みの行**（備考列に`外部連携:xxx`と入っている行）は新しい「外部参照ID」列が
  空のままになるため、同じsourceKeyで次回呼ばれた際に**旧形式の行も見つけられるよう、検索時は「外部参照ID列」
  →見つからなければ「備考列の`外部連携:`プレフィックス」の順にフォールバック検索**する（1回移行すれば以降は
  新形式に統一される。データ移行バッチは不要）
- 既存どおり：振込済みロック中は`{ok:false, locked:true}`で拒否
- 既存どおり：同じsourceKeyなら上書き（idempotent）、無ければ新規追加

### 5-2. ②取得・④状態取得（統合）: `sd_apiGetLines`

```

  {store, monthKey, sourceKey}, ...   // 1invoiceの全行分をまとめて渡せる
]]}
→ { ok:true, lines: [
  { sourceKey, found:true, item, amount, tax, account, subAccount, note,
    locked,        // 振込済み確定 true/false
    editedAt,       // 修正日（既存の「修正日」列）
    plStatus: 'PL対象外' | '振込確定待ち' | 'PL同期待ち' | '店舗月次PL同期実行済み（個別反映未検証）' | 'PL反映済み（個別確認済み）' | 'PLエラー'   // 9-2で定義

```
- 1件ずつ`store`シートを読みに行くと店舗数分I/Oが発生するため、**store単位でグルーピングしてから
  シートを1回だけ読む**実装にする（既存`sd_readRowsCached_`のキャッシュをそのまま使えば速度面も問題ない）

### 5-3. ⑤PL反映状態の追跡（新設計・今回いちばんの新規実装）

**課題**（2章末尾の制約より）: 現在のPL連携は集計後の値をDB_PLへ書くため、個々のsourceKey行が
実際にPLへ含まれたかを直接は追えない。

**提案**: 「集計単位（店舗×月）の同期結果」を精算書側に記録し、そこから個々の明細の状態を導出する。

1. `syncSeisanCategoriesToPl`（tori-dashboard側）が店舗×月の同期に成功/失敗したら、**新規API
   `sd_apiMarkPlSynced(token, store, monthKey, {ok, error, syncedAt})`を呼んで結果を精算書側へ書き戻す**
   （新規シート「PL反映ログ_精算ダッシュボード」に店舗×月をキーに1行、随時上書き）
2. 個々の明細のPL状態は、この同期ログと明細自体の状態から導出する:
   - `account === '対象外'` → **対象外**
   - `!locked`（振込済みでない） → **反映待ち**
   - `locked`かつ 同期ログが無い、または同期ログの`ok===false` → **エラー**
   - `locked`かつ 同期ログの`syncedAt >= その明細のeditedAt` → **反映済み**
   - `locked`かつ 同期ログの`syncedAt < editedAt`（振込確定後に明細を編集したが、まだ次の日次同期が
     走っていない） → **反映待ち**
3. この設計なら明細1件ごとの真の反映有無ではなく「同じ集計に含まれる他の明細と合わせて同期済みか」
   という粒度になるが、**ユーザーが求めている表示（振込確定待ち→PL反映済みに自動で変わる）には
   これで十分**と判断。より厳密な行単位トラッキングにするには「毎回全部消して書き直す」現在のPL書き込み
   方式自体を差分方式に変える必要があり、影響範囲が大きいため今回は見送りを提案

## 9. 2026-09-05 ユーザー方針を受けた結論（4点）

### 9-1. `syncSeisanCategoriesToPl`の実行実態調査 → **担当Aが実物確認する。推測では実装しない**

Apps Scriptエディタの「トリガー」画面・「実行数」画面はGoogleアカウントの認証が必要で、担当A（このAI）は
ユーザーのGoogleアカウントへログインできないため直接確認できない。以下をユーザーに確認してもらう必要がある
（確認できるまでは9-2の状態表示で「振込確定済み・PL同期待ち」と正直に表示し、断定表示はしない）:

1. Apps Scriptエディタ（tori-dashboardのスプレッドシート → 拡張機能 → Apps Script）を開く
2. 左メニューの⏰「トリガー」を開き、`syncSeisanCategoriesToPl`（または関連の親関数）が**登録されているか**・
   **実行時刻・頻度**を確認
3. 左メニューの▷「実行数」を開き、直近の実行一覧から**成功/失敗・最終成功日時・エラー内容**を確認
4. スクリーンショットまたはテキストで共有してもらえれば、それを元に9-2の状態導出ロジックを確定する

**将来の理想形（振込確定→即PL反映、日次バッチは再試行/整合性チェック用）については、まず上記の実態が分かってから
影響範囲を見積もる**。現時点では日次バッチ方式を維持する前提で9-2を設計している。

### 9-2. PL反映状態: 6状態モデルを採用（個別invoiceの反映済みは断定しない）

ユーザー指定のとおり、**「店舗×月の同期成功」を「個別invoiceのPL反映済み」と見せることを禁止**し、以下の
6状態のみを使う（`invoice_pl_reflections.pl_status`列、9-3参照）:

| 状態 | 判定条件 |
|---|---|
| **PL対象外** | 明細の勘定科目（マッピング後）が`対象外`、または人がPL対象外に設定 |
| **振込確定待ち** | まだ`sd_isLocked_`が`false`（精算書側で振込未確定） |
| **PL同期待ち** | 振込確定済みだが、まだ`syncSeisanCategoriesToPl`の当該店舗×月の同期が1度も成功していない |
| **店舗月次PL同期実行済み（個別反映未検証）** | 振込確定済み・店舗×月の同期は成功しているが、**この明細個別がDB_PLに入ったことまでは未検証**（現状の集計方式の限界。5-3参照） |
| **PL反映済み（個別確認済み）** | external_keyをPL側まで引き継ぎ、DB_PL側の行とこの明細を突合して個別に確認できた場合のみ（10章末の段階導入判断参照。**当面は到達しない状態**として実装し、5-3の拡張後に有効化する） |
| **PLエラー** | 同期ログにエラーが記録されている、または同期API呼び出し自体が失敗 |

「店舗月次PL同期実行済み（個別反映未検証）」を新設したことで、**現状の技術的な限界を隠さず正直に表示**できる
（ユーザー指定の設計方針どおり）。個別確認済みへの格上げは、5-3のexternal_key引き継ぎが実装できた範囲から
段階的に有効化する。

### 9-3. `invoice_pl_reflections`は拡張する（新テーブルは作らない）

実際のスキーマ（[supabase/2026-09-03_invoice_pl_reflections.sql](../supabase/2026-09-03_invoice_pl_reflections.sql)）を確認した結果、
**「直接PL書き込み専用」として強く縛られた設計ではなかった**（`account_name`/`sub_account_name`/`year_month`/
`allocations`/`sheet_synced_at`/`sheet_sync_error`はいずれも経路に依存しない汎用的な列）。
「直接PLのみ」という前提は**`pl-fee-reflect`Edge Function側のロジック**（精算対象店舗を明示的に拒否）に
あるだけで、テーブル自体には無い。よって**新テーブルは作らず拡張**する（採用理由: Source of Truthの二重化を
避けるというユーザーの最優先事項に最も合致するため）。

追加する列（担当C実装）:
```sql
alter table invoice_pl_reflections
  add column if not exists reflection_route text not null default 'direct'
    check (reflection_route in ('direct','seisan')),
  add column if not exists seisan_store_name text,      -- 精算書側の店舗名（seisan_target店舗のみ）
  add column if not exists seisan_line_key text,         -- sd_apiAddExternalLineに渡すexternal_key
  add column if not exists pl_status text not null default '振込確定待ち',
  add column if not exists pl_status_checked_at timestamptz;
create index if not exists ipr_route_idx on invoice_pl_reflections(reflection_route);
```
- `reflection_route='direct'`の既存行はそのまま（`pl_status`は都度`pl-fee-reflect`側で埋める）
- `reflection_route='seisan'`の行が「業務委託精算書へ登録」の実体。`sheet_synced_at`/`sheet_sync_error`は
  既存どおり「seisan-dashboardへの登録（`sd_apiAddExternalLine`呼び出し）が成功したか」に使う
- `pl_status`は9-2の6状態のみを保持する専用列（`sheet_synced_at`の有無から都度計算するのではなく、
  取得のたびに5-3の`sd_apiGetLines`を呼んで最新化してキャッシュする）

### 実機で発見・修正したバグ（2件）

その場しのぎの回避ではなく、いずれもA-9拡張のコード自体を修正して解消（コミット
[995333b](https://github.com/mirai-oss/seisan-dashboard/commit/995333b)・[4f07600](https://github.com/mirai-oss/seisan-dashboard/commit/4f07600)）:

1. **PL反映ログ・マッピングシート新規作成直後の`getLastRow()`誤り**: `insertSheet()`直後に`flush()`を
   挟まずに`getLastRow()`を呼んでいたため、初回データ書き込みがヘッダー行を上書きしてしまっていた
2. **「対象月」列がGoogle Sheetsに日付型として自動変換される**: `"2026-08"`という文字列を書き込んでも
   Sheetsが日付として解釈し、`getValues()`で読むとDateオブジェクトになってしまい、文字列比較の
   `sd_plSyncLogGet_`が常に不一致になっていた。列をプレーンテキスト書式に固定し、読み込み側でも
   Date/文字列どちらでも扱えるように修正

いずれもNode.js上のロジック回帰テスト（12章）では検出できなかった、**実際のGoogle Sheets特有の挙動に
起因するバグ**だった。実機テストの重要性を裏付ける結果になった。

### 運営委託費のタイミングについて（ユーザー質問への回答）

振込確定と同時にPLへ反映されるわけではなく、**次に同期が実行されたとき**（1日1回の自動実行 or 手動実行）に
反映される。同期のたびに現在の精算書の合計額で洗い替えるため、「間違えて振込確定→修正→再振込確定」の
ケースでも最終的には正しい金額に上書きされる（二重計上にはならない）。ただし修正後、次の同期実行までは
PL側に古い金額が残る点は運用上の注意点として申し送り。

## 14. 2026-09-05 黒霧屋 新横浜対応: 運営委託費とPL反映の個別ON/OFF

ユーザー要望「黒霧屋 新横浜は運営委託費の自動連携(`syncSeisanFeeToPl`)は対象外のままでよいが、

  引き継ぎ（挙動は変わらない）。黒霧屋 新横浜だけ`seisan_pl_categories_target=true`・`seisan_target=false`に設定
- `syncSeisanCategoriesToPl`（勘定科目ベースの経費PL連携）のみ、対象店舗判定を`seisan_target`→
  `seisan_pl_categories_target`に変更（[tori-dashboardコミット79bb034](https://github.com/mirai-oss/tori-dashboard/commit/79bb034)）。
  `syncSeisanFeeToPl`（運営委託費）・`writeAccountCostToPl_`（MF仕訳→精算書自動追加）は`seisan_target`のまま無改修
